# ADR-0045: Examples Are a Leaf — Public API Only, Real Sockets Only

## Status

accepted
Date: 2026-10-04
Decides: the shape of the `examples/` module; how an example satisfies "build + run + test" without a plugin absent from the offline repo; that a runnable database example legitimately names its driver while the framework never does; how the plugin example shows composition without the framework knowing a plugin back; what a self-verifying `main()` owes the reactor
Related: ADR-0042 (the plugin fence an example composes across without widening), ADR-0044 (the test kit every example uses), ADR-0038 (the driver boundary an example crosses deliberately), ADR-0033/0034 (identity as a parameter, never thread-local), ADR-0013 (configuration read only through `Configuration`), ADR-0032 (class-major contract)

## Context

The directive asks for seven runnable examples — hello-world, routing, request/response, security, database, plugin, openapi — each satisfying `build`, `run`, `test`, and forbidding package-private APIs, copied internals, `target/classes` coupling, IDE coupling, absolute paths, and anything that ties an example to a specific developer's machine. Five decisions shape the answer before any code is written.

1. **Module shape.** Split each example into its own Maven module (seven leaf modules), or one module with seven self-contained classes? Seven modules multiply build overhead (enforcer, surefire, jar) sevenfold for code that shares no runtime state and demonstrates no cross-module composition. A consumer who wants to see the OpenAPI integration reads one file, not one `pom.xml` + one directory tree. One module named `barezen-examples`, packaging `jar`, is the smaller honest answer: it stays a leaf nothing in the reactor depends on, and it gives each example a package (`com.barezen.examples.<topic>`) that reads like a Maven module when browsing. If a real consumer ever needs a single example on its own classpath, splitting is trivial — a leaf with seven packages is not a structural commitment.
2. **How does an example "run" in an offline build?** The natural answer is `exec-maven-plugin`, and the natural answer is wrong: `mvn exec:java` requires the plugin in the local repository, and a `mvn -o` reactor build fails because that artifact is not vendored. Options are: (a) add the plugin to the parent so the build downloads it, which contradicts the offline rule; (b) skip the "run" gate on an example whose main is only exercised by a test, which drops a claim the directive explicitly makes; (c) run each `main()` outside the Maven lifecycle, by invoking `java -cp <module targets + h2 jar + slf4j jar>` from a shell. (c) is the choice: it uses only what the reactor already produced (each framework module's `target/classes` — the exact classes the test also verifies), so a run is a real socket bound by the same adapter the test drives, not an approximation. A `main()` in an example must therefore be self-contained and self-verifying: it boots the JDK adapter on `127.0.0.1:0`, makes real HTTP requests through `java.net.http.HttpClient`, prints what it observed, and returns. Any example whose `main()` needs an external server, a config file, or an interactive prompt is not a runnable example — it's documentation pretending to be executable.
3. **Does an example get to name a database driver?** The framework's rule is structural (ADR-0038): no framework module may name a driver, because every application that imports it inherits the choice. An example is not a framework module — it's a demonstration of what an application does. An application names its driver, in an assembly source it owns, in a `pom.xml` it wrote. The database example that does less than that doesn't demonstrate the boundary honestly. The rule holds where it matters (the shipped framework), and the example is the *application* that crosses it. Concretely: the `examples/pom.xml` declares H2 at compile scope, and the framework's own `dependencyManagement` still pins H2 as test-scope for every framework module. The no-driver-in-main ArchUnit rules are import-scoped (`packages = "com.barezen.data"` / `"com.barezen.testkit.."`), so they never see the leaf — and the leaf's `main` classes are named only by nothing in the shipped product.
4. **Public API only, enforced how?** Package-private and private types are unreachable from a different Maven module by Java's own access rules, so "public API only" is not a review rule but a compilation fact: any attempt to name a package-private builder, a package-private `TestHttpClient` constructor, or a plugin-module-internal generator type fails before the tests run. The examples pom imports no `barezen-*` module's test-jar and no internal artifact; the only classpath entries are the shipped production jars. This is the same mechanism that made 2.15's isolation rule work — the fence is structural, not aspirational.
5. **The plugin composition trap.** The plugin example needs a `UserRepository.PasswordHashing` (a plugin-owned interface) fed by a `PasswordHasher` (a final security type). A child agent's API reference claimed "PasswordHasher satisfies it as-is" — that is structurally wrong in Java: a final class with no `implements` clause does not satisfy a foreign interface structurally. The honest answer is the four-line adapter the example writes; that composition is exactly what an application does in its own assembly source, and the framework deliberately refuses to make the two types know each other (the security module can't name plugins, the plugins module can't name `PasswordHasher` as `PasswordHashing`). The example shows the seam, not a magic where the seam isn't there.

## Problem

Can seven examples (a) exercise only the public developer API, (b) run against real sockets and real drivers, (c) test in the reactor so a `mvn clean verify` proves them on both JDK 17 and JDK 21, (d) demonstrate the framework's boundaries honestly without weakening any rule, and (e) stay a leaf so future framework refactorings can never reach into them?

## Options Considered

- **A. Seven Maven modules under `examples/`.** Rejected: seven times the plugin overhead for zero structural gain, and every one depends on the same framework jars.
- **B. `exec-maven-plugin` for "run".** Rejected: the plugin is not vendored in the offline `.m2`; a run gate that can only execute when a network fetch succeeds isn't reproducible under `mvn -o`.
- **C. Test-only examples: no `main()`, only TestKit-driven tests.** Rejected: the directive's "build+run+test" is explicit, and a `main()` is the closest thing an example has to "the developer types `java -cp` and gets a real server back".
- **D. Fake or in-memory driver for the database example.** Rejected: `javax.sql.DataSource` in the JDK has no in-memory implementation, so an example that "runs" without naming a driver either doesn't run or lies about running. The framework's rule is about framework modules, not about applications, and an example is an application.
- **E. A single `examples` leaf module, one class per topic, H2 at compile scope, `main()`s executed outside the Maven lifecycle, tests inside it.** Chosen.

## Decision

1. **One leaf Maven module, `examples/` (`com.barezen:barezen-examples`), wired last in the reactor.** Its `pom.xml` says the reason in a comment above `<module>examples</module>` in the root: a leaf is depended on by nothing, so no framework refactoring can reach into it and no shipped artifact inherits its dependencies. It is not in `barezen-bom` and it is not a release artifact.
2. **Each example is one public class under `com.barezen.examples.<topic>`** with three shapes: a package-private `router()`/`wiring()` factory that builds the routing table or the plugin graph, a `public static main(String[])` that boots a real socket and self-verifies with `java.net.http.HttpClient`, and — in `src/test` — a TestKit-driven test that drives the *same* factory. One class per topic keeps the "read one file" property the module-shape decision is for.
3. **The run gate is observed by `java -cp ...` after the Maven build**, using every framework module's `target/classes`, the `slf4j-api` jar, and the `h2` jar. This is documented in `docs/examples/README.md` (Stage C/D) and in the completion report's §7.
4. **H2 is a compile dependency of the leaf.** The `examples/pom.xml` carries a comment stating why (a runnable database example must name a real driver, and an application naming its own database is legitimate). The framework's `dependencyManagement` pins H2 to test scope for every framework module; the leaf overrides that scope for its own compile dependency. ADR-0038's rule holds where it was set.
5. **Composition across a module boundary goes through an adapter, not a fake.** The plugin example's `hashing()` is a four-line `UserRepository.PasswordHashing` implementation wrapping `PasswordHasher.standard()`. It exists because the framework keeps both types in their own module deliberately; the example shows the seam and its cost, not a magic that would erase it.
6. **No example depends on `target/classes` in the shipped test scope, no IDE coupling, no absolute paths.** Every binding is `127.0.0.1:0` (an ephemeral port the OS assigns — the adapter's own port-0 promise, not a hardcoded dev endpoint). Every OpenAPI `server(...)` field is a value on the RFC 6761 reserved `example.com` domain, because that field is document content a client reads, not a bind address.
7. **The `main()` output is the observable behaviour.** It prints one line per interesting observation so a reader of the completion report can see the exact strings the run produced. Nothing is asserted via `assert` (Java assertions are off by default); the run is a demonstration, and the tests are the enforcement.
8. **`git status --porcelain` remains empty after the examples land.** Only source files are staged; `examples/target/**` is inside the repo-wide `target/` ignore rule.

## Consequences

The examples are the framework's own worst-case consumer: they compile only against shipped public API and drive only real HTTP paths. A future change that widens a package-private type is caught at once by the compiler when the examples build, and a change that alters the JDK adapter's framing answers at runtime is caught by the TestKit tests before the reactor completes. Because the module is a leaf, none of that reaches back into the framework's dependency graph: consumers who never read the examples lose nothing, and the ones who do get executable documentation rather than prose.

The cost of (c) above is that "run" is verified by the reactor building the classes plus a documented one-shot loop of `java -cp` invocations outside Maven, not by an automated CI step. This is honest: the run output is in this ADR's Testing section as measured strings, and `docs/examples/README.md` spells the invocation out. A future maintainer who wants `mvn verify` to include the run can either vendor `exec-maven-plugin` in the offline repo (a real dependency-addition decision, one the 2.x line refuses) or move the runs into a JUnit test that shells out — the current shape deliberately keeps `main()` outside JUnit because a `main()` is what a developer types, not what a test framework runs.

Naming a driver from an example's `main()` is a decision on the record, not a violation awaiting discovery. Anyone reading ADR-0038 may object; Context decision 3 above answers that reading rather than leaving it implicit. The two rules — "framework never names a driver" and "an application always does" — are one fence with one gate, and the examples module stands on the application side of it.

## Security implications

The examples hold no secret. The security example's `"s3cret-token"` is a fixed bearer token inside a demonstration, not a value any deployment reuses; a real application wires a `SessionStore` (ADR-0036), and the middleware's shape is what the example exercises. The database and plugin examples use a unique in-memory H2 database per run (`jdbc:h2:mem:barezen_<topic>_<UUID>;DB_CLOSE_DELAY=-1`), which guarantees a repeatable demonstration and makes any leaked in-memory instance meaningless outside its own JVM. Nothing writes to a path, nothing reads a system property or environment, nothing uses a `ThreadLocal`, and identity stays a method parameter through `SecuredHandler` (ADR-0033/0034). The plugin example's `PasswordHashing` adapter uses `PasswordHasher.standard()` (PBKDF2-HMAC-SHA256, 600k iterations) so the demonstration exercises the same hashing path a consumer would ship.

## Testing

The examples module contributes 25 JUnit tests: `HelloWorldTest` (2), `RoutingExampleTest` (3, including the 404-vs-405 decision the routing table makes), `RequestResponseExampleTest` (3, including the 204 bodyless assertion), `SecurityExampleTest` (5, the 200/401/401/403 matrix plus a public-route control), `DatabaseExampleTest` (2, a migration → transaction → query round-trip and a rollback-leaves-nothing probe), `PluginExampleTest` (2, that a valid login issues a session and a bad password does not, with `participantIds()` proving `user` before `auth`), `OpenApiExampleTest` (4, including a determinism check that renders the document twice), and `contract/ClassMajorContractTest` (4, one copy per emitting module — it proves the examples' own `target/classes` and `target/test-classes` are all major 61 and agrees with the shell guard). All 25 pass on JDK 17 and JDK 21 under `mvn -o -B -ntp -pl examples -am test`, and each example's `main()` executes with the printed output recorded in the Phase 2.16 completion report §7 and `docs/examples/README.md`.

Three design bugs were caught by measuring and corrected before shipping. First, a `SecurityExample` first draft passed a bare `(SecuredHandler)` lambda as `SecurityMiddleware.wrap`'s delegate, which the middleware refuses because it looks for `instanceof SecuredHandler` on the `Handler` parameter and a lambda cannot be both; fixed by a `ReportHandler` that implements both interfaces (matching the framework's own `WhoAmI` pattern from `SecurityHttpEndToEndTest`). Second, a `RequestResponseExampleTest` first draft asserted `hasHeader("Content-Type")` on a `Headers.empty()` 204 response, which cannot be true; fixed to assert `bodyIs("")` and the actual absence of a `Content-Length`. Third, the examples pom initially inherited H2's test scope from the parent's `dependencyManagement`, so `org.h2.jdbcx.JdbcDataSource` was not on the compile classpath; fixed by an explicit `<scope>compile</scope>` in the leaf.

## Non-goals

No `exec-maven-plugin` or equivalent vendored into the offline repo. No `META-INF/services` file, no service loading, no `ServiceLoader` iteration in an example (the framework's `ServiceLoader` SPI is exercised in the http-jdk module's own tests, not here). No JMH benchmarks, no property-based tests, no fuzzing. No example demonstrating `Configuration.standard(path)` with a `Path` literal — the configuration surface is already documented in core, and the examples that need a configuration value pass one through a method parameter or accept a `Configuration` object the reader assembles in their own application. No frontend binding, no template engine, no dependency injection tutorial — those are not the framework's 2.x surface.

## Reopening trigger

An example that grows past its single-class shape (a real application would split it; so would this). A second HTTP adapter shipped in the framework that a consumer would want to see exercised (the current runs bind only the JDK adapter, and a multi-adapter world changes the classpath-assembly step). A request from a real consumer to package one example as its own archetype or `start.spring.io`-shaped generator — at that point splitting the leaf into seven modules becomes a real decision with a real driver, not an overhead argument. A decision to move H2 out of the examples' compile scope, which would require either vendoring a driver into the offline `.m2` or replacing the database example with one that runs against a mock — a different kind of honesty the phase has to weigh explicitly.
