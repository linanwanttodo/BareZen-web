# ADR-0044: TestKit Is a Downward-Only Test Tool — a Leaf Nothing in the Reactor Depends On

## Status

accepted
Date: 2026-10-04
Decides: where Phase 2.15's test tooling lives; that a framework module naming an adapter is legal only in a consumer-facing test artifact; that testkit never names the plugin layer; how the client is built without a new runtime dependency; where H2 sits; what "testing OpenAPI" means for this phase
Related: ADR-0042 (the plugin fence whose direction rules testkit mirrors but never crosses), ADR-0043 (the generator the docs reference without importing), ADR-0038 (the driver-free `Database(DataSource)` seam the fixture wraps), ADR-0034 (no thread-local, mirrored), ADR-0016 (no configuration back-channels), ADR-0032 (the class-major contract every emitting module re-asserts), ADR-0018 §12 (the adapter layering this module applies one floor lower)

## Context

The directive asks for "integration test tools for consumers that don't expose production internals, all through public API." A first reading suggests a module of utility methods; the actual shape of what a consumer needs is a real HTTP server (a fake proves only the fake), a real HTTP client (a call into a `Handler` skips framing entirely), the fixtures that make the two usable together, and assertions shaped to the framework's own types. Six decisions must be made before code:

1. Is a new Maven module legal, after 2.14 was forced to *avoid* one? Measured: yes. The reason 2.14's generator could not leave `barezen-plugins` is that a framework module naming plugin types breaks ADR-0042 rule ①. TestKit's dependencies all point downward (core, web, http-jdk, security, data), so it sits beside the plugins at the reactor top and crosses no forbidden edge — with one condition this record enforces: **it must never name `com.barezen.plugins` either**, because the two top modules seeing each other sideways would couple every consumer's test classpath to whichever plugin the other chose.
2. May a "framework" module depend on an *adapter*? ADR-0018 §12 says an application depends on an adapter, not the framework on one. TestKit is shipped framework code, so naively the answer would be no. But testkit is *for* a consumer's test classpath: its only user is an application's test source, one floor below the layering ADR-0018 draws. The honest reading is that ADR-0018 §12 applies to a *test tool* the same way it applies to an application — the tool is a consumer of the adapter, exactly as an application is. Naming `JdkHttpServerAdapter` from testkit is the whole point (a fake server proves nothing); what would break the rule is naming it from anything shipped *under* the plugins and required at runtime. This ADR is where that asymmetry gets stated instead of left to a reader.
3. Where does the HTTP client come from? `java.net.http.HttpClient` is JDK-only and already used in-repo by `SecurityHttpEndToEndTest`. Any other choice is a new runtime dependency, which the phase forbids.
4. Where does JSON assertion support come from? A consumer would already have Jackson or Gson, so a *third-party* dependency would be a compile-scope dependency testkit never needs at runtime; the smallest thing that makes the assertion work is a package-private reader in this same module — about 300 lines, no plugin to any library, order-preserving because the OpenAPI document's determinism makes member order a claim worth asserting on.
5. Where does the database fixture sit relative to H2? `TestDatabase` accepts an application-supplied `DataSource` — the exact shape ADR-0038 set for `Database` — and only owns the *reset*, never the connection or the driver. H2 stays test-scope here as it did in 2.12 and 2.13; the framework never names it in `src/main`, and the ArchUnit rule that would look tempting (ban `javax.sql..` in main sources) is deliberately *not* this rule, because `TestDatabase` legitimately needs the port interface. The banned shape is a **driver**, and the rule names driver packages instead.
6. Does "testing OpenAPI" mean testkit reaches the generator? No. Testkit never names plugins (decision 1), so the OpenAPI *document* is exercised only through the framework's own `Router`/`Handler` and the JSON reader — the same way any consumer would. Documentation-only: `docs/testkit/testing-openapi.md` shows a consumer assembling a `barezen-plugins`-supplied `ApiDocument` behind their own test classpath, without any compiled edge here.

## Problem

Can a testkit ship as a framework module and (a) prove real HTTP behaviour (not a fake), (b) add zero new runtime dependencies, (c) refuse to couple consumers to any plugin, (d) let an integration test detect state leaks (a shared counter, a leaked principal, an unreset database, a port not released) rather than paper over them, and (e) never be depended on by anything inside the shipped framework?

## Options Considered

- **A. Utility methods only, no server.** Rejected: it forces every consumer's integration test to hand-build an adapter fixture, which is what `SecurityHttpEndToEndTest` in 2.11 already does — that duplication is exactly the DX problem a testkit exists to close.
- **B. A fake server with an in-memory dispatch.** Rejected: the phase's central claim is integration, and a fake proves only that the fake works. The framing decisions ADR-0028/0029/0030 live in the JDK adapter; a testkit that bypasses the adapter cannot see a framing bug.
- **C. Testkit lives *inside* an existing module (e.g. `barezen-web`).** Rejected: web's shipped jar has zero compile dependencies by ADR-0018, and adding an adapter dependency there would break it; even without an adapter, the assertions and the fixture types would be visible to every consumer of web, which is exactly "exposing production internals."
- **D. Third-party JSON assertion library (AssertJ + Jackson, or RestAssured).** Rejected: RestAssured brings five transitive dependencies (and the max's rule forbids adding a runtime dep for the framework's own testkit), and a library the *test* already owns doesn't need a copy shipped by testkit. A package-private reader costs less to maintain than the version-compatibility surface of a public re-export.
- **E. A new module with strict downward-only edges.** Chosen: legal by construction, and the "nothing in the reactor depends on testkit" rule turns that legality into an executable fact instead of an argument.

## Decision

1. **Placement: `framework/barezen-testkit`, a peer of `framework/barezen-plugins`.** It depends on `barezen-core`, `barezen-web`, `barezen-http-jdk`, `barezen-security`, `barezen-data` — all compile-scope, all downward. Its `pom.xml` states this dependency direction in a comment per edge so a reviewer sees the argument at the point of change, and the root BOM advertises it so consumers add it in test scope only.
2. **The isolation rule is the phase's central claim, made executable.** Six ArchUnit rules over `com.barezen..` in `BarezenTestKitArchitectureTest`:
   - `nothing_in_the_framework_depends_on_testkit` — no class outside `com.barezen.testkit..` may name a testkit type. This is what makes the "test tool the framework does not know about" claim a build fact, not a promise. Spike-proven: a class with package `com.barezen.core` that imports `com.barezen.testkit.TestServer` compiles into testkit's `target/classes` (Java does not check package-vs-directory), the rule fires, and the class is deleted.
   - `testkit_does_not_name_plugins` — the sideways-top-modules ban. Not spike-proven by classpath: `barezen-plugins` is not a compile dependency of `barezen-testkit`, so a source importing a plugin type would fail compilation before ArchUnit ran, which is a stronger fence. Recorded honestly.
   - `no_driver_is_named_in_main_sources` — the banned set is `org.h2..`, `org.postgresql..`, `com.mysql..`, `org.mariadb..`, `org.sqlite..`, `org.hsqldb..`. `javax.sql.DataSource` — the port — stays legal, because `TestDatabase.of(DataSource, String)` takes exactly one and ADR-0038 owns that seam.
   - `no_thread_local`, `no_system_property_or_environment_reads`, `no_static_mutable_state` — mirrored from security (ADR-0034) and plugins (ADR-0042); `no_static_mutable_state` and the env-read rule are spike-proven to bite, and the mutation harness (M3, M4) shows what a `static` fixture field would do even without the rule catching it.
3. **The server wraps the adapter rather than copying it.** `TestServer` owns one `JdkHttpServerAdapter`, binds `InetSocketAddress("127.0.0.1", 0)` so the OS assigns the port, reads it back through `adapter.port()` (which the adapter exposes as `OptionalInt` and this code refuses with a message if it returns empty — a started adapter without a port is a broken adapter, not an "unbound" state), and exposes `port()`, `baseUri()`, `client()`, `isRunning()`, `close()`. `close()` is idempotent via a `volatile boolean closed` (per-instance, never shared — see the mutation M3 note), calls `adapter.stop()` exactly once, and is the *only* path that releases the port. The ThreadProvider the adapter creates with `ThreadPolicy.AUTO` is released by that same `stop()` call, following the proven pattern of `SecurityHttpEndToEndTest`.
4. **The client is `java.net.http.HttpClient` with `followRedirects(NEVER)`.** A 3xx must arrive as itself; a client that silently follows would let a handler bug look like a pass. The seven verbs the router accepts have direct methods, and everything else is reachable through `client().request(HttpMethod, path).header(...).body(...).send()` — a nested builder that returns `TestResponse`. No new framing rules are asserted: the client sends what a browser or curl would, and the adapter decides framing (ADR-0028). `IOException` and `InterruptedException` are wrapped into `TestRequestFailedException` with the method and URI in the message — a connection-refused test failure reads as "your test pointed at nothing," not as a stack trace from an unfamiliar library.
5. **`TestResponse` is a snapshot, not a live connection.** Once returned, the bytes are already read, the header map is already re-keyed into a `String.CASE_INSENSITIVE_ORDER` `TreeMap` wrapped with `Collections.unmodifiableMap`, and the body array is copied on both entry and exit. `Map.copyOf` is deliberately avoided — measured, it drops the comparator and would break the case-insensitive claim `TestResponse.header(name)` documents; that bug was caught before the tests were run and the fix is annotated with a comment.
6. **Fixtures are per-instance by construction, and two tests prove it.** `CountingHandler` and `PrincipalCapturingHandler` each hold their own `AtomicInteger`/`AtomicReference`. `FixturesTest.independentInstances` (×2) makes a second fixture observe the first's counts and asserts the second is at zero — a version of the phase's "fixture state shared" mutation with a byte-restore check, run as an ordinary test. `PrincipalCapturingHandler` implements both `Handler` and `SecuredHandler`, and its plain-`Handler` half is a tripwire that throws `AssertionError`, matching the existing convention in `SecurityHttpEndToEndTest.WhoAmI`.
7. **Assertions are thin and non-fluent.** `Assertions.assertThat(TestResponse)` gives status/header/body/JSON-path checks, `assertThat(int)` a count, `assertThat(Optional<Principal>)` an identity — three entry points, nothing else. `AssertionException extends AssertionError` with a message that quotes both the expected and the actual value; a failed test should not require a debugger. The JSON path is dot-separated (a `ResponseAssert.jsonStringIs("info.title", ...)` reaching a string in `info.title`) with an honest limitation in the javadoc: paths whose key contains a dot are unreachable, and the caller must fall back to `bodyContains`.
8. **`TestDatabase` owns the reset, never the datasource.** It wraps an application-supplied `javax.sql.DataSource`, refuses `null` and blank-reset-statement construction with a reason, and `close()` calls `reset()` once — the isolation test reopens the same datasource through a fresh fixture and asserts the schema is empty. The fixture does not decide whether the test uses H2, PostgreSQL, or a mock; the same seam ADR-0038 draws for `Database` is drawn one floor up for `TestDatabase`.

## Consequences

The consumer's integration test reads like a description of what should happen (`server.client().get("/who")` returns 200 and `handler.seen()` is `alice`), and there is no way to write the same test without exercising the JDK adapter. Every leak a mutation is designed to detect is visible from the same fixture that runs the test — there is no global to inspect. The cost: the JSON reader is ~300 lines that will need maintenance whenever the assertion surface grows. The reader is not public, so growth costs only this module. A consumer who already wants AssertJ+Jackson can keep both; testkit's assertions compose with them and don't compete.

Naming the JDK adapter from a shipped framework module is now a *decision* on the record rather than a violation waiting to be discovered. Anyone reading ADR-0018 §12 in isolation may object; Context's decision 2 above is where that objection is answered rather than left implicit. A future reorganization that moves `JdkHttpServerAdapter` behind an SPI must revisit this ADR together with ADR-0018 §12, because they now argue as one shape.

## Security implications

None of the fixtures hold or produce a secret. `TestFixtures.authenticationFor(String token, Principal)` builds a `Credential`-shaped trust for a test — a real application wires a real `SessionStore` (ADR-0036), and the testkit's role is to exercise the *middleware*, not to store a password anywhere. `PrincipalCapturingHandler.seenNames()` holds the identity sequence a test just ran; nothing escapes into a global. The ArchUnit rules against a static mutable field, a `ThreadLocal`, and an env read are the same fences security and plugins already hold, applied here so a testkit bug cannot become the source of a leak an integration test was meant to detect.

## Testing

81 tests green on JDK 17 in this module (`mvn -o -B -ntp -pl framework/barezen-testkit -am test`): `AssertionsTest` (13), `FixturesTest` (14 including the two `independentInstances`), `JsonReaderTest` (21: scalars, containers, dotted navigation, escapes, malformed structures, malformed Unicode escapes, invalid number forms, raw string controls and non-JSON whitespace), `TestDatabaseTest` (7: construction refusals and the reset/close isolation on a fresh in-memory H2), `TestServerIntegrationTest` (15: every verb round-trips, request headers reach the handler, port/base URI agree, close is idempotent and releases the port so a plain `ServerSocket` can reclaim it, two servers get two distinct ports, an unrouted path answers 404 through the real adapter, the security fixture answers 200/401/401/403 in the right places with a handler count of zero on every refusal, an identity-isolation sequence runs alice→anonymous→bob through the same handler and the recorded sequence is exactly `[alice, bob]`, a JSON body round-trips through the assertion, and a client pointed at a closed server fails with `TestRequestFailedException`, not a bare checked exception), `ClassMajorContractTest` (4, copied per the module convention), `BarezenTestKitArchitectureTest` (6), and `ReadmeTestKitExampleTest` (1) executes the README Phase 2.15 snippet verbatim over a real socket. Stage 2.15-H ran seven mutations — the directive's six named ones plus an extra that kills an echo-fixture bug — every mutation killed with a real `BUILD FAILURE` that actually executed tests, every file restored byte-identical and SHA-256-verified (`PHASE 2.15-G MUTATION GATE: PASS (7/7 killed, all restored byte-identical)`). Two design bugs were caught before this phase's sources shipped and are recorded here as the honest measurement: `PrincipalCapturingHandler`'s first draft implemented only `Handler`, so its `record(Principal)` method was never called by anyone (fixed by implementing both halves to match `WhoAmI` in `SecurityHttpEndToEndTest`), and `TestResponse`'s header map was built with `Map.copyOf` where `Collections.unmodifiableMap` was required to preserve the case-insensitive comparator that the javadoc promises.

## Amendment (2026-11-27): explicit adapter policies

`TestServer.start(Router, Configuration)` passes a caller-supplied snapshot to the real `JdkHttpServerAdapter`.
The one-argument form delegates with an empty in-memory snapshot, so adapter defaults remain unchanged. TestKit still
does not read environment variables or system properties, does not own a second configuration system, and does not
change its dependency direction. The first consumer is a request-body boundary test that needs a small, drainable
surplus rather than the JDK's documented large-body connection reset. `TestServerIntegrationTest` grows from 15 to 16
tests; the new case proves an over-limit body receives 413 with zero handler calls while the exact boundary receives
200.

## Non-goals

Anything a consumer can already do (no re-export of AssertJ, Jackson, Mockito, Testcontainers). A fake or stub server. A test-scope HTTP/2, WebSocket, SSE, or multipart client. A database abstraction over `DataSource` beyond a single reset statement. A fixture that builds an `ApiDocument` or a `Plugin` — the plugins module is unreachable from testkit by rule. Test-ordering tools, retry, parallel-execution configuration, or JUnit-extension plumbing. `HttpMethod.CONNECT` and `TRACE` shortcuts on the client (a routed verb set is what the framework accepts, and ADR-0019's grammar is the constraint). `ThreadLocal`-based context injection (ADR-0034 says no, the same rule applies here).

## Reopening trigger

A named consumer for any non-goal. The first framework module that wants a compile dependency on testkit (which would contradict ADR-0044 §2 rule 1 and force a re-think of whether "test tool" is the right placement at all). A second HTTP adapter module (e.g. Netty) that a consumer would want as the test-server backend — the choice between making testkit adapter-agnostic through a port and making it multi-adapter is a real design decision, and this ADR's answer is only correct while the JDK adapter is the only one. Any proposal to name `com.barezen.plugins` from testkit, which re-opens the sideways-top-modules ban with it.
