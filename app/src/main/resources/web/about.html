这套演示在证明什么

七个文件，同一个 app.js 驱动：它按 body[data-page] 决定接哪几个控件 —— 因为页面带着 Content-Security-Policy，内联脚本根本不会被执行（ADR-0057）。

证明了什么

一个有会话、有增删改查、有审计流、有分页与查询参数、有接口文档的应用，只用公开 API 就能搭起来； 而且它是独立 Maven 模块 —— 框架的包私有类型在这里连编译都过不去，"只用公开面"是编译事实而不是评审意见。

没证明什么

cookie 会话（SecurityMiddleware 只从 Authorization 取凭证，没有第二种 credential source）；流式响应（ADR-0030）；服务端渲染 HTML；跨进程的会话共享（SessionStore 是单进程内存）； servlet 容器里的运行。

分页换来的那个取舍

分开成几页之后，每次导航都会重载文档，所以 token 不能只活在一个 JS 变量里 —— 现在它在 sessionStorage：按标签页隔离、关标签即消失、浏览器不会自动带上（所以仍然没有 CSRF 面）。 代价写清楚：脚本可读的存储意味着一次成功的 XSS 就能读到它，这也是同一份响应把 Content-Security-Policy 定成只允许自身来源的脚本与样式的原因。真正的生产答案是 cookie + HttpOnly，那需要框架开一个 credential source 的口子，按规矩得先有一份 ADR。

界面的来历

这几页复制了文档站 site/assets/site.css 的设计系统 —— 同一批 token、同一种表格与 notes 处理 —— 而不是共享那个文件，因为静态目录和被服务的应用是两种部署形状。量度是这里唯一改掉的东西：文档页给正文 68ch、给页头更宽的 band，控制台却要把账号行、状态行、表单和表格排在同一屏，两种宽度会让它们的左边缘错开，所以这里每条 band 同一个宽度。 重复的那部分样式在 ADR-0055 里被写明。
