# 第 10 章第 2 步：显式事务与归属规则

## 这一步要解决什么

单次 CRUD 已经可用，但它无法保证一组写操作共同成功。现在要把“一个工作单元”变成可见对象：`Database.transaction(TransactionCallback<T>)` 借一条连接，关闭 auto-commit，把 `Transaction` 作为参数交给回调；回调正常返回就 commit，抛出任何失败就 rollback。调用者获得业务结果，repository 只获得执行 SQL 的能力，没有结束事务的能力。

这个设计直接回应 ADR-0039 的三个问题。谁拥有工作单元？组装多个 repository 调用的服务方法。谁能决定提交？只有打开事务的 `Database`，而不是最接近 SQL 的代码。如何执行这条规则？`Transaction.commit()` 与 `Transaction.rollback()` 不写 public，外部代码连方法都看不见；反射测试进一步防止未来有人“为了方便”扩大可见性。

本步还要固定失败决策表。正常返回、回调抛 SQLException、抛 RuntimeException、抛 Error、正常返回但 commit 失败、失败后 rollback 也失败，每一行都必须有确定的调用顺序和异常归属。只测试“插入失败后表里没数据”还不够：commit 失败后是否 rollback、rollback 失败后是否关闭连接、原业务异常是否被 cleanup 异常替换，都是连接池安全的一部分。

最后是生命周期与嵌套。`Transaction` 只在接收它的回调内有效，`decided` 状态在 commit 或 rollback 后拒绝继续 query/update。若 repository 保存事务对象、异步任务或下一个请求继续使用，会立即得到 `DataAccessException`，而不是悄悄占用连接。若在回调内再次调用 `database.transaction`，它会借第二条连接、开第二个独立事务；没有 `REQUIRED`、savepoint 或隐式加入。

## 先想清楚再写

最危险的替代方案是 `ThreadLocal<Transaction>`。repository 不声明依赖也能取到当前事务，服务层看起来只调用了一个方法；可是调用者无法从签名判断它是否提交、在哪个线程提交，线程池复用又可能把上一次请求的事务带给下一次请求。它把归属从代码里藏到运行时。ADR-0039 与第 9 章拒绝 `ThreadLocal` 身份的理由相同：需要知道所有权的对象，应当作为参数到达。

第二种方案是 repository 自己 `begin/commit`。它让“一个 repository 调用是原子的”成立，却破坏“多个 repository 调用组成一个单元”。服务无法撤销第一个 repository 已提交的写入。若把 `Transaction.commit()` 公开，规则立刻退化为“请大家不要调用”；package-private 把规则变成 API 本身无法表达的行为，这比文档和 code review 更稳定。

第三种误解是把所有异常都翻译成 `DataAccessException`。回调抛出的 SQLException 表示 JDBC 路径失败，应翻译并保留 cause；回调主动抛出的 `IllegalStateException` 表示业务决定失败，应原样重抛。`Error` 也属于必须回滚后原样传播的失败，例如 `StackOverflowError`；这与 HTTP 中间件是否捕获 Error 是两件事，data 边界不能因为调用方是 Web 就吞掉严重错误。

提交失败需要特别谨慎。`Connection.commit()` 抛出 SQLException 时，不能断言“肯定没提交”；有些驱动可能已经发送提交但响应失败。当前实现先尝试 rollback、再释放连接、最后报告 commit 的 DataAccessException。rollback 自身失败不会替换 commit 异常，而是作为 suppressed 附在 commit 异常上；回调失败后的 rollback 同样保留第一失败，但回调路径附上的是翻译后的 DataAccessException。两个场景都保留双重失败证据，不能把“best effort”误解为“清理失败可以消失”。

释放连接也不是一句“恢复 auto-commit”就结束。`Transaction.release()` 先尝试 `setAutoCommit(true)`，失败则忽略，再运行 releaser，由 `Database.release` 尝试 close。它没有记录调用DataSource 前的 auto-commit 初值，也没有事务结束后的自动验证；当前设计假定池借出的连接应按默认 auto-commit 状态归还。若一个池配置或驱动采用不同约定，需要独立验证。cleanup 失败不覆盖已知业务结果，是主动选择的异常优先级，不是所有清理都保证成功。

## 动手

先定义回调接口。它返回泛型 `T`，允许无返回值的工作单元使用 `Void` 并显式 `return null`；`throws SQLException` 让原始 JDBC 失败可以被边界识别。

```java
@FunctionalInterface
public interface TransactionCallback<T> {
  T doInTransaction(Transaction transaction) throws SQLException;
}
```

`Transaction` 的构造器是 package-private。它接收 Connection 与 Runnable releaser，立即调用 `setAutoCommit(false)`；若失败，先关闭连接，再抛 `DataAccessException`。这个顺序保证一个不能进入事务作用域的连接不会被交给回调，也不会因为构造失败而泄漏。

`Database.transaction` 是唯一创建 Transaction 的公开路径。它先用 `Objects.requireNonNull` 拒绝 null callback，再 acquire；构造失败发生在 try 之前，因为构造器已经自行负责清理。成功构造后，正常结果保存在局部变量，只有 callback 完整返回才执行 commit；catch 分支先 rollback 并把 cleanup 失败按规则附加；finally 的 `close()` 是最后防线，只处理尚未 decided 的意外出口。

```java
public <T> T transaction(TransactionCallback<T> work) {
  Objects.requireNonNull(work, "work");
  Connection connection = acquire();
  final Transaction transaction = new Transaction(connection, () -> release(connection));
  try {
    T result;
    try {
      result = work.doInTransaction(transaction);
    } catch (SQLException failure) {
      rollbackWithSuppressed(transaction, failure);
      throw new DataAccessException("transaction failed; rollback was attempted", failure);
    } catch (RuntimeException | Error failure) {
      rollbackWithSuppressed(transaction, failure);
      throw failure;
    }
    transaction.commit();
    return result;
  } finally {
    transaction.close();
  }
}
```

见 [Database.java:134](../../framework/barezen-data/src/main/java/com/barezen/data/Database.java#L134)。这里最重要的不是 catch 数量，而是“decide once”：callback 失败时 rollback 会把 decided 设为 true，finally 不再 rollback；callback 成功时 commit 会释放连接并设 decided，finally 不再做任何事。重复决策会被 `requireUndecided()` 拒绝。

`Transaction.executeUpdate` 与 `query` 复用第 1 步的 `JdbcCollect`，但先调用 `liveConnection()` 检查生命周期。它们的异常消息分别带 `inside a transaction`，让调用者知道失败发生在工作单元内。`commit` 与 `rollback` 都在入口设 `decided = true`，即使底层 JDBC 调用失败也不允许再次决定；一个结果未知的事务不能被第二次提交“补救”。

```java
void commit() {
  requireUndecided();
  decided = true;
  try {
    connection.commit();
  } catch (SQLException e) {
    DataAccessException failure = new DataAccessException(
        "transaction commit failed; rollback was attempted", e);
    try {
      connection.rollback();
    } catch (SQLException rollbackFailure) {
      failure.addSuppressed(rollbackFailure);
    }
    release();
    throw failure;
  }
  release();
}
```

见 [Transaction.java:115](../../framework/barezen-data/src/main/java/com/barezen/data/Transaction.java#L115)。`rollback` 同样先设 decided，失败时仍 release，再抛 DataAccessException。`Database.rollbackWithSuppressed` 捕获这个 cleanup 异常并 `failure.addSuppressed(cleanup)`，所以调用者看到原业务异常，同时可以通过 suppressed 检查回滚失败。commit 路径不经过这个 helper：它在 Transaction 内直接保留底层 rollback SQLException，避免重新包装已经明确的 JDBC 失败来源。

应用使用方式必须把同一个 `tx` 传给所有参与调用：

```java
String result = database.transaction(tx -> {
  tx.executeUpdate("INSERT INTO note (id, body) VALUES (?, ?)", 1L, "first");
  tx.executeUpdate("INSERT INTO audit (note_id, action) VALUES (?, ?)", 1L, "created");
  return tx.query("SELECT body FROM note WHERE id = ?", rs -> rs.getString(1), 1L).get(0);
});
```

不要在外层再调用一次 `database.executeUpdate` 并以为它加入当前事务。`Database` 没有 ambient 查询；那个调用会借一条独立连接。需要组合时，把 Transaction 作为 repository 方法参数显式传下去。

## 常见的第一次写错

1. **错误：把 commit/rollback 改成 public，让 repository 自行调用。** 正确：保持 package-private，由 Database 在回调边界决定；反射测试会锁定这一点。
2. **错误：callback 正常返回后只设一个 committed 标志，却不调用 JDBC commit。** 正确：decided 与数据库动作是两件事；必须实际 commit，且释放连接。
3. **错误：callback 抛 RuntimeException 时不 rollback。** 正确：任何 checked/runtime/Error 失败都使工作单元不可信，先回滚再按类型决定是否翻译。
4. **错误：rollback 失败时抛 cleanup 异常覆盖第一失败。** 正确：回调路径把 DataAccessException 作为 suppressed；commit 路径保留 rollback 的 SQLException 作为 suppressed。
5. **错误：commit 失败后直接 close，不尝试 rollback。** 正确：当前策略先 best-effort rollback，因为 commit 结果未知；记录器测试固定实际调用序列。
6. **错误：保存 Transaction 到字段，稍后异步使用。** 正确：只在回调内存活；decided 后公开方法拒绝使用，也不承诺跨线程 JDBC 对象安全。
7. **错误：嵌套调用 `transaction` 期待加入外层。** 正确：它借新连接、开独立事务；需要组合就把外层 `Transaction` 显式传给内层 repository。
8. **错误：认为 setAutoCommit(true) 失败也无所谓，所以不测试。** 正确：它不覆盖结果，但必须被尝试；池借还协议需要验证，当前测试只覆盖成功恢复与注入的进入失败。

## 怎么确认这一步没造错

运行 `TransactionTest` 的十四项测试：

```bash
mvn -o -B -ntp -pl framework/barezen-data -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=TransactionTest
```

预期 14 项全部通过，分解为 DecisionTable 7、Isolation 2、Ownership 4、Concurrent 1。正常提交后另一个连接能看到写入；SQLException 与 IllegalStateException 后 count 为零；repository 已抛出的 DataAccessException 保持自身类型并回滚此前写入。测试不是只观察异常类型，而是查询真实 H2 数据，证明回滚确实发生。

commit 失败测试使用 `RecordingDataSource.failNextCommit()`，断言异常含 `transaction commit failed`，并读取实际 JDBC 序列：

```text
setAutoCommit:false → commit → rollback → setAutoCommit:true
```

`recorded.leaks()` 必须为空。callback 失败测试断言原 `IllegalStateException` 的 suppressed 中存在 `DataAccessException`；新增的双重失败测试同时调用 `failNextCommit()` 与 `failNextRollback()`，要求 commit 的 DataAccessException 恰好附加一个 rollback SQLException，且仍无连接泄漏。三个测试分别验证正常回滚、回调失败的清理附属关系和提交失败的清理附属关系，不能合并成模糊的“失败会回滚”。

Ownership 测试用反射调用 `Transaction.class.getMethod("query", ...)` 证明公开操作存在，同时期待 `getMethod("commit")` 与 `getMethod("rollback")` 抛 `NoSuchMethodException`。这不是测试编译器，而是防止未来通过新增 public 方法绕过约束。生命周期测试在回调中保存 tx，结束后再 update/query，必须得到 `already committed or rolled back`，且迟到写入没有发生。

Isolation 测试让事务内 query 看见自己的未提交行，另一个 Database 借另一连接看不到；提交后外部可见。Nesting 测试在外层插入后进入内层 transaction，内层看不到外层未提交数据，随后外层失败；最终外层两行都不存在。它证明的是“两个独立单元”，并没有证明内层写在外层失败后仍保留，因为当前内层只做读取；要覆盖那个组合需要新的写入测试。

Concurrent 测试用八条线程同时通过同一个 Database 各插入一行，最终恰好八行、ID 1—8。它验证实例没有共享事务或连接字段；DataSource 与真实池的并发容量仍需要应用自己的测试。不要把它夸大为锁竞争、死锁或高并发性能证明。

## 此刻的代码长什么样

现在单次 CRUD 与工作单元已经分成两种清晰形状。单次操作简洁，跨语句操作必须进入一个 lambda，并把 `Transaction` 显式传给协作者。`Transaction` 的公开面只有 query/update，commit/rollback 与构造器都留在包内；回调结束后对象失效，连接在每条正常与失败路径上尝试归还。

下一步处理 schema 如何随部署演进。普通事务的 DML 回滚已经在 H2 上得到验证，但 migration 会执行 DDL，而 H2 对 CREATE TABLE 采用隐式提交。若直接复用“失败全回滚”的故事，会写出一个被实测否定的承诺。下一步将让 Migrator 持有整个迁移运行的一条连接、逐版本提交历史，并用历史表作为“哪些 apply 完成”的权威。

当前还有真实边界没有隐藏：嵌套是独立事务而非传播；没有隔离级别或 savepoint API；没有 XA/分布式事务；setAutoCommit 恢复是 best effort；关闭失败无法回报；八线程测试不是池压力测试。一个轻量框架的价值不在于假装覆盖这些能力，而在于让应用能在需要时明确替换或扩展边界。
