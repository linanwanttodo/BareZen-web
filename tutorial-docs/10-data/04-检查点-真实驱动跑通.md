# 第 10 章第 4 步：检查点——真实驱动跑通

## 这一步要解决什么

前三步分别建立了连接边界、事务归属和迁移历史。现在要把它们组合成一个可执行的验收，而不是继续增加 API。检查点要回答四个问题：测试是否真的经过 H2 驱动；失败路径是否验证了资源释放；模块是否仍然没有 compile 依赖；一个只使用公共 API 的示例能否从空库迁移、提交、查询并在业务失败后回滚。

这里的“真实驱动”不是把 H2 名字放进生产代码，而是让测试通过真正的 JDBC 协议执行 SQL。`DatabaseTest` 与 `TransactionTest` 用第二个连接观察提交或回滚结果；`DatabaseLifecycleTest` 与 commit 失败测试通过动态代理记录实际调用。只 mock 一个 Connection 并预设 commit 被调用，无法证明数据消失，也无法证明 ResultSet 关闭。真实 H2 加记录器同时提供数据库事实与 JDBC 调用事实。

本步还要固定证据范围。当前检查环境是 Linux amd65、Oracle JDK 24.0.2、Maven 3.9.12；项目的字节码基线仍是 release 17，不是“JDK 24 项目”。JDK 21+ 能力探测与虚拟线程属于 HTTP 运行期选择，data 模块没有平台条件分支。测试在 JDK 24 上运行，只能证明当前环境；不能冒充 JDK 17 实机验收，也不能把 H2 结果扩展为 PostgreSQL/MySQL 产品矩阵。

最终验收包括三层：67 项 data 模块测试，2 项 `DatabaseExampleTest`，以及真实 `DatabaseExample.main`。此外用 `dependency:tree -Dscope=compile` 检查编译依赖，用模块字节码契约检查所有输出 class major 61。测试数量来自本轮命令输出，不是从 ADR 抄来的历史数字；两者恰好一致，但证据来源不同。

## 先想清楚再写

写检查点前要先定义“通过”意味着什么。`BUILD SUCCESS` 是 Maven 进程结果；`Tests run` 是 Surefire 发现的测试数；`class-major: checked=49 ...` 是实际扫描的 class 文件数与版本；main 的业务输出是空库到回滚的完整路径。它们互相补充，不能只留一句“测试通过”。尤其要记录零失败、零错误、零跳过，以及每个关键类的测试数量。

测试必须对失败敏感。若把 `Database.executeUpdate` 的连接关闭删掉，RecordingDataSource 的未关闭连接列表会非空；若删掉事务 commit，成功提交测试从另一个连接读不到数据；若删掉 rollback，失败后的 COUNT 仍会看到插入行；若把 commit 改为 public，反射测试会失败；若 migration 不拒绝倒序补号，OutOfOrder 测试会看到 5 被错误执行。探针的价值是让每个核心断言有“反面会红”的对象。

但检查点不能把所有失败都解释成框架 bug。此前 HTTP 模块的 `JdkMethodCaseSemanticsTest` 在当前 JDK 上有已知环境差异，本轮 data 测试使用精确 `-Dtest` 列表，不触发那些无关测试；不能为了让全仓库绿灯而修改它们。data 的架构测试与字节码契约则必须包含，因为“结果正确但依赖漂移”同样是本章失败。

还要区分覆盖与证明。七条 ArchUnit 规则证明当前导入图与调用图不违反边界，不证明未来所有依赖都合理；49 个 class 文件全是 major 61，不证明每个 API 在 JDK 17 上做过运行验收；67 项测试证明 H2 上的契约，不证明真实连接池的坏连接处理、数据库故障切换或 DDL 跨产品行为。把这些范围写进教程，比堆一个漂亮的 coverage 百分比更诚实。

最后，示例代码也需要被检查，而不是因为它能运行就视为无瑕。当前 `DatabaseExample.migrations()` 直接 `connection.createStatement().execute(...)`，没有用 try-with-resources 关闭 Statement。连接最终由 Migrator 关闭，示例可以运行，但这是示例可改进的资源管理点。教程不修改源码，也不把它当作 data 框架行为的反例；它提醒读者：框架只能关闭自己创建的 statement，不能替 migration 中未交回的局部 statement 负责。

## 动手

在仓库根目录运行完整的六类模块测试。`-am` 构建上游依赖，`failIfNoSpecifiedTests=false` 允许没有匹配测试的上游模块继续；测试列表避免误跑已知 JDK 差异用例。公开 API 入口见 [Database.java:80](../../framework/barezen-data/src/main/java/com/barezen/data/Database.java#L80)、[Transaction.java:77](../../framework/barezen-data/src/main/java/com/barezen/data/Transaction.java#L77) 与 [Migrator.java:111](../../framework/barezen-data/src/main/java/com/barezen/data/Migrator.java#L111)；本章测试再通过真实 JDBC 调用验证这些入口的资源与事务行为。

```bash
mvn -o -B -ntp -pl framework/barezen-data -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=DatabaseTest,DatabaseLifecycleTest,TransactionTest,MigratorTest,BarezenDataArchitectureTest,ClassMajorContractTest'
```

本轮实际结果是 `BUILD SUCCESS`，总耗时 5.079 秒。`barezen-data` 汇总为：

```text
Tests run: 67, Failures: 0, Errors: 0, Skipped: 0
class-major: checked=49 unique-majors=[61] expected=61
```

数量分解如下，不能用模块汇总掩盖嵌套类：

| 测试类 | 项数 | 验证重点 |
| --- | ---: | --- |
| `DatabaseTest` | 8 | 构造校验、参数化 CRUD、null 参数、游标顺序、异常翻译 |
| `DatabaseLifecycleTest` | 11 | 连接/statement/cursor 关闭、绑定失败、获取连接失败、进入事务失败 |
| `TransactionTest` | 14 | 七行决策表、隔离、归属、生命周期、嵌套、八线程独立单元 |
| `MigratorTest` | 23 | 六种迁移状态、乱序拒绝、验证、固定 Clock、可查询历史、双重失败与丢失提交响应 |
| `BarezenDataArchitectureTest` | 7 | 层间隔离、无驱动、无 ThreadLocal、无环境读取、无日志、无可变静态字段 |
| `ClassMajorContractTest` | 4 | class major 61、预期常量、shell guard 一致、错误头识别 |

接下来单独运行示例测试。这里让 Maven 构建 examples 及其上游，而不是只执行已存在的 class 文件，以排除旧编译产物造成的结果偏差。

```bash
mvn -o -B -ntp -pl examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=DatabaseExampleTest
```

本轮输出 `DatabaseExampleTest` 2 项、零失败/错误/跳过，`BUILD SUCCESS`，总耗时 1.797 秒。第一项测试执行 migration、提交一行、按 id 查询并得到 `first`；第二项先提交 `kept`，再在事务中插入 `doomed` 后抛 `IllegalStateException`，最后查询只保留 ID 1。它验证示例公共路径，不替代模块内部的注入失败与生命周期测试。

然后检查 compile 依赖。输出文件是命令写入 `/tmp` 的本轮临时证据，不是仓库文件，也不是需要提交的文档产物。

```bash
mvn -o -B -ntp -pl framework/barezen-data dependency:tree \
  -Dscope=compile -DoutputFile=/tmp/barezen-data-compile-tree.txt
```

本轮生成的树只有模块自身：

```text
com.barezen:barezen-data:jar:0.1.0-SNAPSHOT
```

没有任何第三方或框架 artifact。这里的空树是 `-Dscope=compile` 的结果；H2、JUnit、AssertJ 与 ArchUnit 仍存在于 test scope，不能误写成“模块没有测试依赖”。架构测试再禁止主源码导入这些驱动，形成 POM 与字节码导入图的双重证据。

最后运行真实 main。classpath 只包含 examples、data 与本轮使用的 H2 jar；data 模块没有 slf4j 依赖，因此这里不需要其他框架模块。

```bash
M2=$HOME/.m2/repository
CP="$PWD/examples/target/classes:$PWD/framework/barezen-data/target/classes:$M2/com/h2database/h2/2.2.224/h2-2.2.224.jar"
java -cp "$CP" com.barezen.examples.database.DatabaseExample
```

本轮输出如下，`appliedAt` 是运行时值，每次不同：

```text
migrated -> [AppliedMigration[version=1, description=create notes, appliedAt=2026-11-24T11:58:01.368967406Z]]
notes    -> [first, second]
after rollback, rows -> 2 (the doomed insert never landed)
```

这三行对应三个事实：空库接受版本 1；同一事务中的两行提交后按 id 读出；第三行插入后业务异常，回滚使其没有落地。示例用 `jdbc:h2:mem:barezen_example_<UUID>;DB_CLOSE_DELAY=-1` 保证每次 main 从空库开始，名字是应用选择，不是 data 模块硬编码。

## 常见的第一次写错

1. **错误：只运行 `DatabaseExampleTest` 就宣称模块通过。** 正确：示例只有两项，必须运行行为、生命周期、事务、迁移、架构与字节码六类，共 67 项。
2. **错误：把嵌套 Surefire 的单项输出相加后，又加上父类 0 项导致虚高。** 正确：使用模块汇总 65，再列出 8+11+14+23+7+4 的分解，二者一致。
3. **错误：用 ADR 的测试数替代本轮输出。** 正确：本轮实跑并记录命令、耗时、失败/错误/跳过与 class-major 扫描结果。
4. **错误：看到 data 测试通过就修改或绕过 HTTP 的已知 JDK 差异测试。** 正确：精确选择本章测试，不改变无关用户 WIP，也不把环境差异误报为 data bug。
5. **错误：把 compile 依赖为空说成所有依赖为空。** 正确：H2 与测试工具是 test scope；compile 树只证明生产依赖边界。
6. **错误：在 JDK 24 上说“项目就是 JDK 24”或“已在 JDK 17 实机验证”。** 正确：运行环境是 JDK 24.0.2，发布契约是 release 17 / class major 61。
7. **错误：把真实 H2 通过等同于支持所有数据库。** 正确：只测了 H2 2.2.224；SQL 方言、DDL、null 类型与池行为需逐产品测量。
8. **错误：因为示例能运行，就忽略 migration 内未关闭的 Statement。** 正确：记录为示例债务；框架只管理自己创建的 JDBC 资源。
9. **错误：用 67 项或 49 个 class 文件代替业务断言。** 正确：数量是规模，数据可见性、调用顺序和资源关闭才是通过条件。

## 怎么确认这一步没造错

检查日志时应同时确认三个层面。Maven 层面是退出码 0 与 `BUILD SUCCESS`；测试层面是 67/2 项都零失败、零错误、零跳过；事实层面是 rollback 后 COUNT 为预期值、commit 失败序列包含 rollback、commit 与 rollback 同时失败时两类异常都保留、泄漏列表为空、倒序迁移没有运行、DML 回滚后另一连接查不到、H2 DDL 孤儿表按实测保留。只有漂亮汇总而没有这些断言，不能说明边界正确。

字节码输出应为 `checked=49 unique-majors=[61] expected=61`。这个计数包含 data 模块 `target/classes` 与 `target/test-classes` 下的 class 文件；如果为 0，契约测试会主动失败，防止扫描错目录后假通过。`ClassMajorContractTest` 还验证整仓库 shell guard 的预期常量与自身一致，并用伪造的 major 65 和非 class 头测试读取器，不是无条件返回 61。

compile 依赖树应只有 `barezen-data` 自身。若出现 H2、驱动、池、core 或日志 facade，说明边界已经漂移，应检查 POM 与主源码导入。注意 `dependency:tree` 与 ArchUnit 检查的是不同证据：前者看构建依赖，后者看实际字节码引用；一个依赖可以通过 test scope 合法存在，却不能进入主源码。

真实示例的输出应稳定为两行 notes 和回滚后 count 2，只有 appliedAt 随运行变化。如果 count 为 3，说明事务没有回滚；如果 migration 重复创建失败，说明示例数据源没有隔离；如果 classpath 缺 H2，失败发生在应用装配而非 data API。把失败定位到层，是检查点的重要输出。

本轮没有执行整仓库 `mvn verify`，因此不宣称整仓库覆盖率门禁已通过，也不把 ADR 的历史覆盖率数字写成本轮实测。data POM 在 JDK 21+ 激活 JaCoCo 85% 行覆盖率门禁，但 `test` 阶段不执行 verify 的 check goal。若后续要作发布验收，应在独立步骤运行 verify，并保留完整退出码与报告。

## 此刻的代码长什么样

第 10 章到此形成一条完整链路：应用创建 DataSource，`Migrator` 在空库创建历史表并应用版本 1，`Database.transaction` 把多条写入作为一个单元提交，`Database.query` 返回映射列表；第三个事务失败后 rollback，外部查询证明它没有留下数据。模块保持零 compile 依赖，事务决策不暴露，迁移以历史为权威，真实 DDL 失败边界被明确记录。

已经证明的是当前 H2 与注入失败点上的 67 项行为，以及示例 2 项和真实 main。尚未证明的是多数据库产品矩阵、真实池故障、并发迁移、锁竞争、大数据量性能、JDK 17 实机运行、整仓库 verify 与覆盖率门禁。示例 Statement 未显式关闭、commit 响应失败后结果不确定、setAutoCommit 初值未保存、close 失败不回报，都是应保留在代码审查记录里的真实限制。

下一章将把“应用提供一个 DataSource”扩展为“应用允许一组显式插件进入运行时”。插件同样不能靠全局服务定位器或隐藏类路径扫描获得依赖；生命周期、失败与调用边界会像事务一样，被设计成代码中可见、测试中可证的所有权关系。
