# 第 10 章第 3 步：版本化迁移与回滚权威

## 这一步要解决什么

应用已经有事务，但部署新版本时还会遇到另一类问题：某张表是否已经创建？某个列是否已经添加？上次启动是否在第三个 migration 中途失败？`Migration` 与 `Migrator` 要回答的不是“现在 schema 应该长什么样”，而是“数据库已经接受了哪些编号的变更”。这两个问题在 DDL 失败时可能给出不同答案。

本步在 `5c2cd05` 中与数据库入口一起建立。`Migration` 是应用实现的三方法接口：正整数 `version()`、非空 `description()`、接收原始 Connection 的 `apply(Connection)`。`Migrator` 持有 Database 与 Clock，提供 `migrate(List<Migration>)` 和 `history()`。它创建并维护 `barezen_migration_history`，每次只执行未记录的版本，并返回本次实际应用的 `AppliedMigration` 列表。

迁移接收原始 Connection 是经过考虑的例外。DDL、数据库特有类型和数据回填有时无法诚实地塞进 query/update 抽象；此时 SQL 就是迁移作者要负责的语言。但 Connection 的所有权仍不转移：migration 不得 commit、rollback 或 close。Migrator 在 apply 后插入历史行，再提交整个版本；一个版本只有 apply 正常完成才进入历史。

这里最关键的词是“权威”。历史表记录框架能保证的事实，schema 是数据库对 DDL 的实际结果。H2 实测表明，事务内 CREATE TABLE 后 rollback，表仍然存在；DML 对照则会消失。因此本实现不承诺“失败的 migration 不留痕迹”，而承诺“失败版本不记录、后续版本不执行、下次启动会重跑该版本”。恢复方向是向前重跑并修复，不是自动 down。

## 先想清楚再写

最直觉的方案是每次启动运行全部 SQL。第二次 CREATE TABLE 就会撞上已存在的对象；即使全部写成 IF NOT EXISTS，数据回填也可能重复执行，无法区分“从未运行”和“上次已经完成”。另一个方案是只保存一个最大版本，例如 `schema_version=4`；它不能表达 1、2、4 的历史，也无法处理失败的 3 和已成功的 2。一个版本一行、带 description 与 applied_at 的历史表，才能让操作者直接查询数据库事实。

第二个选择是版本标识。列表位置不能作为身份，因为应用新增 migration 后自然会把旧项往后推；随机文件名排序也不可靠。当前选择正整数 long，在给定列表中唯一，一旦应用就不能重用、重编号或修改 SQL。需要说明执行边界：框架会拒绝本次列表中的非正数、重复号和空描述，也会拒绝低于已应用最大值的待执行版本；它不会校验已应用 migration 的 checksum，因此“已应用版本不可修改”是应用纪律，不是代码强制事实。

第三个问题是乱序。给定列表可以是 [2,1]，框架排序后执行 1、2；但数据库已经到 12 时突然补入 7，不能默默运行，因为 7 的 SQL 可能假设 12 之后的结构。检查必须针对 pending，而不是完整列表。若拿列表第一项 1 与最高已应用 12 比较，每次带完整旧列表启动都会误报。当前先读历史、过滤 pending，再比较最小 pending 与最大 applied；最小 pending 高于最大 applied，就允许所有更高版本，包括 1 后直接到 4 的间隔。

第四个问题是异常分类。migration 列表中的重复、空描述、非正版本是代码错误，应在打开数据库前抛 IllegalArgumentException；null 列表或元素是无效输入，以 NullPointerException 拒绝。获取连接、创建/读取历史、apply 的 SQLException、历史查询失败属于数据库边界失败，以 DataAccessException 到达。migration 自己抛出的业务 RuntimeException/Error 则回滚后原样传播，不伪装成数据库故障。异常类型是修复责任的提示，不只是风格。

第五个问题是并发与锁。当前没有迁移锁，也没有并发运行协调。两个应用实例同时启动可能都读到同一 pending 集合并尝试插入同一主键；其中一个可能失败，但不能把这套代码描述为安全的 rolling deployment 协调器。部署应保证单实例迁移或由外部启动步骤串行化。新增一个 lock 表会引入第二个权威与新的失败状态，需要 ADR，而不是顺手加个 `synchronized`——JVM 锁也挡不住另一个进程。

最后是时间。`Migrator.of(database)` 使用 `Clock.systemUTC()`；测试用 `Clock.fixed` 注入。一次 migrate 在开始时读取一个 Instant，并把它用于本轮所有成功版本，而不是每条 SQL 都重新取当前时间。这个时间表示本轮记录时间，不是每个 migration 编译或作者执行的时间，也不能当安全审计凭据。`history()` 从数据库重新读取，不依赖 Migrator 内存。

## 动手

先定义应用侧契约。`Migration` 的 javadoc 明确要求 DDL 步骤可重跑，因为未记录版本下次会再执行；`IF NOT EXISTS` 是 H2 可用的写法，但等价语法属于目标数据库方言，不能宣称这段 SQL 对所有产品都可移植。

```java
public interface Migration {
  long version();
  String description();
  void apply(Connection connection) throws SQLException;
}
```

示例的版本 1 创建 notes 表，版本身份与 SQL 一起位于 [DatabaseExample.java](../../examples/src/main/java/com/barezen/examples/database/DatabaseExample.java) 的 `migrations()`。应用把完整列表交给 Migrator，框架不扫描 classpath，不读取 `.sql` 文件，也不解析文件名。新增 migration 就是新增列表中的显式对象；这与第 7 章的显式装配一致。

`migrate` 的第一阶段完全不接触数据库：`validateAndSort` 检查 null、正整数、非空 description 和重复 version，再复制并升序排序。只有列表有效才 acquire 一条连接。该连接通过 package-private `Database.openConnection()` 借出，跨越创建历史表、读取版本、执行所有 pending migration，最后由 finally 关闭。Migrator 与 Database 同包，因此可以使用这个不公开的连接 seam；应用不能通过 Database 公开 API 拿到它。

```java
List<Migration> ordered = validateAndSort(migrations);
Instant now = clock.instant();
Connection connection = database.openConnection();
try {
  createHistoryTable(connection);
  Set<Long> alreadyApplied = readAppliedVersions(connection);
  List<Migration> pending = new ArrayList<>();
  for (Migration migration : ordered) {
    if (!alreadyApplied.contains(migration.version())) {
      pending.add(migration);
    }
  }
  rejectOutOfOrder(alreadyApplied, pending);
  for (Migration migration : pending) {
    applyOne(connection, migration, now, applied);
  }
  return applied;
} catch (SQLException e) {
  throw new DataAccessException("migration run failed before the first version was recorded", e);
} finally {
  closeQuietly(connection);
}
```

见 [Migrator.java:111](../../framework/barezen-data/src/main/java/com/barezen/data/Migrator.java#L111)。`rejectOutOfOrder` 只在 alreadyApplied 与 pending 都非空时比较；pending 为空时完整旧列表是合法 no-op。版本 5 高于已应用最大 2，即使中间没有 3、4，也会运行；倒序补号则抛 DataAccessException 并在消息中同时写出 5 与 10。

每个版本由 `applyOne` 决定。它关闭 auto-commit，调用 apply，再向历史表插入 version/description/applied_at，成功后 commit。SQLException、RuntimeException 或 Error 都会先 rollback；SQLException 被翻译为带版本和描述的信息，其他类型原样抛出。失败后不会恢复 auto-commit，因为整个运行立即终止并关闭连接；只有成功提交的版本才恢复 auto-commit 并加入返回列表。

```java
connection.setAutoCommit(false);
try {
  migration.apply(connection);
  try (PreparedStatement record = connection.prepareStatement(
      "INSERT INTO " + HISTORY_TABLE
          + " (version, description, applied_at) VALUES (?, ?, ?)")) {
    record.setLong(1, migration.version());
    record.setString(2, migration.description());
    record.setTimestamp(3, Timestamp.from(now));
    record.executeUpdate();
  }
  connection.commit();
} catch (SQLException | RuntimeException | Error failure) {
  rollbackQuietly(connection);
  if (failure instanceof SQLException sql) {
    throw new DataAccessException("migration " + migration.version() + " (\""
        + migration.description() + "\") failed and was rolled back; no later migration ran", sql);
  }
  throw failure;
}
```

见 [Migrator.java:231](../../framework/barezen-data/src/main/java/com/barezen/data/Migrator.java#L231)。“was rolled back”描述的是框架执行了 rollback 动作，不保证 DDL 逆向消失。rollback 自身失败当前被忽略，不附加 suppressed；如果 cleanup 也失败，调用者首先看到导致 apply 中止的 SQLException。另一个必须注意的事实是：成功执行 DDL 后再抛 RuntimeException，框架同样尝试 rollback，但 DDL 可能已隐式提交，版本仍不记录。

历史表使用 `version BIGINT PRIMARY KEY`、`description VARCHAR(512) NOT NULL`、`applied_at TIMESTAMP NOT NULL`。主键是数据库级重复保护，列表校验是更早、更友好的保护。`history()` 若发现表不存在返回空 list；否则按 version 升序读取并构造 `AppliedMigration(long, String, Instant)`。它通过 DatabaseMetaData.getTables 列出表名并忽略大小写比较，避免 H2 大写折叠与 PostgreSQL 小写 folding 的差异。

`history()` 是只读视图，但不是数据库安全边界：应用仍可用自己的 DataSource 直接修改历史表。ArchUnit 或包可见性不能阻止拥有数据库凭据的人执行 SQL；当前承诺是框架不提供公开写历史的方法，操作权限与数据库隔离必须由部署负责。

## 常见的第一次写错

1. **错误：以列表下标或文件名作为版本。** 正确：显式正整数 long，应用后不复用；新增项不改变旧版本身份。
2. **错误：把完整列表第一项与最高已应用版本比较。** 正确：先过滤 pending，再比较最小 pending；否则正常启动永远失败。
3. **错误：数据库到 12 后静默补跑 7。** 正确：拒绝倒序，因为 schema 演进顺序是历史事实；同时允许 1 到 4 的正常间隔。
4. **错误：apply 内自行 commit 或 close。** 正确：只执行变更语句；Migrator 拥有连接并在 apply 后记录和提交。
5. **错误：CREATE TABLE 不带 IF NOT EXISTS，却承诺失败无痕迹。** 正确：H2 DDL 可能留下孤儿表，未记录版本会重跑，因此 migration 必须可重入。
6. **错误：失败后让后续 migration 继续跑。** 正确：立即停止，历史保留最后成功版本，下一启动从失败版本继续。
7. **错误：编辑已应用 migration 的 SQL。** 正确：新增版本；当前没有 checksum 能发现原地修改，纪律必须由 review 保证。
8. **错误：用 JVM synchronized 解决多实例同时启动。** 正确：当前明确不支持并发迁移；部署层串行化，或未来设计数据库锁并写 ADR。
9. **错误：把 history 时间当作可信安全日志。** 正确：它来自主机 Clock 与数据库 timestamp，是审计辅助，不是防篡改记录。

## 怎么确认这一步没造错

运行迁移的二十一项测试：

```bash
mvn -o -B -ntp -pl framework/barezen-data -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=MigratorTest
```

预期 Fresh 3、Existing 2、Duplicate 1、Failure 3、OutOfOrder 3、Validation 3、History 3、Construction 2、RunEffect 1，共 21 项通过。乱序输入测试不仅检查返回列表，还用 tracked migration 记录实际 apply 顺序为 `123`；同一版本执行两次启动只运行一次。空 pending 返回空 list，而不是整个历史。

失败测试创建 orphan 表后抛 SQLException。断言历史为空、后续 migration 计数为零、orphan 表仍然存在。这个“仍然存在”不是测试写错，而是被测数据库的真实行为。恢复测试第一次执行 `CREATE TABLE IF NOT EXISTS item` 后失败，第二次同一 migration 成功并返回版本 1，证明重跑路径可用。它没有证明任意 migration 都幂等；不可重入的 SQL 仍会反复失败。

OutOfOrder 测试覆盖三种不同状态：先应用 2、10 后补入 5 被拒绝；已有 1 时应用 4 被允许；已有 1、2 后传入完整列表再加 3，只应用 3。第三种是防止错误检查回归的关键测试。Validation 测试在非正版本与重复号情况下检查历史表根本不存在，证明“先校验、后连库”不只是注释。

History 测试注入固定 Instant，验证 version、description、appliedAt 三个字段；用另一个 Migrator 和另一条命名内存数据库连接读取相同记录；在未迁移数据库读取空列表。`H2` fixture 用 `DB_CLOSE_DELAY=-1` 保持零连接期间的内存库，所以测试能模拟“上次迁移结束、下次进程重新连接”的持久事实，而不是只在同一个对象里查字段。

## 此刻的代码长什么样

数据模块现在同时拥有两类所有权：普通事务由 Database 在 callback 边界决定，迁移运行由 Migrator 在一条长连接上逐版本决定。应用提供 DataSource 与 Migration 列表，不提供连接生命周期；框架提供 CRUD、工作单元、历史与异常翻译，不提供 ORM、自动发现或 schema diff。

真实边界也已明确：DDL 回滚不保证；已应用 SQL 无 checksum；没有 down；没有并发迁移锁；history 时间不是安全记录；一轮所有迁移共用一个 now；版本重用与原地编辑靠应用纪律。下一步把模块测试、示例测试和真实 main 串起来，验证公共 API 从空库到提交、查询、回滚的完整路径，并记录本次实际测试环境与尚未覆盖的产品矩阵。
