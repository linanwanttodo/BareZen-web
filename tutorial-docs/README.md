# 从空目录建造 BareZen

这是一份框架建造实录，不是 BareZen 的使用手册。读者应当会写 Java，知道一次 HTTP 请求大概经过客户端、服务端和业务代码，但想知道这些词落到源码里以后为什么长成这个形状。我们不从“复制多少功能”开始，而从“此刻缺哪个问题、有哪些答案、怎样证明答案没有造假”开始。

BareZen 的定位是理解 HTTP 框架内部原理的学习项目，加上可以承载小型同步服务的轻量骨架。它刻意不追求成熟框架的功能覆盖面，也不以替代任何框架为目标。手写路由、安全、事务和适配器的价值，在于每个决定都能被压缩成一条可执行规则，再被测试和架构门禁守住。

## 读者画像与前置条件

你需要能够阅读 Java 17 语法、Maven 多模块 POM、JUnit 测试和基本 HTTP 报文。不需要 Spring 经验，也不需要提前理解虚拟线程、MethodHandle 或 Servlet。教程出现这些概念时，先解释它们解决的问题，再给出仓库中真实存在的实现。

本教程按当前仓库的最终实现回放“第一次建造”的顺序，因此个别早期 ADR 的 API 已被后续决定修订。遇到这种地方，本文同时写出历史背景和当前代码，不把已废弃的形状教给读者。代码块来自真实源码、测试或示例，教学性简化会明确标注；它不会凭空补出仓库不存在的 API。

## 十二章地图

| 章 | 目录 | 要解决的问题 |
|:---|:---|:---|
| 1 | `01-what-this-project-is` | 项目是什么，手写哪些规则才真正产生学习价值 |
| 2 | `02-principles` | 字节码基线、运行期能力、模块方向和架构门禁 |
| 3 | `03-lifecycle` | 应用状态机、两阶段启动、失败回滚和最佳努力停机 |
| 4 | `04-http-contract` | 不绑定服务器的 Request、Response、Headers 与无体状态 |
| 5 | `05-router` | 原始路径段、参数提取、字面量优先和不可变路由表 |
| 6 | `06-jdk-http-adapter` | 契约到真实套接字的桥接、请求体上限和线程归属 |
| 7 | `07-configuration-and-assembly` | 配置快照、显式工厂装配和对象所有权 |
| 8 | `08-static-content` | 一文件一 Handler、ETag、条件请求与 304 分帧 |
| 9 | `09-security` | PBKDF2、可撤销会话、认证三态和拒绝路径 |
| 10 | `10-data` | DataSource 边界、显式事务和迁移历史 |
| 11 | `11-plugin-spi` | 插件描述符、ServiceLoader 发现、路由贡献和注册校验 |
| 12 | `12-openapi-testkit` | 声明式 OpenAPI、确定性 JSON 与真实端口集成测试 |

建议按顺序阅读。第四章的契约是第五章路由器的输入，第六章适配器又同时消费路由器和契约；跳着读不会得到编译错误，却会错过“为什么边界画在这里”的因果。每章末尾都是检查点，它把该章的口头承诺变成命令、输出和失败条件。

## 检查点约定

每个检查点都给出可执行的 Maven 命令、具体测试类或示例 `main`，并说明期望看到什么。命令中的 `-pl` 用于选择模块，`-am` 让 Maven 先构建它依赖的模块；`-Dtest=...` 缩小测试范围，但 Maven 仍会编译所选模块。需要同时指定多个测试类时使用逗号分隔，不要误以为一个字符串会做模糊匹配。使用 `-am` 时，上游模块通常没有这些测试类，因此检查点同时加入 `-Dsurefire.failIfNoSpecifiedTests=false`，只忽略“上游没有匹配测试”，不会忽略目标模块的测试失败。

教程编写时的环境是 JDK 24.0.2、Maven 3.9.12。项目产物仍以 `maven.compiler.release=17` 编译，即 major 61；运行期通过 `RuntimeCapabilities` 探测能力，JDK 21+ 才选择虚拟线程。构建主机版本不是产物基线，这个区别会一再出现。

`JdkMethodCaseSemanticsTest` 在当前 JDK 上存在已知的请求行解析差异失败，其表现是非法请求行期待 400、实际得到 405。它不是本教程要修的框架缺陷。相关检查点会指出它，不通过修改断言、跳过整个适配器或扩大清理范围来制造绿色。

## 怎么对照真实代码

仓库中的实现是最终证据，本文是理解它的路线图。每篇步骤的“动手”会列出实际类和关键签名，“怎么确认”会指向真实测试。读完以后，请打开对应源码逐行比较，尤其注意构造校验、防御性复制、资源关闭顺序和异常出口；这些地方最能区分“看起来能跑”和“契约成立”。

ADR 记录决定及其代价，本文把同一决定翻译成第一次实现时的处境。若 ADR 与当前源码看似冲突，先查后续 ADR 是否修订了它，再看当前测试究竟保护哪条行为。不要通过改代码来让文档显得正确。

## 学习产出

完成后，你应该得到一张能自己检查的依赖图：core 不碰 HTTP，web 不绑定服务器，adapter 不制定安全政策，data 不选择驱动，testkit 不反向进入生产依赖。你还会得到一组可复用的判断方法：先写拒绝条件，再写正常路径；先决定所有权，再创建资源；先用失败测试定义边界，再用实现满足它。

这比“会调用某个框架的 API”更耐用。成熟框架会改变 API，但路径歧义、线程生命周期、事务提交权和错误状态压缩仍会以不同形式出现。能解释一项设计保护了什么、牺牲了什么，才真正算理解它。
