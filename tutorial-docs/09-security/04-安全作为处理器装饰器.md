# 第 9 章第 4 步：安全作为处理器装饰器

## 这一步要解决什么

认证结果与授权决策已经存在，现在要让每个受保护请求按固定顺序经过它们。不能修改 `Handler.handle(Request, Map)`，因为普通业务、路由、适配器和测试都依赖这个冻结契约；也不能让每个 Handler 自己写一遍登录判断。`SecurityMiddleware` 的实现方式是接收一个 Handler，返回另一个 Handler：路由注册时看不出新类型，但执行时先认证、再授权、最后才调用业务对象。

需要知道“我是谁”的 Handler 还有第二个小问题：两参数契约没有上下文位置。`SecuredHandler` 作为安全模块自己的可选接口补上第三个参数，中间件用 `instanceof` 分派。普通 Handler 继续接收两个参数且完全看不到身份；不需要身份的路线不必承担安全类型。这就是 ADR-0033 用装饰器而不是 filter chain、请求属性或 ThreadLocal 的原因。

## 先想清楚再写

如果给 `Request` 增加 `principal` 或 attribute bag，最初只是方便，随后所有 Handler 都会依赖这个可变含义的请求对象。路由参数来自客户端路径，安全上下文来自服务端判断，把它们塞进同一个 map 会让参数来源不再可信。若给所有 Handler 增加第三参数，整个 Web 契约会被一个可选能力污染，第二种适配器也必须知道安全；这比实现一个模块内装饰器的代价大得多。

ThreadLocal 看起来更省事，却正好在长连接上出错。一个服务器线程会顺序处理多个请求，若第一个请求设置 currentUser 后没有完美清理，第二个请求可能继承 ada 的身份；异步切换或异常提前返回还会扩大泄漏窗口。把上下文作为局部变量和方法参数传递，使身份生命周期与一次调用一致。请求可以在不同线程继续执行，身份也不依赖线程归属。

装饰器的顺序也不能随意调整。授权需要 Principal，所以认证必须先完成；业务 Handler 必须最后执行，否则被拒绝的请求已经产生副作用。若把 delegate 调用放在权限判断之前，再根据结果“修改响应”，数据库写入、文件删除或消息发送都无法撤回。拒绝路径必须是没有调用，而不是调用后覆盖状态码。

还要决定策略怎样附着到路由。四参数 `wrap` 接收明确的 `Permission`；三参数版本询问 `Permission.ANY`；两参数版本只要求认证。没有自动路由扫描，所以公开路线与受保护路线都能在路由表中直接看见。忘记包装仍然是应用错误，本章不会把它包装成“默认全局安全”。

## 动手

先提供包装工厂。四个协作者都拒绝 null，避免装配期悄悄产生一个无法决策的中间件。三参数与两参数重载最终委托给四参数版本，保证只有一个执行实现：

```java
public static Handler wrap(
    Authentication authentication, Authorization authorization, Permission required, Handler delegate) {
  Objects.requireNonNull(authentication, "the authentication");
  Objects.requireNonNull(authorization, "the authorization");
  Objects.requireNonNull(required, "the required permission");
  Objects.requireNonNull(delegate, "the delegate");
  return new SecurityMiddleware(authentication, authorization, required, delegate);
}

public static Handler wrap(Authentication authentication, Handler delegate) {
  return wrap(authentication, Authorization.allowAll(), Permission.ANY, delegate);
}
```

执行方法位于 `SecurityMiddleware.java:111`。先从 Header 找 `Authorization`：没有头就传 null；超过一个字段直接返回 401，且认证组件与业务 Handler 都不调用，避免代理与后端选择不同凭据。恰好一个字段但没有空格时按 Bearer 值处理；有空格时只在第一个空格处分 scheme 与 value，所以 value 可以包含后续空格。Header 名由 `Headers` 大小写不敏感查找；中间件不规范化 scheme，也不 trim。内置 `Authentication.bearer(...)` 与 `AuthPlugin` 在比较时忽略 scheme 大小写，token 值仍精确匹配。若 scheme 为 Unicode 空白或不是 RFC 9110 token（含分隔符、控制字符或非 ASCII），`Credential` 构造会拒绝；中间件在提取边界返回 401，而不是让客户端输入冒泡成 500。合法 `tchar` 标点仍可用于扩展 scheme。

```java
Credential credential;
try {
  credential = credentialFrom(request);
} catch (IllegalArgumentException malformedCredential) {
  return status(401, "Unauthorized");
}
AuthenticationResult result;
try {
  result = authentication.authenticate(credential);
} catch (RuntimeException e) {
  return status(500, "Internal Server Error");
}
if (!result.isAuthenticated()) {
  return status(401, "Unauthorized");
}
```

只有 authenticated 才构造 `SecurityContext` 并询问权限。授权不是 ALLOW 就返回 403；授权组件抛 `RuntimeException` 返回 500。允许后才进入分派：delegate 若实现 `SecuredHandler`，调用三参数方法；否则调用原两参数方法。错误响应使用固定 UTF-8 正文，Headers 为空，不附 reason 或内部异常。

```java
if (delegate instanceof SecuredHandler secured) {
  return secured.handle(request, parameters, context);
}
return delegate.handle(request, parameters);
```

同一装饰器边界也承载响应安全头。`SecurityHeaders.of(delegate, csp)` 不改变状态码或正文，只补应用缺少的 CSP、`X-Content-Type-Options: nosniff` 与 `Referrer-Policy: no-referrer`。CSP 由调用方提供，因为脚本、样式和连接源是页面策略；已有同名字段则原样保留。这展示了装饰器的另一种职责：不决定请求是否允许，而是在答案离开应用前补上不可遗漏的横切字段。

真实消费者 [SecurityExample.java:85](../../examples/src/main/java/com/barezen/examples/security/SecurityExample.java#L85) 注册三条路线：`/health` 公开，`/report` 要求 `report:read`，`/admin` 要求 `admin`。同一个 ada 身份和 token 在前者得到 200，在后者得到 403。`ReportHandler` 同时实现两个接口，三参数方法读取 `context.principal()`，两参数方法直接抛 `AssertionError`，把“包装后却走错入口”变成显式布线错误。

```java
.route(HttpMethod.GET, "/report",
    SecurityMiddleware.wrap(authentication(), authorization(), REPORT_READ, new ReportHandler()))
.route(HttpMethod.GET, "/admin",
    SecurityMiddleware.wrap(authentication(), authorization(), ADMIN, new ReportHandler()))
```

## 常见的第一次写错

1. **错误：认证成功后立即调用 delegate，再根据授权结果修改 Response。** 正确：先检查 `Decision.ALLOW`，拒绝时直接返回，业务方法调用次数保持为零。
2. **错误：把所有拒绝都返回 403。** 正确：anonymous 与 failure 是 401，authenticated 但 denied 是 403，组件抛 `RuntimeException` 是 500。
3. **错误：把身份放进 `parameters` 或静态 `currentUser`。** 正确：实现 `SecuredHandler`，让中间件把 `SecurityContext` 作为参数传入。
4. **错误：为了支持 Cookie 在 store 中直接读 Request。** 正确：当前中间件只支持 `Authorization` 头；应用若使用 Cookie，应在自己的认证实现中读取并验证，领域 store 不认识 HTTP。
5. **错误：两参数 `wrap` 被视为允许所有人。** 正确：它使用 `allowAll`，但认证门仍然存在；真正公开的路线是不调用 `wrap`。

## 怎么确认这一步没造错

运行中间件二十一项测试、真实连接六项测试与响应安全头四项测试：

```bash
mvn -o -B -ntp -pl framework/barezen-security -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=SecurityMiddlewareTest,SecurityHttpEndToEndTest,SecurityHeadersTest
```

预期合计 31 项全部通过，`BUILD SUCCESS`。`SecurityMiddlewareTest` 的五个嵌套组分别是五种状态、上下文交付、凭证提取、表驱动授权与构造拒绝；前一组有六项测试，因为认证组件损坏与授权组件损坏分别验证。真实连接测试用 HTTP/1.1 客户端依次发送 ada、匿名、grace、匿名、ada，并断言身份不跨请求残留。

本章实跑该组合时出现了 JaCoCo 尝试插桩 JDK 内部 `com/sun/net/httpserver/HttpHandler` 的 `IllegalClassFormatException` 堆栈，但六项 E2E 测试仍全部通过、构建成功。这是覆盖率代理与 JDK 内部类的噪声，不应写成安全测试失败，也不应通过修改框架来掩盖。真正的断言是状态码、正文与 SecuredHandler 是否收到正确身份。

## 此刻的代码长什么样

现在可以把安全能力包成一个普通 Handler 注册到任何现有路由，公开与受保护路线在同一张表中可见。模块没有改动 Web 契约或 JDK 适配器，也没有自动会话、用户库或 TLS。这里的“没有用户库”专指 `barezen-security` 不依赖 JDBC；第 11 章的 plugins 模块已有 `UserRepository` 与 `UserPlugin`。传输是否加密由第 6 章适配器与 ADR-0050 的 keystore 配置决定；一个通过 HTTPS 到达的错误 token 仍然在这里得到 401，TLS 不会替代应用认证。

最后一步要把所有单元、架构、字节码和消费者证据组合起来，尤其检查“拒绝路径没有调用 delegate”。畸形哈希的非正迭代已有拒绝测试；仍未覆盖的事项包括 rotate 的线性化保证（已有失败保留与并发赢家测试）、容量攻击、账户管理策略、会话到 Header 的自动桥接、CSRF 与限流。安全不是把测试数写到 README 就结束，下一步的检查点就是阻止这些边界被无意夸大。
