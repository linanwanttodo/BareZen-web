# 第 9 章第 3 步：认证三态与 401/403 边界

## 这一步要解决什么

会话 store 只能回答“这个值是否找到一条有效记录”，还不能表达客户端究竟有没有提交证明。现在要把认证建模为三种结果：身份已验证、提供了证明但验证失败、根本没有提供证明。随后再引入授权，回答“这个已验证身份是否拥有当前路由要求的权限”。这两道问题必须先分开，401 与 403 才不会在实现中混成一个笼统的“拒绝”。

`7d913bf` 用 sealed `AuthenticationResult` 保存认证三态，用只有 `ALLOW`/`DENY` 的 `Authorization.Decision` 保存授权结果。`Permission` 是大小写敏感的权限名，`Principal` 是已经由认证组件接受的身份名。它们都不是用户表、角色组或策略引擎；复杂映射由应用实现，中间件只提出一个明确的权限问题。

## 先想清楚再写

如果接口返回 `boolean authenticated` 和可空 Principal，调用者只能看到“没有身份”，无法知道是未提供凭据，还是提供后被拒绝。若再返回一个普通 `Optional<Principal>`，失败状态仍会消失。更隐蔽的错误是把失败当成匿名继续做授权：一个策略可能允许匿名，于是错误 token 反而通过了本应受保护的路线。三态的价值不是类型好看，而是让“为什么没有身份”在后续状态机中不可丢失。

`Failure(String reason)` 还引出信息披露边界。原因可以用于应用日志，例如“token 已撤销”或“用户不存在”，但不能原样回给客户端，否则攻击者可以据此枚举账户、区分 token 格式、逐步校准攻击。当前中间件对失败与匿名都返回固定正文 `Unauthorized`，也不会自动记录 reason；应用若需要日志，必须在自己的认证边界中脱敏记录，不能假设模块已经代劳。

授权的默认值同样需要仔细措辞。`Authorization.of(grants)` 对表中没有的 Principal、没有列出的 Permission 都拒绝，`denyAll()` 拒绝一切，这是默认拒绝。但 `SecurityMiddleware` 是显式装饰器：应用若完全忘记 `wrap`，路由仍是公开 Handler，不会自动得到 403。不能把“策略函数默认拒绝”夸大成“框架自动保护全部路由”。两参数 `wrap(authentication, delegate)` 也不是开放权限，它表示只要求认证，用 `allowAll()` 响应 `Permission.ANY`，匿名与失败仍在第一道门被拒绝。

第三个决定是安全组件自身抛异常怎么办。数据库不可达、策略服务损坏不是客户端凭据错误；如果返回 401，客户端会不断更换密码重试，监控也看不到服务端故障。实现选择捕获 `RuntimeException` 并返回固定 `Internal Server Error`，业务 Handler 不运行。它不捕获 `Error`，也不保证捕获认证实现返回 null 后的违约行为；`Authentication` 与 `Authorization` 的接口契约都是“永不返回 null”。

## 动手

先实现 sealed 结果。接口提供三个静态工厂，`Authenticated` 是带 Principal 的 record，`Failure` 是带 reason 的 record，`Anonymous` 是枚举单例。默认 `maybePrincipal()` 返回空、`isAuthenticated()` 返回 false，只有 `Authenticated` 覆盖它们。`maybePrincipal` 不能改名 `principal`，因为 record 的组件访问器是 final，接口不能再用同名默认方法提供更宽泛的可空视图。

```java
static AuthenticationResult authenticated(Principal principal) {
  return new Authenticated(Objects.requireNonNull(principal));
}

static AuthenticationResult failure(String reason) {
  return new Failure(Objects.requireNonNull(reason));
}

static AuthenticationResult anonymous() {
  return Anonymous.INSTANCE;
}
```

接着提供两个明确的认证默认值。`Authentication.anonymous()` 对任何输入都返回匿名；`Authentication.bearer(scheme, value, principal)` 在 credential 为 null 时返回匿名，在 scheme 与 value 都精确匹配时返回 authenticated，否则返回 failure。代码位于 `Authentication.java:47` 与 `:63`，比较大小写敏感，不能把 Bearer 的宽容规则带进身份验证。

```java
return credential -> {
  if (credential == null) {
    return AuthenticationResult.anonymous();
  }
  if (credential.scheme().equals(scheme) && credential.value().equals(value)) {
    return AuthenticationResult.authenticated(principal);
  }
  return AuthenticationResult.failure("credential rejected");
};
```

然后定义权限和授权。`Permission.of(name)` 拒绝 null 与空白名，权限按 record 的名字精确比较；`Permission.ANY` 的名字是 `barezen:any`。`Authorization.of` 复制传入 map，避免调用者随后修改导致策略在运行中漂移；查找时只有“找到集合且集合包含 required”才允许。

```java
Map<Principal, Set<Permission>> table = Map.copyOf(grants);
return (principal, required) -> {
  Set<Permission> held = table.get(principal);
  return held != null && held.contains(required)
      ? Authorization.Decision.ALLOW : Authorization.Decision.DENY;
};
```

`SecurityContext` 只包装一个不可变 `AuthenticationResult`，提供 `principal()` 与 `isAuthenticated()`。它没有静态访问器，也不保存会话 token。此时状态与策略已经独立于 HTTP 可测试，下一步才能把它们接入普通 Handler 装饰器。

## 常见的第一次写错

1. **错误：`if (result.maybePrincipal().isEmpty()) return 403;`。** 正确：没有有效身份时返回 401；只有 authenticated 且授权拒绝才返回 403。
2. **错误：失败时返回 `AuthenticationResult.anonymous()`。** 正确：明确返回 `failure(reason)`，让状态层级保留拒绝原因，即使当前线上正文相同。
3. **错误：把 `Failure.reason` 拼进响应。** 正确：线上使用固定 `Unauthorized`，诊断文本留在服务端；当前中间件本身不记录该 reason。
4. **错误：授权表只检查 Principal 是否存在，不检查所需 Permission。** 正确：必须同时满足“主体在表中”和“权限集合包含 required”，否则拥有任意权限的用户会被允许全部操作。
5. **错误：认为不包装的路由也会默认拒绝。** 正确：默认拒绝属于策略与包装后的路线；路由表里没有 `SecurityMiddleware.wrap` 就没有这道门。

## 此刻的代码长什么样

认证已经能明确产出三种结果，授权已经能对已认证主体提出一个权限问题并得到二元回答，上下文也已经是不可变的请求级值。但还没有任何代码读取 `Authorization` 头，也没有任何对象保证在拒绝时不调用业务 Handler。`Authentication.bearer` 只是测试与最简单场景的便利实现，真实密码认证或会话认证仍需应用组合。

下一步把顺序固定为“提取凭据、认证、授权、调用 delegate”，同时保持 `Handler` 的两参数签名不变。需要知道身份的业务 Handler 将额外实现 `SecuredHandler`；身份通过方法参数到达，而不是通过路由参数、请求属性或线程局部变量。
