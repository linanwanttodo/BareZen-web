# 第 9 章第 2 步：不透明会话与可撤销性

## 这一步要解决什么

密码验证只证明一次身份。接下来要决定客户端在后续请求中出示什么，以及服务端如何让这份证明立即失效。`SessionToken` 与 `SessionStore` 在 `7d913bf` 中同时出现，它们选择的不是 JWT，而是一个三十二字节随机值加一条服务端记录。token 只负责查找，Principal 与过期时间留在服务端，因此删除记录就等于撤销。

这一步也不是实现“自动登录中间件”。当前 `SecurityMiddleware` 只从 `Authorization` 头提取 `Credential`，不会自动创建 Cookie，也不会自动查询 `SessionStore`。应用需要编写一个 `Authentication`，把 Bearer 值或其他凭据交给 store，再把结果转换为三态认证结果。先独立完成会话领域，可以让过期、撤销、轮换都在没有套接字和数据库的情况下被确定性地测试。

## 先想清楚再写

最容易想到的方案是 token 里放 `userId`、权限列表和过期时间，再用服务端密钥签名。它确实能无状态验证，却把撤销推迟到 token 过期；要立即封禁，就得维护撤销名单，服务端又回到了有状态系统。更糟的是权限写进 token 后会冻结：管理员今天移除权限，已签发 token 仍可能继续宣称旧权限。签名密钥轮换、算法混淆和 `kid` 选择还会增加一组与当前需求不成比例的密码学风险。

第二个误区是使用数据库自增 ID 当 token。它可读、可预测，攻击者可以遍历；即使套一层 Base64，编码也没有提供保密性。这里需要 `SecureRandom` 生成三十二字节，再用无填充 Base64url 表示，使它适合放入 HTTP 头。token 不携带用户名、角色或任何可解释字段，拿到一个 token 也不能推导另一个 token。

第三个误区是把过期实现成“每次 lookup 过滤，但保留旧记录”。这样 map 会随攻击者制造的无效 token 或自然到期不断增长。当前实现选择在 lookup 发现过期时删除记录，代价是清理是惰性的：从未被再次查询的已过期会话仍会留在内存。它没有定时任务、容量上限或分布式存储。选择小而明确的模型，就必须同时接受这些代价，而不是把它描述成生产级会话中心。

最后，时间不能散落在业务代码里直接调用 `Instant.now()`。测试若用真实时间验证“到期瞬间失效”，会变得缓慢且不稳定。构造时注入 `Clock`，把 `expiresAt` 保存为确定的 `Instant`，判断条件写成 `!expiresAt.isAfter(now)`，就能让精确边界测试不调用 `Thread.sleep`。`SecureRandom` 也作为构造依赖注入，测试可以固定字节，同时保留生产默认的强随机源。

## 动手

先定义值对象 [SessionToken.java:23](../../framework/barezen-security/src/main/java/com/barezen/security/SessionToken.java#L23) 的 `SessionToken(String value, Instant expiresAt)`。构造器拒绝 null 与空白 value，因为“没有 token”应该用不存在表达，而不是制造一个空 token。`isExpired(Instant now)` 把等于到期时刻也算作过期；`of(value, duration, clock)` 只接受正时长。`toString` 只显示到期时间，不显示 token 值，否则日志会自动复制一份登录凭据。

```java
public boolean isExpired(Instant now) {
  Objects.requireNonNull(now, "the instant to check against");
  return !expiresAt.isAfter(now);
}

public static SessionToken of(String value, Duration duration, Clock clock) {
  Objects.requireNonNull(clock, "the clock");
  Objects.requireNonNull(duration, "the validity duration");
  if (duration.isNegative() || duration.isZero()) {
    throw new IllegalArgumentException("a token's validity duration must be positive");
  }
  return new SessionToken(value, clock.instant().plus(duration));
}
```

然后实现 store。字段只有 `ConcurrentHashMap<String, Session>`、`Clock` 和 `SecureRandom`，没有 HTTP 类型。`create` 生成 32 字节、Base64url 无padding编码，构造 token 与 `Session(token, principal)`，再放入 map。关键代码位于 [SessionStore.java:67](../../framework/barezen-security/src/main/java/com/barezen/security/SessionStore.java#L67)：

```java
byte[] bytes = new byte[32];
random.nextBytes(bytes);
String value = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
SessionToken token = SessionToken.of(value, duration, clock);
Session session = new Session(token, principal);
sessions.put(value, session);
return session;
```

`lookup` 对未知值返回空；对已找到记录检查到期，过期时删除并返回空。`invalidate` 直接删除并返回是否找到。`rotate` 先删除旧值，找不到或已过期就不创建新会话，未过期时才用旧 Principal 创建新 token，所以旧 token 必然失效。代码在 [SessionStore.java:89](../../framework/barezen-security/src/main/java/com/barezen/security/SessionStore.java#L89)、[:108](../../framework/barezen-security/src/main/java/com/barezen/security/SessionStore.java#L108)、[:120](../../framework/barezen-security/src/main/java/com/barezen/security/SessionStore.java#L120)：

```java
Session old = sessions.remove(value);
if (old == null) {
  return Optional.empty();
}
if (old.token().isExpired(clock.instant())) {
  return Optional.empty();
}
return Optional.of(create(old.principal(), duration));
```

这里要准确理解并发保证：`ConcurrentHashMap` 保证单个操作安全，但当前 `rotate` 的“删除再创建”不是原子复合操作。两个请求同时轮换同一 token 时，一个可能先删除，另一个随后得到空；它们不会把旧 token 留在 map 中，但不能宣称整个轮换流程线性化。若未来要求严格 CAS 轮换，需要新的领域设计和测试，而不是只在注释里写下“线程安全”。

## 常见的第一次写错

1. **错误：token 使用 `UUID.randomUUID()` 后直接展示可读 id。** 正确：这里使用 32 字节 `SecureRandom` 与 Base64url，并让 token 不携带业务含义；不要把随机的可打印表示误认为可解释身份。
2. **错误：把权限放进 token，撤销时只修改用户表。** 正确：权限决策所需数据留在服务端会话或应用策略中；撤销通过删除会话记录立即生效。
3. **错误：`expiresAt.isBefore(now)`。** 正确：到期瞬间已经无效，使用 `!expiresAt.isAfter(now)`，并用固定 Clock 在精确时刻断言。
4. **错误：轮换时复制记录却不删除旧 token，或续期过期 token。** 正确：先 `remove` 旧值，检查未过期后才为同一 Principal 创建新值；未知或过期旧 token 都不应顺带创建会话。
5. **错误：让 `SessionStore` 直接读 Header 或写 Cookie。** 正确：领域只接受字符串并返回 `Optional<Session>`；HTTP 绑定留在应用认证实现或未来的边缘适配层。

## 怎么确认这一步没造错

运行 token 与 store 的十八项测试：

```bash
mvn -o -B -ntp -pl framework/barezen-security -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=SessionTokenTest,SessionStoreTest
```

预期 `SessionTokenTest` 5 项、`SessionStoreTest` 13 项，合计 18 项全部通过，`BUILD SUCCESS`。测试使用从 `2026-10-02T12:00:00Z` 开始的手动 Clock：创建三十分钟会话，推进三十一分钟后 lookup 为空且 store size 为零；推进整三十分钟时也断言为空；撤销第二次返回 false；轮换后旧 token 查不到、新 token 找到同一 Principal；过期 token 轮换返回空且不产生替代会话。

还要运行架构规则，证明领域没有依赖 HTTP：

```bash
mvn -o -B -ntp -pl framework/barezen-security -am test \
  -Dsurefire.failIfNoSpecifiedTests=false -Dtest=BarezenSecurityArchitectureTest
```

预期 7 项通过。其中 `the_session_domain_is_transport_ignorant` 禁止 `SessionToken` 与 `SessionStore` 依赖 `com.barezen.web`、`java.net`、JDK server 或 servlet 包。它不是格式检查，而是一条防止未来把 Cookie 逻辑塞回领域的依赖门禁。

## 此刻的代码长什么样

现在有了一条可以从认证成功进入后续请求的会话路径，但还没有决定认证结果的表示。应用可以检查 token 是否存在，却无法仅靠 `Optional<Principal>` 表达“客户端没有提交凭据”和“客户端提交了已撤销 token”的区别；这两种线上回答需要不同的语义。虽然当前模块最终都把两者映射为 401，内部状态仍必须保留，否则未来加入挑战、诊断或部分认证时无法扩展。

下一步先建立 `AuthenticationResult` 的三态层级与 `Authorization` 的允许/拒绝决策，再让装饰器把它们固定为 401、403、500。会话 store 会作为应用认证实现的协作者接入，而不是变成中间件内部的全局对象；这样单 JVM 状态、重新启动失效和容量边界都能在装配处被看见。
