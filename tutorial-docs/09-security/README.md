# 第 9 章：安全不是登录页，而是可验证的拒绝路径

## 本章目标

前八章已经能把字节变成请求、把请求送进正确的 Handler，也能把配置与显式对象装配起来。现在缺的不是一个“登录接口”，而是一组能在请求进入业务代码前回答的问题：客户端提供了什么证明，这份证明是否成立，成立之后的主体被允许做什么，以及每一种拒绝怎样保证业务 Handler 从未运行。安全模块把这些答案固定在普通 Web 契约之上，不修改 `Request`，不向适配器泄露策略，也不给每个 Handler 增加一个隐式上下文参数。

本章的建造顺序来自三个可以逐个检出的提交。`7d913bf` 一次加入十二个生产类，已经包含密码摘要、不透明会话、三态认证、权限决策与 Handler 装饰器；它不是先做一个登录页再补安全，而是先确定边界和拒绝语义。`f315e21` 增加十四个测试与架构文件，把“允许、匿名、失败、拒绝、组件损坏”变成可执行矩阵。`86bb626` 才把五条决定写进 ADR，并记录 99 项测试、98.96% 覆盖率与十四次变异探针。这个顺序提醒读者：文档不是替代测试的事后说明，测试也不是注释的另一种排版。

最终形态可以概括为 `Credential → AuthenticationResult → SecurityContext → Authorization.Decision → delegate`。密码和会话是两条可以独立使用的领域能力，并不会自动接入中间件；应用需要编写 `Authentication` 把它们接到 `Authorization` 头。模块只依赖 `barezen-web`，适配器仅以 test scope 进入，所以同一装饰器理论上可以换一个适配器继续工作。它不是完整身份平台：没有注册、找回密码、CSRF、OAuth2/OIDC、分布式会话、自动锁定或注解安全。这里说的是 `barezen-security` 的模块边界；后来的 `barezen-plugins` 已经提供 H2 用户仓库，不能把“安全模块不拥有 JDBC”误写成“整个仓库没有用户存储”。

完成本章后，你应能解释 PBKDF2 为什么需要随机盐和自描述迭代数，能设计一个查找后立即撤销的会话，能区分“没有有效身份”与“身份有效但无权”，还能证明拒绝路径上的调用次数为零。你也要能指出本实现的真实边界：默认拒绝只对已经包装的路由生效；会话不是 JWT，也不跨进程；TLS 属于 JDK 适配器而不是这个模块；有些 ADR 的概括比当前代码的异常处理更乐观，必须回到代码判断。

## 涉及 ADR

- [ADR-0033：安全是 Handler 装饰器，上下文作为参数到达](../../docs/adr/0033-security-is-a-handler-decorator.md)：冻结的 `Handler.handle(Request, Map)` 不增加安全参数，安全模块用 `wrap` 返回一个 Handler。需要身份的业务对象额外实现 `SecuredHandler`，由中间件调用三参数方法；普通 Handler 原样运行。模块只依赖 Web 契约，生产代码不依赖适配器、core 或 JDBC。
- [ADR-0034：认证有三态并携带拒绝原因](../../docs/adr/0034-authentication-has-three-states.md)：`Authenticated`、`Failure`、`Anonymous` 不能压成布尔值或可空 Principal，否则“未提供”与“提供了但错误”会消失。sealed 层级让新增状态成为所有消费者的编译期检查，拒绝原因属于应用诊断而不是线上回显。
- [ADR-0035：密码哈希采用自描述的 PBKDF2-HMAC-SHA256](../../docs/adr/0035-password-hashing-pbkdf2.md)：默认六十万次迭代、十六字节随机盐、三十二字节派生密钥，并让哈希自己记录算法与次数。这样升级次数不必让旧哈希失效，同时不引入 bcrypt 或 Argon2 依赖；PBKDF2 对 GPU/ASIC 较弱这一代价也被明确记录。
- [ADR-0036：会话是不透明、服务端且可撤销的](../../docs/adr/0036-sessions-are-opaque-and-revocable.md)：三十二字节随机值只作为 `ConcurrentHashMap` 的键，Principal 与过期时间留在服务端。撤销是删除记录，轮换先删除旧值，未过期时才签发新值，因此不需要 JWT 撤销名单；代价是单 JVM 状态与无容量上限。
- [ADR-0037：401/403/500 的边界与默认拒绝](../../docs/adr/0037-status-codes-and-default-deny.md)：未认证或认证失败是 401，已认证但策略拒绝是 403，安全组件抛 `RuntimeException` 是 500。三种拒绝都不调用业务 Handler；三参数包装询问 `Permission.ANY`，四参数包装询问路由明确命名的权限。
- [ADR-0050：TLS 通过 keystore 配置开启，不增加适配器公开 API](../../docs/adr/0050-tls-is-named-by-a-keystore-not-flagged-on.md)：`barezen-http-jdk` 从既有配置快照读取 keystore 路径与密码，构造时决定明文或 HTTPS。没有路径就是明文，有路径缺密码则启动失败，坏 keystore 也在绑定端口前失败；协议、证书续期和 mTLS 不在范围内。本章只把它列为传输边界，不把 TLS 测试冒充安全模块测试。

## 本章完成后的能力清单

你应能使用 `PasswordHasher.standard()` 生成自描述哈希，使用 `PasswordHasher.of(iterations, random)` 写快速且可重复的测试，并知道生产代码不应把测试计数带进部署。你应能调用 `SessionStore.create/lookup/invalidate/rotate`，在精确到期时刻让会话失效，并解释为什么重新启动会丢失全部会话。

你应能用 `Authentication` 自定义凭证验证，用 `Authorization.of(Map<Principal, Set<Permission>>)` 表达显式授权，用 `Permission.ANY` 表示“任意已认证主体可经过此路由”，或给四参数 `wrap` 传入业务权限。你应能从路由表看出哪些路线公开、哪些被包装，因为不存在自动扫描后的隐式保护。你应能让 `SecuredHandler` 接收当前请求的身份，同时禁止 `ThreadLocal`、静态可变身份、环境变量后门和日志依赖。

你还应能陈述未实现事项：中间件只读取 `Authorization` 头，不自动读 Cookie；会话存储不会自动被中间件调用；没有 `WWW-Authenticate` 挑战；失败原因不会由当前中间件写日志或响应；没有密码强度与登录限流；用户存储位于 plugins 的 H2 示例仓库，不在 security 模块，也不具备完整账户管理；路由参数不是身份通道。忘记包装不会触发 401，而是路由继续公开，这是显式装饰器必须靠代码审查和测试守住的责任。

## 不这样设计会坏掉什么

如果直接把 SHA-256 结果当密码存储，攻击者可以用高速硬件批量猜口令；同口令同摘要还会暴露用户复用关系。若把迭代数只放在进程配置里，提高默认值会让旧哈希全部失效；若把损坏哈希当成服务器异常，客户端会收到 500，数据库损坏被伪装成网络故障。若使用顺序 token，攻击者可以从一个合法值推测下一个；若 token 自带权限，撤销用户权限就只能等待 token 过期。

若用布尔值表示认证，匿名与错误凭证会合并，授权失败也可能被错误显示为登录失败。若把 Principal 塞进请求参数或 `ThreadLocal`，路径捕获会混入服务端决策，复用线程还会把上一个用户的身份带给下一个请求。若在适配器里做安全判断，第二种适配器需要重写全部策略；若让每个 Handler 自己检查权限，同一个路由的不同方法可能采用不同顺序，漏检也没有统一门禁。

若把“默认拒绝”误写成“所有未注册路由自动受保护”，会得到虚假的安全感；实际默认拒绝只发生在应用选择包装之后。若把中间件捕获的异常细节返回客户端，会泄露内部依赖与策略；若忽略组件异常继续调用 delegate，则身份服务故障会变成越权。最后，若用 coverage 百分比代替拒绝断言，一个“总能返回 200”的中间件也可能获得高覆盖率，却完全没有安全性。
