# 第 9 章第 5 步：检查点：拒绝路径全覆盖

## 这一步要解决什么

到这里，单独看每个类都可能正确，组合起来却仍可能出错：认证实现可能把失败当匿名，授权可能把 DENY 当 ALLOW，装饰器可能在拒绝后仍调用业务对象，长连接可能串身份，新依赖也可能把 adapter、JDBC 或日志重新引进安全模块。检查点要验证的不是“代码能编译”，而是每一种拒绝都有正确状态码、固定正文、零业务调用，并且架构边界没有被 convenience 破坏。

这个检查点还要把实现测试与消费者测试分开。模块测试可以直接制造五态、检查 delegate 计数；`SecurityExampleTest` 通过 TestKit 验证真实应用组合；`SecurityExample.main` 再绑定 OS 分配的端口走一次 HttpClient。三层证据回答不同问题，不能用一个高覆盖率数字替代另外两层。

## 先想清楚再写

第一次做安全验收最容易只测 happy path：正确 token 返回 200，于是宣布“认证完成”。但安全代码的主要价值在拒绝路径。匿名、错误 token、权限不足、认证服务异常、授权服务异常都必须阻止 delegate；只断言响应状态码，却不断言业务调用次数，无法排除“先执行再返回 403”的严重问题。`AtomicInteger` 调用计数因此不是测试装饰，而是副作用从未发生的证据。

第二类错误是把单元测试当作部署证明。测试直接调用 Handler，能精确控制 credential，却看不到 Headers 到 Request 的转换、适配器分帧和连接复用。E2E 的价值不只是多一层，它专门让多个身份先后经过同一 HTTP/1.1 客户端连接，暴露 ThreadLocal 或静态 currentUser。若只发送匿名请求，身份泄漏可能仍然看不见。

第三类错误是让门禁只检查包名或覆盖率。安全模块需要禁止 `ThreadLocal`、静态非 final 字段、`System.getProperty`、`System.getenv`、主源码日志、JDBC、adapter 与 HTTP 领域耦合；这些都是可以机械检查的漂移。与此同时，七条 ArchUnit 规则通过不代表输入解析完美：当前 `PasswordHasher.verify` 对负迭代的处理、`SessionStore.rotate` 的并发复合语义，都不在现有测试里。验收必须同时记录“已证明”和“未证明”。

最后，不要把 ADR 的历史统计当成当前实跑。`390f57c` 记录 99 项测试与 98.96% 覆盖率，但本章运行的是 `test`，不是覆盖率门禁，因此只声称实际看到的测试结果。日志里有 JaCoCo 对 JDK 内部类的插桩异常堆栈，也有 `sun.misc.Unsafe` 弃用警告和 SLF4J 无 provider 提示；只要 Surefire 的 Failures/Errors/Skipped 都为零且 Maven `BUILD SUCCESS`，这些就不是测试失败。

## 动手

先运行模块完整行为、架构与字节码检查。显式列出十四个测试类，避免 `-Dtest` 让上游同名 `ClassMajorContractTest` 意外扩张范围；`-am` 仍会编译所需上游模块。

```bash
mvn -o -B -ntp -pl framework/barezen-security -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=PrincipalTest,CredentialTest,AuthenticationResultTest,SecurityContextTest,AuthenticationTest,PermissionTest,AuthorizationTest,PasswordHasherTest,SessionStoreTest,SessionTokenTest,SecurityMiddlewareTest,SecurityHttpEndToEndTest,BarezenSecurityArchitectureTest,ClassMajorContractTest'
```

本章实际结果如下：

| 范围 | 结果 |
| --- | --- |
| core / web / http-jdk 上游字节码契约 | 各 4 项，均通过，major 61 |
| `barezen-security` | 99 项，0 失败、0 错误、0 跳过 |
| 安全模块 class-major | `checked=42 unique-majors=[61] expected=61` |
| Maven | `BUILD SUCCESS` |

其中 `SecurityMiddlewareTest` 18 项、`SecurityHttpEndToEndTest` 6 项、`PasswordHasherTest` 15 项、`SessionStoreTest` 12 项、`SessionTokenTest` 5 项、`BarezenSecurityArchitectureTest` 7 项，共 63 项；结果类、认证、权限与上下文测试共 32 项，安全模块字节码契约 4 项，合计正好 99 项。不能把嵌套组显示的 `Tests run: 0` 误认为父类没有测试；实际执行数在各 `$Nested` 组中。

再运行真实消费者的 TestKit 测试。它会启动真实端口，验证公开路线、缺失 token、有效 token、权限不足和错误 token：

```bash
mvn -o -B -ntp -pl examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false -Dtest=SecurityExampleTest
```

预期 examples 模块 `Tests run: 5, Failures: 0, Errors: 0, Skipped: 0`，`BUILD SUCCESS`。本章已实际执行。测试源码位于 [SecurityExampleTest.java:11](../../examples/src/test/java/com/barezen/examples/security/SecurityExampleTest.java#L11)，它不只是检查状态码，还检查 `/report` 正文为 `report for ada`，证明身份确实作为参数到达 SecuredHandler。

最后直接运行示例 main。仓库文档给出的 classpath 由各模块 `target/classes`、slf4j-api 与 H2 组成；这里使用绝对 `$PWD`，避免 class 文件存在却因相对路径歧义出现 `ClassNotFoundException`：

```bash
M2=$HOME/.m2/repository
CP="$PWD/examples/target/classes"
for m in core web http-jdk content security data plugins; do
  CP="$CP:$PWD/framework/barezen-$m/target/classes"
done
CP="$CP:$M2/org/slf4j/slf4j-api/2.0.16/slf4j-api-2.0.16.jar:$M2/com/h2database/h2/2.2.224/h2-2.2.224.jar"
java -cp "$CP" com.barezen.examples.security.SecurityExample
```

本章实际观察到的关键输出：

```text
verify correct password -> true
verify wrong password   -> false
GET /health           -> 200
GET /report (none)    -> 401
GET /report (bearer)  -> 200
GET /admin  (bearer)  -> 403
```

这里同时出现密码验证真假和四种路由结果。固定 token 只用于演示装饰器，不是生产会话系统；`SecurityExample` 的类注释也明确说明它没有实现用户存储。

## 常见的第一次写错

1. **错误：看到 401 就算通过，忽略 delegate 计数。** 正确：每个拒绝测试都同时断言状态码、固定正文和 `calls == 0`。
2. **错误：把“99 项通过”写成“所有攻击都不会成功”。** 正确：它只证明现有断言覆盖的行为；未测的并发、容量和畸形输入必须单列。
3. **错误：把 ADR 的 98.96% 覆盖率当成本次 `test` 输出。** 正确：历史数据注明来自 ADR，当前检查点只报告实际执行的 99 项与字节码 major。
4. **错误：为了减少日志关闭架构规则，或修改用户 WIP 测试。** 正确：保留噪声并解释来源，只提交 `tutorial-docs/09-security/` 的文档变更。
5. **错误：检查点只跑测试，不核对提交范围。** 正确：提交前查看 `git status`，确认 framework、examples、app 与 target 均未进入暂存区。

## 怎么确认这一步没造错

上面的三条命令就是本章的最终检查点，必须全部以零退出完成。还应从文档反向追踪每个公开 API：`PasswordHasher.standard/of/hash/verify`、`SessionStore.standard/of/create/lookup/invalidate/rotate`、`SessionToken.of/isExpired`、`Authentication.anonymous/bearer/authenticate`、`Authorization.allowAll/denyAll/of/authorize`、`SecurityMiddleware.wrap/handle` 与 `SecuredHandler.handle` 都应对应真实源码，不能存在只在教程中成立的便利方法。

提交本章前执行：

```bash
git diff --check
git status --short
git diff --stat -- tutorial-docs/09-security
```

预期没有空白错误，六篇新文档都位于 `tutorial-docs/09-security/`。工作树中已有的两个 JDK 测试改动与 app 临时探针属于用户 WIP，不能暂存、修改或删除。提交信息使用 `docs(tutorial): 第9章 安全`，不 push。

仍需明确记录四项未覆盖边界：`verify` 对可解析但非正迭代尚无专门拒绝测试；`rotate` 不是原子复合操作且没有并发轮换测试；store 没有容量上限、后台清理或多实例共享；中间件没有自动 Cookie/会话桥接、CSRF、限流和用户持久化。ADR-0050 的 TLS 属于适配器检查点，本章没有运行 `JdkTlsSemanticsTest`，因此不把它计入 99 项。

## 此刻的代码长什么样

本章完成后，前八章的框架多了一个只依赖 Web 契约的安全模块：它能哈希密码、管理单 JVM 可撤销会话、表达认证三态与权限决策、装饰 Handler、传递请求级身份，并用架构规则阻止最危险的便利捷径。它仍然是一个学习资产与轻量骨架，不是身份管理产品；路由保护是否完整仍取决于应用是否正确包装每条路线。

下一章进入 `barezen-data`。安全模块明确禁止 JDBC，正好让数据访问保持独立：下一章会创建 DataSource 边界、显式事务和版本化迁移，应用可以在自己的认证实现中消费数据库，但框架核心不会因此把安全、连接池和生命周期搅成一个全局容器。
