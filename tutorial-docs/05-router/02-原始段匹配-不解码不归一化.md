# 02 原始段匹配：不解码不归一化

## 这一步要解决什么

路由表第一个实现问题不是“怎么写正则”，而是“比较的到底是什么”。Request 在第四章已经保证 path 保留客户端原始形式；如果 Router 马上调用 URI.getPath、解码百分号或清理点段，就把刚建立的边界破坏了。一个编码斜杠可能从一段变成两段，一个编码点段可能被解释成目录上一级，最终选中的资源不再由原始请求目标决定。

本章采用最朴素的比较单位：去掉前导 `/` 后按 `/` 切分，保留空段。模式与请求使用同一函数，段数必须完全相同；每个位置要么是字面量精确相等，要么是参数段接受一个非空文本。没有 URI、没有 normalize、没有大小写折叠，也没有尾斜杠补偿。

这条规则会拒绝一些“看起来更方便”的匹配。`/users` 不自动服务 `/users/`，`/a/b` 不服务 `/a%2Fb`，`/Users` 不服务 `/users`。这些都是明确选择：框架不替应用合并 URL 空间，应用需要两种拼写就显式注册两种。

## 为什么这样设计

segmentsOf 只有一行核心逻辑：`List.of(path.substring(1).split("/", -1))`。`-1` 不是随手写的性能参数，它保留末尾空字符串。`/users` 得到 `[users]`，`/users/` 得到 `[users, ""]`，所以精确段数自然把两者分开。`/` 得到一个空段，`//` 得到两个空段；它们也是不同形状。若使用默认 split，尾部空段会被丢弃，尾斜杠规则就无法由同一个段数比较表达。

字面量用 String.equals，大小写敏感且包含百分号原文。`/a/../b` 作为模式只匹配同样的原始文本，不匹配 `/a/%2e%2e/b`。这看起来不够“智能”，却保证规则对称：模式不被解码，请求也不被解码，任何一边发生隐式转换都会让比较结果依赖框架政策而不是应用声明。

参数段接受任何非空段，包括 `%2F`、`%20`、`+` 和未知编码文本。Router 不验证它是不是合法数字、UUID 或文件名，因为模式没有声明类型。它只证明这是完整的一段非空原文；值的意义由 Handler 决定。空段例外很重要：`/users/` 不能让 `{id}` 捕获空字符串，否则 Handler 会拿到一个无法验证的标识符。

不解码也是安全边界，但不能被夸大为“自动阻止路径穿越”。Router 只是保留攻击形态，让资源所有者能看见并拒绝它。真正访问文件系统的组件仍必须定义解码、绝对路径、符号链接和根目录约束；把这些工作推给 Router 既不可能正确，也会把 HTTP 路由变成文件系统策略。

精确段数还控制匹配成本与可预测性。没有前缀匹配，`/users` 不会吞掉 `/users/42`；没有尾通配符，静态文件“顺带放在任意路径下”就不能悄悄出现。新增一种匹配形状需要新的 ADR，因为它改变的不只是实现，还有现有路由的含义。

## 怎么验证

测试不应只写一个 happy path，而应围绕“不能发生的转换”构造对照：

| 模式 | 请求 | 预期 | 证明的规则 |
| --- | --- | --- | --- |
| `/users/{id}` | `/users/a%2Fb` | 命中，id=`a%2Fb` | 编码斜杠仍是一段 |
| `/a/b` | `/a%2Fb` | 不命中 | 编码路径与解码路径不同 |
| `/a/{x}/b` | `/a/%2e%2e/b` | 命中，x=`%2e%2e` | 不归一化点段 |
| `/Users` | `/users` | 不命中 | 字面量大小写敏感 |
| `/users` | `/users/` | 不命中 | 尾斜杠增加一段 |
| `/a//b` | `/a/b` | 不命中 | 中间空段不可丢弃 |
| `/users/{id}` | `/users/` | 不命中 | 参数不接受空段 |
| `/users/{id}` | `/users/1/2` | 不命中 | 参数不能跨段 |

[anEncodedSlashStaysOneSegmentAndStaysEncoded](../../framework/barezen-web/src/test/java/com/barezen/web/RouterTest.java#L565) 是核心测试。它不仅断言命中，还断言捕获值不含 `/`，因此不会出现“碰巧匹配成功但值已经解码”的假阳性。`aPlusInAPathIsNotASpace` 则防止把 query 的 form 编码习惯带进 path。

OPTIONS * 需要单独测试。注册 `OPTIONS "*"` 应在注册时失败；对 Request 的 `*` 调用 match 应得到 empty，methodsFor("*") 也得到空集合。`74ea0fb` 的适配器实测说明当前 JDK 可能在 Handler 介入前拒绝该目标，但 Router 仍保留明确分支，让第二个适配器得到可预测的数据答案。

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest='RouterTest$Encoding,RouterTest$TrailingSlash,RouterTest$StaticRoutes'
```

做反向控制时，可以把 equals 改成 equalsIgnoreCase，或把 split 的 `-1` 去掉，观察哪一组测试变红。不要把测试改成接受新行为来“修复”失败；这里要验证的正是原始语义没有漂移。

## 常见错误与失败后果

调用 `URI.normalize()` 会合并点段，调用 `URLDecoder` 会把 `+` 变空格并处理 `%2F`，两者都改变路由输入。只解码参数、不解码字面量，会让“看起来相同”的两个 URL 因位置不同而得到不同政策。自动去掉尾斜杠则会让两个缓存键共享一个 Handler，应用却没有机会显式同意。

用 startsWith 实现前缀匹配会吞掉更深的未知路径；用正则在整个 path 上提取参数，很容易意外允许跨段。为了“兼容常见框架”加入这些规则，还会改变 duplicate shape 和优先级定义，因为匹配对象已经不只是固定段数。当前实现的限制不是遗漏，而是保持语义封闭的代价。

这也解释了为什么 Request 的校验只检查“以 `/` 开头或等于 `*`”，而不检查重复斜杠、点段和百分号格式。请求解析采用最小政策，路由采用原始比较政策；若 Request 提前拒绝某条路径，第二个服务器适配器就无法再按自己的规则处理它。需要更严格 URL 校验时，应在 Handler 或资源层表达并返回明确错误，而不是让所有消费者共享一套隐含规范化。
