# 03 字面量优先的优先级规则

## 这一步要解决什么

假设同一 GET 同时注册了 `/users/me` 和 `/users/{id}`。请求 `/users/me` 显然应该选静态入口，不能因为 `{id}` 先注册就被参数 Handler 截走。但“显然”还不够：当 `/a/{x}/c` 与 `/a/b/{y}` 同时匹配 `/a/b/c` 时，谁更具体？注册顺序能不能决定？两个参数名称不同是否算重复？

本章把“形状”定义为：固定段数下，每个位置是字面量还是参数的二进制序列。`/users/{id}` 和 `/users/{userId}` 形状相同；`/users/me` 与 `{id}` 不同。然后只用两条规则：同方法同形状不允许重复；不同形状同时命中时，从左到右第一个字面量/参数分歧处，字面量获胜。

这套规则没有数值 priority、没有注册序号裁决，也不比较字面量内容。左段通常描述更稳定的资源分类，所以第一个分歧更有意义；比较整条模式有多少字面量会产生不直观的平局。例如 `/a/{x}/c` 与 `/a/b/{y}` 都有两个匹配位置，若只数字面量会打平；按第一个分歧则后者胜出，因为它固定了第二段。

## 先想清楚再写

把参数名称排除在 shape 外，是因为名称只影响 Handler 收到的 Map key，不影响哪些 Request 会被命中。若按完整模式文本去重，`/users/{id}` 与 `/users/{userId}` 会同时存在，却对每一个请求都给出相同胜负条件。注册时允许这种组合，只会在 match 中留下永远无法稳定解释的 tie。

shape 保留空段也很重要。ADR-0019 记录初版 shape 曾跳过空段，导致 `/` 与 `//` 都得到同一个空字符串形状。行为测试之所以能发现它，是因为测试分别请求了根路径和双斜杠，而不是只观察 toString。正确实现让 segments 同时服务匹配与 shape，两个环节就不会各自维护一套空段政策。

优先级按逐段比较实现为“谁先遇到不同”。若当前段一边是参数、另一边是字面量，当前 Registration 是参数则不胜出，是字面量则胜出；若双方类型相同就继续。段数相同的候选才有资格比较，否则 overlaps 已排除。因为字典序的二进制序列严格全序，两个不同形状不可能互相都觉得更具体，也不需要第三个 tie-breaker。

同形状在不同 method 下可以共存：`GET /users/{id}` 和 `POST /users/{id}` 回答不同动词，不构成冲突。同一 shape 同 method 即使在中间插入其他路由、即使 Handler 对象相同，也必须拒绝。错误消息应解释两者会回答相同请求，而不是只说“重复”；后者无法帮助插件作者定位装配问题。

注册失败必须是局部的。Builder.route 先完整校验、解析和检查冲突，成功后才加入列表；抛异常时不留下半条路由。`anInvalidPatternLeavesTheTableUntouched` 先注册有效路由，再尝试坏模式和冲突模式，最后构建并证明有效路由仍可命中。没有这条规则，一次失败可能污染 Builder，使上层捕获异常后继续启动，得到一个缺路由或含坏路由的应用。

## 常见的第一次写错

按路由数量、字符串长度或参数数量挑“更具体”的模式，都可能出现平局。先注册先匹配最简单，但插件装配顺序会改变公开行为；后注册覆盖则让一个合法插件悄悄拿走别人的请求。匹配成功后再报重复已经太晚，因为用户请求已经抵达运行时；注册时拒绝才能变成带 participantId 的启动失败。

把优先级放在 Handler 或注解上，会把 Router 与框架扫描器绑在一起，也让一个简单内存表必须解析元数据。为两个冲突形状添加“更具体者获胜”看似方便，却破坏 shape 全序，让相同模式的不同名字拥有隐蔽优先级。当前模型明确拒绝这些复杂度。

读者可以手工证明这条顺序的传递性：把二进制 shape 看成字符串，字面量为零、参数为一，字典序大的候选更具体。由于同方法同 shape 已在注册时排除，match 不需要比较 Handler、注册时间或完整 pattern。实现中的 isMoreSpecificThan 因此只有几行，却同时服务于行为测试、插件冲突诊断和未来的等价性测试。

shape 还让注册错误可以在 build 前发现，而不是等到某个特殊请求才出现。只要两个注册同时存在，它们就永远竞争同一组请求；把冲突推迟到 match 会让故障取决于流量，使单元测试很容易遗漏。Builder 的职责因此不只是收集，还承担最小的一致性校验，但不会读取任何运行配置或容器状态。

## 怎么确认这一步没造错

优先级测试至少覆盖三种位置：

1. 第一段：`/{anything}` 对 `/health`。
2. 中间段：`/a/{x}/c` 对 `/a/b/{y}`，请求 `/a/b/c`。
3. 最后一段：`/users/{id}` 对 `/users/me`。

同时交换注册顺序再跑。若结果改变，实现就偷偷把注册顺序变成优先级。静态测试还应确认 `/users/{id}` 与 `/users/{userId}` 的冲突在不同方法下表现不同，以及冲突异常不会删除已有 Handler。

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest='RouterTest$Priority,RouterTest$Duplicates'
```

反向控制可以做两次：把参数名称拼进 shape，应让同形状改名测试变红；把 isMoreSpecificThan 改成“先注册者胜出”的恒真判断，交换顺序测试就会暴露问题。ADR-0019 §22 正是记录了一个初版 best 比较表达式始终为真的错误，这比只写正常用例更能解释为何测试矩阵不能省。

## 此刻的代码长什么样

Router 现在能对冲突请求给出与注册顺序无关的确定答案，并在注册时拒绝不可区分的重复。下一步把匹配得到的段转换为 Handler 可以使用的命名参数，同时解决初版“已经匹配却无法把 id 交给 Handler”的缺口。
