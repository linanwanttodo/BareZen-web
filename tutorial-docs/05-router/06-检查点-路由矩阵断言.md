# 06 检查点：路由矩阵断言

## 这一步要解决什么

前五步分别建立了职责、原始段、形状、参数和快照语义，但独立正确不代表组合正确。一个请求可能同时命中静态与参数路由，参数模式可能在交错位置出错，两个插件可能在启动时注册相同形状，Handler 可能收到正确 Map 却仍被旧架构规则误放行。本章用真实测试把这些问题放在同一条链路上验证。

检查点不是“跑绿就行”。我们要能解释每个测试组在保护哪条规则，并区分三个层次：Router 单元测试证明内存匹配，架构测试证明公开表面和依赖没有越界，示例测试证明真实消费者可以装配。HTTP 状态码的 socket 行为属于下一章，不能因为示例调用了服务器就把整条传输层算作已证明。

## 先想清楚再写

RouterTest 不是把几十个断言堆进一个方法，而是按语义切组。Duplicates 检查同形状冲突与失败原子性，Encoding 检查原始值，TrailingSlash 检查空段，Delivery 检查参数真正到达 Handler，Concurrency 检查隔离。测试名直接陈述行为，例如“Router 永不调用它注册的 Handler”，失败时无需先猜是哪条产品规则被破坏。

RouteMatchTest 单独验证公共值对象，避免所有问题都塞进 RouterTest。它检查 null、防御复制、冻结、顺序、原始值、record 的 value equality 与 toString 脱敏。ArchitectureTest 则从类型和依赖结构检查单元测试看不到的边界：Router 不能依赖 Response，Handler 签名不能漂移，Request 不能新增路由字段，Router 不能突然实现容器或生命周期接口。

插件集成测试把 Builder 交给真实参与者。两个插件共享一张表，但不需要相互依赖；这个自定义夹具在 initialize 中注册，因此重复路由在 application.start 时变成 StartupException，participantId 指向 clash，根因是 IllegalArgumentException。它证明旧时序中的拒绝不仅能由 Builder 抛出，也能被生命周期回滚识别并归属到参与者。当前标准 `RouteContributor` 贡献发生在装配期，冲突直接抛 IllegalArgumentException；第 11 章会对照两种证据，不能混用它们承诺的失败时机。

示例测试只提供最小消费视角：GET `/books/42` 返回 book 42，GET `/books` 返回空目录文本，POST `/books` 返回 201，未知 path 返回 404，已知 path 用 DELETE 返回 405。它不重复 RouterTest 的全部矩阵，而是证明外部用户只依赖公开 API 就能完成装配。

## 常见的第一次写错

只运行 RouterTest 会漏掉 Handler 签名变化；只运行示例测试会把 wire 层的 404/405 误当成 Router 的直接职责。把嵌套类测试数量漏算，会得到“0 tests”的错误结论。为了通过 JDK 环境差异去修改路由语义，则会把测试问题变成框架问题；本章命令不涉及已记录的 JdkMethodCaseSemanticsTest 环境失败。

反向验证必须针对真实规则。例如把 Handler 第二参数删掉，签名规则与 Delivery 测试应失败；给 Request 加一个参数 accessor，Request 封闭表面规则应失败；让 Router import Response，依赖规则应失败。若 mutation 后测试仍绿，优先怀疑测试没有真正瞄准目标，而不是认为保护已经足够。

验收时还应保留可复查的测试入口。Surefire 会在各模块 target 下生成报告，但本教程不把 target 当作文档资产；需要比较历史数量时，应记录命令、日期和输出摘要，而不是复制构建产物。若后续新增 RouteContributor 测试，完整 RouterTest 数量不变也不代表路由能力没有变化，必须同时检查 RouteContributorTest 和架构规则。

另一个检查点是提交边界。`18e8fef` 建立初始表，`2eddb0d` 才完成参数传递，`74ea0fb` 才补星号分支；用最终源码回看初版时，要能从 git show 中分辨哪些测试当时并不存在。教程引用真实提交，是为了说明设计如何被反馈逐步修正，而不是把最终实现伪装成一次写完的完美方案。

阅读失败报告时还要确认测试确实覆盖了当前源码。如果修改后 Maven 没有重新编译测试，看到旧报告绿灯并不构成证据；应先清理对应模块的旧结果或强制重新运行，再检查 Surefire XML 的时间与用例名。教程要求命令可复现，正是为了避免把“以前跑过”误写成“当前通过”。

最后应留下未覆盖清单：OPTIONS * 在当前 JDK 上的拒绝行为、HEAD 的 representation 长度、304 的 framing、请求体超限与 Handler 异常如何变成 HTTP 响应。它们都不是路由单元测试的失败，而是下一层适配器需要提供的新证据。诚实的缺口比一份看似完整的检查表更有教学价值。

## 怎么确认这一步没造错

先运行 149 项聚焦测试：

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=RouterTest,RouteMatchTest,HandlerTest,BarezenWebArchitectureTest,RouterPluginIntegrationTest
```

本次实测结果：Tests run: 149，Failures: 0，Errors: 0，Skipped: 0，BUILD SUCCESS。数量构成为 RouterTest 84、RouteMatchTest 12、HandlerTest 24、ArchitectureTest 23、插件集成 6。再运行 examples 模块的真实示例测试：

```bash
mvn -o -B -ntp -pl examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=RoutingExampleTest
```

实测 3 项全部通过。然后运行完整 barezen-web 测试，当前为 248 项；本章聚焦数量不应被误写成完整模块总数。

可以按下面矩阵复核失败信号：

| 失败位置 | 首先检查 | 不应如何掩盖 |
| --- | --- | --- |
| Surface | 是否新增公共方法或 Route 类型 | 删除测试而不是收缩 API |
| Static/Method | match 是否只比较 method/path | 在 Router 中生成状态码 |
| Duplicates | shape 是否忽略参数名、注册是否原子 | 后注册覆盖 |
| Parameters/Delivery | 捕获顺序、Map 冻结、Handler 签名 | 从 path 再解析一次 |
| Encoding/TrailingSlash | 是否解码、是否丢空段 | 自动 normalize |
| Priority | 第一个分歧是否决定胜负 | 引入注册序号优先级 |
| Concurrency | 是否共享 Map 或 best | 加锁掩盖共享状态 |
| Architecture | Handler 精确签名与依赖白名单 | 放宽整个包依赖 |

## 此刻的代码长什么样

本章交付一张可复现的路由语义证据表：149 项聚焦测试、3 项示例测试和 248 项完整 web 测试。尚未证明的是真实 HTTP 分帧、异常回复、请求体上限和 JDK 的 HEAD/304 行为；这些缺口将在第 6 章由适配器测试补齐，而不是在本章伪造结论。
