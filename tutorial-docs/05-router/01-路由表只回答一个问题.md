# 01 路由表只回答一个问题

## 这一步要解决什么

第四章之后，应用已经能写出 `(request, parameters) -> Response`，却还不能把请求交给它。没有路由层时，每个入口都得复制一套 if/else：先看方法，再比较路径，最后决定参数怎么读。更糟的是，这些判断很容易和“没有路由时返回什么”混在一起，于是路由代码开始 new Response(404)，随后又加上 JSON 错误格式和异常处理。

本章把问题压缩成一个：给定 Request，哪个已注册 Handler 应对它负责，以及模式捕获了什么？Router.match 的返回类型是 `Optional<RouteMatch>`，不是 Response，也不是 Handler 本身。没有命中就返回 empty，不猜状态；命中就返回 handler 与 parameters，不执行它。Adapter 仍然是唯一调用 Handler 并写字节的组件。

第二个问题“这个 path 上有哪些方法”由 methodsFor 单独回答。它和 match 一起给适配器足够信息区分 404 与 405，但 Router 自己不决定客户端看到哪种错误。这个分工看起来保守，却让同一个路由表可以服务不同错误政策的服务器。

## 先想清楚再写

路由的最小输出不是 Handler，而是 RouteMatch。静态路由只需要 Handler，但 `/users/{id}` 一旦存在，匹配还决定了 `42` 就是 `id`；调用者无法只从 Handler 或 Request 恢复这个名称与值的对应关系，因为 Request 不含模式。RouteMatch 正是为了携带这第二个不可重建的事实而存在。它不增加 pattern、route name、handler class 或 priority，因为当前没有消费者。

match 返回 Optional，而不是三态密封结果，是为了不把错误政策塞进路由层。Unknown path 是 empty；method mismatch 也是 empty。两者对 match 来说确实是同一件事：没有选中 Handler。若调用者想知道区别，再问 methodsFor(path)：空集合表示这个 path 没有路由，非空集合表示路径存在但方法不匹配。两个小而独立的问题，比一个 Matched/NotFound/MethodNotAllowed 联合类型更容易测试和复用。

Router 不调用 Handler 是另一条硬边界。调用 Handler 需要处理异常、构造 Response、决定 500，还会让“匹配”和“执行”无法分别测试。[theRouterNeverCallsTheHandlerItRegistered](../../framework/barezen-web/src/test/java/com/barezen/web/RouterTest.java#L131) 注册一个必定抛异常的 Handler，然后只调用 match、methodsFor 和 toString；三者都必须正常返回。这个测试比检查 import 更直接，因为一个偷偷分派的 Router 即使没有新 import 也会让它失败。

methodsFor 返回不可变 Set，并保持注册顺序。顺序不是优先级，只是适配器构造 Allow 字段时可使用的稳定罗列。Set 去重也避免同一 path 上多个参数形状重复报告同一个方法。Router 不把这个集合转换成字符串或 Header，因而不会替任何服务器决定错误响应的序列化方式。

注册与执行也属于不同时间。Builder.route 接收应用已经构造好的 Handler，不查容器、不扫描注解、不调用工厂。当前扩展方式是应用在装配期调用 `Builder.contributing(...)`，由 `RouteContributor.contributeRoutes(Router.Builder)` 向同一个 Builder 注册；贡献完成后 build 冻结快照，再交给适配器启动。插件若同时是 RouteContributor，也不会因此获得一个生命周期中的 Router 上下文。这样路由表不是生命周期资源：它没有端口、线程或文件，也不需要 start/stop。

## 常见的第一次写错

让 match 返回 Handler 会丢失参数名称；返回裸 Map 又丢失 Handler。让 Router 返回 null 表示未命中，会把 Optional 的显式缺失重新变成每个调用者的空指针风险。让 methodsFor 返回可变 Set，调用方可以修改一个看似只是查询结果的集合，下一次诊断就会得到不同答案。

把路由注册放到运行中的 Router 上，会引入注册与请求读取之间的竞态。把 Handler 调用放进 match，则路由单元测试不得不处理业务异常和响应政策。另一个隐蔽错误是给 RouteMatch 加 `pattern()`“方便日志”：这会给一个目前没有消费者的新字段建立永久 API 承诺，而摘要需求可以由 Router 的模式列表满足。

学习时还要区分“数据答案”和“协议答复”。`methodsFor("/users")` 返回非空，只证明至少有一条同路径路由存在；它不证明适配器最终会发送 405，也不证明 Allow 的内容和顺序。真实客户端看到的状态行、Header 与 body，必须由服务器测试观察。把这个边界说清楚，Router 才不会被无意扩成一个错误响应框架。

## 怎么确认这一步没造错

先写一张职责表，再为每一格写测试：

| 输入或操作 | 允许的输出 | 不允许的输出 |
| --- | --- | --- |
| match 命中 | RouteMatch | Response 或异常 |
| match 未命中 | Optional.empty | 404 Response |
| methodsFor | 不可变方法集合 | Allow Header 或 405 Response |
| route | 更新 Builder | 修改已构建 Router |
| toString | 方法与模式摘要 | Handler 值或请求数据 |

行为测试从公开方法观察，不访问私有 Registration。[arouterIsBuiltAndThenOnlyAsked](../../framework/barezen-web/src/test/java/com/barezen/web/RouterTest.java#L63) 用反射固定 Router 的四个公开方法，Builder 的初始两个注册/构建方法以及后来增加的 contributing。`thereIsNoPublicRouteType` 同时防止内部记录被提升成 API。

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=RouterTest,RouteMatchTest,BarezenWebArchitectureTest
```

当前这组会连同嵌套测试类一起运行。若只看到某个外层类显示 0 项，应继续查看 `$Surface`、`$NoRoute` 等 Surefire XML；真实数量在嵌套类中，不能据此判断测试没有执行。

反向验证可以让 match 在未命中时直接构造 Response，观察 `the_router_never_answers_a_request_itself` 是否变红。实验结束后必须恢复源码字节，并重新运行测试；不能把“制造失败”本身当成交付物。

## 此刻的代码长什么样

你现在有一个只回答匹配问题的表：match 给出 Handler 与参数，methodsFor 给出路径上的方法，RouteMatch 保持两个组件。它仍不知道 404/405 的 wire 形状，也还不能监听端口。下一步把匹配规则落实到最基础的原始段比较，先确保 Router 不会偷偷改写客户端路径。
