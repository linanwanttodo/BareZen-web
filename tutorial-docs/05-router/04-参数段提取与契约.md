# 04 参数段提取与契约

## 这一步要解决什么

初始 Router 能选中 Handler，却只给调用者一条路径字符串；参数名称藏在 Handler 的闭包或适配器自己重新切分 path 的逻辑里。这会产生两个问题：同一匹配规则被实现两次，以及包装器可以伪造一套与 Router 不一致的“参数”。尤其 `/a/{x}/b/{y}` 这种交错模式，按名称与 path 简单 zip 很容易把第一段字面量 `a` 错抓成 x。

本章让 match 返回完整 RouteMatch，captured 按参数在模式中出现的顺序消费 path 段，Handler 直接接收第二个 Map 参数。Map 的 key 来自模式，value 保持原始文本；静态路由得到空 Map，不用 null 表示“没有参数”。每次匹配产生新 Map，不能跨请求复用。

这是第二次提交 `2eddb0d` 的核心，不是后续润色。它把 Router 的答案推进到 Handler 内部，也迫使架构测试把旧的单参数分派规则改为新签名，否则规则可能因方法不存在而变成永不匹配的绿色装饰。

## 先想清楚再写

捕获不能依赖参数名集合和 path 段的 zip，因为参数只占部分位置。正确算法在遍历模式段时，只有遇到参数才把当前 path 段放进 `parameterNames.get(next++)` 对应的 key。这样 `/a/{x}/b/{y}` 对 `/a/1/b/2` 得到 x=1、y=2，而不是 x=a、y=1。LinkedHashMap 保持声明顺序，错误日志和调试能稳定看到 x 再 y。

参数段的语法刻意很窄：整段必须形如 `{name}`，name 首字符是字母，后续只允许字母、数字和下划线；同一模式内不得重复名称。花括号不能出现在普通字面量中，`/x-{id}`、`/{id}/x-{id2}` 都不是“部分参数”规则，而是非法模式。这样无需转义花括号，也不需要在一个段内维护字面量与参数的混合文法。

RouteMatch 的 compact constructor 再做一次防御复制与冻结，即使 Router.captured 已返回不可变 Map，也不能依赖内部调用者的好心。这是公共类型边界：调用者可能自己 new 一个 RouteMatch，组件可变 Map 就会绕过 Router 的承诺。每次 match 创建参数容器也确保两个并发请求不会看到彼此的 id。

为什么不把参数放回 Request？Request 的定义是客户端发送的五种事实，path 中并没有“id”这个独立字段。给它增加路由结果 Map 会污染这个语义，让直接构造的测试 Request 能携带虚假路由值。为什么不接受 `RouteMatch` 作为 Handler 第二参数？那会把 Handler 自己交回给 Handler，诱发内部再分派，也让没有经过 Router 的调用者必须伪造一个 RouteMatch。

为什么删除单参数重载，不留默认桥接方法？旧 Handler 若静默忽略 Map，会继续从 path 重切参数，本章修复的缺口又回来了；适配器也无法判断实现是否真正使用路由答案。`2eddb0d` 因此是破坏性变更，示例、测试、适配器和架构规则一起更新。它发生在 0.1.0-SNAPSHOT 阶段，比留下永久双签名便宜。

## 常见的第一次写错

把捕获值解码再交给 Handler，会让 `%2F` 变成 `/`，使应用无法区分路径段与内容；跳过空段会让 `/a//b` 意外匹配另一个形状。用 HashMap 破坏声明顺序不一定让功能失败，却让诊断输出不稳定。返回可变 Map 或缓存一个共享 Map，则 Handler 的一次修改可能污染后续请求。

保留旧单参数重载会让“迁移完成”变成假象，测试若只覆盖新签名，旧消费者仍可编译并在生产中丢参数。签名固定规则若仍搜索 `handle(Request)`，在代码改成双参数后会因为“没有匹配方法”而保持绿色；所以规则本身也必须由 mutation probe 验证确实有目标可检查。

测试还应检查静态路由的 Map 不是 null。调用者必须能用同一种循环或序列化逻辑处理静态与动态路由，而不是先判断 parameters 是否存在。空 Map 是可遍历、可复制且语义明确的“零个捕获”，null 则把内部特殊情况泄漏给每个消费者。Map 的顺序保证也属于诊断契约：声明为 x、y，输出就应按 x、y，而不是由 HashMap 的散列布局偶然决定。

迁移检查还应覆盖所有 lambda 形状。单参数 lambda 看似能自动适配，但函数式接口只有一个抽象方法，删除旧签名后编译器会直接报参数数量不符；默认方法或显式匿名类则可能留下旧重载，成为绕过新契约的入口。因此 `2eddb0d` 同时修改 main、test、examples 与架构规则，而不是只改 Router 和一处调用。

对调用者而言，还应保留“参数 Map 不等于 query 参数”的区别。前者由模式命名并证明段的位置，后者来自客户端查询文本，可能重复、可能没有 key，也可能采用完全不同的解码规则。把两者合并会再次引入 Router 不拥有的解析政策。

## 怎么确认这一步没造错

参数测试要同时观察三件事：选中的 Handler、Map 内容、Map 是否可修改。交错参数测试固定位置对应；重复名称与非法语法测试固定注册失败；两个并发测试固定隔离。尤其不能只断言值正确却让 Handler 修改 Map 后影响下一次请求。

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest='RouterTest$Parameters,RouterTest$Delivery,RouterTest$Concurrency,RouteMatchTest,HandlerTest'
```

[theHandlerReceivesWhatTheRouterCapturedWithoutParsingThePath](../../framework/barezen-web/src/test/java/com/barezen/web/RouterTest.java#L963) 使用一个内部会抛异常的 path accessor 包装 Request，证明 Handler 完全可以不读取 path。若 Handler 仍通过包装器重切路径，这个测试会暴露对原始字符串的依赖。

插件集成测试把这条规则带到真实 LifecycleOrchestrator：UserPlugin 把 Builder 作为构造参数，在 initialize 注册两个路由，engine 启动后 build，测试从 RouteMatch 取 Map 并调用 Handler，store 只收到 `42` 一次。这是该集成夹具自定义的时序；当前标准 `RouteContributor` 扩展在装配期贡献并冻结路由，第 11 章会展开。两条路径都证明应用无需上下文或容器即可消费参数，但不能把旧夹具当成现行扩展 API。

## 此刻的代码长什么样

match 现在交付完整、不可变、按模式命名的参数，Handler 无需重切 path。下一步把 Router 与 Builder 的构建时复制、可复用性和并发安全连成一条证据链，同时诚实说明线性扫描的当前成本。
