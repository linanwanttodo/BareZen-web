# 05 不可变路由表与并发匹配

## 这一步要解决什么

Builder 可以在应用启动前不断注册路由，但一旦交给服务器，请求就可能并发到来。若 build 只是把 Builder 列表包装成 unmodifiable view，后续注册仍会改变正在服务的表；若 Router 缓存一份参数 Map，两个请求可能共享或覆盖 id；若 match 在临时结构中累加最佳候选却跨请求复用，并发行为更难推理。

本章让 build 复制注册列表，让 Router 实例只读，让每次 match 独立创建参数 Map。并发安全不依赖 synchronized，而来自“没有可写共享状态”这个更简单的性质。Builder 仍可复用，后加路由只影响之后构建的新 Router，已有表保持快照。

这里还要划清框架边界：Router 没有生命周期、容器或中间件接口，也没有为了“以后可能需要”预留注册表。它的成本是每请求线性扫描所有注册项，ADR 明确记录这是当前选择，而不是暗示它已经具有高性能 trie 的复杂度。

## 先想清楚再写

List.copyOf 是不只是“让外部不能 add”。Registration 本身不可变，列表复制又切断 Builder 后续增长与已构建表之间的联系。unmodifiableList(registrations) 只阻止调用者修改列表，却仍观察原列表，因此不能建立快照。[aBuiltRouterDoesNotSeeRoutesRegisteredAfterwards](../../framework/barezen-web/src/test/java/com/barezen/web/RouterTest.java#L800) 正是先在 Builder 上构建，再注册新路由，最后要求旧 Router 不认识它。

Router 的 registrations 和 Builder 的 registrations 都是 final 引用，避免 reassignment 带来的发布复杂性。Builder 是可变的，但只在装配阶段使用；Router 不可变，适合安全发布给多个请求线程。这里没有“注册锁”，因为动态注册根本不在 API 中。需要改变路由就构建新表并让应用在明确的装配点替换它。

参数 Map 则必须每次新建。静态路由可以复用 Collections.emptyMap，因为它没有可写内容；动态路由用新的 LinkedHashMap 捕获，再经 RouteMatch 防御复制。9 个线程、每个 200 轮、3 个 id 的测试要求每个 id 恰好出现 200 次；只断言“没有异常”不足以证明值没有串线。

这里有两层隔离，不能只做一层。Registration.captured 为每次命中建立新的 LinkedHashMap，防止两个请求先共享同一个捕获容器；RouteMatch 构造器再复制并冻结传入 Map，防止调用者在匹配完成后修改它。第一层解决 Router 内部跨请求写入，第二层解决结果跨组件暴露后的修改。静态空 Map 可以共享，是因为它没有任何可写位置。复制带来的分配成本是当前明确选择，不能一边享受无锁推理简单，一边又把不可变结果缓存成跨请求可变对象。

Router 不实现 LifecycleParticipant，意味着没有人需要为它启动或停止服务。当前标准扩展由 `RouteContributor.contributeRoutes` 在装配期向 Builder 注册，应用执行 `Builder.contributing(...)` 后 `build()` 冻结表，再启动生命周期。仓库的 `RouterPluginIntegrationTest` 仍保留一个自定义旧时序：插件把 Builder 作为构造参数，在 initialize 注册，启动后 build；它证明这种组合可以工作，却不是后来引入的 `RouteContributor` 扩展契约。两条路径都让 Router 保持普通数据：Table 可以在 orchestrator 关闭后继续使用，不存在需要释放的 socket 或线程。

不实现 Handler 也很重要。Router 不接收 Request 并返回 Response，所以不能直接注册到另一张 Router，也不能绕过适配器调用。它没有 resolve、service、context、registry 等查找方法，因为“哪些 Handler 存在”完全由应用显式注册。后续 RouteContributor 只让多个插件向 Builder 提供路由，不给 Router 增加服务定位能力。

线性扫描的优点是规则统一：每个候选都经过 method、段数和位置比较，不需要维护前缀树节点、压缩边或动态重平衡。缺点是注册增多时每请求成本上升，本章没有基准数据，不能宣称它适合高吞吐场景。真实优化应先测量，再保持旧行为建立等价测试，不能为了理论性能破坏原始段语义。

## 常见的第一次写错

只把列表设为 unmodifiable 不能防止 Builder 后续写入；只复制列表但 Registration 内含可变对象也不行，本例 Registration 的组件都已冻结或不可变。缓存最佳 Registration 供下次请求使用会跨请求泄漏，缓存捕获 Map 则会串值。为了让并发测试稳定而加 Thread.sleep，通常只是放大竞态窗口，不能替代正确的状态隔离。

把 Router 注册成 LifecycleParticipant 会制造没有资源的 start/stop 回调，并诱导插件通过上下文查找路由。让它实现 AutoCloseable 也缺少真正要关闭的对象。另一个过度设计是增加 remove、clear 或热更新方法；一旦可写表进入运行期，就必须重新定义发布、回滚和并发优先级，远超当前需求。

并发测试通过也不等于吞吐量证明。它只验证特定线程数和轮次下的逻辑隔离，没有测 GC、锁竞争或每请求延迟。Router 的线性成本需要独立基准，且必须固定路由数量、命中位置、参数数量和 JVM 条件。把“没有锁”写成“一定更快”会越过测试证据；本章能证明的只是共享状态更少、推理边界更清楚。

## 怎么确认这一步没造错

不可变性测试覆盖四个方向：构造拒绝 null、注册列表不能外部修改、构建后 Builder 再注册不影响旧表、同一 Builder 可以构建多个不同快照。并发测试则覆盖静态匹配和动态参数，两者使用同一个 Router 而非各自 new 一份。

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest='RouterTest$Immutability,RouterTest$Concurrency,RouterTest$Delivery,RouterTest$Printing,RouteMatchTest'
```

打印测试不是装饰。Router.toString 只输出注册顺序的 `METHOD pattern`，RouteMatch.toString 只输出参数名与数量，不输出参数值或 Handler。路径参数可能包含 token、邮箱或内部对象标识；把值写进诊断字符串会把“错误日志”变成数据泄露渠道。测试固定脱敏输出，比只检查“有 toString”更严格。

反向验证可以把 build 改成 unmodifiable view，观察旧快照测试失败；把 captured 的 Map 提升为字段共享，观察并发隔离测试失败。实验后恢复源码并重跑。不能用增加 synchronized 掩盖共享可变状态，因为那会同时掩盖设计错误和引入不必要的锁成本。

## 此刻的代码长什么样

Router 成为装配期生成、运行期只读的快照；参数按请求隔离；并发安全来自不可变共享与独立局部结果。最后一步把所有语义组成可重复的路由矩阵，运行真实测试并明确哪些 wire 行为仍未被证明。
