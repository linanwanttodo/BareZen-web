# 02 参与者的启动顺序与依赖

## 这一步要解决什么

上一章只定义了对象何时进入生命周期，还没有定义多个组件谁先启动。假设参与者依次是“数据库”“报表缓存”“HTTP 运行时”：如果 HTTP 先 start 并绑定端口，报表缓存还没初始化，外部请求会读到空数据或触发延迟加载；如果数据库最后 start，缓存初始化却已经读取连接，启动又会在错误阶段失败。

框架可以给每个参与者增加 priority，让组件自己声明“我最先”，也可以把依赖关系做成一张图自动拓扑排序。这两条路都没有采用。组件最了解自己的资源，却不一定了解整个应用的启动策略；让一个插件给自己打分，会把局部偏好误当全局顺序。BareZen 把顺序留在应用装配代码：先注册依赖方依赖的基础设施，再注册使用它的组件，最后注册对外服务。

这个决定记录在 [ADR-0003](../../docs/adr/0003-global-two-phase-startup.md#L19)，并由 [LifecycleParticipant.java:22](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleParticipant.java#L22) 的契约直接说明。参与者是普通对象，依赖通过构造参数可见地进入，生命周期回调不接收一个巨大的上下文对象。

## 先想清楚再写

四个方法不是“生命周期有四个必须实现的步骤”，而是四种不同所有权。initialize 获取资源、完成内部接线和注册，不对外可观察；start 才激活服务，例如绑定端口或开始消费。stop 释放已成功 initialize 的资源，因此必须容忍“初始化过但从未 start”；abort 只处理 initialize 自身失败后留下的半成品。空默认方法让没有该阶段工作的组件不必写空实现。

把资源获取放在 initialize，而不是构造函数，回滚才有统一入口。构造函数失败的实例根本不会进入参与者列表，其自身必须负责局部清理；进入 initialize 后，无论后续哪个参与者失败，orchestrator 都能逆序调用 stop。若 initialize 自己抛错，它可能处于内部不完整状态，所以只调用 abort，不假装已经走到完整停止状态。

注册顺序同时是启动顺序和逆序停止顺序。可以把它写成应用中的一段直白结构：

```java
LifecycleOrchestrator app = LifecycleOrchestrator.builder()
    .threadPolicy(ThreadPolicy.PLATFORM)
    .register("database", databaseParticipant)
    .register("cache", cacheParticipant)
    .register("http", httpParticipant)
    .build();
```

这里的关键不是三个 id 字符串，而是 variables 的依赖必须已经通过构造器准备好。cacheParticipant 不应在 start 中突然向全局查询 databaseParticipant，否则启动顺序只解决了调用先后，没有解决对象可见性。构造参数让依赖图在代码中可读，也让单元测试可以用替身替换一个参与者。

优先级方案看起来只增加一个 int，实际会引入同值处理、不同组件分别声明时谁覆盖谁、运行时发现顺序是否影响结果等问题。最终系统仍需要装配层裁决。既然裁决无法消失，把它集中到 register 调用顺序，比隐藏在各组件的注解或字段里更诚实，也更容易在集成测试中观察。

串行启动的代价必须承认：一个慢 initialize 会推迟全部 start，当前没有并行启动和子系统超时。这是明确接受的 MVP 边界，不是性能优化漏做。并行还需要处理部分组件已对外可观察时的并发回滚，复杂度远大于多开几个线程。

## 常见的第一次写错

把端口绑定写进 initialize，会破坏“所有 initialize 完成后才进入 start”的安全窗口，早绑定的服务已经能收到半初始化请求。把 stop 写成“必须 start 过才有效”，会让启动失败回滚在只 initialize 的对象上再次抛错。让 abort 抛异常，会污染原始初始化失败，使调用方无法判断第一病因。

重复注册同一个 id 会被 builder 拒绝，见 [LifecycleOrchestrator.java:362](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L362)。若绕过校验把同一个实例注册两次，它可能被 start 两次、stop 两次，而清理幂等不能替代发现装配错误。id 是日志和失败报告中的稳定标识，不是可以随手重复的显示名称。

最后，不要假设参与者注册顺序会替代构造依赖。一个后注册对象可以在构造时引用先创建但尚未 initialize 的对象，只要它不在 initialize/start 前调用对方尚未完成的方法。真正的运行期依赖仍要转换成构造顺序和生命周期顺序，而不是服务定位器。

## 怎么确认这一步没造错

顺序测试应断言一条完整事件序列，而不是分别检查每个组件“最终被调用过”。[LifecycleOrchestratorTest.java:38](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleOrchestratorTest.java#L38) 用 RecordingParticipant 记录 a/b/c 的 initialize 与 start；停止测试清空事件后要求 b.stop、a.stop。测试辅助类在 `framework/barezen-core/src/test/java/com/barezen/core/kernel/RecordingParticipant.java`，不是生产 API。

还可以用失败注入验证逆序：让第三个参与者在 start 抛错，预期第三个、第二个、第一个都收到 stop，且每个恰好一次。让第二个 initialize 抛错，预期第二个收到 abort，第一个收到 stop，第三个从未被 initialize。这样的测试比“回滚方法被调用”更具体，因为它同时锁住顺序和 abort/stop 的选择。

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=LifecycleOrchestratorTest,LifecycleRollbackTest
```

本章检查点已经与 ShutdownTest 一起执行，共 27 项通过。单独运行时 Surefire 会过滤到对应测试；父模块没有指定测试时由 failIfNoSpecifiedTests=false 跳过，这是命令参数，不是关闭失败检查。

## 此刻的代码长什么样

你现在拥有一个有顺序的参与者列表：应用显式注册，接口只声明阶段，回滚按逆序进入过的对象执行。下一步深入两个启动循环，解释为什么 initialize 只允许准备和注册，start 才允许对外服务，以及两阶段如何共同避免启动窗口。
