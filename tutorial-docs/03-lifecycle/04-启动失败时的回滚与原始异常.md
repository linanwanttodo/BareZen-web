# 04 启动失败时的回滚与原始异常

## 这一步要解决什么

启动不是成功就 RUNNING、失败就抛异常这么简单。失败发生时，先前的参与者可能已经持有连接池、文件句柄或后台线程；失败对象自己也可能在 initialize 中拿到一半资源。若框架只是把异常抛给应用，应用很难知道清理到哪一步、谁需要 abort、谁已经 start、谁还没有被调用。

本章让启动路径自行完成参与者回滚，再把 StartupException 交给应用。目标有两个：第一，失败原因永远可见；第二，清理继续尝试所有已进入对象，不因其中一个 stop 抛错而提前退出。回滚不是补偿事务，也不承诺修复坏数据，它只释放当前进程内参与者已经获得的资源。

这里的“释放”必须精确理解。orchestrator 保证尝试回滚并清空 entered 列表；如果参与者的 stop 自身失败，资源可能仍然存在，只是失败被记录。它不是跨系统分布式回滚，也不负责关闭应用通过 ServiceAssembly 创建的对象；但它会在参与者回滚后关闭自己持有的 ThreadProvider。

## 先想清楚再写

initialize 失败与 start 失败的对象状态不同。initialize 失败者从未被加入 entered，因为无法假设它完成了内部接线，所以只调用 abort。之前 initialize 成功的参与者逆序 stop。start 失败者已经完成 initialize，并且已经加入 entered，因此它和所有已 initialize 的参与者都逆序 stop；即使某个参与者的 start 尚未轮到，stop 也必须能释放它 initialize 中取得的资源。

以 [failureInInitializeAbortsFailingAndStopsPreceding](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleRollbackTest.java#L32) 为例，a、b 成功 initialize，c 的 initialize 失败，d 尚未被调用，事件精确为：

```text
a.initialize, b.initialize, c.initialize, c.abort, b.stop, a.stop
```

d 没有 initialize，所以连 stop 都不调用。若框架为了“统一”把所有注册对象都 stop，会制造不存在的生命周期，迫使每个组件防御从未获得的资源。entered 列表不是全部参与者列表，而是“框架已经调用过 initialize 且成功返回”的回滚栈。

[start 失败测试](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleRollbackTest.java#L54) 则要求 a、b、c 全部 initialize 后，a.start、b.start 失败，随后 c.stop、b.stop、a.stop。c 从未 start 仍被 stop，b 失败于 start 也不 abort。这个测试同时排除了两种常见错误：只回滚已经 start 成功的对象，以及把 start 失败者当半初始化对象。

原始异常通过 StartupException 的 cause 保留，phase 与 participantId 让调用方知道失败发生在哪个阶段。清理失败放入 rollbackFailures，同时逐个 addSuppressed。这样只打印 getCause 的日志仍能看到启动原因，检查 suppressed 或结构化列表的诊断工具也能看到所有清理问题。[rollbackFailureNeverReplacesTheStartupFailure](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleRollbackTest.java#L161) 用 b initialize 失败与 a stop 失败验证这条规则。

abort 自身失败也不会覆盖 initialize 失败。实现把 abort 的异常作为 ShutdownFailure 放到回滚列表开头，因为它是失败对象自身的第一项清理问题；随后才是先前参与者的逆序 stop。若 abort 和 stop 都调用，同一个半初始化对象可能被清理两次，因此 [abortAndStopAreMutuallyExclusive](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleRollbackTest.java#L129) 专门锁住互斥关系。

### 当前实现边界：回滚不等于关闭全部资源

成功启动后的正常 stop 顺序是参与者逆序 stop，然后 threads.close()。参与者仍能向 ThreadProvider 提交最后的清理任务，因此提供者必须最后关闭。这与 ADR-0011 的所有权一致：orchestrator 只关闭自己创建或持有的提供者，不借用其他所有者的对象。

启动失败现在使用同一顺序：releaseEntered() 清空参与者回滚栈后调用 threads.close()，然后设置 FAILED 并抛 StartupException。ThreadProvider.close 按契约不抛错，因此不会替换启动异常；FAILED 上的 stop 返回缓存报告，也不会再次关闭。[startupFailureClosesThreadProviderAfterRollback](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleRollbackTest.java#L76) 同时断言 b.stop、a.stop、provider.close 的顺序与 stop 的幂等性。

边界仍然存在：参与者 stop 失败只代表框架尝试过，不证明业务资源确实释放；ServiceAssembly 创建的对象仍由 application 在 orchestrator.stop 后关闭。线程 provider 的补关修复不跨越这两层所有权。

## 常见的第一次写错

用 finally 简单调用全部 stop，会忽略 initialize/start 阶段差异，并把尚未构造或尚未进入生命周期的对象卷入清理。用 cleanup 异常覆盖 startup 异常，会让日志显示一个次要 stop 失败，真正导致启动失败的端口占用或配置错误反而消失。只记录第一个清理失败，会让其他资源继续泄漏。

另一些错误来自过度承诺：把“尝试 stop”说成“资源一定释放”，把“entered 清空”说成“所有对象都关闭”，或把 StartupException 的 Javadoc 中“完成回滚”扩大为“清理零失败”。实际 stop 可以失败，框架只是收集并报告。诚实文档必须区分尝试、成功与资源所有权。

## 怎么确认这一步没造错

回滚测试必须同时断言事件、异常类型和报告。只断言抛了 StartupException，无法发现失败对象被 stop 而不是 abort；只断言事件，无法发现清理异常替换原始异常；只检查第一次 stop，无法证明 FAILED 不会再次执行清理。

[everyEnteredParticipantIsAttemptedDuringRollback](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleRollbackTest.java#L150) 让 a、c 的 stop 失败、d 的 start 失败，预期四个参与者都收到 stop，rollbackFailures 按清理尝试顺序为 c、a。失败没有阻止 b、a 的清理，说明“最佳努力”不是遇到错误就退出。

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=LifecycleRollbackTest,LifecycleOrchestratorTest,ShutdownTest
```

本章检查点已实际运行，27 项通过。该测试组证明参与者回滚的顺序与报告，也覆盖启动失败后关闭 ThreadProvider；源码审阅与新增回归共同保留这条保证。
