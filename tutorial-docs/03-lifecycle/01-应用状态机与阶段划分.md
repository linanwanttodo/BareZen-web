# 01 应用状态机与阶段划分

## 这一步要解决什么

对象构造完成不代表应用已经可服务。生命周期引擎必须让调用方知道：现在是刚 build、正在初始化、可以接流量，还是已经停止或启动失败。若只有一个 running 布尔值，并发 start、启动中途 stop、重复 close 都只能靠竞态和额外标志拼补，最终很难证明每个回调只执行一次。

本章使用 [ApplicationState.java](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/ApplicationState.java#L15) 的六个枚举值，不增加 INITIALIZED。这不是省略一个中间过程，而是故意不把“全局 initialize 已完成”暴露成一个可分支的业务状态。两个启动阶段内部都有自己的循环与失败原因，外部统一处于 STARTING，才能避免调用方在初始化完成后误以为可以接收请求。

初始提交 `2670984` 已经同时带入这套状态机和 [LifecycleOrchestrator.java](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L120)。这说明项目先决定“启动失败由谁负责”，再逐步长出 HTTP 模块。不是等 Web 写完以后补一个 try/finally，而是给之后所有参与者一个共同协议。

## 涉及的核心文件与变更

- [ApplicationState.java](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/ApplicationState.java#L15)：六个状态及 terminal() 查询。
- [LifecycleOrchestrator.java](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L120)：start、stop、close 和状态守卫。
- [LifecycleException.java](../../framework/barezen-core/src/main/java/com/barezen/core/error/LifecycleException.java)：非法状态转换异常，不等于参与者业务失败。
- [LifecycleOrchestratorTest.java](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleOrchestratorTest.java#L187)：连续启动、停止后启动、未启动关闭等状态断言。
- [ADR-0012](../../docs/adr/0012-new-to-stopped-is-legal-and-idempotent.md)：NEW 可以直接 STOPPED，且后续调用不改变结果。

后续 `e0bc31b` 让 orchestrator 获得 Builder.configuration(...)，`6aac12f` 又删除该入口和 threadKind()。这个来回正好说明状态机边界不是“读配置方便不方便”，而是 kernel 是否越界承担应用装配。当前 builder 接收 RuntimeCapabilities 与解析后的 ThreadPolicy，不持有 Configuration 对象。

## 为什么这样设计

六个状态各自表达一种所有权。NEW 表示还没有任何参与者回调发生，唯一允许的启动从这里开始。STARTING 表示启动路径持锁并负责失败回滚，任何外部 stop 都不能抢走清理集合。RUNNING 表示全局 start 已成功完成，可以正常停机。STOPPING 表示清理正在进行，重入 stop 不应递归调用参与者。STOPPED 与 FAILED 都是 terminal，但来源不同：前者是正常结束，后者是启动失败。

`start()` 第一步是 `requireState(NEW, "start")`，见 [LifecycleOrchestrator.java:269](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L269)。因此 RUNNING 再 start 会抛 LifecycleException，不会再次 initialize；STOPPED 后也不能重新启动，恢复运行需要重新构建 orchestrator。单次生命周期不做暂停和重启，可以避免“同一个参与者实例第二次 start 是否安全”这个无法由引擎保证的问题。

`terminal()` 只是 STOPPED/FAILED 的集合判断，不是权限，也不会自动释放资源。应用不能因为 state.terminal() 为 true 就假设 ThreadProvider 已关闭；尤其在 FAILED 分支，这个假设当前不成立。查询状态是观察，清理是另一个显式动作，两者不能混为一谈。

还要区分 build 与 start。[Builder.build():390](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L390) 在没有显式传入 threads 时会调用 ThreadProviders.create(...)，然后才返回状态为 NEW 的 orchestrator。也就是说，NEW 已经可能拥有线程提供者，只是尚未驱动任何参与者。显式请求 VIRTUAL 而运行期不支持时，build 就会失败，根本不存在可 stop 的实例；这也是为什么状态机从 NEW 开始，却不能包办构造阶段的资源获取。

这个边界解释了为什么 stopBeforeStart 测试除了断言 NEW→STOPPED，还检查 close 不 resurrect 状态，以及 provider 相关测试把资源释放放在正常停止路径。若把 build 当启动，测试会误以为创建 executor 与参与者 initialize 是同一阶段；若把 NEW 当“绝对没有资源”，又会漏掉提供者所有权。状态表达生命周期进度，资源所有权由创建代码和正常关闭路径共同决定。

`stop()` 从 NEW 合法进入 STOPPED，且不调用任何参与者 initialize/start/stop/abort；但正常路径仍会关闭 orchestrator 自己创建的 ThreadProvider。这里容易误读成“什么都没做”。正确理解是“没有需要停止的已进入参与者，但拥有者仍要释放自己创建的资源”。

[close():203](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L203) 直接调用 stop() 并丢弃报告，因此 AutoCloseable 只为 try-with-resources 提供统一出口，不负责把清理问题变成第二异常。需要诊断停机失败的应用应显式调用 stop() 并检查 ShutdownReport，而不能只依赖 close。

## 怎么验证

用测试而不是目测状态切换。[startAfterStopIsRejected](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleOrchestratorTest.java#L204) 覆盖 RUNNING 与 STOPPED 两种拒绝；[stopBeforeStartMovesNewStraightToStopped](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleOrchestratorTest.java#L105) 覆盖 NEW→STOPPED；[tryWithResourcesClosesWithoutStart](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleOrchestratorTest.java#L177) 验证 build 后直接离开作用域不会触发参与者回调。

并发测试让四个线程同时 start，预期恰好一个成功、三个收到 LifecycleException。这里验证的不只是“线程安全”口号，而是 initialize/start 序列只出现一次。若状态检查和赋值不在同一把锁内，多个调用者可能都看到 NEW，随后重复启动。

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=LifecycleOrchestratorTest,LifecycleRollbackTest,ShutdownTest
```

本章写作时已实际运行，结果为 Tests run: 25，Failures: 0，Errors: 0，Skipped: 0，BUILD SUCCESS。它包含本章状态测试，也包含后面回滚与停机的联合证据。

## 常见错误与失败后果

把 initialize 完成当作 RUNNING，会让 HTTP 在其余参与者尚未 start 时提前开放。把 STARTING 的 stop 当成立即停止，会让外部线程和启动线程同时清理同一集合，出现 stop 两次甚至未初始化对象被 stop。把 FAILED 当普通 STOPPED，会以为再次 close 能补回启动失败时未关闭的线程提供者，实际当前实现只返回缓存报告。

另一种错误是给状态转换散落布尔标志：initialized、started、closing 分别修改，调用方看到的组合可能根本不是合法状态。集中在锁保护的 enum 中，测试才能用一个明确入口观察竞态，而不是从三个布尔值推测系统处于哪种半成品情况。

## 本步交付物

你现在有一个六态生命周期骨架：start 只接受 NEW，stop 可以从各状态安全返回报告，close 复用停止路径，重启不被支持。下一步不再增加状态，而是把组件放入这张图，明确注册顺序怎样表达依赖，以及 initialize 和 start 各自允许做什么。
