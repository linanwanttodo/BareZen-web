# 03 两阶段启动：先配置后服务

## 这一步要解决什么

上一章确定了注册顺序，但还有一个更隐蔽的窗口：如果每个组件都按“initialize 后立刻 start”执行，先注册的 HTTP 可能已经监听端口，后注册的数据库或安全组件却还没有完成 initialize。此时端口不是不可达，而是暂时对一个不完整的应用可达，这类问题在部署时最难复现。

本章把启动拆成两个完整循环。第一轮只获取资源、完成内部接线；第二轮才让组件对外可观察。当前标准的 `RouteContributor` 路由贡献发生在装配期，`Router.Builder.contributing(...)` 执行贡献后，应用已经可以 `build()` 冻结表。对所有参与者完成 initialize 之前，没有任何参与者会进入 start，因此不存在“HTTP 已启动而参与者资源尚未准备好”的中间窗口。

这不是增加一个 INITIALIZED 状态。状态机只有 STARTING，因为“第一轮结束”只是 start() 内部的进度，不是调用方可以据此接流量或执行停止的状态。[LifecycleOrchestrator.java:208](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L208) 的 initializeAll 返回 null 后，[startAll:224](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L224) 才开始遍历同一份参与者列表。

## 先想清楚再写

initialize 是“可以失败但不能被外部看见”的准备阶段。它适合创建内部资源、验证配置组合、补齐线程池名称，不适合监听端口、发布“服务可用”信号或接受后台任务。标准路由贡献不应推迟到这个阶段：它由装配代码在启动前执行并冻结。一个简单判断标准是：如果此时外部客户端已经能调用它，看到的是否是完整应用？如果答案是否定的，这段工作就属于 start，而不是 initialize。

start 是“可以对外服务”的激活阶段。即使某个参与者在 start 中途失败，已经先 start 的组件可能短暂可观察，但 orchestrator 会立即逆序 stop 它们。两阶段不能消除所有运行时故障，只能消除“所有初始化尚未完成就已经开始服务”的结构性窗口。这个保证来自循环顺序，而不是组件自觉遵守注释。

entered 集合的更新位置同样重要。initialize 抛错的对象不会被 addLast，因为框架无法假设它已经完成资源获取；这种半成品由 abort 处理。initialize 成功的对象立即进入 entered，即使第二轮所有 start 都还没执行，后续任一失败也能逆序 stop。因此 stop 必须覆盖“只初始化、从未启动”的合法状态。

成功路径上还有三步：先设置 RUNNING，再安装 shutdown hook，最后写日志。shutdown hook 绑定的是同一个 stop()，不是另一套清理实现，所以进程退出与显式停机走相同顺序。[installShutdownHook:276](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L276) 只有在全局 start 成功后调用；[failedStartupDoesNotInstallAHook](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ShutdownTest.java#L118) 验证失败启动不会留下一个以后操作 FAILED 对象的钩子。

宿主容器如果已经负责进程生命周期，应用应调用 registerShutdownHook(false)，否则应用 hook 与容器停机机制可能竞争。关闭开关不会关闭自动 stop 的能力，只是不额外注册 JVM 级入口。CapturingShutdownHookRegistry 是测试替身，真实 JVM 的 hook 不便在单元测试中反复添加和触发，因此包私有接口只暴露给 kernel 测试包。

参与者集合在 build 时固定，start 过程中不能注册邻居。这避免“初始化到一半又增加一个参与者”的不可预测顺序。需要新增能力，应在 build 前装配完成；否则先前已 start 的服务会与新加入组件的 initialize 状态不一致。

## 常见的第一次写错

把 start 当第二次 initialize，会让同一资源创建两次；把 initialize 当精简 start，又可能提前打开端口。两者都会让 abort/stop 无法判断对象处于什么状态。若在 start 前安装 hook，启动失败后 JVM 退出可能调用 stop，而启动路径也在回滚，两个所有权会相互覆盖。

若每轮使用不同顺序，例如 initialize 按注册顺序、start 按优先级，停止逆序将不再对应真实启动依赖。当前两个循环遍历同一个 LinkedHashMap，停止逆序遍历 entered，三者共享一套顺序来源，减少策略分裂。

最后，两阶段不等于异步启动。start() 在锁内同步完成所有回调，慢组件会推迟 RUNNING 和 hook 安装。这是当前串行模型的明确代价；教程不把它描述成自动并行或带超时的启动系统。

## 怎么确认这一步没造错

最强顺序断言是一次记录全部事件。[LifecycleOrchestratorTest.java:38](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/LifecycleOrchestratorTest.java#L38) 注册 a、b、c 后要求：

```text
a.initialize, b.initialize, c.initialize,
a.start, b.start, c.start
```

只要实现退回逐组件 init/start，哪怕每个回调都被调用，测试也会失败。这个测试的价值不在于覆盖行数，而在于把 ADR 的结构承诺转成不可含糊的事件顺序。启动成功后 state 必须为 RUNNING，hook 测试另行证明安装发生在成功路径。

还可以在重入测试中观察 STARTING：参与者在 initialize 内调用 stop()，预期它拿到空报告并立即返回，启动继续，最后统一 stop。这里验证外部“想停止”不能夺走启动路径的回滚所有权。stop 不阻塞等待启动完成，也不递归调用参与者；它明确把清理留给启动线程。

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=LifecycleOrchestratorTest,ShutdownTest
```

本章联合检查点仍使用三组生命周期测试，27 项全部通过。这个结果只证明测试所覆盖的顺序与钩子行为，不表示任意业务组件的 initialize 都满足“不对外可观察”的约定；后者是接口契约和代码审查责任。

## 此刻的代码长什么样

你现在得到一个没有可服务中间窗口的启动协议：全局 initialize 完成后才全局 start，start 成功后才 RUNNING 并安装 hook。下一步处理失败：初始化失败和启动失败为什么调用不同清理方法，原始异常怎样避免被清理噪声覆盖，以及 orchestrator 当前究竟释放到哪一层。
