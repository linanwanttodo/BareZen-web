# 第 12 章第 4 步：可运行示例与统一检查点

## 这一步要解决什么

前三步分别得到声明式模型、确定性 JSON 和真实 HTTP 工具。若它们只存在于各自模块的测试里， stranger consumer 仍可能遇到最后一个问题：公开 API 拼起来是否顺畅？应用需要哪些 Maven 依赖？`main()` 与 JUnit 测试运行的是同一份装配吗？在没有真实端点的机器上，示例能否可重复地启动和停止？

提交 `0971abc64b56f72430f572ffa9536cd0815997c5` 新增七个可运行示例，正是为了把这些边界合到消费者一侧。它们位于一个叶子模块 `examples`：routing、requestresponse、security、database、staticcontent、plugins、openapi。每个主题一个 public 入口类，main 启动真实服务并打印观察结果，同包测试通过 TestKit 驱动同一个 package-private factory。示例不是新的框架层，也不能被任何框架模块依赖。

[ADR-0045](../../docs/adr/0045-examples-are-a-leaf-public-api-only.md) 解释了“可运行”的严格含义：build 得到 classes，`java -cp` 执行 main，main 绑定 `127.0.0.1:0` 并用 JDK HttpClient 请求，finally 停止 server；test 在 Maven reactor 中执行同一份路由或装配。不能只写一个永远不被调用的 main，也不能只在 JUnit 里构造一个与 main 不同的 router，然后声称示例已经验证。

本章聚焦 `OpenApiExample`，但它的验证方式适用于全部七个示例。这里要证明的不是“一个文档类能生成 JSON”，而是消费者从公开 API 组装 document，注册 handler，经过真实 socket 得到声明过的 JSON，并在响应中看到稳定结果。同时必须承认：示例的 `/users` 只存在于 document，router 实际只有 `/openapi.json`；它证明文档服务，不证明用户业务。

## 先想清楚再写

第一项选择是一个 examples 模块，而不是七个 Maven 模块。七个独立模块会重复 parent、enforcer、surefire、jar 和 classpath 配置，却没有跨模块组合可展示。单模块的七个包仍保持“读一个文件”的入口清晰度；将来真有消费者需要单个示例 classpath 时，拆分叶子比现在付出七倍构建成本更合理。

这个模块必须处在 reactor 最后。它 compile 依赖所需的框架模块（含 plugins），是应用而不是发布产物；没有任何框架模块反向依赖它，它也不进入 BOM。`examples/pom.xml` 中的 H2 是 compile scope，因为 DatabaseExample 作为应用必须选择真实驱动。框架模块仍只在 test scope 使用 H2。一个示例不这样做就无法运行，而假装运行只会让“driver-free”规则误伤应用层。

第二项选择是 main 与测试共享 factory。`OpenApiExample.document()` 构造声明，`router()` 只负责把 `document().handler()` 挂到 GET `/openapi.json`；main 使用 router，测试也使用同一个 router。若测试另写一份 document，就可能出现 main 的标题、schema 或路径已经坏掉，测试却全绿。共享 factory 不能证明 document 的每项内容都正确，但能保证测试观察的正是用户运行的装配。

main 的自验证不是 Java `assert`。Java 断言默认关闭，用它表达“示例通过”会得到虚假安全感。当前 main 打印 HTTP 状态、Content-Type 和 body 长度，由运行者观察；真正的 enforcement 在 `OpenApiExampleTest`。`main()` 也没有交互输入、外部配置文件或常驻服务，因此不会在 CI/脚本里无限等待。

第三项选择是不引入 `exec-maven-plugin`。离线仓库没有该插件，`mvn -o` 不应为了运行示例临时联网。ADR 选择 reactor 构建后用 shell 的 `java -cp` 执行，classpath 由各模块 `target/classes`、slf4j-api 和 H2 jar 组成。这不是“绕过 Maven”，而是把 run gate 明确放在构建之后；代码仍然必须通过 Maven 编译和测试。

第四项选择是文档字段与 bind address 分离。示例声明 `server("https://api.example.com")`，它是客户端读取的 OpenAPI server 元数据，使用保留示例域名；真实 socket 却绑定 `127.0.0.1:0`。把二者混为一谈会导致应用为了测试去绑定 example.com，或把本机地址永久写进公开文档。示例把两个用途分别放在 document 和 adapter 构造点。

第五项选择是测试断言分层。document 测试检查 title、version、servers、paths 和重复渲染一致；HTTP 测试检查 200、application/json、openapi 版本、info、两条 path 和 User 组件；404 测试证明 `/docs` 不存在；双请求测试比较完整 body，证明跨 socket 的响应稳定。它们不需要解析 JSON 后丢掉字段顺序，也不应假设一个未实现的 UI 路径存在。

最后是检查点的选择。175 项不是“框架所有测试”，而是本章相关测试类的显式选择；九组 ClassMajorContractTest 也不是全部字节码文件的数量，而是各产物 actual classes 与 test-classes 的 major 扫描结果。每个数字都必须能回到 surefire XML 或具体输出。把检查点写成“所有测试通过”会掩盖未选择的测试，也会让环境噪声被误当成框架回归。

## 动手

`OpenApiExample.document()` 位于 [OpenApiExample.java:41](../../examples/src/main/java/com/barezen/examples/openapi/OpenApiExample.java#L41)。它声明 User 的 id/name，GET `/users/{id}` 使用 integer path 参数和 bearer requirement，返回 200 User 或 404；POST `/users` 声明 required JSON body，返回 201。两条 operation 都有响应、summary 和 tags，`ApiDocument` 再接收 server、schema、security scheme 和 operations。

router 只有以下结构：

```java
return Router.builder()
    .route(HttpMethod.GET, "/openapi.json", document().handler())
    .build();
```

这段代码来自 [OpenApiExample.java:72](../../examples/src/main/java/com/barezen/examples/openapi/OpenApiExample.java#L72)。`document()` 被调用后立即 build，任何无效声明都会在 server 启动前失败。handler 在装配时渲染一次，后续请求复用同一份字节；测试的两次真实 GET 因而比较的是跨连接的相同内容，而不是两次动态生成碰巧相同。

main 的核心位于 [OpenApiExample.java:78](../../examples/src/main/java/com/barezen/examples/openapi/OpenApiExample.java#L78)。它先打印 document JSON 长度，再启动 adapter、读取 OS 端口、发送 GET、打印状态与 Content-Type/body 长度，finally 调 `server.stop()`。这里不是 TestServer，因为示例要展示应用如何直接使用生产 adapter；TestKit 是测试工具，不应被误写成应用运行必需依赖。

七个示例的类名是 `HelloWorld`、`RoutingExample`、`RequestResponseExample`、`SecurityExample`、`DatabaseExample`、`StaticFileExample`、`PluginExample`，加上本章的 `OpenApiExample`。每个 main 都使用真实资源：数据库示例使用独立 H2 内存库，静态内容示例在系统临时目录创建两个文件并为每个文件注册 GET/HEAD 路由，同时注册 jar 内的 classpath 资源，其他示例使用真实 loopback socket。读者可以逐个运行，不必启动额外服务器。

先在仓库根执行本章统一测试选择：

```bash
mvn -o -B -ntp \
  -pl framework/barezen-plugins,framework/barezen-testkit,examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=OpenApiPluginTest,OpenApiModelTest,JsonWriterTest,OpenApiDocumentTest,ReadmeDocumentExampleTest,AssertionsTest,FixturesTest,JsonReaderTest,TestDatabaseTest,TestServerIntegrationTest,ReadmeTestKitExampleTest,BarezenTestKitArchitectureTest,OpenApiExampleTest,ClassMajorContractTest'
```

实际结果是 `BUILD SUCCESS`，总耗时约 1 分 12 秒。175 项分布为：上游 core/web/http-jdk/security/content/data 各 4 项 ClassMajor，共 24；plugins 66；testkit 77；examples 8。plugins 的 66 是 OpenApiPlugin 11、OpenApiModel 24、OpenApiDocument 19、JsonWriter 7、ReadmeDocumentExample 1、ClassMajor 4。examples 的 8 是 OpenApiExample 4 与 ClassMajor 4。全部 0 failure、0 error、0 skipped。

构建后再运行 main。classpath 使用本仓库 classes 和本地 Maven 仓库中已存在的依赖，不下载新内容：

```bash
M2="$HOME/.m2/repository"
CP="$PWD/examples/target/classes:$PWD/framework/barezen-core/target/classes:$PWD/framework/barezen-web/target/classes:$PWD/framework/barezen-http-jdk/target/classes:$PWD/framework/barezen-security/target/classes:$PWD/framework/barezen-content/target/classes:$PWD/framework/barezen-data/target/classes:$PWD/framework/barezen-plugins/target/classes:$M2/org/slf4j/slf4j-api/2.0.16/slf4j-api-2.0.16.jar:$M2/com/h2database/h2/2.2.224/h2-2.2.224.jar"
java -cp "$CP" com.barezen.examples.openapi.OpenApiExample
```

本次实际输出为：

```text
document -> 1201 bytes of JSON
SLF4J(W): No SLF4J providers were found.
SLF4J(W): Defaulting to no-operation (NOP) logger implementation
SLF4J(W): See https://www.slf4j.org/codes.html#noProviders for further details.
GET /openapi.json -> 200 application/json 1201 bytes
```

这里 `.length()` 统计 String 字符数，本次 JSON 内容是 ASCII，因此与 UTF-8 字节数一致；不要把这个巧合推广成“任何 document 的字符数都等于字节数”。SLF4J 警告来自临时运行 classpath 没有日志绑定，core 的 no-op logger 仍允许请求成功，不是 HTTP 失败。

九组字节码检查全部为 major 61：core 151 个、web 92、http-jdk 84、security 42、content 12、data 49、plugins 82、testkit 48、examples 23。ClassMajorContractTest 每个产物检查其实际 classes 与 test-classes；数字会随真实代码新增而变化，本章记录的是本次提交树的结果。

同一个 reactor 还出现大量 JaCoCo 插桩警告，例如 `Error while instrumenting javax/sql/DataSource`，涉及 CommonDataSource、ResultSet、Connection 等 JDK SQL 类型。原因是覆盖率代理尝试处理 JDK 内部类型，不是断言失败。Maven 仍为 BUILD SUCCESS，选定测试全部通过。文档不修改测试、不关闭 adapter 覆盖，也不把警告从日志里隐藏；若未来要让日志完全安静，应单独调查覆盖率代理配置，而不是把它混入本章功能修改。

## 常见的第一次写错

1. **错误：示例把 router 写在 main，测试另写一份。** 正确：二者共享 package-private factory。
2. **错误：把 TestServer 当作生产依赖。** 正确：main 使用 JdkHttpServerAdapter，test 才使用 TestKit。
3. **错误：用 `assert` 当作 main 的验证。** 正确：main 打印观察结果，JUnit 提供 enforcement。
4. **错误：为了 run gate 新增 exec 插件。** 正确：离线构建后用真实 `java -cp` 运行。
5. **错误：让框架模块依赖 examples。** 正确：examples 是 reactor 最后的应用叶子。
6. **错误：禁止 examples 命名 H2。** 正确：应用选择驱动；框架生产代码继续 driver-free。
7. **错误：把 OpenAPI server 字段当 bind address。** 正确：文档元数据与真实 socket 地址分开。
8. **错误：请求 `/users` 来证明业务。** 正确：该示例只有 `/openapi.json`，`/users` 仅是声明。
9. **错误：把 175 项说成整个项目测试总数。** 正确：它只是本章显式选择的测试集合。
10. **错误：把 JaCoCo 警告说成测试失败，或完全忽略。** 正确：记录原因与实际 BUILD SUCCESS，不修改源码掩盖。
11. **错误：把字符数直接叫 UTF-8 字节数。** 正确：只有当前 ASCII 输出恰好相等。
12. **错误：只跑 main 不跑 reactor 测试。** 正确：build/test/run 是三层不同证据。

## 怎么确认这一步没造错

先看 `OpenApiExampleTest` 四项断言。`documentIsWellFormedAndItsJsonIsTheDocument` 检查文档字段，并比较两个独立 document 的 JSON；`theHandlerServesTheJsonOnItsOwnRoute` 使用 TestServer 检查版本、标题、两条 path 和 schema；`unknownDocumentPathIsNotFound` 请求 `/docs` 得到 404；`handlerServesTheSameBytesTwice` 比较两次真实响应的完整字符串。四项分别证明模型、路由、未知路径和网络稳定性。

再检查 main 输出是否与源码对应。`/openapi.json` 的 200 来自 Router；`application/json` 来自 document handler 的 Response；1201 来自当前 document 的 JSON 长度；没有 `/users` 请求，因为 router 没有注册它。若输出中出现 `/users` 业务结果，说明示例已经改变，本章描述必须重新核对。

还要验证消费者边界：examples 主代码不得依赖 testkit 或 JUnit，测试代码才引入二者；package-private `JsonWriter`、`OpenApiJson` 不能被 examples 导入。Java 编译器会拒绝跨包访问，这正是 ADR-0045 所说的结构事实。框架内部的 helper 即使恰好 public，也不应被示例当成稳定 API 使用。

最后用 surefire XML 复核各类数量，而不是只相信汇总。对每个 `TEST-*.xml` 读取 `<testsuite>` 的 tests/failures/errors/skipped，再与 Maven 汇总相加。若某个类没有被选择，不能拿旧报告冒充本次运行；本章命令包含 `-Dsurefire.failIfNoSpecifiedTests=false` 是为了让上游模块在只有 ClassMajor 被选择时继续构建，不是把失败测试跳过。

## 此刻的代码长什么样

第 12 章的链路已经闭合：应用声明 operation metadata 与 schema，Operation/document 在 build 时拒绝矛盾，ApiDocument 产生稳定 JSON，Router 把 handler 暴露为普通 HTTP 路由，TestServer 用真实 adapter 验证字节，main 则从消费者一侧再次运行同一装配。所有验证都只使用公开 API，模块依赖方向没有被示例或测试工具倒置。

它也明确留下了未自动证明的部分：文档与真实业务是否一致，完整 OpenAPI 3.0.3 是否符合外部 oracle，YAML/UI 是否可提供，多适配器测试是否可行。示例不是这些能力的替代品；它证明当前轻量子集可以被 stranger consumer 从公开 API 拼起来并运行。12 章教程至此结束，下一份工作应是回看整条提交时间线，检查每章承诺与实际源码、ADR 和检查点是否仍一致。
