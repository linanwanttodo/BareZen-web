# 第 12 章第 1 步：从元数据到声明式投影

## 这一步要解决什么

第 11 章结束时，`OpenApiPlugin` 已经能记录一条 operation：HTTP method、path pattern、summary 和 tags。它拒绝重复的 `(method, path)`，返回按 path、method 排好序的不可变快照，也提供 `clear()` 给自身或测试重置。但它不知道路径参数应该是什么类型，不知道请求体是否存在，更不知道 200 与 404 的响应分别是什么样子。

这不是 collector 的实现遗漏，而是上一阶段主动留下的边界。若在 collector 中直接塞入完整 OpenAPI 对象，它就要同时承担 API 声明、schema 建模、跨字段校验和序列化四种责任；每加一种文档字段，都可能改变插件状态与生命周期。当前设计让 collector 只保存路线身份和人类可读标签，再由独立模型做**单向投影**：模型读取 metadata，补充应用声明，但绝不把补充结果写回 collector。

本步的主体是提交 `e49587f7bb0a347ad0e215131a9c9aa1c40cbcfe`。它新增九个生产 Java 类型：`ApiDocument`、`Operation`、`Parameter`、`RequestBody`、`ApiResponse`、`Schema`、`Security`、`OpenApiJson`、`JsonWriter`。加上原有 `OperationMetadata` 与 `OpenApiPlugin`，文档生成路径才完整。随后的 `fae6b463b85701c4263c23212194525550d91a7f` 记录 ADR-0043，并补上 README 可执行示例、无体响应与更深层引用校验。

一个必须提前接受的事实是：这些类型仍然位于 `framework/barezen-plugins`，没有新建 `barezen-openapi` 模块。[ADR-0043 的 Placement 决定](../../docs/adr/0043-openapi-generator-is-a-declared-data-projection.md)指出，任何位于 `com.barezen.plugins..` 之外的框架类，只要引用这些类型，就会破坏插件依赖方向。为了一个包拆分而违反已经执行的架构规则，是把发布方便置于结构诚实之上。因此这里的“新阶段”是同一模块内的新代码面，不是新的 Maven 产物。

## 先想清楚再写

先确定事实来源。`HttpMethod` 与 path 来自应用声明的路线；summary、tags 来自 collector；参数位置、schema、请求体、响应描述、security requirement 来自应用补充；`operationId` 由 method 与 path 派生；`openapi: 3.0.3` 是生成器固定的格式版本。把这些来源混成一个“扫描 Router 后自动生成一切”的想象，会立即遇到现实阻力：Router 不枚举路线，handler 的 Java 字节码也不表达某段 JSON 实际返回什么。

第二项选择是 schema 如何产生。反射 DTO 看似减少重复：扫描字段、推断类型、自动生成 schema。但反射同时带来四个需要不断证明的问题：字段顺序是否稳定、循环类型如何终止、类路径扫描边界在哪里、私有字段与注解优先级听谁的。当前实现不建立一套复杂的反射策略，而是把 schema 当值写出来。应用已经知道自己的 API，就应该明确声明它。

声明式 schema 的代价也必须说清：`User` Java 类型与 `Schema.object(...)` 是两份需要对齐的描述。若后端新增字段却忘记更新文档，框架不会从运行结果中自动发现。这项代价换来的是可预测的排序、结构性循环安全和零扫描。它延续了路由模块早就做出的选择：路线模式与应用处理器本来就是两份相邻声明，而不是从处理器签名反推出来的东西。

第三项选择是 `$ref` 的表达。一个 `User` 可以有 `friends: List<User>`，如果 `Schema.ref("User")` 在生成时立即展开目标，就会无限递归。当前引用节点只保存组件名，渲染时输出 `#/components/schemas/User` 并停止。目标组件作为独立根节点只输出一次，是否声明则在 `ApiDocument.build()` 的统一检查中解决。循环安全因此来自数据结构，而不是来自一个可能漏掉某条边的 visited set。

第四项选择是 operation 与 document 的分工。`Operation.Builder.build()` 能看到一个 operation 的全部参数与路径模板，适合检查“模板有 id，却漏了 path id”“query id 与 path id 重名”“同一 `(location, name)` 参数声明两次”“一个响应都没有”。`ApiDocument` 构造器能看到全部 operation、组件与 security scheme，适合检查跨 operation 的重复 identity、operationId 碰撞、悬空引用和未声明 scheme。校验放在能看见相关事实的最小层，不把所有错误推迟到 JSON 写出后。

最后决定投影方向。`Operation.builder(OperationMetadata)` 接收 metadata，`ApiDocument.Builder.operations(...)` 接收已经建好的 operation。整条链没有 setter 能修改 collector。应用若需要更多响应，只能修改 Operation；修改文档不会偷偷增加一条路由，也不会让 `OpenApiPlugin.size()` 变化。这个方向看起来限制了自动化，却让“文档描述什么”和“应用实际注册什么”成为两个可以分别测试的声明。

## 动手

collector 的入口在 [OpenApiPlugin.java:51](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/openapi/OpenApiPlugin.java#L51)。它把传入值构造成 `OperationMetadata`，以 `method + "\u0000" + path` 为键放入私有 `LinkedHashMap`。`operations()` 另建列表，按 path、再按 method text 排序，最后 `List.copyOf` 冻结快照。NUL 分隔符避免 method 与 path 的文本拼接产生歧义，排序则让不同装配枚举顺序得到相同的 collector 输出。

不可变快照不等于线程安全。collector 内部使用普通 `LinkedHashMap`，没有同步，适合在路由冻结前由单线程装配；`clear()` 也是公开操作，调用方可在装配后主动清空它。当前测试覆盖快照隔离与 clear，但没有并发 add/read/clear 测试，也没有把它设计为运行期动态注册表。collector 与 Router 之间没有自动一致性校验：重复 `(method,path)` 只在 collector 内拒绝，漏写、多写或路径漂移仍须由应用测试检查。

投影时，应用对每条 metadata 建一个 `Operation`。核心代码位于 [Operation.java:149](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/openapi/Operation.java#L149)：

```java
public Operation build() {
  if (responses.isEmpty()) {
    throw new IllegalArgumentException("operation documents no response");
  }
  List<String> patternNames = pathParameterNames(metadata.path());
  Set<String> declared = new HashSet<>();
  for (Parameter parameter : parameters) {
    String key = parameter.location().name() + "\u0000" + parameter.name();
    if (!declared.add(key)) {
      throw new IllegalArgumentException("duplicate parameter " + parameter.location() + ":" + parameter.name());
    }
    if (parameter.location() == Parameter.Location.PATH && !patternNames.contains(parameter.name())) {
      throw new IllegalArgumentException("path parameter is absent from the pattern");
    }
  }
  for (String name : patternNames) {
    if (parameters.stream().noneMatch(p ->
        p.location() == Parameter.Location.PATH && p.name().equals(name))) {
      throw new IllegalArgumentException("pattern path parameter is undocumented");
    }
  }
  return new Operation(this);
}
```

这段检查是双向的：多写的 path 参数拒绝，少写的 path 参数也拒绝；同名 query/header 参数不能占据模板已经保留的名字。同一 `(location, name)` 出现两次同样拒绝，但 query `q` 与 header `q` 是不同参数，仍然合法。模板本身也遵循 Router 语法：花括号必须占满整段，名称首字符为字母、后续为字母/数字/下划线，同一模板不能重复名称，路径不能携带 `?`。path schema 只允许 string 或 integer，因为 Router 捕获的是原始字符串片段，文档可以告诉客户端“按整数解析”，但不能谎称框架已经完成了解析。

`Parameter` 的构造点也固定了 OpenAPI 的路径规则。[Parameter.java:44](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/openapi/Parameter.java#L44) 拒绝 `Location.PATH && !required`。路径参数不可能是可选项：没有该片段就会匹配另一条路线，这不是同一路线的一个空字段。query 与 header 则可以通过工厂方法或完整 record 构造器声明 required/description。

schema 的最小写法可能如下：

```java
Schema user = Schema.object(List.of(
    new Schema.Property("id", Schema.integer(), true),
    new Schema.Property("name", Schema.string(), true),
    new Schema.Property("friends", Schema.array(Schema.ref("User")), false)));
```

它来自 [ReadmeDocumentExampleTest.java:29](../../framework/barezen-plugins/src/test/java/com/barezen/plugins/openapi/ReadmeDocumentExampleTest.java#L29) 的结构，真实循环示例可见 [OpenApiDocumentTest.java:39](../../framework/barezen-plugins/src/test/java/com/barezen/plugins/openapi/OpenApiDocumentTest.java#L39)。`integer()` 固定为 `int64`；`booleanSchema()` 不能写成 Java 关键字 `boolean`；`asNullable()` 返回新 schema，而不是修改原对象。object 的属性顺序就是传入 `List` 的顺序，required 列表由 property flags 派生，因此没有两份可能互相矛盾的 required 声明。组件 schema 名称必须匹配 `[A-Za-z0-9._-]+`，与 `$ref` 使用的组件键语法一致。

响应与请求体同样在构造时拒绝明显谎言。[ApiResponse.java:22](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/openapi/ApiResponse.java#L22) 要求 description 非空，状态文本只能是三位码、`NXX` 或 `default`；204/304 有 body schema 时直接失败。[RequestBody.java:21](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/openapi/RequestBody.java#L21) 固定媒体类型为 `application/json`，把“整个 body 是否必需”与“对象内哪些字段必需”分开表达。

security 只有一层可复用声明和一层 operation 使用声明：`Security.Scheme.bearer(name)` 描述组件，`Security.Requirement.of(name, scopes)` 描述某个 operation 需要它。两者在 `ApiDocument` 中配对校验，名称也必须符合 OpenAPI 组件键正则 `[A-Za-z0-9._-]+`。当前 subset 只有 HTTP bearer，因此 scopes 必须为空；OpenAPI 3.0.3 只允许 OAuth2 或 OpenID Connect requirement 声明 scope 名称。当前没有 OAuth2 或 apiKey scheme，因为框架没有实现对应认证流程；文档不能替应用承诺不存在的登录协议。

## 常见的第一次写错

1. **错误：让 OpenApiPlugin 直接返回完整文档。** 正确：collector 保持 metadata 状态机，文档由应用显式投影。
2. **错误：新建独立 openapi 模块，让 core/web 引用它。** 正确：生成器留在 plugins 包内，保持框架向上的依赖禁令。
3. **错误：用反射自动扫描 DTO。** 正确：当前版本明确采用声明式 schema；反射需要重新打开 ADR 并提供四项验收条件。
4. **错误：把 path 参数声明为 query，只因名字相同。** 正确：位置必须双向匹配模板，path 参数还必须 required。
5. **错误：响应省略 description。** 正确：OpenAPI Response Object 需要它，模型在构造时拒绝 null/blank。
6. **错误：给 204 或 304 添加 JSON schema。** 正确：HTTP 契约规定无体，文档必须与分帧规则一致。
7. **错误：引用组件时立即递归展开。** 正确：REFERENCE 只保存名字，目标组件作为独立根输出。
8. **错误：把投影结果写回 collector。** 正确：投影是单向的，测试必须证明 `collector.size()` 不因补全文档而增加。
9. **错误：把 document build 当成 Router build。** 正确：二者验证不同事实；文档甚至可以在没有注册真实路线时构造成功，因此还需要行为测试。
10. **错误：只按参数名去重。** 正确：参数身份是 `(location, name)`；query `q` 与 header `q` 可以共存，同位置同名必须拒绝。
11. **错误：OpenAPI 只要找到花括号就提取名称。** 正确：模板必须服从 Router 的整段参数、标识符、重复名与无 query 规则，否则文档会描述一条无法注册的路线。
12. **错误：给 HTTP bearer requirement 添加 OAuth scopes。** 正确：当前 subset 没有 OAuth2/openIdConnect，scopes 数组必须为空，否则不是合法 OpenAPI 3.0.3。

## 怎么确认这一步没造错

先运行模型与投影测试：

```bash
mvn -o -B -ntp -pl framework/barezen-plugins -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=OpenApiPluginTest,OpenApiModelTest,OpenApiDocumentTest,ReadmeDocumentExampleTest
```

本章统一检查点中，这四类共 62 项：`OpenApiPluginTest` 11、`OpenApiModelTest` 30、`OpenApiDocumentTest` 20、`ReadmeDocumentExampleTest` 1。它们全部通过，0 failure、0 error、0 skipped。plugins 模块所选测试总数 73，另外 7 项是 `JsonWriterTest`，第 2 步会单独运行；各模块的 `ClassMajorContractTest` 4 项不在这次 `-Dtest` 选择中。

不要只数绿色数量，要检查每类测试咬住什么。`OpenApiModelTest` 验证 record 构造、operation 参数/响应规则、schema 形状与 security 值；`OpenApiDocumentTest.Refusals` 用六个命名测试覆盖六类拒绝，并额外固定组件名称语法；`Determinism` 改变装配顺序并比较完整字符串；`CycleSafety` 让自引用组件实际完成生成；`Serving.projectionFromCollector` 则证明投影后 collector 仍只有原来的一条 operation。

还应主动观察失败位置。无 response 在 `Operation.build()` 失败；无 title 在 `ApiDocument.build()` 失败；未声明 `$ref` 要等 document 才能判断，因为只有 document 拥有完整组件表。把错误一律塞到 emitter 会让“模型已经成立”与“JSON 临时拼凑”难以区分，也无法在服务启动前拒绝错误声明。

历史提交也值得对照。`e49587f` 建立主体模型与测试；`fae6b46` 补了 README 执行示例和边界覆盖。阅读时用 `git show fae6b46 -- framework/barezen-plugins/src/test` 看新增断言，能直观看到“文档生成成功”如何被收紧成“文档声明与 HTTP 无体规则一致”。

## 此刻的代码长什么样

此时框架拥有一个从 metadata 到 checked document 的单向数据链，但还没有证明 JSON 字节稳定，也还没有把 document 通过真实网络交给客户端。`ApiDocument` 中的 paths、components、security schemes 已有确定顺序，operation 的 responses 与 parameters 则保留声明顺序；`toJson()` 只负责按这个顺序渲染。

下一步要解决的是“确定性究竟由谁保证”。模型排错一次，emitter 仍可能用无序 map 或额外排序破坏结果；emitter 写对顺序，模型也可能把相同声明保留成不同顺序。只有把两边的责任分开并分别测试，才能把“看起来通常稳定”变成“相同声明产生相同字节”的可执行承诺。
