# 02 条件请求与 304 的长度规则

## 这一步要解决什么

上一步每次请求都会重新读取文件并返回完整 200。浏览器第二次请求时，其实已经保存了字节和 ETag，却只能再下载一次。本步实现条件 GET：服务端仍读取当前字节并计算验证器，如果客户端在 `If-None-Match` 中提供的标签覆盖当前表示，就回答 304，不再发送正文。

这不是简单的“省流量”优化。它同时规定验证器由什么产生、客户端哪些写法有效、304 要保留哪些字段，以及长度到底归谁。BareZen 的 ETag 来自内容 SHA-256 的前 8 字节，不是文件修改时间；匹配支持弱比较、通配符和逗号列表；304 返回 ETag、null body，不带 Content-Length。实现集中在同一个 FileHandler 的一次调用里，没有新公开 API。

历史上，ADR-0029 在没有真实条件请求消费者时已经选择“304 无长度”，并留下触发器：等一个真正处理条件 GET 的组件出现，再重新测量。`24a0240` 的 StaticContent 正是这个消费者，它甚至已经知道当前文件全部字节。结果不是“现在可以写长度了，所以改变决定”，而是通过真实套接字复测后保留原规则。这正是本章最值得学习的推理方式：新证据可能确认旧决定，也可能推翻它，但不能只看技术可行性。

## 先想清楚再写

先确定 ETag 的语义。强 ETag 表示表示字节逐字节相同；弱 ETag 只表示语义上等价。条件 GET 使用弱比较，因此服务端生成强标签 `"ec185bc08f4786af"` 后，客户端发送 `W/"ec185bc08f4786af"` 仍应匹配。If-None-Match 还允许逗号分隔多个候选标签，任意一个匹配即可；`*` 表示客户端想确认任意当前表示是否存在。实现不应要求字段只有一个值，也不能因为客户端加了弱前缀就返回完整 200。

标签取内容而非时钟，是为了消除文件系统与部署差异。mtime 会受复制、解压、时间戳粒度和时区影响；同一内容从一个文件复制到另一个文件可能时间不同，而不同内容在同一秒修改可能时间相同。SHA-256 只依赖即将返回的字节，重启、换机器都不会改变标签。这里截取 8 字节是为了缩短比较值，不是加密强度声明；ETag 是内容身份，不是 MAC、签名或授权凭证。

为什么不支持 `If-Modified-Since`？它会引入第二个验证器与另一套日期比较规则，而内容哈希已经回答了当前问题。没有 Last-Modified，也就不必模拟服务器时钟或解析客户端时区。这个取舍不是“日期条件请求永远错误”，而是本框架选择一种可测试、跨文件系统稳定的验证机制。

304 的长度最容易被“我们算出来了”诱导。RFC 9110 允许 304 带 Content-Length，但若带，值必须等于同一请求假设 200 的正文字节数。StaticContent 确实读到了字节，似乎能满足；然而 Response 契约禁止所有 Handler 写 Content-Length 与 Transfer-Encoding，adapter 才是分帧所有者。为 304 开口会新增“未发送正文的表示长度”通道，而单个 Response 无法验证这个断言是否与假设 200 相同。错误长度会污染缓存，正确长度对已经持有该表示的客户端也没有新增收益。

还要区分 304 与 HEAD。304 是状态本身禁止正文与长度；HEAD 是方法，它需要 GET 表示的 Content-Length，同时 adapter 不发送正文。两者都不是“Handler 返回空数组”就能表达。StaticContent 为 HEAD 注册的仍是同一个 Handler，返回完整 200 body；adapter 根据原始请求 token 决定写长度、抑制正文。

最后，304 必须继续携带 ETag。它是本次验证成功的标签，客户端缓存可以据此保持表示与验证器关联。若只返回状态码，缓存也许不会立即失效，但协议语义不完整，测试会明确要求标签原样返回。

## 动手

标签生成的核心只有哈希与十六进制编码：

```java
MessageDigest digest = MessageDigest.getInstance("SHA-256");
byte[] hash = digest.digest(content);
StringBuilder tag = new StringBuilder(18).append('"');
for (int index = 0; index < 8; index++) {
  tag.append(String.format("%02x", hash[index]));
}
return tag.append('"').toString();
```

实际实现位于 [StaticContent.java:202](../../framework/barezen-content/src/main/java/com/barezen/content/StaticContent.java#L202)，并捕获 NoSuchAlgorithmException 后抛 IllegalStateException，因为项目支持的 JDK 必须提供 SHA-256。`String.format` 使用默认 Locale 来格式化数字在输出内容上不依赖地区；扩展名比较则显式使用 Locale.ROOT，避免土耳其语等 locale 影响大小写转换。

条件匹配把弱前缀和引号剥离后比较：

```java
for (String candidate : ifNoneMatch.split(",")) {
  String trimmed = candidate.trim();
  if (trimmed.equals("*") || unquote(trimmed).equals(unquote(etag))) {
    return true;
  }
}
```

对应 [StaticContent.java:226](../../framework/barezen-content/src/main/java/com/barezen/content/StaticContent.java#L226)。unquote 同时接受 `W/` 与 `w/`，再移除首尾成对引号。null 或全空白字段按普通 GET 处理。它不是完整通用 HTTP 缓存实现，只实现本模块声明的 If-None-Match 条件 GET；不要把这段代码描述成支持 If-Match 或实体更新并发控制。

FileHandler 在读取与计算标签后分支：

```java
if (matches(request.headers().first("If-None-Match").orElse(null), etag)) {
  return new Response(304, Headers.of("ETag", etag), null);
}
return new Response(200,
    Headers.of("Content-Type", contentType).with("ETag", etag), content);
```

这是 [StaticContent.java:185](../../framework/barezen-content/src/main/java/com/barezen/content/StaticContent.java#L185) 的实际核心。Response 构造器在 [Response.java:99](../../framework/barezen-web/src/main/java/com/barezen/web/Response.java#L99) 检查无正文状态并复制字节；304 分支不传 Content-Type，因为没有正文表示要描述，只保留验证器。200 分支的类型是 Handler 的选择，长度则完全由 adapter 从 body 派生。

线上长度由 [JdkExchangeBridge.java:205](../../framework/barezen-http-jdk/src/main/java/com/barezen/http/jdk/JdkExchangeBridge.java#L205) 的 send 决定。普通非空 200 声明 body.length；304 的 statusCarriesABody 为 false，因此 declared 为 -1，JDK 不写 Content-Length；HEAD 且状态允许正文时，adapter 用 body.length 写入 Content-Length，再以 -1 声明不发送正文。Handler 不参与这三个分支的判断。

## 常见的第一次写错

- **错误：** ETag 用路径、mtime 或当前时间拼接。**正确：** 只对本次表示字节做哈希，同内容同标签。
- **错误：** 只有字符串完全相等才匹配。**正确：** 条件 GET 用弱比较，接受 W/ 前缀与列表。
- **错误：** If-None-Match 为空视为匹配一切。**正确：** 空字段按普通 GET，只有显式 `*` 通配。
- **错误：** 304 只返回状态，丢掉 ETag。**正确：** 标签必须随 304 返回。
- **错误：** 因为知道文件大小，在 304 写 Content-Length。**正确：** 保持 D1，分帧仍由 adapter 拥有。
- **错误：** 用 304 的空 body 模拟 HEAD。**正确：** HEAD 走正常状态与完整表示，由 adapter 抑制正文并声明表示长度。
- **错误：** 在客户端或测试库层读取长度。**正确：** 用原始套接字确认字段是否存在，避免客户端规范化 framing。

## 怎么确认这一步没造错

运行条件匹配与套接字测试：

```bash
mvn -o -B -ntp -pl framework/barezen-content -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=StaticContentTest$Revalidation,StaticContentTest$Wire'
```

本次实跑 7 项，0 失败、0 错误。Revalidation 5 项覆盖匹配标签、弱客户端标签、候选列表、通配符、缺失或空白标签；Wire 2 项在 `127.0.0.1:0` 启动真实 JDK adapter，并用 RawHttp 直接读字段行与正文。前者说明 Handler 的条件判断，后者说明最终 wire framing，两者不能互相代替。

[StaticContentTest.java:265](../../framework/barezen-content/src/test/java/com/barezen/content/StaticContentTest.java#L265) 对 14 字节 CSS 依次发出 GET、带相同 ETag 的 GET 与 HEAD，断言三行：200 有 `Content-Length: 14` 和正文；304 无正文、ETag 相同且该字段数量为零；HEAD 有 `Content-Length: 14`、正文为空。测试刻意不用 HttpClient 读取这一结论，因为高层客户端可能把“无字段”归一化为默认值，掩盖真正要验证的线上事实。

反向验证可以临时把 matches 改为永远 false：5 个 Revalidation 测试会失败；让 304 丢掉 ETag，则 Handler 与 Wire 测试都会失败；把 304 加上 Content-Length 会先被 Response 契约拒绝，即使绕过契约，Wire 测试仍要求该字段不存在。ADR-0051 记录了原阶段做过的类似 mutation：常量 ETag、忽略条件、404 回显路径、未知类型当文本、304 丢标签都各有 killer。

本次 JDK 24 运行日志出现了 JaCoCo 尝试插桩 `com.sun.net.httpserver.HttpHandler` 时的 IllegalClassFormatException 堆栈；对应 Wire 测试仍全部通过，构建成功。它是当前覆盖率工具与 JDK 内部类的噪声，不能据此声称测试失败，也不能把静态内容行为错误地归因于它。Maven 自身的 sun.misc.Unsafe 弃用警告同样不是失败。

## 此刻的代码长什么样

StaticContent 现在能从当前字节生成稳定标签，理解客户端常见的 If-None-Match 写法，并在真实套接字上保持 200、304、HEAD 三种分帧。实现没有引入缓存、日期条件或 Range；每次条件请求仍先读取文件，因此它验证的是当前磁盘内容，而不是内存副本。

下一步把镜头转向消费者。`c2ca0f8` 删除文档站服务器后，StaticFileExample 必须承担套接字证明；在写这个真实程序时，GET-only 路由对 HEAD 返回 405 的问题会暴露出来。那个问题不是 304 算法错误，而是“谁负责注册方法”的边界终于有了实际使用者。
