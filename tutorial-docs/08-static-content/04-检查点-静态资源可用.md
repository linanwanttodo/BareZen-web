# 04 检查点：静态资源可用

## 这一步要解决什么

前三个步骤分别建立了文件 Handler、条件请求和真实消费者，但“每个小测试都绿”还不等于一条链成立。检查点要把它们放在同一次构建中：生产模块只依赖契约，Handler 行为正确，线上 framing 正确，字节码仍是 major 61，示例只通过公开 API 工作，静态文档树的链接也确实存在。

这里的验收不是重新实现一个静态服务器，而是逐项确认本章的决定没有在模块拼接时失真。content 的 POM 是否真的只有 web 作为生产依赖？adapter 是否只以 test scope 进入？private FileHandler 是否真的不可继承？200 的长度是否来自正文，304 是否没有长度，HEAD 是否声明表示长度但不发送？examples 是否注册了 HEAD，Pages 文件是否使用相对地址？

本次使用 JDK 24.0.2、Maven 3.9.12 验证，但项目仍以 `maven.compiler.release=17` 生成 major 61。运行环境提供虚拟线程能力，与静态文件行为无关；不能因此把项目表述为 JDK 24 项目。字节码契约测试会读取本模块真实 class 文件，而不是只相信 POM 中的声明。

## 先想清楚再写

检查命令必须避免两种假绿。第一，只运行 `mvn test -pl framework/barezen-content` 可能使用仓库中已经安装的旧 web 或 adapter，无法证明当前源码的组合；因此加 `-am`，让 Maven 从根 reactor 构建所选模块需要的上游。第二，`-Dtest=...` 指定 examples 才有的测试类时，上游模块可能一个都匹配不到，Surefire 默认会报“No tests matching pattern”；因此加 `-Dsurefire.failIfNoSpecifiedTests=false`。它只允许上游没有匹配类，不会把目标模块的真实失败变成成功。

测试选择也要覆盖不同证据层。StaticContentTest 直接驱动 Handler，证明字节、类型、ETag 与条件匹配；它的 Wire 嵌套类启动真实 JDK adapter，证明最终字段与正文；BarezenContentArchitectureTest 验证模块边界；ClassMajorContractTest 验证产物；StaticFileExampleTest 验证应用侧枚举与 GET/HEAD 注册。少任何一层，都会有一块承诺只剩口头说明。

本次组合命令会让上游七个模块各自运行 ClassMajorContractTest，因此日志中的测试总数大于 content 与 examples 的业务测试数。统计时应按模块理解：core、web、http-jdk、security、data、plugins、testkit 各 4 项，共 28；content 为 4 项字节码、36 项 StaticContentTest、6 项架构规则，共 46；examples 为 4 项字节码与 7 项 StaticFileExampleTest，共 11。总计 85，而不是把每个类重复相加。

日志噪声同样要会读。Maven 与 ArchUnit 使用的 Guava 在当前 JDK 上会触发 sun.misc.Unsafe 弃用警告；JaCoCo 尝试插桩 JDK 的 HttpHandler 时可能打印 IllegalClassFormatException 堆栈。它们不是断言失败，判断依据是 Surefire 的 Failures/Errors 与 Maven 最终退出码。不能因为警告难看就修改框架源码，也不能只截取 BUILD SUCCESS 而忽略测试数为零。

文档检查与 Java 测试是两条独立路径。[scripts/check-site.sh](../../scripts/check-site.sh) 不启动 BareZen，它检查 href/src、可达性、双语配对、语言属性与唯一样式表。Java 示例证明条件请求，脚本证明 Pages 文件部署约束；任何一边都不能替代另一边。

## 动手

从仓库根目录运行完整聚焦验收：

```bash
mvn -o -B -ntp -pl framework/barezen-content,examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=StaticContentTest,BarezenContentArchitectureTest,ClassMajorContractTest,StaticFileExampleTest
```

本次实跑结果如下，数字与日志中的模块汇总一致：

| 范围 | 测试数 | 失败 | 错误 | 跳过 |
| --- | ---: | ---: | ---: | ---: |
| 上游七个模块的字节码契约 | 28 | 0 | 0 | 0 |
| barezen-content | 46 | 0 | 0 | 0 |
| barezen-examples | 11 | 0 | 0 | 0 |
| 合计 | 85 | 0 | 0 | 0 |

最终 Maven 输出 `BUILD SUCCESS`。content 的字节码检查输出 `checked=12 unique-majors=[61] expected=61`，examples 同样为 major 61。StaticContentTest 的 36 项包括 Serving 5、Revalidation 6、Ranges 11、Types 2、Refusals 4、Wire 3、ClasspathResources 5；ArchUnit 6 条规则全部执行，不是 allowEmptyShould 造成的空跑，因为 content 确有生产类。示例的 7 项包含一条公开 API 的 206/416 范围测试。

随后直接运行消费者，确认它不是只有测试夹具能访问：

```bash
M2="$HOME/.m2/repository"
CP="$PWD/examples/target/classes"
for m in core web http-jdk content security data plugins; do
  CP="$CP:$PWD/framework/barezen-$m/target/classes"
done
CP="$CP:$M2/org/slf4j/slf4j-api/2.0.16/slf4j-api-2.0.16.jar:$M2/com/h2database/h2/2.2.224/h2-2.2.224.jar"
java -cp "$CP" com.barezen.examples.staticcontent.StaticFileExample
```

本次实际输出包含六条路由和五个关键观察：`GET /notes.txt -> 200, 44 bytes`，标签 `"ec185bc08f4786af"`；相同标签的 GET 为 304、0 字节、Content-Length absent；HEAD 为 200、声明 44、收到 0 字节；`Range: bytes=0-3` 为 206、4 字节、`Content-Range: bytes 0-3/44`；未注册路径为 404、正文 `Not Found`。六条路由来自两个临时文件与一个 classpath 资源，各有 GET/HEAD；临时目录后缀变化属于预期，44 字节、标签与范围由示例固定内容决定，可重复核对。

最后运行：

```bash
./scripts/check-site.sh
```

本次当前树输出 `checked 34 pages, 1 stylesheet(s)`，随后输出 `OK: the static site is self-consistent (34 pages in two languages, every link relative)`。这个数字是现在的实测值；ADR-0054 的 12 页与 124 个链接目标属于当时快照，不能直接复制为当前结果。

验收后可以用 Git 确认没有把示例产物误当成文档改动：

```bash
git status --short
git diff --stat -- tutorial-docs/08-static-content
```

第一条应只看到预期的教程文档与用户原有 WIP；第二条检查本章 Markdown 的规模。不要用 `git add .` 把 target 或用户其他文件带入提交。

## 常见的第一次写错

- **错误：** 只运行 Handler 单测就宣称套接字语义成立。**正确：** 同时运行 Wire 与 StaticFileExampleTest，直接读取线上字段。
- **错误：** 用 `-pl` 去掉 `-am`，结果加载旧依赖。**正确：** 从根 reactor 构建上游当前源码。
- **错误：** 上游没有匹配测试就删掉 failIfNoSpecifiedTests 配置。**正确：** 只忽略上游“无指定测试”，保留目标模块失败。
- **错误：** 把 Surefire 的 skipped 当失败，或把警告当失败。**正确：** 分别检查断言结果、退出码与日志原因。
- **错误：** 只相信 release=17 声明。**正确：** 读取 class major，并核对非空检查集合。
- **错误：** 用 HttpClient 的默认长度推断 304 无字段。**正确：** 使用 RawHttp 检查字段数量。
- **错误：** 把 ADR 的历史测试总数写成今天。**正确：** 当前命令、当前输出、当前数字分别记录。
- **错误：** 因为示例能跑，就声称 Pages 也有 ETag。**正确：** 分开验证 Java 服务与静态文件树。

## 怎么确认这一步没造错

结果必须满足四个独立条件：命令退出码为 0；目标模块测试数非零且失败/错误为 0；Wire 明确断言 304 的 Content-Length 字段数量为零；站点脚本退出码为 0。只满足其中一个都不能说明本章闭环。

还可以在不改源码的情况下做反向审查。想象把 `matches` 改成永远 false，Revalidation 的 5 项会红；把 304 的 ETag 去掉，Handler 与 Wire 会红；把示例 HEAD 注册删除，`aFileRegisteredOnlyForGetRefusesHead` 与正常 HEAD 测试会红；把某个页面样式表改为绝对路径，站点脚本会报告越出树。每个承诺都有能失败的观察点，才不是靠测试名称自我安慰。

若只验证“绿灯”而没验证断言会红，可以另开临时工作副本做 mutation，再恢复文件；本章不要求为了制造红色而修改用户工作树。关键是先读懂对应测试的断言，确认它检查的是行为本身，而不是恒真条件或空集合。

API 一致性也应逐项核对：[StaticContent.java:71](../../framework/barezen-content/src/main/java/com/barezen/content/StaticContent.java#L71) 的公开方法包括 `file(Path)`、`file(Path, String)`、`resource(ClassLoader, String)`、`resource(ClassLoader, String, String)` 与 `contentTypeOf(String)`；Range 是请求字段，不增加 factory 或 stream 方法。同文件私有的 FileHandler 与 ResourceHandler 都实现 `Response handle(Request, Map<String, String>)`；示例 router 为每个平铺文件注册 GET 与 HEAD；[JdkExchangeBridge.java:205](../../framework/barezen-http-jdk/src/main/java/com/barezen/http/jdk/JdkExchangeBridge.java#L205) 的 `send` 接收 exchange、writesBody 与 Response。文档没有发明 directory、cachePolicy 或 stream 方法，也没有把 Configuration 注入文件读取器。

## 此刻的代码长什么样

到检查点为止，静态内容能力已经完成一个可验证的最小闭环：应用显式选择文件，content 通过 web 契约返回当前字节、内容验证器或一个字节范围，adapter 负责正文与长度，examples 用真实端口复现，Pages 用纯文件与脚本验证自己的约束。它不是通用静态服务器，但每个已支持行为都有清楚的来源和测试；第 5 步继续拆解单范围边界的实现理由。

第 9 章将在这个普通 Handler 之上增加安全装饰器。密码与会话是新的能力模块，StaticContent 不会变成安全例外：应用仍通过路由和装饰器决定谁能取得文件，而不是在磁盘读取器里藏一套身份规则。
