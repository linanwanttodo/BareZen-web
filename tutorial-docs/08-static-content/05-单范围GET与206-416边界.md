# 05 单范围 GET 与 206/416 边界

## 这一步要解决什么

前四步已经能返回完整表示、验证器、HEAD 和 404，但客户端有时只需要文件的一段。若为此引入流式响应，就要同时重新回答返回后谁写 socket、谁关闭资源、HEAD 与 304 如何计算长度；这些正是 ADR-0030 暂缓流式 body 的原因。单范围 GET 可以在现有 `byte[]` 模型内完成：先读取完整表示，再复制请求的一段。

本步不增加公开 factory。磁盘文件与 classpath 资源继续通过 `StaticContent.file(...)` 或 `resource(...)` 注册；范围只是 GET 请求中的 `Range` 字段。GET 的一个 `bytes` 范围得到 206，不可满足的合法范围得到 416，HEAD 与条件 304 保持原语义。多部分范围、压缩、缓存策略与流式大文件仍不在能力清单里。

[ADR-0051 的 2026-11-27 修订](../../docs/adr/0051-static-content-is-one-handler-per-file.md#amendment-2026-11-27-one-byte-range-on-get)记录了这次扩展：它复用已有 ETag、MIME、全量缓冲和 adapter 分帧，只增加一个请求范围内的表示选择。

## 先想清楚再写

第一项选择是只实现一个范围。`bytes=2-5`、`bytes=7-` 与 `bytes=-3` 覆盖闭区间、开放结尾与后缀三种常见形式。逗号分隔的多范围会要求 multipart 边界、每部分 header 与总长度规则，也更容易出现缓存和拼接错误；当前遇到多范围时返回完整 200，而不是伪造一个 206 或实现一半 multipart。

第二项选择是把“非法”与“不可满足”分开。未知单位、非数字、溢出、末段小于首段以及重复 Range 字段行都是无法可靠解释的请求，回退完整 200。语法合法但首段越过表示末尾、后缀长度为 0，或空表示上的合法范围，回答 416，并用 `Content-Range: bytes */size` 告诉调用者完整表示的大小。若把两者都当 416，客户端无法区分“请求写错”和“资源里没有这段”。

第三项选择是 Range 只对 GET 生效。HEAD 仍返回完整 200 表示，adapter 声明完整长度并抑制正文；它不把 `Range: bytes=0-3` 改成 4 字节的 HEAD。若 HEAD 采用范围长度，同一个 URL 的表示长度就会随请求字段变化，破坏 HEAD 的探测用途。

第四项选择是 `If-Range` 使用强比较。客户端只有在 `If-Range` 恰好等于当前强 ETag 时才请求范围；陈旧标签、`W/` 弱标签、HTTP 日期或重复字段行都回退完整 200。这样客户端在表示已变化时不会误把新文件的一段当作旧文件的一段。框架不解析日期，也不为 Range 引入第二个时钟验证器。

第五项选择是条件请求优先。`If-None-Match` 匹配时仍返回 304，即使同一个请求也带 Range。重复的 `If-None-Match` 字段行与每行内的逗号列表合并成一个候选集合；不能只检查第一行，否则第二个匹配标签会被错误忽略。

## 动手

响应分支集中在 [StaticContent.java:248](../../framework/barezen-content/src/main/java/com/barezen/content/StaticContent.java#L248)。概念上只有以下形状：

```java
if (range.first() < 0) {
  return new Response(416,
      representation.with("Content-Range", "bytes */" + content.length), new byte[0]);
}
Headers rangeHeaders = representation.with("Content-Range",
    "bytes " + range.first() + "-" + range.last() + "/" + content.length);
return new Response(206, rangeHeaders,
    Arrays.copyOfRange(content, (int) range.first(), (int) range.last() + 1));
```

`representation` 已含 Content-Type、ETag 与 `Accept-Ranges: bytes`。Handler 仍不写 Content-Length；206 的长度由 adapter 从选中的 byte[] 派生，416 的空正文长度为 0。构造 206 时只添加一个 Content-Range，不能先添加 `bytes */size` 再用 `with` 追加实际范围，因为 `Headers.with` 表达重复字段而不是替换。

范围解析位于 [StaticContent.java:281](../../framework/barezen-content/src/main/java/com/barezen/content/StaticContent.java#L281)。位置只接受 ASCII 十进制数字，先解析为 `long`，再与内存表示的 `int` 大小比较并夹紧。开放结尾直接使用 `size - 1`；后缀长度大于整个表示时取完整表示。复制前已验证 `0 <= first <= last < size`，因此不会把客户端数字变成非法数组下标。

| 请求字段 | 结果 | 关键响应 |
| --- | --- | --- |
| `Range: bytes=2-5` | 206 | `Content-Range: bytes 2-5/10`，正文 `2345` |
| `Range: bytes=7-` | 206 | `Content-Range: bytes 7-9/10` |
| `Range: bytes=-3` | 206 | `Content-Range: bytes 7-9/10` |
| `Range: bytes=8-99` | 206 | 末段夹紧为 9 |
| `Range: bytes=10-` | 416 | `Content-Range: bytes */10`，空正文 |
| `Range: bytes=-0` | 416 | 后缀 0 不含字节 |
| 空文件上的 `bytes=0-` | 416 | `Content-Range: bytes */0` |
| `Range: bytes=3-1` | 200 | 逆序是非法语法，不是不可满足 |
| `Range: bytes=0-1,3-4` | 200 | 多范围暂回退完整表示 |
| HEAD 加任意 Range | 200 | 完整表示长度，线上无正文 |
| 匹配的 If-None-Match 加 Range | 304 | ETag，空正文，无 Content-Range |

若客户端使用范围恢复下载，应先取得完整 ETag，再发送单值强 `If-Range`。服务端返回 200 时，客户端应重新按完整表示处理，不能假设自己收到的是请求范围。

## 常见的第一次写错

1. **错误：为 Range 新增 stream factory。** 正确：先复制已有 byte[] 的一段，流式触发条件仍归 ADR-0030。
2. **错误：任何解析失败都返回 416。** 正确：非法请求回退 200，合法但无字节才返回 416。
3. **错误：末段超过文件大小就拒绝。** 正确：夹紧到 `size - 1`。
4. **错误：后缀长度大于文件大小时产生负数起点。** 正确：取完整表示。
5. **错误：空文件的开放区间被当成无 Range。** 正确：合法范围在空表示上不可满足，返回 416。
6. **错误：If-Range 接受弱标签或日期。** 正确：只接受当前强 ETag 的精确匹配。
7. **错误：只读首个 Range 或 If-Range 字段行。** 正确：重复行无法可靠合并时回退完整 200。
8. **错误：Range 优先于 If-None-Match。** 正确：验证器命中仍返回 304。
9. **错误：用 `Headers.with` 替换同名字段。** 正确：它追加重复值；206 与 416 分别只构造一个 Content-Range。
10. **错误：把单范围说成完整 RFC Range 实现。** 正确：明确保留 multipart、压缩、缓存与流式非目标。

## 怎么确认这一步没造错

先运行本步的范围与线上测试：

```bash
mvn -o -B -ntp -pl framework/barezen-content -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=StaticContentTest$Ranges,StaticContentTest$Wire'
```

当前实跑 14 项，全部通过：Ranges 11 项覆盖三种范围、夹紧、416、非法与多范围回退、If-Range、HEAD、空文件、classpath、304 优先级和重复字段行；Wire 3 项覆盖原始 200/304/HEAD，以及 206、416 的真实 Content-Length、Content-Range 与正文。

测试不是先写实现再补绿色。初始 7 项范围测试中，旧实现有 6 项因返回 200 而失败，真实套接字范围测试也失败；重复字段测试随后分别暴露 If-None-Match 只读首行、Range 首行优先和 If-Range 首行优先；最后的边界测试证明空文件 `bytes=0-` 错回 200、逆序越界范围错回 416。每个修正都对应一个可观察的失败，而不是仅增加成功样例。

再运行消费者测试，确认示例不是另一个装配：

```bash
mvn -o -B -ntp -pl examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=StaticFileExampleTest
```

当前 7 项全部通过。其中 `aSingleByteRangeAndAnUnsatisfiableRangeUseThePublicApi` 通过 TestServer 请求 `/notes.txt`，断言 `bytes=0-3` 得到 206、正文 `stat` 与 `Content-Range: bytes 0-3/44`，`bytes=44-` 得到 416 与 `bytes */44`。main 也打印前一个请求的状态、正文长度和 Content-Range。

最后运行第 4 步的完整聚焦命令。当前结果是上游字节码契约 28 项、content 45 项、examples 11 项，总计 84 项，0 failure、0 error、0 skipped。content 的 45 项由 StaticContentTest 35、ArchUnit 6 与 ClassMajor 4 组成；不能把 84 说成整个 reactor 的测试总数。

## 此刻的代码长什么样

StaticContent 现在能在同一个普通 Handler 内回答完整表示、条件 304、单范围 206 与不可满足 416，磁盘文件和 classpath 资源共享规则。它没有新增公开类型、依赖或分帧入口；客户端输入在复制数组之前被解析、夹紧和验证，所有结果仍由真实 adapter 写到套接字。

这一步也留下清楚边界：不支持多部分范围、If-Match、日期验证器、压缩、Cache-Control 或大文件流式传输。需要其中任何一项时，应先找到真实消费者，再按 ADR-0051 的重开条件决定是否改变范围模型、响应体契约或缓存所有权。
