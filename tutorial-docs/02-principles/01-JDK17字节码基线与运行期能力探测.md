# JDK 17 字节码基线与运行期能力探测

## 这一步要解决什么

空仓库首先要承诺产物兼容到哪个 JDK，否则后续所有 API 选择都建立在流沙上。本章只建立编译基线，不急着使用虚拟线程；同时为运行期能力留一个明确入口，让“同一个 jar 在不同 JDK 上选择不同实现”成为受控设计。

## 先想清楚再写

最直觉的做法是读取 `java -version`，然后告诉使用者“本项目需要 JDK 21”。这会让构建主机决定架构：JDK 17 用户无法加载 major 65 的类，而 JDK 21 用户又被迫接受一个本来为旧平台设计的所有限制。更糟的是 IDE、本地 Maven 与 CI 可能使用不同 JDK，同一个提交会生成不兼容的产物，却没有任何 POM 显示异常。

`--release 17` 的价值在于同时检查三件事：语言特性不能超过 17，引用的 API 必须存在于 JDK 17，生成字节码必须是 major 61。它比只设置 source/target 更严格，因为后者可能在新 JDK 上意外链接到旧平台没有的 API。父 POM 应成为唯一声明者，子模块不覆盖，这样不会出现某个“小模块”单独抬高基线。

但编译基线不应阻止运行期使用新能力。虚拟线程在 JDK 21 可用，在 JDK 17 不存在；正确问题不是“现在用什么 JDK 编译”，而是“此刻运行的 JVM 暴露了什么”。因此需要 `RuntimeCapabilities` 快照。先探测，再选择 ThreadProvider，业务代码只依赖工厂和能力结果，不直接判断版本字符串。

还不要把 capability 做成无所不包的环境对象。只有虚拟线程有真实消费者，快照就只保留 Java feature、virtualThreads 与 vendor。提前加入 TLS、ALPN、压缩算法等字段会诱使模块按环境扩散分支，却没有对应测试和职责。能力模型也应和实现选择放在一起，避免第二处代码用不同标准判断“是否支持”。

## 动手

在父 POM 中声明一次，不把版本复制到每个子模块：

```xml
<maven.compiler.release>17</maven.compiler.release>
```

编译器插件读取该属性：

```xml
<configuration>
  <release>${maven.compiler.release}</release>
</configuration>
```

`barezen-core` 的 POM 故意没有自己的 release 配置。运行期入口保持为一个不可变快照：

```java
RuntimeCapabilities detected = RuntimeCapabilities.detect();
System.out.println(detected);
```

真实 `detect()` 读取 `Runtime.version().feature()`、`VirtualThreadProbe.supported()` 和 `java.vm.vendor`。构造器拒绝非正 feature 与空 vendor；这不是无关紧要的防御，而是防止调用方伪造出无法解释的能力状态。真正创建虚拟线程执行器的动作仍留在 `RuntimeCapabilities`，探测与实例化共用同一个 seam。

这一阶段先写测试，不写 adapter。测试用可控能力对象覆盖 AUTO 的回退与显式 VIRTUAL 的拒绝，再用真实运行环境测试可用路径。这样“支持虚拟线程”不是一句注释，而是工厂行为的一部分。

### 提交切片：`2670984` 先同时立下编译与运行承诺

真实历史没有“先提交一个空父 POM，再单独提交能力探测”这样整齐的步骤。`2670984 feat: 实现应用生命周期内核` 一次变化 48 个文件、3829 行，同时包含根 POM、BOM、core、`RuntimeCapabilities`、`VirtualThreadProbe`、ThreadProvider、生命周期内核、初始架构测试和 `scripts/check-jdk-baseline.sh`。本教程为了解释设计把它拆成几个小步，但对照 git 时应知道它们属于同一个初始骨架提交。

可以这样读这次提交，而不是只看最终文件：

```bash
git show --stat 2670984
git show 2670984:pom.xml
git show 2670984:framework/barezen-core/src/main/java/com/barezen/core/runtime/RuntimeCapabilities.java
```

当前最终入口位于 [RuntimeCapabilities.java](../../framework/barezen-core/src/main/java/com/barezen/core/runtime/RuntimeCapabilities.java)。record 的 compact constructor 拒绝非正 `javaFeature` 和空白 `vendor`，`detect()` 只读取当前 JVM 的三个事实；`newVirtualThreadPerTaskExecutor()` 又先检查快照标志，再委托唯一 probe。把探测与实例化放在一起，避免出现“报告不支持，但另一个工具类仍能创建”的口径分裂。

选择发生在 [ThreadProviders.java](../../framework/barezen-core/src/main/java/com/barezen/core/concurrent/ThreadProviders.java)，核心判断是：

```java
boolean virtualRequested = policy == ThreadPolicy.VIRTUAL
    || (policy == ThreadPolicy.AUTO && runtime.virtualThreads());
```

因此 AUTO 是“能升级则升级”，PLATFORM 是明确不升级，VIRTUAL 是明确要求且不得偷偷降级。这里不是简单地 `javaFeature >= 21`：版本达到 21 后，probe 还可能因方法不可访问或 LinkageError 失败。能力标志必须来自实际探测结果，而不是仅来自版本号。

另一个提交坐标是 `4c9feda build: 将字节码版本校验纳入构建与 CI`。它没有改变 release 17 的设计，而是补上“声明正确但产物错误”的防线。这个时间差本身值得记住：写 POM 是承诺，写 class-major 测试与脚本是证明。后来增加模块时，不必重新发明兼容策略，只要继承父 POM 并加入同样的产物契约。

## 常见的第一次写错

- **错误：在子模块把 release 改成 21。** 正确：父 POM 统一拥有 17，子模块只继承。
- **错误：只设 source/target。** 正确：使用 release，让编译器同时检查 JDK 17 API。
- **错误：到处比较 `Runtime.version().feature()`。** 正确：集中到 RuntimeCapabilities，由 ThreadProviders 选择实现。
- **错误：提前加入所有可能能力。** 正确：只为已有消费者增加字段，并配对应 ADR 与测试。
- **错误：把开发 JDK 版本当成兼容承诺。** 正确：分别记录构建环境、编译 release 与运行期能力。

## 怎么确认这一步没造错

先检查声明是否被子模块覆盖：

```bash
scripts/check-jdk-baseline.sh
```

预期包含 `OK: JDK 17 baseline intact`，退出码为零。脚本会先去除 POM 注释再检查 `<release>`，因为注释中解释规则不算覆盖；它也会拒绝 barezen-jdk* 与 barezen-runtime 目录。

再运行能力工厂与产物测试：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=ThreadProvidersTest,ClassMajorContractTest
```

预期 `BUILD SUCCESS`，并看到 core 的 `class-major: checked=... unique-majors=[61] expected=61`。具体 checked 数量随真实产物变化，不应硬编码成永远正确的数字。

## 此刻的代码长什么样

现在父 POM 已经承诺 release 17，core 拥有一个无 HTTP、无 SQL 的能力入口，测试能验证不同运行期选择。还没有任何监听端口的代码，但这不代表骨架为空：编译产物已经有一致兼容目标，版本相关决策也已经有了唯一所有者。

下一步要处理这个入口的代价。`--release 17` 无法编译 `Executors.newVirtualThreadPerTaskExecutor()`，所以必须有一种不直接引用新符号的桥接方式。我们会比较 preview、内部模块与 MethodHandle，并说明为什么最终只接受一个受限探测点，而不是让每个模块自行“兼容一下”。
