# 检查点：空仓库与门禁就位

## 这一步要解决什么

到这里已经分别写下 release 17、运行期能力探测、模块方向和 ArchUnit 规则，但“分别看起来正确”还不是交付证据。这个检查点要按真实构建顺序验证三件不同的事：POM 声明没有漂移、当前类图没有越界、实际写出的每一个 class 文件都是 major 61。

## 先想清楚再写

最危险的验收方式是把 `BUILD SUCCESS` 当成全部答案。Maven 成功只说明它在当前命令、当前 JDK、当前 POM 下完成了构建。若命令行带有 `-Dmaven.compiler.release=21`，父 POM 的 17 仍在，声明脚本也仍会通过，但输出可以是 major 65。JDK 17 用户看到的是一个无法加载的 jar，而不是配置错误。这正是 ADR-0032 把“声明”与“产物”拆开的原因。

只检查产物同样不够。有人提高父 POM 的 release，子模块却可能暂时没有重新编译，旧 target 里仍是 major 61；一次针对旧产物的检查会制造虚假的安全感。反过来，POM 正确也不能保证某次命令没有覆盖它。因此正确顺序是先检查声明，再 clean 构建并执行测试，最后对这次构建留下的完整 target 做产物检查。CI 的 [backend-ci.yml](../../.github/workflows/backend-ci.yml) 就是这样排列的。

检查范围也不能只列今天已知的三个模块。`4c9feda` 新增 `check-class-major.sh` 时只有 core、web、http-jdk 三个模块的 `ClassMajorContractTest`；后续模块继续增加，脚本则从仓库根扫描全树 class。这样新模块不会因为忘记加入白名单而漏检，误放到其他 target 子目录或仓库里的 class 文件也不会被静默忽略。允许集合应明确且可验证，而不是一份需要手工同步的模块名单。

“零文件通过”是另一个隐蔽失败。若 build 配置错误、源码目录未被发现或检查脚本找错根目录，循环可能一次都不执行；此时如果只判断“所有已检查文件都合法”，空集合当然全绿。当前脚本在没有任何 class 时直接失败，并逐一要求有 main/test 源码的模块在对应输出目录发射非空 class 集合。它检查的是 measured count，不是想象中应该存在的模块。

脚本还必须识别文件本身。class 文件开头四字节应为 `CA FE BA BE`，major 位于偏移 6，按大端读取。若把一个改名为 `.class` 的 ZIP 或截断文件当作正常输出，后续偏移读取可能得到毫无意义的值。先验证 magic，再读取 major，失败信息才能区分“不是 class 文件”和“是 class 文件但版本错误”。

还要注意构建主机与 PATH 工具不一定是同一个 JDK。本次 `java -version` 和 `mvn -version` 都报告 Oracle JDK 24.0.2、Maven 3.9.12；但 `scripts/check-jdk-baseline.sh` 末尾调用 shell 找到的 `javac`，实际打印的是 25.0.5.1。这不是需要抹平的矛盾，反而说明为什么不能用某一条 `java -version` 代替产物验证：Maven 运行 JDK、PATH 上的 javac、POM 的 release 是三个可以分别变化的事实。

## 动手

先用只读方式对照两个提交，理解当前基线的两层证据来自哪里：

```bash
git show --stat 2670984
git show --stat 4c9feda
git show 4c9feda:scripts/check-class-major.sh
```

`2670984` 一次带来父 POM、BOM、core、能力探测、初始生命周期和声明脚本；`4c9feda` 才补上独立产物脚本、三个模块的 class-major 测试与 CI 步骤。教程按最终仓库回放，不会假装这些保护在第一天就以现代形态全部存在。

第一步检查声明。脚本从自身位置回到仓库根，要求父 POM 含 `<maven.compiler.release>17</maven.compiler.release>`，去除 XML 注释后拒绝子 POM 出现 `<maven.compiler.release>` 或 `<release>`，并拒绝 `barezen-jdk*`、`barezen-runtime` 目录：

```bash
scripts/check-jdk-baseline.sh
```

第二步执行目标模块的契约、能力与架构测试。这里使用 `-pl framework/barezen-core -am`，保证父 POM 与 core 一起进入 reactor；测试选择器中的三个类都真实存在于 core：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=ThreadProvidersTest,BarezenCoreArchitectureTest,ClassMajorContractTest
```

`ClassMajorContractTest` 位于 [framework/barezen-core/src/test/java/com/barezen/core/contract/ClassMajorContractTest.java](../../framework/barezen-core/src/test/java/com/barezen/core/contract/ClassMajorContractTest.java)。它从 surefire 实际加载测试类的 code source 找到本模块输出，不依赖一个可能写错的相对路径；同时检查 `target/classes` 和 `target/test-classes` 非空。它的第四项测试还构造 major 65 的八字节头和伪 class 头，确认读取器不会把错误版本或外来文件都答成 61。这是对检查器本身的反向控制，比只检查真实构建输出更能证明它确实会区分版本。

完整交付前应使用 clean，而不是在旧 target 上继续 test：

```bash
scripts/check-jdk-baseline.sh
mvn -o -B -ntp clean verify
scripts/check-class-major.sh
```

本教程写作时没有改动 framework、examples 或 app 源码，也没有执行全仓 clean，以免触碰用户正在进行的测试修改和既有构建状态；上面是读者在干净工作副本中应采用的完整顺序。本次文档检查点实际运行的是定向 core 测试和当前全树产物脚本，下面分别记录结果。

第三步读取真实产物。脚本的核心不是调用 `javap`，而是直接看字节：

```bash
expected_major=61

major_of() {
  od -An -tu1 -j6 -N2 -- "$1" | awk '{ printf "%d", $1 * 256 + $2 }'
}

magic_of() {
  od -An -tx1 -N4 -- "$1" | tr -d ' \t\n'
}
```

按字节组合避免 `od -tu2` 受机器字节序影响。脚本先收集并排序全树 `*.class`，再逐个校验路径、magic 和 major；最后把每个有源码模块的 classes/test-classes 数量打印出来。因此输出中的文件数可以随代码增加，不能写死成永久期望值。

## 常见的第一次写错

- **错误：只运行 `mvn test` 就宣布 JDK 17 兼容。** 正确：同时检查声明、目标模块 class-major 测试和 clean 后的全树产物。
- **错误：在父 POM 提高 release，同时把脚本期望值改成 65。** 正确：恢复基线；独立字面量测试就是防止 expected 跟着错误产物一起漂移。
- **错误：只扫描 `framework/*/target/classes`。** 正确：扫描全树并拒绝约定目录之外的 class，覆盖 test-classes、examples、app 和未来模块。
- **错误：没有 class 时返回成功。** 正确：零文件和应有源码却零输出都必须失败。
- **错误：把 shell 的 javac 版本当成 Maven 编译器版本。** 正确：检查实际输出；本次 PATH javac 与 Maven 运行 JDK 就不同。

## 怎么确认这一步没造错

本次实际执行声明检查，退出码为零，输出为：

```text
OK: JDK 17 baseline intact (javac 25.0.5.1)
```

随后执行定向 core 测试，目标模块结果为：

```text
Tests run: 38, Failures: 0, Errors: 0, Skipped: 0
BareZen Parent ..................................... SUCCESS
BareZen Core ....................................... SUCCESS
BUILD SUCCESS
```

其中 `BarezenCoreArchitectureTest` 单独报告 21 项通过。架构测试输出包含 ArchUnit 的已知警告日志，但最终 failures/errors 为零；不要把警告行误判为测试失败，也不要把结尾成功当作整份日志都没有异常噪声。

最后执行：

```bash
scripts/check-class-major.sh
```

本次仓库现有产物为 646 个 class，结果如下：

```text
checked=646 unique-majors=[61] expected=61
OK: every emitted class file is major 61 across 646 files
```

646 是 2026-11-24 这次检查的实测数量，不是教程硬性常量。新增源码后它应自然变化；验收重点是 unique-majors 始终只有 61、每个有源码的模块两类输出都非空、脚本退出零。若需要复现本章核心测试而不构建其他消费者，仍使用前面的定向 Maven 命令；若需要证明完整 reactor 的产物，则必须在 clean verify 之后运行脚本。

## 此刻的代码长什么样

最小骨架现在拥有可重复的边界：父 POM 声明 release 17，ArchUnit 守住依赖与调用形状，ClassMajorContractTest 守住每个模块的输出，全树脚本守住最终 reactor 产物。运行期能力探测允许同一个 jar 在 JDK 21+ 选择虚拟线程，同时不改变字节码基线。

它仍然没有监听端口，也不会把“检查点通过”误解为框架已经能处理 HTTP。下一章进入生命周期：对象如何从 NEW 走到 STARTED，为什么 initialize 必须整体先于 start，启动失败怎样逆序释放，停止失败怎样被汇总而不是吞掉。有了本章这些门禁，后面每增加一个参与者或适配器，都能继续用同一套证据方式确认架构没有漂移。
