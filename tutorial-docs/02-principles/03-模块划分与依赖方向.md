# 模块划分与依赖方向

## 这一步要解决什么

基线确定以后，需要决定哪些代码分别放在哪个 Maven 模块。模块不是文件夹美化，而是依赖、发布和所有权边界：一个模块拥有什么，就应能拒绝不属于自己的依赖。本章建立 core、web 与未来 adapter 的方向，并说明为什么空占位模块不如暂时不存在。

## 先想清楚再写

如果按技术层机械切分，很容易得到 controller、service、dao 一类目录，却说不清每个 jar 对消费者的承诺。BareZen 的模块按问题域与依赖方向划分：core 提供生命周期、线程、配置等通用能力；web 定义 HTTP 契约与路由；具体服务器是 adapter；安全、数据、静态内容和插件各自拥有可组合能力。examples 与 app 是消费者，不反向进入框架。

把 HTTP 放进 core 看起来能减少模块数量，实际会让每个使用生命周期或配置的消费者继承 HTTP 概念，也让 core 无法在非 Web 程序中独立测试。把 adapter 接口放进某个具体服务器模块则相反：web 会绑定 JDK，未来第二个服务器无法复用同一契约。正确方向是契约不依赖实现，实现依赖契约，应用依赖实现。

依赖还必须单向。若 security 依赖 web，web 就不能反过来拿 SecurityMiddleware；若 testkit 为了“方便”把插件类型加入编译依赖，两个顶层模块会横向耦合，每个消费者的测试 classpath 都会背上不相关能力。例子是叶子：它能组合所有模块，但没有任何框架模块可以依赖它。这样重构框架时不会意外改变示例行为。

不要提前创建没有源码的 aggregator。ADR-0008 删除 barezen-runtime，因为 HTTP runtime 端口已经在 web，JDK 实现在 http-jdk，那个目录没有东西可聚合。占位 POM 会让 reactor 看似完整，却没有编译错误、测试或依赖图约束；新模块也应在拥有真实代码和职责时出现。设计文档可以预测未来，构建输入不能靠预测运行。

core 的依赖数量同样需要说明。唯一第三方编译依赖是 SLF4J API，应用选择日志实现；Logback 只在 test scope。数据层只使用 JDK 的 `javax.sql`，DataSource 由应用提供；具体 JDBC 驱动由应用选择。这里的“驱动无关”不是忽略数据库差异，而是不替消费者选择数据库。

## 动手

先画依赖图，再写 POM。当前根 reactor 的真实顺序包括 parent、bom、九个框架模块、examples 和 app。核对命令是：

```bash
mvn -o -B -ntp -DskipTests validate
```

core 的依赖声明刻意保持简单：

```xml
<dependencies>
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
  </dependency>
</dependencies>
```

其余 JUnit、AssertJ、ArchUnit 与 Logback 都声明为 test scope。web 则没有这些编译依赖。新增模块时，先回答三个问题：它拥有哪个公开类型？允许依赖哪些下层模块？是否有任何上层会依赖它？回答不清，就不急着创建目录。

依赖版本由 BOM 和父 POM 的 dependencyManagement 统一管理，不在子模块随意写死版本。这样升级 SLF4J 或测试工具时只有一个来源，也能让 enforcer 的版本收敛与禁止依赖规则真正生效。模块边界既在源码 import 上，也在 artifact 依赖上。

### 提交切片：现代 reactor 是逐步长出来的

阅读当前 [根 POM](../../pom.xml) 时，很容易误以为九个框架模块从 `2670984` 起就全部存在。真实提交只列出 parent、BOM、core 两个模块。后续提交按真实需求扩展 reactor，而不是一次性创建九个占位目录：

| 提交 | 新增的结构 | 对依赖图的含义 |
| --- | --- | --- |
| `2670984` | parent、barezen-bom、barezen-core | 先建立生命周期、线程、配置等通用内核 |
| `32ebc41` | barezen-web | HTTP 契约成为独立模块，不放进 core |
| `6ef05b9` | web 内的服务器适配器契约 | 具体实现有可依赖的端口 |
| `a2e05fa` | barezen-http-jdk | 第一个服务器实现进入独立 artifact |
| `50cd3cc` | barezen-http-servlet | 第二个实现证明契约没有绑定 JDK server |
| `68e0c67` | barezen-plugins | 首批插件能力拥有自己的模块 |
| `743ae96` | barezen-testkit | 集成测试工具成为只向下依赖的叶子 |

这些提交都同时修改根 POM 的 module 列表和 BOM；不是先在文件系统建目录、等以后补构建定义。`bfef5d5` 则为 http-jdk 新增 546 行架构测试，证明“新模块进入 reactor”与“新模块受到边界约束”通常应在同一轮交付中考虑。

当前 core 的 POM 仍保留这种克制。唯一 compile 第三方依赖是 SLF4J API，版本由父 POM 管理为 2.0.16；JUnit、AssertJ、ArchUnit、Logback 全是 test scope。web 主产物没有编译依赖，data 只使用 `javax.sql`，security 的编译依赖是 web。这里要区分“模块在依赖图哪一层”和“应用最终 classpath 有什么”：后者当然需要日志实现、JDBC 驱动或 Servlet 容器，但它们不应被框架核心替所有消费者决定。

examples 与 app 的叶子位置也不是偶然。它们可以组合 core、web、adapter、security、data 和插件；反向依赖一旦出现，就意味着框架发布必须等待示例，或示例的一个接口变化会迫使框架修改。测试时可以用 `dependency:tree` 检查 artifact 关系，用各模块 ArchitectureTest 检查源码关系，两者覆盖不同的绕行方式。

## 常见的第一次写错

- **错误：core 依赖 web 以复用 Request。** 正确：HTTP 概念只属于 web，core 保持通用。
- **错误：web 依赖具体 JDK adapter。** 正确：契约定义端口，adapter 实现端口。
- **错误：testkit 与 plugins 互相依赖。** 正确：TestKit 是只向下依赖的叶子，不命名插件层。
- **错误：为了未来功能建立空模块。** 正确：有真实源码、产物或子模块时才进入 reactor。
- **错误：让 examples 成为框架依赖。** 正确：示例组合框架，框架永远不组合示例。

## 怎么确认这一步没造错

先运行架构规则，再用 Maven 查看真实依赖：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=BarezenCoreArchitectureTest
mvn -o -B -ntp -pl framework/barezen-testkit dependency:tree -Dscope=compile
```

预期第一条 `BUILD SUCCESS`；第二条应显示 TestKit 对 core、web、http-jdk、security、data 的向下依赖，不出现 plugins。`core_depends_only_on_jdk_and_slf4j` 与 `core_has_no_web_or_persistence_concepts` 是核心边界，其他模块也各有自己的架构测试。

再确认空模块守卫：

```bash
scripts/check-jdk-baseline.sh
```

它拒绝 barezen-jdk* 和 barezen-runtime 目录。模块数量不是验收目标；每个列出的模块都应对应实际产物和职责。

## 此刻的代码长什么样

现在依赖图已经能解释每个模块存在的原因，父 POM 与 BOM 集中管理版本，core 保持最小依赖，消费者叶子位于框架之外。还没有 HTTP 行为，但未来代码可以插入已有方向，而不是在模块之间来回搬类型。

仅有图还不够。下一章步骤会把这些边界变成 ArchUnit 规则：不仅检查“不能依赖某包”，还检查“只有 runtime 能使用方法调用式探测”“DI 不能扫描反射”“某方法不能变成按 Class 查找对象的服务定位器”。架构门禁必须足够具体，才能挡住真实维护中最常见的绕过形状。
