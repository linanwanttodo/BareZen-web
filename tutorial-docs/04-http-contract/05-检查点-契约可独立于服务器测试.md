# 05 检查点：契约可独立于服务器测试

## 这一步要解决什么

前四步已经写出契约，但“没有服务器依赖”不能只靠 POM 注释或源码目测。它必须同时体现在编译依赖、运行时测试和架构规则上：主源码无法引用 HttpExchange，测试不启动端口也能验证 Handler，公开表面不会悄悄多出 setter 或上下文入口。

本章运行两层检查。第一层只选 Request、Response、Headers、HttpMethod、Handler 和架构测试，验证本章边界；第二层运行 barezen-web 全部测试，确认当前同模块 Router 与后续能力没有破坏契约。两层结果分开报告，不把路由测试数量冒充成本章新增能力。

## 先想清楚再写

单元测试直接构造契约对象，不启动 socket。RequestTest 可以精确控制原始 path、空 query、二进制 body 和可被复用的输入缓冲；ResponseTest 可以构造 204、304、重复 framing 等难以在真实服务器上稳定复现的形状。没有网络等待，断言能落在唯一差异上。

表面测试用反射检查声明方法，而不是只检查当前用法。Request 多一个 setter、Response 多一个 send、Handler 多一个 handle 重载，都可能被现有示例忽略，却会把新的可变性或分派歧义带给所有消费者。过滤 synthetic 方法是为了避免 JaCoCo 在 verify 时注入的实现细节被误认为源码 API。

Header 和 Response 测试按规则覆盖一组输入，而不是只测一个示例。无体状态覆盖整个 1xx 家族和 204/304；framing 覆盖大小写、空值、重复同值和重复异值。这样才能防止“只修 204”或“只拒绝大写 Content-Length”的局部补丁通过。

架构测试补上单元测试看不到的跨文件依赖。允许 java.lang/java.util 的白名单会拒绝 java.net.URI、java.nio.file.Files、executor 和日志；独立规则点名 JDK HttpServer、Servlet 与常见服务器框架；core 隔离规则防止主源码依赖 test scope 中可见的 core。javac 是第一道边界，ArchUnit 是第二道可读的边界。

compile dependency tree 则检查 POM 事实。即使源码没有 import 服务器，只要 compile scope 引入依赖，消费者 jar 就会传递它。空树比“目前没用”更可靠，因为未来的无意 import 会先遇到编译失败，而不是先把依赖带进生产。

## 常见的第一次写错

| 问题 | 本章能否证明 |
| --- | --- |
| Handler 能否在没有服务器时调用 | 能 |
| Request/Response 是否保持不可变 | 能，构造与读取复制测试 |
| 原始 path/query 是否保留 | 能 |
| 重复 Header 是否保留 | 能 |
| 204/304 非空 body 是否在构造时拒绝 | 能 |
| Handler 是否不能写 framing 字段 | 能 |
| 主源码是否引用服务器类型 | 能，javac 与 ArchUnit |
| HEAD 实际 wire 上是否有 representation length | 不能，需第六章适配器 |
| 304 实际 wire 上是否没有 Content-Length | 不能，需适配器矩阵 |
| 请求体上限是否生效 | 不能，上限属于适配器 |

这个区分很重要。ResponseTest 能证明 Handler 无法声明 Content-Length，不能证明适配器为 HEAD 推导了正确长度；RequestTest 能证明 body 被复制，不能证明服务器在 Handler 之前拒绝超大请求。不要把构造契约测试和真实传输测试混成一句“HTTP 全部正确”。

若聚焦命令失败，先看失败类属于哪个边界：签名或不可变测试失败，说明公共契约发生变化；依赖白名单失败，说明主源码越过了包边界；compile tree 出现子依赖，说明 POM 已把实现细节带进生产 jar。三者需要不同修复，不能用“完整模块也绿”抵消聚焦失败。完整模块的 250 项用于回归，不能替代对失败规则的解释。

做反向验证时，可以临时给主源码加一个禁止包 import，观察编译或架构测试在哪一层拒绝，再撤销实验；不要为了证明测试有效而长期修改源码。对 Handler 加第三个抽象方法则应先遇到 FunctionalInterface 的编译约束。测试的价值不只是今天全绿，而是未来发生越界时能指出被破坏的是哪条承诺。

### 识别失败信号

只运行一个 Handler happy path，会漏掉空 query、重复 Header、body 别名和非法状态。只看依赖树，会漏掉主源码引用 JDK 内部类型；只看源码，会漏掉 POM 意外引入传递依赖。只跑完整模块而不记录聚焦数量，会让读者误以为 250 项都属于本章。

把 SLF4J 无 provider 提示当失败，会促使作者给零依赖契约加入日志实现，恰好破坏本章目标。把 Unsafe 警告当服务器依赖，也会误判工具链；应查看依赖树、架构规则和最终退出状态，而不是凭警告文本推断。

## 怎么确认这一步没造错

本章聚焦检查点：

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=RequestTest,ResponseTest,HeadersTest,HttpMethodTest,HandlerTest,BarezenWebArchitectureTest
```

实际输出：

```text
Tests run: 132, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

| 测试类 | 数量 | 主要证明 |
| --- | ---: | --- |
| RequestTest | 21 | 原始值、Optional、字节副本、请求目标字符拒绝、表面不可变 |
| ResponseTest | 26 | 状态、不可变 body、无体状态、framing 拒绝 |
| HeadersTest | 25 | 重复值、大小写、缺失、ASCII token、控制字符、脱敏 |
| HttpMethodTest | 13 | 标准值、未知 token、大小写规则、非法 token 与合法标点 |
| HandlerTest | 24 | 两参数签名、异常原样传播、装饰组合 |
| BarezenWebArchitectureTest | 23 | 依赖白名单、服务器隔离、core 隔离 |
| 合计 | 132 | 0 failures，0 errors |

完整模块回归：

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test
```

实际结果为 Tests run: 256，Failures: 0，Errors: 0，Skipped: 0，BUILD SUCCESS。多出的 124 项主要来自 Router、RouteMatch、RouteContributor 和插件集成，不属于本章契约五类型，但证明新增路由没有破坏既有输入输出边界。

依赖检查：

```bash
mvn -o -B -ntp -pl framework/barezen-web dependency:tree -Dscope=compile
```

实际树只有模块自身，没有任何 compile 子依赖。测试输出中的 SLF4J “No providers” 提示来自 core 的 test classpath；web 主产物仍没有日志依赖。Maven 关于 sun.misc.Unsafe 的警告来自测试工具，不是契约调用内部 API 的证据，最终以 BUILD SUCCESS 和架构规则为准。
