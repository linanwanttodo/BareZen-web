# 01 为什么契约不等于服务器

## 这一步要解决什么

第三章留下一个能启动的应用骨架，却没有定义“一个请求到达 Handler 时，Handler 拿到什么”。最省事的做法是直接使用服务器对象：JDK 给 HttpExchange，Servlet 给 HttpServletRequest，业务代码照单全收。这样第一个示例确实能跑，但 BareZen 会变成服务器 API 的别名。

本章先冻结传输边界。应用 Handler 只接收 Request 和路由参数 Map，返回 Response；谁读取 socket、谁绑定端口、谁写 Content-Length、谁把异常变成 500，都不属于契约。目标不是让 HTTP 消失，而是让“理解一个请求并回答它”可以在没有服务器的情况下编写和测试。

## 涉及的核心文件与变更

- [Handler.java:75](../../framework/barezen-web/src/main/java/com/barezen/web/Handler.java#L75)：当前唯一函数式扩展点，签名是两个参数、一个返回值。
- [Request.java:45](../../framework/barezen-web/src/main/java/com/barezen/web/Request.java#L45)：客户端消息的五类事实。
- [Response.java:58](../../framework/barezen-web/src/main/java/com/barezen/web/Response.java#L58)：应用答案的三个字段，没有写出方法。
- [Headers.java:57](../../framework/barezen-web/src/main/java/com/barezen/web/Headers.java#L57)：不可变、有序、可重复的字段集合。
- [HttpMethod.java:36](../../framework/barezen-web/src/main/java/com/barezen/web/HttpMethod.java#L36)：九个标准值加任意原始方法名的值类型。
- [barezen-web/pom.xml:29](../../framework/barezen-web/pom.xml#L29)：主产物零 compile 依赖，core 只在 test scope。
- [BarezenWebArchitectureTest.java:55](../../framework/barezen-web/src/test/java/com/barezen/web/BarezenWebArchitectureTest.java#L55)：JDK 包白名单、服务器黑名单与 core 隔离规则。
- [ADR-0018](../../docs/adr/0018-http-is-a-contract-not-a-server.md#L55) 与 [ADR-0020](../../docs/adr/0020-route-parameters-contract.md)：初始五类型与后续参数契约。

`32ebc41` 一次带入 POM、五类类型、ADR、397 行架构测试和契约测试，规模超过 3000 行。这个提交不是“先定义几个 DTO”，而是同时定义边界和证明边界的方法。`2eddb0d` 随后修改 Handler，删除单参数重载，避免旧签名悄悄忽略路由捕获结果。

阅读这两个提交时，建议先看 Handler 的删除行，再看测试如何同步改变。只比较最终文件会漏掉兼容性成本：删除旧重载不是清理 unused code，而是明确要求每个包装器都把 parameters 原样交给内层。[awrapperPassesTheParametersThroughUntouched](../../framework/barezen-web/src/test/java/com/barezen/web/HandlerTest.java#L309) 因此使用对象身份断言，而不是只比较 Map 内容。两个内容相同的 Map 仍可能代表一次重新构造，而重新构造会让路由所有权和后续扩展点变模糊。

这里还要区分“编译依赖”和“测试依赖”。web 测试需要 core 来验证插件能通过构造函数注册路由、由真实生命周期引擎驱动；如果为了测试把 core 提成 compile dependency，生产消费者就会被迫接受它。POM 中一行 scope 的差别，决定契约能否被一个完全不使用 BareZen core 的服务器实现引用。架构测试使用 DoNotIncludeTests 检查 shipped surface，正是为了防止测试便利悄悄变成生产耦合。

## 为什么这样设计

当前签名是：

```java
Response handle(Request request, Map<String, String> parameters);
```

它不是 ADR-0018 最初写的 `Response handle(Request)`。Router 出现后， RouteMatch 已经能捕获 `{id}`，但 Handler 没有参数入口，应用只能重新切片 Request.path()。`2eddb0d` 用最小改动把捕获值直接传进来，同时删除旧重载：保留两种签名会让静态路由与包装器难以判断应用究竟会不会消费参数。

第二个参数只放路由匹配结果，不把 RouteMatch 整体交给 Handler。RouteMatch 还包含被选中的 Handler，若 Handler 能拿到它并再次调用，就出现了“Handler 内部再路由一次”的递归分发。参数 Map 也不会写回 Request，因为 Request 应该保持客户端实际发送的五类事实，而不是变成 attribute bag。

Handler 同步返回 Response，不声明 checked exception。异步 CompletableFuture 会把 executor、取消和完成时机塞进签名，让契约拥有线程生命周期；可检查异常则迫使每层装饰器重复 catch/declare，而它们通常只能原样传递。异常由 Handler 自己决定是否翻译，或留给后续适配器处理，契约不自动捕获。

返回值让装饰成为可能。一个认证包装器可以调用内层 Handler，检查 Response，再返回增加安全字段的新 Response；短路时直接返回 401，不调用内层。若 Handler 收到输出流并立即写字节，外层就无法在写入前改变状态或字段。返回模型不是减少能力，而是把组合能力留在应用层。

零 compile 依赖是这套边界的机械证明。[barezen-web/pom.xml](../../framework/barezen-web/pom.xml#L29) 只有 core 的 test scope，测试可用真实 LifecycleOrchestrator 验证插件集成，但主源码 import core 会直接编译失败。生产 jar 不依赖 SLF4J，所以测试中 core 打印 “no providers” 提示是 test classpath 的结果，不是 web 主产物需要日志实现。

架构规则进一步限制 JDK 表面：主源码只允许 java.lang、java.util 和 com.barezen.web，不允许 java.net、java.io、java.nio、线程或日志。这个白名单比“禁止 Netty”更重要，因为以后有人为了静态文件加入 Files，或为了 ETag 加入 MessageDigest，同样会把平台行为带进契约。规则在后续真实消费者出现时再扩展，而不是提前猜测。

## 怎么验证

先证明 Handler 没有额外入口。[HandlerTest.java:38](../../framework/barezen-web/src/test/java/com/barezen/web/HandlerTest.java#L38) 反射检查只有一个 handle、参数类型恰好 Request 与 Map、没有 checked exception、没有重载，并确认仍是 lambda 可用的 FunctionalInterface。反射过滤 synthetic 方法，避免 JaCoCo 在 verify 阶段注入的方法污染“公开表面”断言。

再证明 Handler 可以独立调用：

```java
Handler handler = (request, ignored) -> new Response(
    200, Headers.of("Content-Type", "text/plain"),
    request.path().getBytes(StandardCharsets.UTF_8));

Response response = handler.handle(
    new Request(HttpMethod.GET, "/healthz", null, Headers.empty(), null),
    Map.of());
```

这段代码没有端口、HttpExchange 或 Servlet，却完整产出一个应用答案。它来自 [HandlerTest.java:77](../../framework/barezen-web/src/test/java/com/barezen/web/HandlerTest.java#L77) 使用的调用形状，只保留理解边界所需的部分。

最后运行依赖树：

```bash
mvn -o -B -ntp -pl framework/barezen-web dependency:tree -Dscope=compile
```

本章实测输出只有 `com.barezen:barezen-web:jar:0.1.0-SNAPSHOT`，没有任何子依赖，BUILD SUCCESS。空树正是“契约不依赖服务器”的证据，而不是遗漏安装依赖。

## 常见错误与失败后果

把 Handler 定义成 `void handle(Request, Response)`，会让写入时机早于装饰器，组件无法修改已经提交的状态。让 Request 携带 `HttpExchange` 作为可选字段，看似保持兼容，实际所有 Handler 都能偷偷依赖它，零依赖边界名存实亡。给 Request 加 `service(Class)` 或 `context()`，会把服务定位器重新引进来。

保留单参数与双参数两个 Handler 重载也不是兼容层，而是两种语义：一个忽略路由参数，一个消费参数。包装器无法替应用决定调用哪个版本。当前选择删除旧方法， breaking change 写进 ADR-0020，而不是用默认参数掩盖。
