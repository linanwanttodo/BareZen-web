# 04 线程提供者作为工厂

## 这一步要解决什么

配置链已经产生 ThreadPolicy，但它还没有决定真正使用哪种 executor。本步实现线程提供者：输入策略、运行期能力和关闭超时，输出一个局部 ThreadProvider；provider 再创建有界或无界 executor，并记录自己创建了哪些资源。它不是全局线程池，也不读取配置。

这部分比配置层更早出现。`2670984` 建立生命周期内核时就有 ThreadProvider、两种实现和共同一致性测试；`e0bc31b` 才把配置接到它上面；第 6 章又让 JDK adapter 拥有或借用 provider。把它放在本章，是因为 ThreadProvider 是“工厂加所有权”最纯粹的样本：选择规则集中、能力可探测、资源归属可验证。

## 先想清楚再写

先否定注册表形状：`executors.get("http")`、`register("scheduler", pool)` 或静态 singleton 看似方便，却让任何模块都能拿到别人的池。HTTP 服务器停止时该关哪个池？事件总线是否还需要同一个 pool？名字无法回答创建者是谁，共享也无法表达单个子系统的生命周期。正确单位是 provider 实例：每个子系统创建自己的 provider，它只记录自己 handed out 的 executor，关闭时也只处理这些 executor。

接口还要防止变成通用并发工具箱。若增加 `callBlocking(...)`，阻塞策略就被放进线程模型；但“是否阻塞”属于调用点，平台线程池和虚拟线程模型只是执行载体。当前接口只有 kind、name、preferred、newBoundedExecutor、newUnboundedExecutor、close 六个方法。preferred 用于日志观察 AUTO 的选择，不是让调用者再次投票；bounded 的并发上限在两种实现中必须一致。

策略与能力必须分开。PLATFORM 在 JDK 24 上也应该得到平台 provider，不能因为“有更好的”而升级；VIRTUAL 在 JDK 17 上必须失败，不能悄悄变成 platform；只有 AUTO 可以在能力缺失时回退。若把 `Runtime.version().feature() >= 21` 直接写在 provider 构造器里，测试无法模拟 JDK 17，字节码基线也无法保持 release 17。RuntimeCapabilities 作为显式快照，把真实探测与策略判断分开。

能力探测本身也不能直接导入 `java.lang.Thread.ofVirtual()` 后靠编译成功来证明。release 17 的 classpath 没有这个方法，直接引用会破坏字节码基线。真实实现通过 VirtualThreadProbe 在运行期尝试加载所需类型，再报告能力；工厂只读取结果。这里“能编译 JDK 24”不等于“支持 JDK 17”，与“release 17”也不等于“只能在 JDK 17 运行”是三件不同的事。

有界与无界也要区分资源边界。无界虚拟 provider 是每任务一个虚拟线程，平台 provider 是 cached pool；它不等于请求层没有上限。请求体大小、连接数和有界任务仍需调用方控制。newBoundedExecutor 在平台实现中是固定池，在虚拟实现中是无界虚拟 executor 外加 semaphore gate，所以切换模型不会意外放大“最多同时执行 N 个”的承诺。超额任务排队，不丢弃。

关闭责任与生命周期相关，但关闭策略不能混进生命周期状态机。provider 的 close 是幂等且终态：先 orderly shutdown，再有界 force stop，最后报告无法终止的任务；close 不抛异常。orchestrator 自建 provider 时在 stop 中关闭；JDK adapter 自建时也关闭，借用则不关。DI assembly 不负责 provider，因为 provider 不是通过 ServiceAssembly.factory 创建的业务服务。

## 动手

工厂只接受已经解析的值：

```java
public static ThreadProvider create(
    ThreadPolicy policy, RuntimeCapabilities runtime, Duration closeTimeout) {
  if (policy == null) {
    throw new NullPointerException("policy must not be null");
  }
  if (runtime == null) {
    throw new NullPointerException("runtime must not be null");
  }
  if (closeTimeout == null || closeTimeout.isNegative()) {
    throw new IllegalArgumentException(
        "closeTimeout must be non null and not negative but was " + closeTimeout);
  }
  long millis = closeTimeout.toMillis();
  boolean virtualRequested = policy == ThreadPolicy.VIRTUAL
      || (policy == ThreadPolicy.AUTO && runtime.virtualThreads());

  if (!virtualRequested) {
    return new PlatformThreadProvider(runtime, millis);
  }
  if (!runtime.virtualThreads()) {
    throw new ThreadCapabilityUnavailableException(
        policy, runtime, "virtual threads are not supported by this JVM");
  }
  return new VirtualThreadProvider(runtime, millis);
}
```

这是 [ThreadProviders.java:52](../../framework/barezen-core/src/main/java/com/barezen/core/concurrent/ThreadProviders.java#L52) 的实际核心。`virtualRequested` 一行同时表达两条规则：显式 VIRTUAL 总请求虚拟；AUTO 只在支持时请求虚拟。PLATFORM 永远走 false。随后先处理不需要虚拟能力的情况，再检查能力并创建 VirtualThreadProvider，因此 AUTO 在 JDK 17 不会进入异常分支。

provider 接口的两个 executor 工厂在 [ThreadProvider.java:57](../../framework/barezen-core/src/main/java/com/barezen/core/concurrent/ThreadProvider.java#L57) 与 [ThreadProvider.java:70](../../framework/barezen-core/src/main/java/com/barezen/core/concurrent/ThreadProvider.java#L70)。调用示例必须自己保存 provider 并关闭，而不是创建全局变量：

```java
RuntimeCapabilities runtime = RuntimeCapabilities.detect();
ThreadProvider provider = ThreadProviders.create(policy, runtime);
try {
  ExecutorService executor = provider.newUnboundedExecutor("http");
  executor.submit(() -> System.out.println("request work"));
} finally {
  provider.close();
}
```

真实 adapter 不会在每次请求时创建 provider；它在服务器构造/启动阶段创建一个，并复用其 executor。orchestrator 的 builder 在没有外部 provider 时调用 create，build 完成后持有它，stop 时关闭，见 [LifecycleOrchestrator.java:390](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L390)。builder.threads(...) 接受外部 provider 时，orchestrator 仍然拥有其关闭，这与 adapter 的 borrowed provider 语义不同，不能把两个“外部”混为一谈。

运行时模型应始终写成：Maven `maven.compiler.release=17` 生成 major 61 字节码；运行期由 RuntimeCapabilities 探测；JDK 21+ 的 AUTO 选择虚拟线程，JDK 17 回退平台线程。当前验证环境 JDK 24 能运行虚拟线程，不代表项目是“JDK 24 项目”。显式 VIRTUAL 才是能力要求，AUTO 是兼容策略。

## 常见的第一次写错

- **错误：** 用静态 Map 保存命名 executor，所有模块共享。**正确：** 每个子系统持有局部 provider，关闭只影响它创建的 executor。
- **错误：** AUTO 与 VIRTUAL 都在无能力时回退。**正确：** 仅 AUTO 回退；显式 VIRTUAL 抛 ThreadCapabilityUnavailableException。
- **错误：** PLATFORM 在 JDK 21+ 被自动升级。**正确：** 显式请求原样满足，运行时能力不是覆盖用户策略的理由。
- **错误：** 直接编译期引用虚拟线程 API。**正确：** release 17 加运行期 probe，工厂消费能力快照。
- **错误：** 创建 executor 后由多个模块分别关闭。**正确：** provider 是这些 executor 的单一所有者；借用 provider 的 adapter 不关闭它。

## 怎么确认这一步没造错

运行策略与一致性测试：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=ThreadProvidersTest,PlatformThreadProviderConformanceTest,VirtualThreadProviderConformanceTest
```

本次实跑 31 项，0 失败、0 错误、0 跳过。ThreadProvidersTest 13 项检查默认关闭超时、参数、策略与能力组合；两个 ConformanceTest 各 9 项，在同一组行为上验证平台和虚拟实现。Virtual 测试通过 RuntimeCapabilities.detect 判断能力，JDK 17 上会按假设跳过，因为那台运行期没有可比较的虚拟实现。

[ConfigurationToThreadsTest.java:153](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ConfigurationToThreadsTest.java#L153) 用模拟 JDK 17/21 能力固定三条规则：AUTO 在 17 是 platform、在 21 是 virtual；PLATFORM 在 21 仍是 platform；VIRTUAL 在 17 失败。[ConfigurationToThreadsTest.java:193](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ConfigurationToThreadsTest.java#L193) 还证明不可满足的请求在 orchestrator build 时失败，参与者事件为空，不会半启动。

共同套件不能只测“能 submit”。它验证重复关闭、关闭后不能再创建 executor、bounded 的并发上限、shutdown 与强制停止等相同契约。日志中的 force-stopping warning 是测试刻意构造不终止任务后的预期报告，不是测试失败。反向验证可让 VIRTUAL 走 AUTO 回退，或让 PLATFORM 被能力升级；对应策略断言会立即变红。

## 此刻的代码长什么样

配置快照现在可以落到真实 executor 工厂，且 provider 的接口、策略和所有权都有测试。HTTP adapter 可以创建自己的 provider，事件总线也可以创建另一个；停止一个不会误关另一个。能力不足在 build 时暴露，AUTO 保持 JDK 17 可运行，显式策略保持可预测。

剩下的关键问题是失败清理。ServiceAssembly 成功构建后可以 close，但如果第 3 个 factory 抛异常，build 根本没有返回 assembly，前两个已经打开的资源怎么办？下一步检查点会把配置、DI、生命周期边界与 provider 一起运行，并重点观察 `79790a5` 如何修复这个无人释放的半成品。
