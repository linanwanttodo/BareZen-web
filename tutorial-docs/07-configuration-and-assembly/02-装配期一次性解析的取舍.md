# 02 装配期一次性解析的取舍

## 这一步要解决什么

上一步得到配置快照，但快照自己不知道怎样变成线程策略，更不该知道怎样创建服务。本步要接上第一条业务链：应用读取 `barezen.runtime.threads`，转换成一个 `ThreadPolicy`，再把策略与运行期能力交给线程工厂。重点是“只解析一次、只传值、只让应用做组合”，而不是增加更多自动绑定。

这里要同时读两个历史状态。`e0bc31b` 的初版让 `LifecycleOrchestrator.Builder.configuration(...)` 解析快照；`6aac12f` 又删除这个入口，理由由 ADR-0015 记录。最终源码中没有 configuration builder 方法，教程必须明确标注旧 API，不能把演进中的便利设计误写成当前用法。

## 先想清楚再写

第一种诱人做法是给 Configuration 增加一个通用 binder：扫描 record 的每个组件，按字段名找 key，用反射转换。它最初只需要处理 ThreadPolicy，却很快会遇到嵌套对象、集合、默认值缺失、枚举别名与“未知字段要不要报错”。每增加一个语法，配置错误就从编译期移到运行期；改一个字段名可能悄悄绑定另一个键，而编译器无法提醒。BareZen 的选择是手写一个四行左右的 `from`，让类型改名与键声明在同一个文件里暴露给审查者。

第二种做法是把 Configuration 注入 RuntimeConfig 或 ThreadProvider，等需要时再 get。这样配置快照确实只有一份，但依赖也变成双向：线程层可以在任意时刻查询任意键，应用无法从构造参数判断它到底读了什么。测试也不能只传一个 ThreadPolicy，而必须准备整套全局状态。值对象应小而完整：`RuntimeConfig` 当前只有一个 `ThreadPolicy threads` 组件，没有保存 Configuration 引用，下游没有回头查询的路径。

第三种做法是把解析放在 orchestrator 里。初版的好处是入口集中，应用写 `.configuration(configuration)` 就能启动；代价是 kernel 为了一个 ThreadPolicy 导入 config 包，生命周期引擎开始理解配置来源。再增加端口、TLS 或数据库配置时，它就会变成应用总装配器，最后离 ApplicationContext 只有几步。ADR-0015 的修正是把那一行解析放回应用：orchestrator 接收已经决定的策略，既不知道键名，也不知道来源。

还有一种失败必须提前分开：值合法不等于能力可满足。`virtual` 是合法枚举，但在 JDK 17 上没有虚拟线程。配置层能报告“这个值可以转换成 ThreadPolicy.VIRTUAL”，线程工厂才能结合 RuntimeCapabilities 报告“当前 JVM 无法满足”。所以转换错误应是 `ConfigurationException`，带 key、原始值、source；能力错误应是 `ThreadCapabilityUnavailableException`，描述请求与运行期，不拿配置文件路径污染基础设施异常。AUTO 可以回退，显式 VIRTUAL 不可以。

一次性解析的代价是没有热更新。改文件后必须重启，正在运行的对象不会突然更换线程模型。这是有意的可预测性：部署、测试和日志都对应启动那一刻的快照。若未来真的需要 reload，就要重新定义原子替换、并发使用和失败策略，而不是在现有 getter 后面偷偷重读文件。

## 动手

先写窄绑定，不设计万能接口：

```java
public record RuntimeConfig(ThreadPolicy threads) {
  public static final ConfigurationKey<ThreadPolicy> THREADS =
      ConfigurationKey.of("barezen.runtime.threads", ThreadPolicy.class, ThreadPolicy.AUTO);

  public static RuntimeConfig from(Configuration configuration) {
    Objects.requireNonNull(configuration, "configuration must not be null");
    return new RuntimeConfig(configuration.get(THREADS).orElseThrow(() ->
        new ConfigurationException("configuration key '" + THREADS.name()
            + "' resolved to nothing, which cannot happen while it declares a default")));
  }
}
```

完整实现见 [RuntimeConfig.java:24](../../framework/barezen-core/src/main/java/com/barezen/core/concurrent/RuntimeConfig.java#L24)。默认 AUTO 属于 key，而不是每个调用点的 fallback。`orElseThrow` 在当前默认存在时不可达，但明确保留“绑定结果不能为 null”的边界：未来若误删默认，启动会得到可诊断的配置错误，而不是 record 构造器里的普通空指针。

然后在应用自己的装配代码里完成当前链：

```java
Configuration configuration = Configuration.standard(Path.of("application.properties"));
RuntimeCapabilities runtime = RuntimeCapabilities.detect();
ThreadPolicy policy = RuntimeConfig.from(configuration).threads();

LifecycleOrchestrator app = LifecycleOrchestrator.builder()
    .threadPolicy(policy)
    .runtimeCapabilities(runtime)
    .registerShutdownHook(false)
    .build();
```

这不是虚构示例的组合：各部分都来自当前 API；orchestrator builder 的默认值、threadPolicy 和 build 见 [LifecycleOrchestrator.java:311](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L311)。`registerShutdownHook(false)` 用于应用自行管理退出或测试，不是业务必需条件。真实应用还要构建 ServiceAssembly 并注册参与者，第 3、5 步会补齐。

历史入口可以用 git 阅读，但不能复制到当前代码：

```bash
git show e0bc31b -- framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java
git show 6aac12f -- framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java
```

`e0bc31b` 同时增加 `threadKind()` 与 `Builder.configuration(Configuration)`；`6aac12f` 删除两者。threadKind 的唯一用途是测试读取 provider 类型，属于“为测试增加公共 API”；configuration 方法则让 kernel 依赖 config。最终 [LifecycleOrchestrator.java:333](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L333) 只接受 ThreadPolicy，[LifecycleOrchestrator.java:398](../../framework/barezen-core/src/main/java/com/barezen/core/kernel/LifecycleOrchestrator.java#L398) 在 build 时创建 provider。策略与能力都在调用 start 之前决定。

## 常见的第一次写错

- **错误：** 给 `Configuration` 加 `getBean` 或 `getService`，让解析顺便创建对象。**正确：** 它只有值解析；对象构造属于 ServiceAssembly。
- **错误：** RuntimeConfig 保存 Configuration 字段，组件以后自己 get。**正确：** record 只保存 ThreadPolicy，把依赖画成单向值流。
- **错误：** 当前代码调用 `.configuration(configuration)`。**正确：** 应用先 `RuntimeConfig.from(...).threads()`，再 `.threadPolicy(policy)`；旧入口已删除。
- **错误：** 把 `virtual` 拼错时直接使用 AUTO。**正确：** 配置转换失败，保留 key、原值和来源；合法但不可满足的 virtual 则由能力工厂失败。
- **错误：** 为了让部署灵活，每次读取都重载文件。**正确：** 启动时解析一次；需要热更新时先定义并发和失败语义，不偷偷改变快照含义。

## 怎么确认这一步没造错

运行贯通测试：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=ConfigurationToThreadsTest,ApplicationAssemblyBoundaryTest
```

本次实跑 26 项：ConfigurationToThreadsTest 18 项，其中 host 相关 11 项在 JDK 24 上有 1 项按“不支持虚拟线程”的假设跳过；ApplicationAssemblyBoundaryTest 8 项。0 失败、0 错误。host 类中的跳过是能力条件，不是测试未执行或被静默忽略。

[ConfigurationToThreadsTest.java:95](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ConfigurationToThreadsTest.java#L95) 把 auto/platform/virtual 及大小写拼写逐一绑定；[ConfigurationToThreadsTest.java:104](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ConfigurationToThreadsTest.java#L104) 固定 typo 不降级；[ConfigurationToThreadsTest.java:116](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ConfigurationToThreadsTest.java#L116) 验证文件、环境、系统属性的赢家一路进入 provider 决策。更重要的是 [ConfigurationToThreadsTest.java:131](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ConfigurationToThreadsTest.java#L131)：它反射检查 RuntimeConfig 的组件只有 ThreadPolicy，并检查 ThreadProviders 的公开方法参数没有 Configuration。这不是测试实现细节，而是在固定单向边界。

边界测试的 [ApplicationAssemblyBoundaryTest.java:302](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ApplicationAssemblyBoundaryTest.java#L302) 枚举 orchestrator 与 builder 的公开方法，明确不包含 configuration，也不允许任何方法参数来自 config 包。反向验证可临时恢复旧入口：方法表面断言与架构测试应同时变红，证明“文档说不能依赖”已有执行证据。

## 此刻的代码长什么样

配置快照、RuntimeConfig 与 ThreadPolicy 已经形成一条单向链。应用能在启动前决定线程模型，错误按“配置转换失败”与“能力不可满足”分别报告；orchestrator 只接收策略和能力，不再了解配置文件。

但对象创建仍未解决。线程 provider 可以由 orchestrator 创建，业务服务和它们的依赖不能也塞进 kernel。下一步引入 ServiceAssembly：应用写下每个构造过程，装配器按依赖顺序执行，并保持生命周期词汇完全在自身之外。
