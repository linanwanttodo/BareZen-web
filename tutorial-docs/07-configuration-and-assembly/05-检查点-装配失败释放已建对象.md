# 05 检查点：装配失败释放已建对象

## 这一步要解决什么

前四步分别建立了配置、应用侧解析、显式工厂与线程 provider，现在必须验证它们组合后没有资源缺口。最重要的检查不是“happy path 能 start”，而是第 3 个 factory 抛异常时，前两个已经创建的对象有没有在异常传播前释放，且释放顺序是否正确、原始异常有没有被清理错误覆盖。

真实提交 `79790a5` 专门修复这个问题；`6aac12f` 又用 ApplicationAssemblyBoundaryTest 固定应用在 DI 与生命周期之间的组合责任。本步运行这两条失败路径，并汇总本章聚焦测试结果，作为进入第 8 章前的可执行检查点。

## 先想清楚再写

先推演 `e2c9902` 初版的漏洞：build 创建 Pool，再创建 Session，第三个 factory 抛 IllegalStateException。因为 build 没有返回 ServiceAssembly，调用者的 catch 块即使想 close 也没有对象可关；前两个资源就此泄漏。若应用把整个 build 放进 try-with-resources，资源变量也未成功赋值，同样无法补救。唯一有能力释放它们的是正在执行 build 的 builder，因为它持有 Resolution.owned 列表。

修复不能简单在 catch 中正序调用 close。创建顺序是依赖在前，关闭必须反转：Session 先用 Pool，因此 Session 先 close，并应在 close 内观察到 Pool 仍 open。只记录“close pool”“close session”两个事件还不够，必须让 fixture 在下层关闭时仍可用，才能证明顺序真的保护依赖。正常 assembly.close 与 failed build 应共用 releaseAll，避免两条路径以后走向不同。

原始异常也不能丢。第三个 factory 的 IllegalStateException 才是应用要修的根因；如果 Pool.close 又抛异常，catch 不能让清理异常替代它。当前实现把关闭失败聚合为 AssemblyException：第一个 close 失败作为 cause，其余作为 suppressed；原 build 异常继续向上抛，同时把聚合 cleanup 挂为 suppressed。聚合 cleanup 又反向挂入原异常，所以从任一入口都能看到另一边。没有清理失败时，build 异常保持原对象身份，不被无意义包装。

覆盖范围也要准确。build catch 的是 RuntimeException 与 Error，因为工厂可能抛 AssertionError 等；releaseAll 内部只捕获 AutoCloseable.close 声明的 Exception，不假装吞掉 close 抛出的 Error。finally 负责把当前类型移出 inProgress，避免一次失败留下错误递归状态。builder 第一次 build 后不能重试，因为已有对象可能已经释放，再次运行工厂会得到另一套资源；需要重试就创建新 builder。

只捕获 Exception 也意味着“每个对象都尝试关闭”不是无条件承诺：若某个 close 抛 Error，循环立即中断，后续 owned 对象不会释放，原 factory 异常也来不及完成 suppressed 汇总。factory 在返回对象之前打开的资源同样无法进入 owned。assembly 成功 close 后也不清空实例表，require/find 仍可返回已关闭对象；教程不把这种查询解释为合法使用，应用应在 close 后停止访问。

另一个容易混淆的边界是“构建失败”与“启动失败”。build 失败时还没有 orchestrator，assembly 自己释放已创建对象；start 失败时 assembly 已经成功返回，orchestrator 只回滚参与者，不跨层关闭 DI 对象，应用随后调用 assembly.close。两条责任都是单向的。停止时正常顺序仍是 app.stop 后 assembly.close，因为参与者的 stop 可能使用池。

最后，ServiceAssembly.close 与 lifecycle stop 的失败契约不同。ADR-0005 说 orchestrator.stop 尽力而为、不抛并返回 ShutdownReport；ServiceAssembly.close 则在对所有抛出 Exception 的对象尝试关闭后，抛 AssemblyException 汇总这些失败。不能为了“统一”让 assembly 静默吞掉异常，也不能让 lifecycle close 抛异常掩盖正在传播的启动异常。相似的最佳努力原则，在不同 API 上可以有不同报告方式。

## 动手

build 的失败清理核心如下，来自 [ServiceAssembly.java:225](../../framework/barezen-core/src/main/java/com/barezen/core/di/ServiceAssembly.java#L225)：

```java
Resolution resolution = new Resolution(bindings);
try {
  resolution.createEverything();
} catch (RuntimeException | Error failure) {
  List<Exception> cleanupFailures = ServiceAssembly.releaseAll(resolution.owned());
  if (!cleanupFailures.isEmpty()) {
    AssemblyException cleanup = ServiceAssembly.aggregate(cleanupFailures);
    cleanup.addSuppressed(failure);
    failure.addSuppressed(cleanup);
  }
  throw failure;
}
return new ServiceAssembly(resolution.instances(), resolution.owned());
```

`releaseAll` 从 owned.size()-1 倒序遍历，只处理 AutoCloseable，逐个捕获 Exception 并继续，见 [ServiceAssembly.java:129](../../framework/barezen-core/src/main/java/com/barezen/core/di/ServiceAssembly.java#L129)。`aggregate` 把首个失败作为 cause，其余 addSuppressed，见 [ServiceAssembly.java:144](../../framework/barezen-core/src/main/java/com/barezen/core/di/ServiceAssembly.java#L144)。owned 只包含 factory 注册的对象；instance 注册的外部对象不会进入这个列表，因此 failed build 也不会关闭调用者的池。

正常路径仍由应用明确组合：

```java
ServiceAssembly assembly = ServiceAssembly.builder()
    .factory(ConnectionPool.class, services -> new ConnectionPool())
    .factory(Reporter.class, services -> new Reporter(services.require(ConnectionPool.class)))
    .build();
LifecycleOrchestrator app = LifecycleOrchestrator.builder()
    .register("reporter", assembly.require(Reporter.class))
    .build();
app.start();
app.stop();
assembly.close();
```

实际应用还应在 start 失败时关闭 assembly；测试在 [ApplicationAssemblyBoundaryTest.java:205](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ApplicationAssemblyBoundaryTest.java#L205) 分别验证 rollback 后关闭，以及 build 失败时不需要 orchestrator。这里的 ConnectionPool/Reporter 是测试 fixture，不是框架公开类型；读者应复用自己已经实现的等价资源，不要臆造 API。

## 常见的第一次写错

- **错误：** build 失败只抛异常，期待调用者清理。**正确：** builder 释放自己创建的 owned 对象，因为调用者拿不到失败的 assembly。
- **错误：** 按注册顺序关闭。**正确：** 按实际创建顺序反转，保证依赖仍可用于使用者的 close。
- **错误：** failed build 也关闭 instance 对象。**正确：** 外部对象由调用者拥有，只有 factory 路径进入 owned。
- **错误：** 第一个 close 异常中断清理。**正确：** 捕获并继续，最后聚合所有失败；原始 factory 异常仍是主异常。
- **错误：** start 失败让 orchestrator 跨层关闭 assembly。**正确：** orchestrator 回滚参与者，应用随后关闭 assembly；失败所有权保持单向。

## 怎么确认这一步没造错

先运行本章完整聚焦集合：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=ConfigurationTest,ConfigurationPrecedenceTest,StandardConfigurationTest,ConfigurationToThreadsTest,ServiceAssemblyTest,AssemblyToLifecycleTest,ApplicationAssemblyBoundaryTest,ThreadProvidersTest,PlatformThreadProviderConformanceTest,VirtualThreadProviderConformanceTest
```

本次在 JDK 24.0.2、Maven 3.9.12 实跑：**Tests run: 136，Failures: 0，Errors: 0，Skipped: 1，BUILD SUCCESS**。跳过来自 ConfigurationToThreadsTest 的 host 能力假设：在支持虚拟线程的 JDK 24 上，“无虚拟线程时 explicit virtual 失败”的 host 分支不适用。模拟 JDK 17 的对应测试仍执行并通过，因此不能把跳过理解成该规则未验证。

重点读三个失败测试：

- [ServiceAssemblyTest.java:333](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L333)：第三个 factory 失败后，事件严格为 create pool、create session、close session（pool 仍 open）、close pool。
- [ServiceAssemblyTest.java:351](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L351)：failed build 不关闭调用者的 Pool。
- [ServiceAssemblyTest.java:368](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L368)：抛出的对象仍是原始 IllegalStateException，cleanup AssemblyException 挂在 suppressed，并反向引用原异常。

还要检查 [ApplicationAssemblyBoundaryTest.java:161](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ApplicationAssemblyBoundaryTest.java#L161)：Reporter.stop 内部断言池仍打开，随后 assembly.close 才关闭池。[ApplicationAssemblyBoundaryTest.java:259](../../framework/barezen-core/src/test/java/com/barezen/core/kernel/ApplicationAssemblyBoundaryTest.java#L259) 连续多次 close，确保每个对象只释放一次。这里的顺序断言不是只看日志文本，而是在使用资源的当下检查状态。

反向验证至少做三项：删除 failed build 的 releaseAll，第一条应看到资源事件停在创建；把逆序循环改为正序，Session 的 close 应观察到 pool 已关闭；用 cleanup 异常替换原异常，原始身份断言应失败。若只想得到绿灯而放宽这些断言，就会把 `79790a5` 修复的真实价值删掉。

## 此刻的代码长什么样

本章结束时，配置是固定优先级的不可变快照，应用在启动前完成类型绑定，ThreadPolicy 与 RuntimeCapabilities 在工厂处决定 provider，DI 急切构造显式注册的对象。成功构建后，参与者由 orchestrator 驱动、DI 拥有的资源由 assembly 逆序释放；构建失败时 builder 自己清理已创建对象，启动失败时应用在回滚后关闭 assembly。

这些能力仍是一个轻量骨架：没有热更新、YAML、命名绑定、请求作用域、通用 binder 或自动应用容器；ServiceAssembly 不支持与使用并发的 close；ThreadProvider 也不是全局线程池。知道不做什么，和知道做什么同样重要。下一章开始静态内容处理，所有配置与装配仍保持启动前职责，不向请求路径增加新的全局查找。
