# 01 配置源与合并解析

## 这一步要解决什么

真实服务器已经能启动，但应用必须能决定线程策略、端口等行为。现在缺的不是一个 `Properties.load`，而是一套不会随调用位置改变的规则：配置从哪里来、谁优先、错误值算谁的、构造完成后还能不能变。本步先解决来源和解析，把结果做成不可变快照；下一步才决定谁消费它。

真实提交是 `e0bc31b`：它一次加入 config 包、`RuntimeConfig`、配置异常、orchestrator 入口，以及配置到线程决策的端到端测试。第一次写时应把配置看成一个有边界的小子系统，而不是随手增加静态 `Config.get(...)`。只要任何组件都能查询进程状态，测试隔离和依赖方向就已经输了。

## 先想清楚再写

先推演最便宜的写法：每个组件在构造时调用 `System.getProperty`。端口可能读文件，线程池可能读环境变量，另一个 Handler 又读取系统属性；同一个应用在容器、命令行与本机开发中会得到不同组合，而且读取时机不同。测试想固定一个端口，不得不修改 JVM 全局状态，测试结束后还要恢复；并行测试稍一交错就会互相污染。更糟的是，线上日志显示端口来自文件，线程策略却来自另一个来源，排错者无法从一条装配链复现它。

第二个常见错误是把所有来源放进一个 `Map` 后逐个 put。这个顺序必须极其明确：key 默认值低于文件，文件低于环境变量，环境变量低于系统属性。写反一次，运维通过 `-D` 临时覆盖容器默认值就会失效，而应用仍“正常启动”，只是运行在错误的模型上。框架选择“参数从弱到强，内部反转后从强到弱查找”，让优先级成为可读的参数顺序，而不是藏在每个 source 里的数字等级。

第三是“坏值回退”。假设文件写 `platform`，环境写 `virtul`，系统属性没有该键。如果转换失败后继续找文件，应用会以 platform 启动，操作员却以为 virtual 已生效。正确规则是高层来源一旦回答这个键，它就是唯一赢家；转换失败必须抛 `ConfigurationException`，附上 key、原始值和来源。低层来源没有资格在高层值坏掉时替代它。

快照也不能只是包着 `System.getProperties()` 的句柄。系统属性可写，文件也可变；若对象在每次 get 时重读，两个组件可能在不同时间看到不同值。三个标准 source 都在构造时复制输入，文件只读一次。这里没有 reload、watch 或配置中心：运行中的应用就是启动时验证过的那个配置。教学上先接受“不热更新”，比假装提供一套并发安全的动态配置简单得多，也诚实得多。

最后，source 只应知道如何按名字找字符串。若 Properties source 自己把值转 Integer，Environment source 又要支持 Duration，同一字符串会在不同层得到不同解释。转换必须属于 key 的类型，由一个 `ValueConverter` 统一完成；优先级属于 `MergedConfiguration`，source 连优先级概念都没有。

## 动手

先声明带名字、类型和默认值的键。名字不是任意字符串：每一段允许字母、数字、短横线和下划线，用点分隔，避免 `a..b` 这种永远无法配置的拼写被当成“未设置”。

```java
public record ConfigurationKey<T>(String name, Class<T> type, T defaultValue) {
  public static <T> ConfigurationKey<T> of(String name, Class<T> type) {
    return new ConfigurationKey<>(name, type, null);
  }

  public static <T> ConfigurationKey<T> of(String name, Class<T> type, T defaultValue) {
    return new ConfigurationKey<>(name, type, defaultValue);
  }
}
```

对应实现是 [ConfigurationKey.java:21](../../framework/barezen-core/src/main/java/com/barezen/core/config/ConfigurationKey.java#L21)。键声明与使用分离，让 `barezen.runtime.threads` 只出现在 `RuntimeConfig.THREADS` 这一处；调用者不能临时拼一个字符串再强转结果。

source 的表面只有 `name()` 与 `find(String)`，见 [ConfigurationSource.java:14](../../framework/barezen-core/src/main/java/com/barezen/core/config/ConfigurationSource.java#L14)。Properties source 用 `Properties.load(Reader)` 解析转义、注释与续行，但显式包一层 UTF-8 `InputStreamReader`。直接调用 `Properties.load(InputStream)` 会按 ISO-8859-1 解码，非 ASCII 值会随平台期待变成乱码。文件不存在是合法的空层；文件存在却不可读则必须失败，不能把权限问题伪装成“没有配置”。

环境 source 只做一条名称映射：点变下划线，再用 `Locale.ROOT` 大写。因此 `barezen.runtime.threads` 对应 `BAREZEN_RUNTIME_THREADS`，见 [EnvironmentVariablesSource.java:53](../../framework/barezen-core/src/main/java/com/barezen/core/config/EnvironmentVariablesSource.java#L53)。系统属性 source 使用原样点分名字，并过滤非 String 的键和值。两者都复制 map，而不是保留全局对象的活引用。

工厂方法把生产顺序写出来：

```java
static Configuration standard(Path propertiesFile) {
  return new MergedConfiguration(
      PropertiesConfigurationSource.fromFile(propertiesFile),
      EnvironmentVariablesSource.current(),
      SystemPropertiesSource.current());
}
```

这段来自 [Configuration.java:70](../../framework/barezen-core/src/main/java/com/barezen/core/config/Configuration.java#L70)。参数名 `sourcesWeakestFirst` 很重要：调用者按弱到强传入，构造函数反转存储，get 从强到弱查找。没有 source 时空配置非法；in-memory map 会被复制，适合测试与程序化嵌入，不需要临时改全局状态。

`MergedConfiguration.get()` 找到赢家后立即转换，找不到才返回 key 的默认值，见 [MergedConfiguration.java:34](../../framework/barezen-core/src/main/java/com/barezen/core/config/MergedConfiguration.java#L34)。当前转换支持 String、Integer、Long、Boolean、Duration 与 enum。Boolean 只接受大小写不敏感的 true/false，`Boolean.parseBoolean("tru")` 会返回 false，这种静默错误不能出现；enum 用 `toUpperCase(Locale.ROOT)` 对应 Java 常量，配置里写小写；Duration 直接采用 ISO-8601，例如 `PT10S`。转换先 trim，但空字符串仍是“存在的值”，不会变成缺失。

## 常见的第一次写错

- **错误：** `System.getenv(name)` 直接查 `barezen.runtime.threads`。**正确：** 通过 EnvironmentVariablesSource 查 `BAREZEN_RUNTIME_THREADS`，映射规则只有一个实现。
- **错误：** 文件读不到就返回默认值。**正确：** 不存在返回空 source；存在但读取或解析失败抛 `ConfigurationException` 并保留 cause。
- **错误：** 高层值转换失败后继续找低层。**正确：** 第一个 `find(...).isPresent()` 就是赢家，转换失败立即终止。
- **错误：** 用 `Boolean.parseBoolean` 接受任意字符串。**正确：** 仅 true/false，其他值列入错误消息，避免拼写错误把开关静默关闭。
- **错误：** Configuration 提供 put、reload 或 getService。**正确：** 只提供类型化 `get`；配置回答值，不创建协作者，也不承担服务定位。

## 怎么确认这一步没造错

在仓库根目录运行三个聚焦测试：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=ConfigurationTest,ConfigurationPrecedenceTest,StandardConfigurationTest
```

本次实跑 44 项，0 失败、0 错误、0 跳过。`ConfigurationTest` 的 18 项检查键名、默认值、支持类型与转换失败；`ConfigurationPrecedenceTest` 的 18 项逐层证明默认值 < 文件 < 环境 < 系统属性；`StandardConfigurationTest` 的 8 项直接走生产工厂，证明真实全局输入确实被读取并复制。

优先读 [ConfigurationPrecedenceTest.java:49](../../framework/barezen-core/src/test/java/com/barezen/core/config/ConfigurationPrecedenceTest.java#L49) 的逐层覆盖和同键替换。它没有只说“环境优先”，而是分别删除中间层，确保某一层缺失时低层仍可见；[ConfigurationPrecedenceTest.java:169](../../framework/barezen-core/src/test/java/com/barezen/core/config/ConfigurationPrecedenceTest.java#L169) 把缺失文件与不可读目录分开，[ConfigurationPrecedenceTest.java:213](../../framework/barezen-core/src/test/java/com/barezen/core/config/ConfigurationPrecedenceTest.java#L213) 在构造后修改原 map，证明快照没有变。

反向验证应让“转换失败后继续查找”重新出现，观察优先级测试变红；让 EnvironmentVariablesSource 使用点分名字，观察映射测试变红；保留全局 map 引用，观察快照测试变红。仅运行成功路径不够，这些规则都容易在后续重构中被一句“兼容处理”破坏。

## 此刻的代码长什么样

现在 config 包能提供固定优先级的只读快照，`Configuration` 不依赖 Spring，也不增加解析库；core 的第三方编译依赖仍只有 slf4j-api。来源、优先级、转换和错误报告各有位置，但它们还没有决定线程模型，也没有创建任何服务。

还缺的是“谁在什么时候读快照”。如果让 `ThreadProvider` 自己查询，前面的单向边界会立刻消失；如果让生命周期引擎持有 Configuration，又会把配置句柄带入内核。下一步将沿真实历史展示第一次入口为何放在 orchestrator，以及后来为什么必须移回应用。
