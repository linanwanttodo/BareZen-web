# 03 显式工厂注册替代反射扫描

## 这一步要解决什么

应用现在有了值，却仍需要把值交给构造函数，并保证依赖先于使用者存在。本步实现 `ServiceAssembly`：应用注册类型和工厂，工厂体直接写 `new A(b)`，build 时创建全部对象。它只构造和释放，不 initialize、不 start、不 stop，因此不会和第三章的生命周期引擎争夺控制权。

真实提交 `e2c9902` 加入 ServiceAssembly、Services、AssemblyException、架构规则与装配测试。这个阶段的重点不是“支持多少注入方式”，而是把容器限制到能回答一个问题：应用声明了什么，容器按什么顺序执行。没有扫描、qualifier、Primary、request scope 或延迟代理。

## 先想清楚再写

如果走反射路线，第一步是注册一个 class，第二步挑一个构造函数，第三步根据参数类型递归查找依赖。代码看似少了 factory lambda，却增加了更多隐含规则：有多个构造器怎么办，只有一个带注解的构造器怎么办，接口有两个实现怎么办，循环引用怎么办，字段为空是不是可选依赖。为了解决这些问题，容器会逐步需要名称、优先级、作用域和生命周期回调，应用最终必须运行容器才能知道对象图。

BareZen 反过来要求工厂体写出构造调用。`services -> new SqlRepository(services.require(DataSource.class))` 既声明依赖，又执行构造；编译器检查参数类型，读者不需要启动任何东西就能沿 new 往下看。lambda 里可以出现分支吗？当然可以，但它属于应用的装配代码，不交给一套隐藏的 DSL 猜。显式并不等于所有逻辑自动正确，而是错误发生在应用作者能够阅读和修改的位置。

注册顺序不能当成依赖顺序。应用可能先写 Endpoint，再写 UseCase，最后写 Store；若 build 严格按注册顺序执行，第一个工厂就找不到 Store。正确模型是“注册顺序决定无依赖对象的遍历起点，工厂第一次 require 某类型时递归创建它”。这样 Store、UseCase、Endpoint 的实际创建顺序与注册书写顺序无关，却始终是依赖在前。释放时反转实际创建列表，就能保证使用者在依赖仍可用时先关闭。

急创建也是核心取舍。若 find 在 build 后还能触发 factory，缺失依赖、循环和构造异常会推迟到首个请求；应用可能已经监听端口、接受流量，才发现基础服务没造好。build 必须创建所有注册对象，之后 map 不再写入，查询无需锁也不会意外创建新对象。代价是启动成本全部前移，以及没有惰性单例；当前没有真实成本问题需要这两个复杂能力。

循环必须显式检测。A 工厂 require B，B 工厂 require A，如果只靠 Map 判断“已创建”，两者都尚未完成，递归会直到 StackOverflowError。这种 Error 难以 usefully 捕获，堆栈也没有一条清晰的类型路径。Resolution 维护 inProgress 列表，再次进入正在创建的类型就抛出 `AssemblyException`，消息列出 `A -> B -> A`。这个列表不公开，应用不能查询或操纵依赖图。

所有权由注册方式决定，不由对象是否 closeable 决定。factory 表示 assembly 调用构造逻辑并得到对象，因此若它实现 AutoCloseable，assembly 负责关闭；instance 表示调用者已经建好，assembly 只转交引用。实现 AutoCloseable 的 LifecycleParticipant 通常注册为 instance，让 orchestrator 独占 stop，避免 assembly.close 又调用 close 造成双重释放。这里的“创建”要理解为工厂路径的所有权，而不是某个对象的字节码里是否有 new。

最后，Services 是工厂执行期间的临时视图，不是可以注入业务类的服务定位器。若工厂把 services 存进产品，build 后产品还能 require 任意类型，依赖就重新藏回方法体。Resolution 在 createEverything 完成后设置 finished，任何后续 require/find 都抛 AssemblyException，提示把依赖放进构造函数。这个拒绝必须可测试，否则“禁止 service locator”只是一句愿望。

## 动手

公开表面保持两个注册方法：

```java
public <T> Builder instance(Class<T> type, T object) {
  Objects.requireNonNull(type, "type must not be null");
  Objects.requireNonNull(object, "the object registered as " + type.getName() + " must not be null");
  register(new Binding(type, ignored -> object, false));
  return this;
}

public <T> Builder factory(Class<T> type, Function<Services, ? extends T> production) {
  Objects.requireNonNull(type, "type must not be null");
  Objects.requireNonNull(production, "the factory registered for " + type.getName() + " must not be null");
  register(new Binding(type, production, true));
  return this;
}
```

它们来自 [ServiceAssembly.java:177](../../framework/barezen-core/src/main/java/com/barezen/core/di/ServiceAssembly.java#L177)。`assemblyOwnsIt` 布尔值把两种注册统一进 Resolution，同时保留关闭所有权。相同 Class 第二次注册立即抛 AssemblyException；这里没有“最后一个覆盖”或“第一个优先”的隐含规则。

```java
ServiceAssembly assembly = ServiceAssembly.builder()
    .instance(DataSource.class, dataSource)
    .factory(UserRepository.class, services ->
        new SqlUserRepository(services.require(DataSource.class)))
    .factory(UserService.class, services ->
        new UserService(services.require(UserRepository.class)))
    .build();
```

这个形状与 ADR-0014 一致。DataSource 由调用者创建，因此 close 不触碰它；另两个对象由 factory 创建，若 closeable，关闭顺序是 UserService 后 UserRepository。构建期 ServiceAssembly 本身也实现 Services，但它的 find 只读最终 map，不会创建对象。

Resolution 的创建逻辑可以压缩为三个判断：已创建则直接返回；仍在 inProgress 则抛循环路径；否则加入 inProgress、执行 production、拒绝 null 或类型不匹配，再放入 instances 和 owned，finally 移除 inProgress。见 [ServiceAssembly.java:333](../../framework/barezen-core/src/main/java/com/barezen/core/di/ServiceAssembly.java#L333)。类型检查集中在 build，而不是注册和查询各做一次；编译器通常已经阻止错误类型，剩余检查覆盖刻意擦除泛型的调用。

build 只能调用一次。若允许第二次，工厂会再运行，第一批对象可能已经无人持有，关闭责任却还挂在旧 assembly 上。Builder 在第一次 build 前设置 built=true，后续调用直接失败。build 成功后返回不可变 map 与 owned 列表的快照；lookup 不创建、不加锁，因为应用线程尚未启动，图已经固定。当前 close 不与使用并发，这是 shutdown 约定，不是承诺任意线程安全。

## 常见的第一次写错

- **错误：** 用注册顺序作为执行顺序。**正确：** factory 第一次 require 时创建依赖，实际创建顺序才决定逆序释放。
- **错误：** 同一类型注册两次并让后者覆盖。**正确：** 立即拒绝；两个实现注册为两个具体类型，由应用明确选择。
- **错误：** build 后 find 触发新 factory。**正确：** build 创建全部，完成后只读；启动后发现缺失比首请求才发现好。
- **错误：** 把 Services 注入业务类。**正确：** 只在工厂 lambda 中使用，产品通过构造参数接收已经解析的对象。
- **错误：** assembly 对 instance 和 factory 都调用 close。**正确：** 所有权跟随创建；参与者由 orchestrator 驱动，不能出现两个释放者。

## 怎么确认这一步没造错

运行装配与交接测试：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=ServiceAssemblyTest,AssemblyToLifecycleTest
```

本次实跑 35 项，0 失败、0 错误。ServiceAssemblyTest 31 项：BuilderHygiene 7、OwnershipAndReleaseOrder 6、Cycles 3、FailedBuild 3，外层类还有 12 项直接测试；AssemblyToLifecycleTest 4 项检查构建与生命周期的交接。Surefire 对嵌套类分别报告，不能只看外层聚合为 0 的那一行。

[ServiceAssemblyTest.java:177](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L177) 故意把最外层 Endpoint 注册在最前，仍断言 Store、UseCase、Endpoint 的创建顺序；[ServiceAssemblyTest.java:421](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L421) 验证两类型、自引用和三类型循环都给出路径；[ServiceAssemblyTest.java:471](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L471) 不仅检查 close 事件顺序，还在 Session/Statement.close 中断言下层仍 open，避免“事件名看起来对但资源先关”的假证明。

API 表面测试在 [ServiceAssemblyTest.java:660](../../framework/barezen-core/src/test/java/com/barezen/core/di/ServiceAssemblyTest.java#L660)：ServiceAssembly 的公开操作只有 builder/require/find/close，Builder 只有 instance/factory/build，Services 只有 require/find，去重后的公开操作总计七个。AssemblyToLifecycleTest 还检查 assembly 没有 initialize/start/stop/abort/refresh，也不是 LifecycleParticipant。反向验证可让 build 后 find 创建对象，或允许工厂保存 Services 后继续查询，相应测试必须变红。

## 此刻的代码长什么样

应用现在可以显式构造整张对象图，缺失、循环和 null 在 build 时失败，创建顺序与释放顺序可证明。ServiceAssembly 没有生命周期状态，也不会启动参与者；它只持有已创建对象并在 close 时逆序释放。

目前还有一个真实缺口：build 中途失败时，已经创建的对象由谁释放？第 5 步会回到 `e2c9902` 之后的 `79790a5` 修复。先看第 4 步的 ThreadProvider，因为它是“工厂加所有权”的另一个具体例子，能帮助区分 provider 创建的 executor、DI 创建的服务和 orchestrator 驱动的参与者。
