# 手写安全边界意味着什么

## 这一步要解决什么

路由解决“请求去哪”，安全解决“请求能不能进入那个 Handler”。第一章用它说明，安全不是登录成功后加一个 if，而是认证事实、授权决定、拒绝状态和会话撤销共同组成的边界。每条边界都必须有明确所有者，否则最危险的漏洞往往出现在组件交接处。

## 先想清楚再写

最诱人的简化是让认证器返回 `boolean`。但“客户端没有带凭据”和“客户端带了错误 token”都会得到 false；授权组件随后无论怎么努力，也无法知道这是该要求登录，还是该拒绝一个已经声称的身份。更糟的是把空 Optional 同时解释为匿名与失败，会让 401 的诊断、统计与测试全部失去事实依据。

BareZen 的 `AuthenticationResult` 是 sealed interface，包含 `Authenticated`、`Failure` 与 `Anonymous`。成功态携带 Principal，失败态携带应用自己的 reason，匿名态表示没有尝试认证。reason 可以用于服务端诊断，但不能回显到响应，否则攻击者可能通过错误文案逐个试探 token 结构。

第二项必须先想清楚的是会话撤销。若把 Principal 直接 Base64 编码或签名进 token，服务端只验证签名，就无法在用户登出、密码修改或设备丢失后让旧 token 立即失效。当前实现选择 32 字节 `SecureRandom` 随机值，token 本身无结构，状态放在 `SessionStore` 的 `ConcurrentHashMap` 中。撤销只是删除映射；代价是状态不跨重启、不跨实例，也不能把 `size()` 当成有效会话数，因为过期记录只在 lookup 时被删除。

第三项是安全异常。认证器或授权器抛 `RuntimeException` 时，中间件返回固定 500，不把异常文本交给客户端。它当前也不会自动记录异常，应用若需要日志必须自己在协作者中处理。这个实现事实与“默认拒绝”同样重要：安全框架不能替应用假设日志后端，也不能假装所有诊断已经自动完成。

凭据解析也有明确但有限的规则。中间件读取大小写不敏感的 `Authorization` 头，按第一个空格分出 scheme 与值；没有空格的单段值默认视为 Bearer。它不会把整套认证协议都塞进这里，也不会把 token 持久化到请求上下文。认证器只接收一个 `Credential`，因此可以分别用真实 SessionStore、测试夹具或其他实现替换，而不改变路由和响应契约。

## 动手

真实中间件把三个关注点按固定顺序包成一个 Handler：

```java
public static Handler wrap(
        Authentication authentication, Authorization authorization, Permission required, Handler delegate)
```

进入 `handle(Request, Map<String, String>)` 后，它从 `Authorization` 头提取 `Credential`，先认证；未认证返回 401；再授权；拒绝返回 403；最后才调用普通 Handler，或把 `SecurityContext` 传给同时实现 `SecuredHandler` 的委托。拒绝路径上委托调用计数必须保持为零。

会话创建来自 `SessionStore`，不是中间件自己生成 token：

```java
SessionStore sessions = SessionStore.standard();
SessionStore.Session issued = sessions.create(new Principal("ada"), Duration.ofHours(8));
String token = issued.token().value();
Optional<SessionStore.Session> found = sessions.lookup(token);
boolean revoked = sessions.invalidate(token);
```

这里没有签名密钥，也没有把 Principal 写进 token。第一次实现时先让 create、lookup、invalidate 三个动作成立，再考虑轮换与插件组合。测试可注入 `Clock`，所以过期行为不需要真实等待八小时。

当前 `handle` 的顺序可以直接对照源码：`credentialFrom` 提取头，`authentication.authenticate` 得到三态结果；未认证立即 401；创建本次请求的 `SecurityContext`；授权拒绝返回 403；只有允许后才调用 `SecuredHandler.handle(..., context)` 或普通 delegate。认证与授权各自捕获 `RuntimeException` 并返回固定 500，但 catch 块没有日志调用，因此教程不能声称“错误已经自动记录”。

会话的创建同样能逐行核对：`create` 生成 32 字节，使用不带 padding 的 Base64url 编码，再放入 `ConcurrentHashMap`。`lookup` 发现过期会删除该映射；`invalidate` 直接删除；`rotate` 未过期时先创建新会话，再条件删除旧值；过期则返回空，创建失败时旧会话仍保留。`size()` 只是 map 大小，所以仍包含尚未被 lookup 或 rotate 清理的过期记录。把这些细节写出，比笼统说“支持会话轮换和过期”更接近真实契约。

`f315e21` 的端到端测试说明装饰器还必须经过真实 HTTP 路径验证；单元测试则用可控认证器和计数 delegate 证明拒绝时业务 Handler 从未运行。两者不能互相替代：真实网络测试证明组合能工作，单元测试精确证明哪一步阻断。后续第 9 章会把这些提交继续拆成密码、会话和插件安装步骤。

## 常见的第一次写错

- **错误：用 `Optional<Principal>` 代替三态。** 正确：Anonymous 与 Failure 必须是不同类型，成功态才包含 Principal。
- **错误：把失败 reason 拼进 401 响应。** 正确：响应固定为 `Unauthorized`，详细原因留在服务端。
- **错误：授权失败也返回 401。** 正确：身份已知但权限不足返回 403，让客户端能区分两类问题。
- **错误：token 里直接放用户 ID。** 正确：使用不可猜测的不透明值，服务端保存状态以支持撤销。
- **错误：把 rotate 当作无条件刷新。** 正确：rotate 会删除过期映射并返回空，只有未过期 token 才能换得新会话。

## 怎么确认这一步没造错

运行中间件测试，重点检查六条路径：

```bash
mvn -o -B -ntp -pl framework/barezen-security -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=SecurityMiddlewareTest
```

预期 `BUILD SUCCESS`。`authenticatedAndAllowed` 是唯一进入委托的正常路径；`anonymousIsRefused` 与 `failureIsRefused` 都返回 401；`deniedIsForbidden` 返回 403；`brokenAuthenticationIsAServerError` 与 `brokenAuthorizationIsAServerError` 返回 500。`noIdentityLeakBetweenRequests` 证明身份不通过 ThreadLocal 泄漏到下一次请求。

再验证会话和密码哈希：

```bash
mvn -o -B -ntp -pl framework/barezen-security -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=SessionStoreTest,PasswordHasherTest,AuthenticationResultTest
```

预期全部通过。测试使用可控 Clock 与测试随机源，不依赖系统当前时间或打印真实秘密。

## 此刻的代码长什么样

此时已经拥有可撤销的内存会话和三态认证结果，安全中间件仍是 web 契约上的 Handler 装饰器。它不读取环境变量，不持有静态身份，不侵入适配器；认证与授权协作者由应用构造并传入。PBKDF2 负责把登录密码变成存储值，不负责维护登录状态，两者不能混成一个“用户对象”。

这个边界还揭示了明确的部署限制：当前 SessionStore 重启丢会话，也不支持多实例共享；非本机应用若要支持横向扩展，需要另行设计共享存储和撤销传播。第 9 章会沿这条线展开密码哈希参数、会话插件与完整拒绝矩阵。下一章先看另一类边界：为什么单元测试、契约测试和架构门禁必须同时存在，任何一层都不能冒充完整证明。
