# 给读者的话：跟着造一遍能得到什么

## 这一步要解决什么

第一章末尾需要把“为什么读教程”说清楚，否则读者很容易在第二章看到 POM 与能力探测时失去方向。目标不是复制一个更小的 Spring，也不是背下 BareZen 的 API，而是获得一种能审查框架设计的直觉：知道一个便利功能会把责任推给谁，知道一条边界如何被测试证明，也知道项目主动放弃了什么。

## 先想清楚再写

如果以“最后得到多少功能”衡量学习，读者会自然追求更多注解、更多自动发现和更多默认值。但那些成果主要证明自己跟完了教程，不能证明理解了框架。更危险的是把“手写”浪漫化：手写如果缺少规则与测试，只会得到难以维护的重复代码。 BareZen 值得学的并不是拒绝库，而是每次拒绝都给出可执行理由。

版本模型是一个很好的练习。很多项目通过提高编译版本来使用新 API，却把兼容性成本转嫁给所有消费者；另一些项目为每个 JDK 复制模块，又把测试和发布复杂化。BareZen 选择单一 release 17 产物，在运行期探测虚拟线程能力。这个选择并不轻松：必须有一个受限的探测点，必须保证 JDK 17 上没有 Java 21 符号泄漏，还必须测试 AUTO 在能力可用与不可用时的不同结果。

路由与安全也遵循同一方法。一个看似友好的自动解码可能让资源身份改变；一个看似简洁的布尔认证可能让错误状态不可恢复；一个看似完整的集成测试若绕过适配器，可能完全没有看过网络字节。学习的目标就是识别这些“局部正确、整体错误”的形状，并用测试把错误形状挡在构建之外。

请把本教程当作对照实验，而不是不可质疑的规范。真实源码是当前事实，ADR 是当时理由，你的任务是理解两者如何相互约束。若未来代码改变，先查后续决定和测试，再修改自己的理解；不要为了维护本文而隐藏仓库中的真实缺陷。

## 动手

把学习记录写成四列表，每完成一章就追加一行：本章拥有什么能力、明确拒绝什么、用什么测试证明、还缺哪一层。第一章可以先填：

| 层 | 当前能力 | 明确拒绝 | 证明方式 | 缺口 |
|:---|:---|:---|:---|:---|
| 项目边界 | 九个小模块，依赖向下 | 空模块与万能容器 | POM、ArchUnit | 尚未建立 |
| HTTP 路由 | 原始段匹配 | 隐式解码与重定向 | RouterTest | 真实适配器 |
| 安全 | 三态与内存会话 | ThreadLocal 身份 | SecurityMiddlewareTest | 共享存储 |
| 版本 | release 17 与运行期探测 | JDK 专属构件 | ClassMajorContractTest、ThreadProvidersTest | 跨 JDK CI 证据 |

这不是框架代码，而是给自己的检查表。它能把“看过了”变成“能复述并核对”。真实代码片段继续以仓库为准，例如运行期入口是：

```java
RuntimeCapabilities runtime = RuntimeCapabilities.detect();
ThreadProvider provider = ThreadProviders.create(ThreadPolicy.AUTO, runtime);
```

这行代码只说明策略如何进入工厂；它不表示可以随处创建并忘记关闭。下一章和第七章会分别解释能力选择与资源所有权。

### 提交切片：把“我看过”变成“我能复现”

学习记录还应增加一列 commit。每读完一章，不只写最终 API，还写下这次建造最有解释力的一个提交，以及它改变的边界。例如初始 `2670984` 同时建立 core 与基线；`18e8fef` 用不可变路由表固定路径语义；`7d913bf` 把安全做成装饰器；`4c9feda` 证明声明不等于产物。这样，下一次看到相似改动时，你知道应该比较哪些文件和测试，而不是只搜索类名。

```bash
git log --reverse --format='%h %s'
git show --stat 18e8fef
git show --name-only 7d913bf
git show --stat 4c9feda
```

读提交时先看文件清单，再选一个核心实现和一个测试。若一次提交包含大量文件，不要假设它们都属于同一章；真实开发会把文档、生命周期和构建配置一起推进。教程拆开解释，是为了让因果可读，而不是要求你回到历史提交重新写一遍。

最终的自检问题可以很具体：你能否指出 Router 为什么没有 404 方法？能否从 SecurityMiddleware 的 catch 块看出它没有自动日志？能否解释 ClassMajorContractTest 为什么要伪造 major 65 和外来文件头？能否从 TestServer 的构造器看出它使用真实 adapter 和随机端口？这些问题都有文件证据，比“我感觉理解了”可靠。

## 常见的第一次写错

- **错误：把教程当成 API 大全。** 正确：先理解问题与代价，再查源码确认最终接口。
- **错误：认为每项设计都没有替代方案。** 正确：ADR 的价值正是记录被拒绝方案与 reopening trigger。
- **错误：把已知构建失败当成必须修复的教程作业。** 正确：记录环境事实并缩小检查范围，不修改用户 WIP。
- **错误：只记录成功命令。** 正确：也记录错误输入应得到什么失败，拒绝条件同样是契约。
- **错误：为了“完整”增加无消费者功能。** 正确：先有真实使用场景，再决定抽象和模块。

## 怎么确认这一步没造错

这一章的检查点不是新增测试，而是确认你已经能独立找到四组证据。运行：

```bash
mvn -o -B -ntp -pl framework/barezen-web,framework/barezen-security -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=RouterTest,SecurityMiddlewareTest,SessionStoreTest
mvn -o -B -ntp -pl framework/barezen-core -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=ThreadProvidersTest,ClassMajorContractTest
```

预期均 `BUILD SUCCESS`。第一条同时选择两个模块时，Maven 会构建它们共同需要的上游；若某个模块没有匹配到指定测试，应检查 Surefire 是否因为选择规则报错，而不是忽略退出码。

随后从 [全部 ADR 中文索引](../../docs/adr-index-zh.md) 进入，检查 0002、0019、0033、0034、0036、0037、0044、0045 是否都能追溯到原文。能说出每条决定“保护什么、牺牲什么、由哪个测试守住”，才算通过本章。

## 此刻的代码长什么样

第一章没有增加任何生产类型，但建立了后续学习的坐标系：学习资产与轻量骨架是定位；原始路径与三态认证是显式规则；真实 socket 与架构门禁是证据；release 17 与运行期探测是兼容性模型。它们都不是独立技巧，而是同一种工程习惯的不同表现。

下一章开始真正搭骨架。第一步不是写一个能返回字符串的 HTTP 服务，而是先决定产物基线、能力探测和模块方向。你会看到，有时最重要的代码在服务启动之前就已经写完：它确保之后所有“方便”的实现都不能偷偷改变项目对自己的承诺。
