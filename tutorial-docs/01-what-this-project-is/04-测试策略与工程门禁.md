# 测试策略与工程门禁

## 这一步要解决什么

“代码能跑”只证明某一次输入经过了某一条路径，不能证明契约、并发边界和依赖方向都成立。第一章的最后一项学习价值，是理解不同测试各自回答什么问题，以及为什么它们不能相互替代。BareZen 同时使用单元测试、契约测试、真实套接字测试、ArchUnit 和覆盖率门禁，它们组成的是证据链，而不是同一件事重复五遍。

## 先想清楚再写

如果只测 Router，可以证明 `/users/new` 在字面量与参数路由之间选择了字面量，却不能证明 JDK 适配器真的没有发送 HEAD body。若只测真实 socket，可以观察状态码和 body，却很难覆盖所有路径矩阵，网络失败也会让原因变得含混。若只有示例 `main`，输出能给人直觉，却不是自动门禁；若只有架构规则，能阻止反向依赖，却不能证明业务语义正确。

真实套接字测试尤其容易被假对象替代。直接调用 Handler 会跳过 Request 解析、Headers 转换、响应分帧、连接关闭与异常边界；一个内存“服务器”若自己模拟这些规则，就只能证明模拟器与测试作者有相同误解。TestKit 因此绑定 `127.0.0.1:0`，读取 OS 分配的端口，再通过 `java.net.http.HttpClient` 发请求。它不追求网络性能，只追求让生产适配器真正参与。

ArchUnit 解决的是另一类回归：设计者已经解释过 core 为什么不能依赖 web，却无法保证几个月后没人为了方便加一条 import。把规则写成测试后，审查不必每次重新争论同一原则。覆盖率则回答“还有多少已编译路径未被执行”，但高覆盖率不等于断言正确；一个没有断言的测试也能覆盖一行代码。

两阶段启动的测试还必须观察状态，而不只是“没抛异常”。初始化失败后，已启动对象是否逆序停止？原始异常是否被清理异常覆盖？若没有资源计数和状态断言，回滚代码看起来执行了，实际可能留下半启动服务。下一章的状态机正需要这种证据。

## 动手

先按证据类型给测试命名，而不是把所有测试塞进一个 `AppTest`。仓库中的职责划分很清楚：

```text
RouterTest                         路径与匹配语义
SecurityMiddlewareTest             认证、授权、拒绝和身份隔离
TestServerIntegrationTest          真实端口上的完整 HTTP 路径
BarezenCoreArchitectureTest        模块边界与禁用结构
ClassMajorContractTest             已发射字节码，而非配置声明
```

TestKit 的服务器形状来自 ADR-0044：

```java
try (TestServer server = TestServer.start(router)) {
    TestResponse response = server.client().get("/users");
    Assertions.assertThat(response).statusIs(200);
}
```

教学片段保留真实构造与断言形状；实际路由仍由应用构建。关键是端口由 OS 分配、请求经过真实适配器、资源在 try-with-resources 作用域内释放，而不是在测试结束后靠进程退出清理。

架构测试则直接表达禁止关系。例如 core 的规则禁止命名 `com.barezen.web..`，TestKit 的规则禁止框架其他部分依赖 testkit。这里检查的是源码依赖，不是运行时是否碰巧加载成功；Java 允许包名与目录不一致，编译成功也不能证明分层成立。

### 提交切片：每增加一种消费者，就增加一种证据

测试设施也沿真实需求增长。`bfef5d5` 为 JDK adapter 增加 546 行架构测试；`4c9feda` 把 class-major 测试与全树脚本纳入构建和 CI；`743ae96` 新增 TestKit；`0971abc` 才一次加入七个可运行示例及对应测试。不要把这些提交倒推成“先有完整测试平台，再写所有功能”：

```bash
git show --stat bfef5d5
git show --stat 4c9feda
git show --stat 743ae96
git show --stat 0971abc
```

当前 [TestServer.java](../../framework/barezen-testkit/src/main/java/com/barezen/testkit/TestServer.java) 固定了几个关键选择：包装真实 `JdkHttpServerAdapter`，绑定 `127.0.0.1:0`，从 adapter 读取实际端口，使用 `HttpClient` 的 HTTP/1.1 且不自动跟随重定向，在 `close()` 中停止 adapter。它没有另写一个内存分派器，因此不会在测试里重复生产代码的假设。

这带来一张证据矩阵：RouterTest 检查路径规则；SecurityMiddlewareTest 检查固定顺序和拒绝计数；TestServerIntegrationTest 检查报文真正经过适配器；ArchitectureTest 检查依赖关系；ClassMajorContractTest 检查真实输出字节；示例测试检查公开 API 能组合。任何一项都不能单独代表“整个框架正确”，但缺少任何一项都会留下不同盲区。

`0971abc` 的示例同时覆盖 routing、request/response、security、database、plugins 和 OpenAPI。示例不是生产模块的依赖，也不使用内部类型；它们像陌生消费者一样编译公开 API。若示例必须 import 一个包私有类才能完成常见任务，就说明公开边界还不完整，而不是应该把内部类赶紧转成 public。

## 常见的第一次写错

- **错误：用 mock Handler 代替真实端口。** 正确：单元测试可以 mock，网络契约必须由真实适配器验证。
- **错误：硬编码 8080。** 正确：绑定端口 0，并从适配器或 TestServer 读回实际端口。
- **错误：测试成功只打印结果，不做断言。** 正确：示例负责演示，测试负责比较状态与计数。
- **错误：把覆盖率当质量分数。** 正确：同时检查断言是否真的区分正确与错误结果。
- **错误：架构规则只覆盖新类。** 正确：让规则扫描整个相关包，新增绕过者也会失败。

## 怎么确认这一步没造错

先跑纯契约与安全测试，再跑 TestKit 真实网络测试：

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=RouterTest,ClassMajorContractTest
mvn -o -B -ntp -pl framework/barezen-testkit -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=TestServerIntegrationTest,FixturesTest
```

两条命令都应 `BUILD SUCCESS`。TestKit 用例覆盖动词往返、404、401/403、身份隔离、端口释放与重复关闭；这些现象无法由直接调用 Router 或 Handler 得到。

最后单独运行架构测试：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=BarezenCoreArchitectureTest
mvn -o -B -ntp -pl framework/barezen-testkit -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=BarezenTestKitArchitectureTest
```

预期成功。若规则没有编译到任何类、扫描范围写错或测试被跳过，不能把它当作门禁已生效。真正的证据是失败用例出现时规则会变红，而不只是绿色构建里有它的名字。

## 此刻的代码长什么样

目前我们还没有开始写这些测试，但已经知道它们未来分别保护什么。后续每一步都应同时交付实现和一个能区分“写对/写错”的检查点；一个测试若把错误实现也判为成功，就没有完成设计。示例则站在消费者一侧，只使用公开 API，用真实 socket 或真实驱动展示组合方式。

从这个角度说，工程门禁不是项目完成后的装饰，而是设计语言的执行器。下一章会先建立最简单的门禁：字节码基线、运行期能力探测、模块边界和“没有内容就不建模块”。在 HTTP 出现之前，我们必须先保证以后写出的每一层都不会破坏这些已经确认的约束。
