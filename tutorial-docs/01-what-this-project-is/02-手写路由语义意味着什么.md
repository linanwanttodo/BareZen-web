# 手写路由语义意味着什么

## 这一步要解决什么

一个 Handler 被写出来以后，请求怎样找到它，必须有一条完整且可测试的规则。第一章用路由说明“手写”的具体价值：不是重新实现一个字典，而是把默认框架藏在背后的路径歧义、重复注册和错误职责逐个写成显式决定。

## 先想清楚再写

假设最初只写 `Map<String, Handler>`，再逐渐加上 `/users/{id}`。很快会出现几个看似局部的问题：先注册的参数路由是否吃掉后注册的字面量路由？`/users/a%2Fb` 应该算一段还是两段？`/users` 要不要自动服务 `/users/`？两个参数名不同但位置相同的路由为什么可以共存？

如果没想清楚，最常见的修复是加一个优先级数字，让调用方自己排序。这样把责任推给了每个注册者，插件一多就无法知道最终胜者。另一种修复是调用 `URI.normalize()` 或解码后再匹配，它会把 `/a%2Fb` 悄悄变成 `/a/b`，让客户端点名的资源与服务端选择的资源不一致；路径遍历表达也可能在进入 Handler 前被改写，应用反而看不到原始输入。

真正需要先定的是职责。Router 只回答“哪个 Handler、哪些参数”；404 与 405 需要同时知道“路径不存在”和“路径存在但方法不支持”，所以 `match` 与 `methodsFor` 提供两个事实，由适配器决定响应。若 Router 自己返回 404，它马上会拥有错误格式、状态码和内容协商，最终变成一个缩小版 Web 容器。

完整规则因此可以列成短句：按 `/` 切原始段；段数必须相同；字面量大小写敏感；恰好 `{name}` 的段捕获一个非空原始段；重复的 method 加 shape 在注册时拒绝；胜者由第一个字面量与参数量的分歧决定。规则少而完整，比不断增加例外更好验证。

还要把空段与尾斜杠写进同一套语义。`/users` 与 `/users/` 的段数不同，因此不自动互相匹配；应用若希望两个地址都有效，就明确注册两个路由。`{id}` 不接受空段，所以 `/users//` 不会产生一个空用户标识。这里不引入配置开关，因为一个开关很快会衍生重定向状态码、缓存键与永久地址选择等新问题。让地址精确，短期多写几行注册代码，却让每个 URL 的含义保持稳定。

## 动手

真实实现从两个值开始：`HttpMethod` 与原始路径。注册时保存模式、分段和参数名；匹配时只比较这两项，不读 header、query 或 body。下面是来自 `RoutingExample` 的注册形状：

```java
Router router = Router.builder()
        .route(HttpMethod.GET, "/books", (request, parameters) ->
                text(200, "the library has no books yet"))
        .route(HttpMethod.GET, "/books/{id}", (request, parameters) ->
                text(200, "book " + parameters.get("id")))
        .route(HttpMethod.POST, "/books", (request, parameters) ->
                text(201, "created"))
        .build();
```

`Router.match(Request)` 返回 `Optional<RouteMatch>`，其中 `RouteMatch` 包含 Handler 与不可变参数 Map。`Router.methodsFor(String)` 返回该原始路径能匹配的 method 集合。第一次实现时，先让这两个查询返回数据，不急着让它们产生 HTTP 响应。

参数捕获要沿模式段的位置走，而不是把参数名列表与整个请求段列表压缩配对。`/a/{x}/b/{y}` 的 `x` 来自索引一，`y` 来自索引三；直接把名字和请求段前两项配对会把 `a` 错当成 `x`。`RouterTest.twoParametersAreCapturedAtTheirOwnPositions` 正是为这个错误存在的。

## 常见的第一次写错

- **错误：先解码再分段。** 正确：先按原始 `/` 分段，`a%2Fb` 始终是一段，捕获值也保持 `a%2Fb`。
- **错误：用 `Map<String, Handler>` 只以路径为键。** 正确：路由身份是 method 与 shape，GET 和 POST 可共存。
- **错误：后注册覆盖先注册。** 正确：相同 shape 直接拒绝，不把顺序偷偷变成优先级。
- **错误：Router 返回 `new Response(404, ...)`。** 正确：返回 Optional，并把 404/405 的响应写出决定留给适配器。
- **错误：用参数名判断重复。** 正确：`{id}` 与 `{userId}` 形状相同，都是 `/users/{}`，必须冲突。

## 怎么确认这一步没造错

运行 Router 的完整测试：

```bash
mvn -o -B -ntp -pl framework/barezen-web -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=RouterTest
```

预期 `BUILD SUCCESS`。重点观察 `anEncodedSlashStaysOneSegmentAndStaysEncoded`、`anEncodedDotSegmentIsNotNormalisedAway`、`aStaticRouteBeatsAParameterRoute`、`registrationOrderDoesNotChangeTheWinner`、`aParameterDoesNotMatchAnEmptySegment` 和 `theRouterNeverCallsTheHandlerItRegistered`。它们分别证明原始输入、优先级、参数边界和“只匹配不执行”。

再运行示例测试，确认真实应用注册形状可以工作：

```bash
mvn -o -B -ntp -pl examples -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=RoutingExampleTest
```

预期三项测试通过。这个检查点不启动整个 reactor，因此不会把本章任务与 `JdkMethodCaseSemanticsTest` 的已知 JDK 差异混在一起；但 RoutingExampleTest 仍会使用 TestKit 的真实适配器路径。

## 此刻的代码长什么样

此时 Router 还是一个纯数据组件：构造完成后不可变，不拥有线程、socket、配置或容器。它能列出匹配结果和可用方法，却不能直接回答客户端。参数值保持原始文本，应用若需要业务解码，必须在自己知道字段语义的地方进行，并为解码失败选择响应。

这个“不替应用做决定”的边界看起来保守，却为后续章节省下大量耦合。第六章适配器可以消费它而不引入错误页面策略；第十一章插件可以向 Builder 贡献路由而不获得容器能力；安全装饰器可以包住最终 Handler，而不改变匹配语义。下一章会进一步说明，为什么认证与授权也采用同样的显式边界，而不是藏进 Router 或适配器。
