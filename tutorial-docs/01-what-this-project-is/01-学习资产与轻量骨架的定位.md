# 学习资产与轻量骨架的定位

## 这一步要解决什么

在写第一行框架代码之前，先确定这个项目承诺什么。没有定位，后续每个“要不要支持”的问题都会滑向功能堆叠；有了定位，才能判断一项方便是否值得增加一层抽象。BareZen 的承诺不是成为生产级通用框架，而是把 HTTP 框架内部的重要规则亲手实现、解释并验证。

## 先想清楚再写

最容易发生的误判，是把“不依赖 Spring”当成“因此更轻、更快、更适合所有小项目”。依赖少只能说明依赖图的一个维度，不能证明吞吐量、生态、可维护性或生产可靠性。这个仓库的价值恰恰在另一处：一个学习者能打开 Router，完整读出路径如何匹配；打开 SecurityMiddleware，看到请求在哪个条件下不能进入业务 Handler。

如果把定位写成“另一个企业框架”，第一章就会鼓励读者追求注解、自动配置、插件市场和隐式行为。那些目标会把学习时间花在配置表面，而不是路径、状态和所有权。更隐蔽的问题是没有退出条件：功能需求永远合理，边界却越来越难解释。 BareZen 当前版本仍是 `0.1.0-SNAPSHOT`，也没有 LICENSE 文件；这些事实都应如实呈现，而不是用定位文案掩盖。

“轻量服务骨架”同样需要限定。它适合小型同步服务、内部工具和学习项目，因为模块少、依赖方向显式、请求模型完整缓冲。它不适合需要成熟生态、响应式流式处理、复杂模板与序列化栈、广泛运维集成的生产系统。写下不适合的场景，不是贬低项目，而是防止读者把学习框架误部署到它没有验证过的负载上。

定位还会影响依赖方向。核心模块只提供生命周期、线程和配置等通用能力，HTTP 契约属于 web，具体服务器属于 adapter；如果因为“项目小”而把这些层塞进一个包，短期能少建几个 Maven 模块，长期却会让安全、数据和应用示例都共享同一份隐式上下文。模块数不是越少越好，而是每个模块都应能说明自己拥有什么、允许谁依赖它。这个标准比功能列表更适合作为建造起点，也能解释为什么 examples 与 app 必须站在框架外面。

## 动手

先不创建模块。把定位写成一份可检查的约束，再让目录和代码服从它。当前真实模块包括 core、web、http-jdk、http-servlet、security、data、content、plugins 与 testkit；examples 和 app 是消费者叶子。可以用下面的命令核对模块事实，而不是凭印象写架构图：

```bash
mvn -q -DskipTests help:evaluate -Dexpression=project.version -DforceStdout
```

当前根 POM 返回 `0.1.0-SNAPSHOT`。接着读取模块表：

```bash
find framework -mindepth 2 -maxdepth 2 -name pom.xml -print | sort
```

这不是要求新写的示例 API，而是本章唯一的“动手”：建立一个拒绝伪造的事实来源。真实编译基线则写在父 POM：

```xml
<maven.compiler.release>17</maven.compiler.release>
```

运行期的另一个事实来自 `com.barezen.core.runtime.RuntimeCapabilities`：

```java
RuntimeCapabilities detected = RuntimeCapabilities.detect();
System.out.println(detected);
```

输出形状是 `RuntimeCapabilities[jdk=..., virtualThreads=..., vendor=...]`。把这两个事实放在一起，就得到本项目的版本模型：产物兼容 JDK 17，新版能力在运行期选择，而不是把开发机版本写进项目名称。

## 常见的第一次写错

- **错误：把“无 Spring 依赖”写成性能结论。** 正确：只写依赖与架构事实，性能需要可复现基准，本项目教程不提供这种结论。
- **错误：承诺覆盖所有 Web 场景。** 正确：列出小型同步服务和学习用途，同时说明流式响应、成熟生态与生产验证等缺口。
- **错误：用当前 JDK 版本定义产物基线。** 正确：release 17 决定字节码，RuntimeCapabilities 决定运行期分支。
- **错误：先建很多空模块以显示完整。** 正确：模块必须拥有职责和产物；ADR-0008 已拒绝没有内容的聚合模块。

## 怎么确认这一步没造错

定位是文档承诺，不能靠单测证明措辞，但可以逐条核对它引用的事实。运行：

```bash
java -version
mvn -version
mvn -o -B -ntp -pl framework/barezen-core -am test -Dsurefire.failIfNoSpecifiedTests=false -Dtest=ThreadProvidersTest
```

预期 `BUILD SUCCESS`。测试会覆盖平台线程和虚拟线程提供者，但选择结果仍取决于运行 JDK；不要在 JDK 17 上期待虚拟线程测试成立。再核对父 POM 的 release 和当前产物：

```bash
javap -verbose framework/barezen-core/target/classes/com/barezen/core/runtime/RuntimeCapabilities.class | grep 'major version'
```

预期 `major version: 61`。如果 build 尚未执行，先完成上面 Maven 命令；不要用 IDEA 设置或未构建的目录代替证据。

## 此刻的代码长什么样

此刻尚未写任何框架实现，但已经有了一份事实清单：九个框架产物、两个消费者叶子、同步 Handler、release 17、运行期能力探测，以及明确的能力缺口。模块边界不再由想象决定，而是由后续每一章要解决的问题决定。

下一章会把这张清单变成构建约束。我们仍不写 HTTP，但会先保证任何新模块都不会通过改 release、引入内部 JDK API或反向依赖来绕过已经说清的定位。这样，定位才不是 README 里的宣传句，而是每次构建都能检查的边界。
