# 第 11 章第 2 步：依赖声明与纯校验汇合

## 这一步要解决什么

上一步让插件能声明 `id` 和依赖 id，但没有代码读取完整集合。若两个 jar 都声明 `auth`，应用启动时会有两个参与者竞争同一个身份；若 `auth` 依赖的 `user` 根本不存在，只有进入 auth 的某个方法后才可能暴露；若 a 依赖 b、b 依赖 a，orchestrator 只会按照应用传入的顺序启动，无法知道这个顺序不可能满足声明。

本步对应提交 `72eaf7063538385ebc8d63d7d08dd4c98ae89ca9`，新增 `PluginRegistration` 和 15 项测试。它只提供一个静态方法：

```java
public static List<Plugin> validate(List<Plugin> plugins)
```

这个方法不构造插件、不调用生命周期、不保存结果，也不提供 `register`。它读取已经存在的对象，返回一个按依赖关系排序的不可变列表。应用仍然要把返回值交给 orchestrator，框架不会在某个隐蔽角落自动扫描并校验所有插件。

需要区分三个动作：**发现**回答“类路径上找到了谁”，**校验与排序**回答“这批对象能否组成一致集合”，**装配与启动**回答“这次应用实际运行谁”。本步只实现第二项，因此可以保持纯函数。把三件事塞进一个 registry 会让测试依赖全局状态，也让应用失去对本次运行的控制。

## 先想清楚再写

最直接的方案是在 `LifecycleOrchestrator.Builder.register` 中解析依赖。调用者每注册一个插件，builder 就检查依赖是否已经注册。它有两个问题：依赖可能稍后注册，当前对象却已经被接受；循环只能到 build 时才可能发现；非插件参与者也会被迫进入这套图语义。更好的边界是在应用拥有完整列表之后做一次独立校验，orchestrator 的重复 id 检查继续作为第二道防线。

第二种方案是让 `PluginRegistration` 成为有状态的 registry，提供 `add`、`order`、`get`。这样调用者可能注册一半就查询顺序，也可能在启动后继续添加。校验结果与真实生命周期对象也会分家：registry 排好序，应用却把原列表注册进 orchestrator，排序等于没有发生。纯函数让“校验返回什么”和“应用使用什么”成为同一段可读代码。

第三种方案是按字母排序。它很简单，却不是依赖排序：名为 `z-user` 的 user 插件会排在 `a-auth` 之后，auth 的依赖仍然失败。正确规则是拓扑关系：一个插件只有在其全部依赖已经放置后才 ready；每轮收集所有 ready，再一起放置。独立插件保持调用者给的相对顺序，而不是按 id 重排。

可选依赖看起来是常见需求，但当前描述符没有 optional 标志，校验器也不发明这个语义。缺失就是缺失，要么从集合补上，要么修改声明。若悄悄忽略缺失依赖，启动顺序仍然可能错误，而错误信息只说“插件启动了”，维护者很难找到声明问题。

还要预先决定 null 的含义。null 列表不是一个空应用，空集合才是；列表中的 null 不能跳过，否则调用者可能以为注册了 N 个插件，实际少了一个；null descriptor 同样拒绝，因为插件身份不是可选装饰。依赖 id 的 null/blank 已在描述符构造时拒绝，校验器仍会检查完整集合中的缺失关系。

拓扑算法的时间成本也要诚实。当前实现反复扫描未放置插件，属于小而直观的 O(n²) 过程，没有 trie 或复杂图引擎。插件数量通常是应用作者显式写出的少量项，先选择可审计算法；若真实规模使扫描成为问题，可以在不改变公共 API 的情况下替换私有实现。

## 动手

核心入口位于 [PluginRegistration.java:61](../../framework/barezen-core/src/main/java/com/barezen/core/plugin/PluginRegistration.java#L61)。第一步检查 null 列表和 null entry；随后 `index` 为每个插件读取 descriptor，拒绝 null descriptor，按 id 建表并拒绝重复。重复异常消息包含冲突 id 与两个实现类，因为“有两个 auth”不如“A 和 B 都声明 auth”可操作。

真正排序的是这段循环：

```java
List<String> order = new ArrayList<>(byId.size());
Set<String> placed = new HashSet<>();
while (placed.size() < byId.size()) {
  List<String> ready = new ArrayList<>();
  for (Map.Entry<String, Plugin> entry : byId.entrySet()) {
    if (!placed.contains(entry.getKey())
        && placedAll(entry.getValue().descriptor().dependencies(), placed)) {
      ready.add(entry.getKey());
    }
  }
  if (ready.isEmpty()) {
    List<String> stuck = new ArrayList<>();
    for (String id : byId.keySet()) {
      if (!placed.contains(id)) {
        stuck.add(id);
      }
    }
    throw new IllegalArgumentException("no registration order satisfies the plugin set: these plugins"
        + " depend on each other in a cycle " + stuck + "; a plugin that needs a plugin that needs it back"
        + " describes two halves of one unit");
  }
  order.addAll(ready);
  placed.addAll(ready);
}
```

`byId` 是 `LinkedHashMap`，所以扫描顺序来自调用者列表。每轮 ready 也按这个顺序加入，独立插件因而保持相对次序。若 `[auth, user, openapi, reports]` 中 auth 依赖 user、reports 也依赖 user，第一轮只能放置 user 与 openapi；第二轮才能放置 auth 与 reports，结果为 `[user, openapi, auth, reports]`。

`ready.isEmpty()` 的准确含义是“剩余插件没有任何一个可以放置”。它可能由纯循环造成，也可能是“循环加一批依赖循环的下游插件”。异常列出所有无法放置的 id，而不武断地说其中每一个都在环上。开发者需要从集合和声明中找出环；对大型图，这个列表可能比一个不准确的单环路径更诚实。

缺失依赖在 `index` 阶段处理：遍历每个 descriptor 的 dependencies，若 byId 不含该 id，就拒绝并指出依赖方与缺失 id。因为这一步先于拓扑循环，缺失依赖不会被误报成循环。自依赖已经在 `PluginDescriptor` 构造时拒绝，也不需要一个特殊的排序分支。

最后，代码按排好序的 id 从 byId 取回原对象，返回 `List.copyOf(ordered)`。输入列表没有被排序或删除，调用者仍持有原列表；返回列表不可修改，但不能据此声称插件对象本身不可变。插件仍可能在生命周期中改变自己的资源状态，这是它的正常职责。

在真实示例中，汇合只发生在应用：

```java
static List<Plugin> assemble(Wiring wiring, List<Plugin> announced) {
  List<Plugin> merged = new ArrayList<>(wiring.built());
  merged.addAll(announced);
  return PluginRegistration.validate(merged);
}
```

源码见 [PluginExample.java:119](../../examples/src/main/java/com/barezen/examples/plugins/PluginExample.java#L119)。手工列表和 discovered 列表先成为一批对象，再一次性校验。这样跨来源的重复 id 不会被各自独立校验漏掉，依赖也可以从 jar 指向手工插件，或反向指向 discovered 插件。

## 常见的第一次写错

1. **错误：把 validate 放在 registry 构造器里，并缓存结果。** 正确：应用对本次完整列表调用静态函数，避免全局状态与重复注册语义。
2. **错误：只检查依赖是否出现，不检查重复 id。** 正确：重复 identity 必须先失败，否则 byId 会覆盖前一个对象。
3. **错误：依赖缺失时跳过该插件。** 正确：缺失是装配错误，应抛异常并命名依赖方与缺失 id。
4. **错误：按 id 字母序生成“稳定结果”。** 正确：只让拓扑关系决定约束，独立项保持调用者相对顺序。
5. **错误：在原地排序调用者列表。** 正确：返回新的不可变列表，让输入与输出可分别检查。
6. **错误：把 dependencies 当成对象注入。** 正确：它只约束顺序；协作者依旧来自构造参数。
7. **错误：认为 validate 会自动启动。** 正确：它不调用任何生命周期方法，应用必须注册返回对象并显式 start。
8. **错误：循环时报“第一个插件有问题”。** 正确：报告所有无法放置的 id，避免把下游插件误判为环本身。

## 怎么确认这一步没造错

运行：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=PluginRegistrationTest,BarezenCoreArchitectureTest
```

本章统一检查点中 `PluginRegistrationTest` 实跑 15 项：Registrable 8、Refusals 4、InputShape 2、PackageDiscipline 1；core 架构测试 21 项。全部通过，没有 failure、error 或 skip。

Registrable 覆盖无依赖、单依赖、链式依赖、多依赖、独立顺序、输入不变与返回不可变等行为。Refusals 覆盖重复 id、缺失依赖和循环。InputShape 检查 null 列表、null entry 与 null descriptor；PackageDiscipline 则固定这个类型是无状态工具，而不是可注册 participant 或 manager。

一个有效测试应当同时检查顺序与对象身份。只比较 id 列表能证明字符串被排序，却不能证明返回的是原插件实例；若实现复制或重建插件，生命周期会发生在另一个对象上。只比较对象身份又可能容忍顺序错误。真实测试同时固定两者，这才与“路由贡献和生命周期使用同一个 reports 实例”的要求一致。

还应手工推演一个失败输入：`[a(dep=b), b(dep=a)]` 第一轮没有 ready，异常必须失败且列出 a、b；`[a(dep=missing)]` 在索引阶段失败，不能进入排序；`[a, a]` 在建立索引时失败，消息应包含两个实现类。把这些输入写成测试，比只测试一条 `[a, b]` 成功链更能证明校验器存在。

## 此刻的代码长什么样

插件集合现在能在启动前回答两个问题：身份是否唯一，依赖顺序是否存在。返回值可以直接用于 orchestrator 注册，应用也能清楚看到这次运行的实际顺序。校验器没有成为新的生命周期引擎，也没有持有对象；它只是一段对输入负责、对输出负责的纯计算。

但“顺序正确”仍不等于“对象协作正确”。auth 可以在 user 之后启动，却可能因为没有拿到密码验证端口而无法登录；user 可能在自己 initialize 中创建 schema，却把 SQL 散落到 auth；openapi 可能收集了 operation，却误以为自己已经能提供 HTTP 文档。下一步加入具体插件，验证构造参数、端口方向和模块边界。
