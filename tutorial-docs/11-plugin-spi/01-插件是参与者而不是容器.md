# 第 11 章第 1 步：插件是参与者，而不是容器

## 这一步要解决什么

前面各章的对象都有清楚归属：handler 由应用构造，router 是冻结值，adapter 拥有 socket，repository 使用显式事务。现在第一次允许一个组件由应用作者之外的开发者提供。它可能是一个权限来源、一个报表端点，也可能在启动时创建自己的表。我们需要一个公共名字告诉 orchestrator“这个对象可以参与生命周期”，但不需要因此建立第二个应用容器。

本步对应提交 `780af74e7190e301d8e3c0556e1fe8aa1e4a96d7`。它新增 `Plugin` 与 `PluginDescriptor`，修改 core 架构测试，并增加 14 项插件契约测试。第一次提交没有插件发现、没有依赖排序，也没有 `barezen-plugins` 模块。这个顺序很重要：先定义“插件能做什么”，再逐步增加校验、具体实现、扩展与发现，后一项才能在前一项边界上回答为什么存在。

`Plugin` 位于 `framework/barezen-core/src/main/java/com/barezen/core/plugin/Plugin.java`，不在具体插件模块。它继承 `LifecycleParticipant`，只增加一个声明方法 `PluginDescriptor descriptor()`。因此一个插件天然已经能 initialize、start、stop、abort；框架不需要重新定义这些阶段，也不需要知道插件内部有多少资源。

这一步真正要拒绝的形状是 `PluginManager`。一个管理器通常包含插件列表、Class 到对象的映射、启动方法和停止方法，接着又会加入 `install`、`uninstall`、依赖解析和上下文。到那时，框架不仅驱动插件，还拥有插件图和一套启动调度。它与 ADR-0015 拒绝的 `Application`、ADR-0006 拒绝的 service locator 是同一个问题换了名字。

## 先想清楚再写

第一种方案是让插件实现一个独立接口，提供 `init`、`start`、`stop`，再由管理器调用。它看似给了插件自由，实际创造两套生命周期。普通参与者在所有 initialize 完成后才 start，插件却可能 init 一个就 start 一个；HTTP adapter 提前开始接受请求时，另一个插件尚未完成注册。两套引擎也会对失败回滚产生不同理解。

第二种方案是给 `Plugin` 一个 `PluginContext`，里面放 config、events、registry 和 `require(Class)`。它减少了构造参数，却让“这个插件需要什么”无法从签名读出。缺失依赖不会在装配时失败，而要等插件某次调用 context 才暴露；插件还可以在运行期临时查找任何对象，依赖图随之失去意义。ADR-0006 已经把这条路封住，本步不能借插件之名重开。

第三种方案是让 core 定义完整插件模型：id、version、description、provides、capabilities、priority。这里每一项都像“以后会用到”，但当前没有消费者。priority 会让两个插件竞争启动顺序，provides 很快需要注册表，capabilities 很快需要查找。最小模型只保留 orchestrator 注册所需的 id，以及校验依赖所需的依赖 id 列表；更多元数据必须等真实调用出现。

`PluginDescriptor` 是 record，而不是可写 bean。`id` 不能 null 或 blank；`dependencies` 不能 null，要用 `List.of()` 明确表示没有依赖；每个依赖也不能 null 或 blank；插件不能声明自己依赖自己。构造器最后用 `List.copyOf(dependencies)` 冻结列表。这样应用在启动前读到的描述符不会因为外部列表随后修改而变化。

这里容易混淆“依赖”与“注入”。`dependencies` 只包含其他插件的字符串 id，用来决定启动先后；它不会创建依赖对象，也不会把某个插件放进字段。Auth 需要 User 实现的 `PasswordVerifier`，仍然必须通过构造参数取得。描述符表达的是参与者顺序，Java 构造器表达的是对象协作，两者不能互相替代。

## 动手

先写一行几乎不像“框架”的接口：

```java
public interface Plugin extends LifecycleParticipant {
  PluginDescriptor descriptor();
}
```

源码见 [Plugin.java:37](../../framework/barezen-core/src/main/java/com/barezen/core/plugin/Plugin.java#L37)。`LifecycleParticipant` 的四个方法都有默认空实现，所以一个无资源的插件只实现 descriptor 就能参与启动；有资源的插件只覆盖自己确实拥有的阶段。`Plugin` 没有默认 descriptor，编译器会迫使每个实现回答“我是谁”。

描述符的构造校验可以直接读 [PluginDescriptor.java:36](../../framework/barezen-core/src/main/java/com/barezen/core/plugin/PluginDescriptor.java#L36)。它返回的是值对象，不包含 Plugin 引用，因此应用可以先读取 id 再注册，而不需要 descriptor 反向持有对象。两个不同插件实例返回相同 id 是否合法，本步尚不判断；下一步的 `PluginRegistration` 会在完整列表上拒绝重复。

最小插件可以这样写：

```java
public final class HealthPlugin implements Plugin {
  @Override
  public PluginDescriptor descriptor() {
    return new PluginDescriptor("health", List.of());
  }
}
```

应用仍然是装配者：

```java
Plugin health = new HealthPlugin();
LifecycleOrchestrator app = LifecycleOrchestrator.builder()
    .register(health.descriptor().id(), health)
    .build();
app.start();
try {
  // 应用自己的工作
} finally {
  app.stop();
}
```

这段代码没有框架替应用 `new HealthPlugin()`，也没有 `PluginManager.start()`。`register` 的 id 是 orchestrator 参与者身份，descriptor 则让插件自己说明该使用哪个身份。应用可以刻意用不同注册 id 做测试，但正式装配应保持两者一致，否则异常中的参与者 id 会难以对应到描述符。

生命周期顺序完全沿用第 3 章：所有插件与非插件参与者先 initialize，再全部 start；停止按注册反序。若某参与者 initialize 失败，已经 initialize 的参与者反序 stop，失败的那个调用 abort；orchestrator 抛 `StartupException` 并进入 `FAILED`。插件不会获得“跳过 rollback”或“自己管理失败”的特殊待遇。

core 架构规则也同步增加。它们禁止 plugin 包变成 DI、事件总线或注册表，并固定最小公共表面。具体生产插件不能放进 core：如果 core 出现 `AuthPlugin`，它就会依赖 security 或 data，而这些模块又可能依赖 core，模块图马上成环。SPI 住在 core 是因为 LifecycleParticipant 与生命周期异常住在 core，不代表业务插件也住在这里。

## 常见的第一次写错

1. **错误：创建 `PluginManager` 保存所有插件并统一 start。** 正确：应用把插件实例注册进现有 `LifecycleOrchestrator`；manager 会复制容器职责并隐藏关闭 owner。
2. **错误：给插件新增 `install`、`uninstall`、`enable`。** 正确：这些词暗示动态安装与第二状态机；当前只有构造、注册、启动、停止。
3. **错误：在 Plugin 接口里放 `config()`、`events()`、`require()`。** 正确：协作者通过构造参数进入，配置在装配处解析，贡献通过组件自己的扩展点表达。
4. **错误：让插件构造器打开端口或创建线程。** 正确：构造只接收依赖；拥有资源的阶段在 initialize/start，关闭在 stop，半初始化失败由 abort 处理。
5. **错误：把 descriptor 做成可修改类。** 正确：record 加不可变依赖列表，身份与依赖在启动前固定。
6. **错误：用 dependencies 自动注入字段。** 正确：字符串依赖只决定顺序；构造参数才决定对象引用。
7. **错误：把 SPI 放进 `barezen-plugins`。** 正确：core 定义 `Plugin`，plugins 提供实现；否则具体模块会拥有核心生命周期词汇。
8. **错误：每个插件内部再保存 STARTING/RUNNING。** 正确：只有 orchestrator 的应用状态；插件资源是否就绪由自身方法实现表达。

## 怎么确认这一步没造错

本步的核心命令是：

```bash
mvn -o -B -ntp -pl framework/barezen-core -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=PluginTest,BarezenCoreArchitectureTest,ClassMajorContractTest
```

本章统一检查点实跑结果中，`PluginTest` 为 14 项：Identity 5、MinimalSurface 3、OneLifecyclePath 4、Ownership 2；core 架构测试 21 项、字节码契约 4 项，均无失败或错误。`ClassMajorContractTest` 检查 151 个 core class，唯一 major 为 61，与 release 17 基线一致。

Identity 测试固定 Plugin 继承 LifecycleParticipant、descriptor 是唯一新增声明方法，以及四个生命周期方法来自父接口。MinimalSurface 检查没有 install/context/lookup 等成员。OneLifecyclePath 不是只断言“调用过 start”，而是观察 initialize 全部完成后才开始 start，并验证失败时进入 orchestrator 的回滚路径。Ownership 则确认插件实例由调用者创建，框架不会在 descriptor 或 register 时偷偷实例化另一个。

运行架构测试时还要故意想象一次违规：若在 `Plugin` 上加 `Services require(...)`，编译可能成功，但 plugin 与 DI 的边界规则应失败；若在 core 主源码加入具体 AuthPlugin，框架依赖具体插件命名空间的规则应失败。只跑happy path 测试无法证明这些边界，架构规则的价值正是在下一次“临时方便”出现时让构建变红。

这个检查点运行在 JDK 24.0.2、Maven 3.9.12。class major 61 证明产物仍以 Java 17 字节码为基线，不等于本轮在 JDK 17 上执行了完整矩阵。JDK 21+ 的虚拟线程能力属于并发与 adapter 的既有决策，插件本身不选择线程。

## 此刻的代码长什么样

此时 core 只有插件身份与描述符，应用可以把插件当普通参与者注册。它已经拥有和所有组件相同的启动、停止与失败语义，但还无法判断多个插件是否重复、依赖是否存在、谁应该先启动。描述符里的 dependencies 暂时只是数据，下一步才让它产生行为。

这也说明“最小插件接口”不是功能完成，而是一条边界。若第一步就加入 manager、discovery 与 registry，后续每个提交都要在已经复杂的基础上打补丁；先固定一个参与者，后续校验器可以保持纯函数，具体插件可以保持构造可见，发现机制也可以只负责搜索。

本步结束时，插件没有容器、没有上下文，也没有自动发现。它只是一个能说明 id 和依赖的 LifecycleParticipant。下一步增加 `PluginRegistration.validate`，不增加任何生命周期方法，而是让应用在启动前验证完整插件集合。
