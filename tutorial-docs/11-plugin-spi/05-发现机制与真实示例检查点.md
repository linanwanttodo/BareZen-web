# 第 11 章第 5 步：发现机制与真实示例检查点

## 这一步要解决什么

到这里，应用已经知道如何手工构造插件、校验依赖和贡献路由。最后一个问题是：一个不需要应用协作对象的插件 jar，能否只通过 classpath 中的声明进入候选集合？如果没有发现，每个可选插件都要改应用源码；如果发现之后自动启动，应用又会失去对本次运行的控制。

本步对应 `f478c1c38be1757e657cfe8e3756ff5c3f6238fe` 与 `517aee7cf856b2ba7cfc1be84eacf0229156575f`。前者在 core.plugin 新增 `PluginDiscovery`、两个测试 fixture 与 services 文件；后者新增 `ReportsPlugin`，让真实示例合并手工与自动发现来源。发现不是新的 registry，而是对 JDK `ServiceLoader` 的一层薄封装。

`PluginDiscovery` 只有两个公开方法：

```java
public static List<Plugin> discover()
public static List<Plugin> discover(ClassLoader loader)
```

无参版本调用 `ServiceLoader.load(Plugin.class)`；指定版本要求 loader 非 null。每次调用重新读取并实例化 provider，返回 fresh immutable list。没有 provider 时返回空列表；`ServiceConfigurationError` 原样传播，不静默跳过坏 jar。

这条规则与“DI 不扫描”并不矛盾。ADR-0014 禁止 DI 使用反射、Class.forName 与 ServiceLoader 构造服务图；插件 SPI 的发现由 ADR-0048 明确修订 ADR-0016 的早期拒绝。允许搜索插件，不等于允许插件从容器查找协作者，也不等于允许 EventBus 或 DI 开始扫描。边界按职责划分，而不是看到一个类名就全局禁止。

## 先想清楚再写

第一种方案是写 `PluginManager.discoverAndStart()`。它把搜索、选择、去重、排序与生命周期放在一个调用里，应用无法在启动前观察候选，也无法拒绝一个不想要的 provider。测试还可能共享 manager 的缓存实例。正确顺序是应用先 discover，得到列表；再与手工列表合并；再 validate；再决定注册与 start。

第二种方案是缓存单例。它能让重复 discover 返回同一对象，却会让一个应用第二次加载得到已经 initialize 的实例，或者让两个 orchestrator 共享同一资源。当前实现刻意每次创建新实例，也不保存 ClassLoader 或 provider 列表。调用者若需要避免重复发现，应在自己的装配中只调用一次，并让完整列表的重复 id 校验发现错误。

第三种方案是让 ServiceLoader 支持任意构造参数。JDK SPI 要求 provider 是 public 类型且有 public no-arg 构造器；AuthPlugin 需要 SessionStore、PasswordVerifier、scheme、lifetime，UserPlugin 需要 UserRepository，它们不能直接用这种机制发现。不能为了发现给它们添加静态全局 DataSource，那是用更大的错误换一点便利。需要协作的插件由应用手工构造，无依赖插件才适合声明。

services 文件是注册事实，不是启动开关。没有 `META-INF/services/com.barezen.core.plugin.Plugin`，类路径上存在一个 Plugin 实现也不会被发现；文件存在但应用从不调用 discover，也不会发生任何事。这种惰性让 provider jar 的加入不会自动改变运行，应用仍明确决定本次使用哪些候选。

## 动手

发现入口位于 [PluginDiscovery.java:63](../../framework/barezen-core/src/main/java/com/barezen/core/plugin/PluginDiscovery.java#L63)：

```java
public static List<Plugin> discover() {
  return collect(ServiceLoader.load(Plugin.class));
}

public static List<Plugin> discover(ClassLoader loader) {
  Objects.requireNonNull(loader,
      "the class loader to search; null would fall back to the context loader, which is the one loader this"
          + " overload exists to override");
  return collect(ServiceLoader.load(Plugin.class, loader));
}

private static List<Plugin> collect(ServiceLoader<Plugin> providers) {
  List<Plugin> discovered = new ArrayList<>();
  for (Plugin plugin : providers) {
    discovered.add(plugin);
  }
  return List.copyOf(discovered);
}
```

collect 只迭代并复制。它不按 id 排序，不选择 preferred，不调用 initialize/start，也不做去重。重复 id 是完整应用集合的问题，因此留给 `PluginRegistration.validate`，而不是让 discover 提前决定“保留第一个”。

core 测试 services 文件声明两个 fixture：`DiscoveredEchoPlugin` 与 `DiscoveredStatusPlugin`。Echo 是无依赖插件，内部记录 initialize/start 阶段，`phases()` 返回不可变快照；只发现它时 phases 为空，只有 orchestrator 驱动后才变化。Status 声明 `List.of("echo")`，所以两个 fixture 合并后为 validate 提供真实依赖边。

examples 的 services 文件只有一行：

```text
com.barezen.examples.plugins.ReportsPlugin
```

真实装配顺序位于 [PluginExample.java:155](../../examples/src/main/java/com/barezen/examples/plugins/PluginExample.java#L155)：先 wiring(dataSource()) 手工创建 auth/user/openapi，再 `PluginDiscovery.discover()` 找到 reports，再 assemble 合并并 validate，再 router 完成装配期贡献，最后 start。discover 只调用一次，返回的 reports 实例同时用于路由贡献和生命周期注册。

```java
List<Plugin> announced = PluginDiscovery.discover();
List<Plugin> plugins = assemble(wiring, announced);
Router routes = router(plugins);
LifecycleOrchestrator app = start(plugins);
```

若应用把 discover 调用两次并合并，fresh 实例会拥有相同 reports id，validate 必须拒绝。这个行为不是“发现不可重复”，而是“同一个应用集合不能有两个身份相同的参与者”。发现 API 本身保持可重复，且不缓存。

UserPlugin.initialize 创建用户表，因此登录必须发生在 app.start() 之后。示例先创建 ada、授予 report:read，再用正确密码签发 session，随后用 Bearer credential authenticate。错误密码返回 empty，不会生成 session。这些步骤把前四章的 data、security、plugin lifecycle 与 route contribution 串成同一条公共 API 路径。

## 常见的第一次写错

1. **错误：discover 后直接 start。** 正确：先与手工列表合并并 validate，再由应用注册和启动。
2. **错误：缓存 discovered 单例。** 正确：每次返回 fresh immutable list；生命周期 owner 是应用，不是 discovery。
3. **错误：认为类路径上的 Plugin 会自动加载。** 正确：必须有 services 声明，且应用显式调用 discover。
4. **错误：吞掉 ServiceConfigurationError。** 正确：让调用者看到坏 provider 或 services 文件，避免静默缺插件。
5. **错误：把 null ClassLoader 当默认值。** 正确：显式拒绝；需要默认时调用无参重载。
6. **错误：要求 AuthPlugin/UserPlugin 支持无参发现。** 正确：它们需要协作者，由应用手工构造。
7. **错误：在 DI 或 EventBus 中复用 ServiceLoader。** 正确：插件发现是独立 SPI 决策，不扩散到其他边界。
8. **错误：路由与生命周期使用两个 reports 实例。** 正确：对同一 validated 列表完成 RouteContributions.of 与 orchestrator 注册。
9. **错误：宣称示例 main 监听真实端口。** 正确：main 只验证内存路由匹配；真实 socket 行为由 PluginExampleTest 覆盖。

## 怎么确认这一步没造错

本章统一检查点命令如下，实际执行成功：

```bash
mvn -o -B -ntp \
  -pl framework/barezen-core,framework/barezen-web,framework/barezen-plugins,examples -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=PluginTest,PluginRegistrationTest,PluginDiscoveryTest,BarezenCoreArchitectureTest,ClassMajorContractTest,RouteContributorTest,BarezenWebArchitectureTest,AuthPluginTest,UserPluginTest,OpenApiPluginTest,PluginCompositionTest,RouteContributionsTest,BarezenPluginsArchitectureTest,PluginExampleTest'
```

结果 `BUILD SUCCESS`。选定测试总数为 202：core 65、web 43、http-jdk 4、security 4、content 4、data 4、plugins 65、testkit 4、examples 9。这里包含依赖模块因 `ClassMajorContractTest` 选择器执行的字节码契约，不应把它写成“202 项全是新增插件测试”。其中 PluginDiscoveryTest 11、PluginExampleTest 5。

字节码检查分别覆盖 core 151、web 92、plugins 82 等 class，全部唯一 major 61。这个结果证明 release 17 字节码基线，不证明本轮在 JDK 17 运行；实际环境是 JDK 24.0.2 与 Maven 3.9.12。

真实 main 使用已构建模块与 H2、SLF4J API 运行：

```bash
M2="$HOME/.m2/repository"
CP="$PWD/examples/target/classes:$PWD/framework/barezen-core/target/classes:$PWD/framework/barezen-web/target/classes:$PWD/framework/barezen-security/target/classes:$PWD/framework/barezen-data/target/classes:$PWD/framework/barezen-plugins/target/classes:$M2/org/slf4j/slf4j-api/2.0.16/slf4j-api-2.0.16.jar:$M2/com/h2database/h2/2.2.224/h2-2.2.224.jar"
java -cp "$CP" com.barezen.examples.plugins.PluginExample
```

实际输出：

```text
announced on the classpath -> [reports]
assembled order -> [user, openapi, auth, reports]
startup order -> [user, openapi, auth, reports]
route table -> Router[GET /health, GET /reports/status]

```

SLF4J 输出 No providers 与 NOP logger 警告，是因为 classpath 没有日志绑定；core 使用 no-op logger，示例仍可运行。这不是插件失败，也不应为了消除警告修改源码或添加产品依赖。

`PluginExampleTest` 的 5 项测试另行覆盖真实 HTTP socket：使用 ephemeral port 启动 JDK adapter，GET `/reports/status` 与 GET `/health` 返回 200，POST `/reports/status` 返回 405。main 本身没有启动 socket，不能用它的输出宣称端到端网络验收；测试才是网络证据。

本轮没有运行整仓库 clean verify，也没有宣称覆盖率门禁通过。选定的 202 项测试、真实 main 与示例 socket 测试是本章证据范围，不能扩展成所有数据库、JDK、浏览器或部署环境的承诺。HTTP 模块的方法 token 测试属于另一条证据链，本章命令不选择它。

发现测试本身也应限定范围。`PluginDiscoveryTest` 在 exploded test classpath 与临时目录 `URLClassLoader` 上验证 provider 顺序、fresh 实例、不可变列表、空 loader、坏 provider 与 null loader；它没有把插件打成 jar 后验证打包发现，也没有测试 classloader 关闭、卸载、重载或 child-first 类型身份。provider 构造器与静态初始化会在迭代时执行，但测试没有把其副作用隔离作为产品保证。部分 provider 失败时整次发现直接中止，不存在“跳过坏插件继续启动”的恢复策略；这些都不能从“ServiceLoader 能用”推导出来。

## 此刻的代码长什么样

插件体系已经闭合：core 定义 SPI、描述符、纯校验器与发现；plugins 提供具体实现与路由收窄；web 声明路由扩展点；应用合并来源、冻结路由、注册生命周期并启动 adapter。发现结果不再绕过任何一步，手工插件与自动插件在同一个 validate 输入中接受相同规则。

最终示例的依赖顺序是 `[user, openapi, auth, reports]`，不是源码列表 `[auth, user, openapi, reports]`。这个变化直接证明 descriptor 与 validate 正在发挥作用。路由表同时包含应用 `/health` 与 reports 贡献的 `/reports/status`，证明 RouteContributions 筛选的是已经汇合的真实实例。登录成功与坏密码无 session 则证明 auth/user 通过端口协作，而不是直接引用 sibling。

仍然存在的边界也要保留：发现要求 public no-arg，协作插件必须手工装配；没有并发迁移或插件热装载；没有 down/卸载；贡献路由不自动获得安全；OpenApiPlugin 仍只收集 metadata；ServiceLoader 发现不等于框架替应用选择。每一条都不是“以后补文档”的遗漏，而是当前公共契约的一部分。

下一章将把 openapi metadata 显式组装为可测试的文档，并引入 testkit，验证真实 HTTP 行为。插件系统提供组合边界，OpenAPI 与 testkit 消费这些边界，不会再回头把 PluginContext 或通用 registry 加回来。
