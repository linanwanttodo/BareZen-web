# 第 11 章第 4 步：路由扩展点与装配期贡献

## 这一步要解决什么

插件已经能参与生命周期，也能声明依赖，但还不能为应用增加 URL。若让应用在知道每个插件后手写 `if (plugin instanceof ReportsPlugin) routes.route(...)`，应用就绑定了具体实现，每加一个插件都要改装配代码。若让 Router 反向依赖 core 的 Plugin，web 契约就会为了插件概念依赖生命周期核心，模块方向随之反转。

本步对应三个提交。`d7c7e831b5805afe6bf41c6420ff2dce8701fa83` 在 web 新增 `RouteContributor` 并扩展 Router.Builder；`1b52c537df2f9d69f439f72b0a276ed064e7889b` 在 plugins 新增 `RouteContributions`，把“同时认识 Plugin 与 RouteContributor”的代码放在正确模块；`8978333e31e3ede80b68bb4f7ba75ecb9110b45f` 让真实示例的 ReportsPlugin 通过该扩展点贡献路由。

核心决定是：**扩展点由拥有资源的组件声明。** Router 属于 web，所以 web 声明 `void contributeRoutes(Router.Builder routes)`。core 只声明 Plugin，不知道 HTTP；plugins 可以同时依赖 core 与 web，所以它负责从插件集合中筛选贡献者。应用负责按顺序调用 contributing，并在 build 后把冻结 Router 交给 adapter。

这与早期 ADR-0019 的描述不同。ADR-0019 曾展示插件在 initialize 中向 Router.Builder 注册路由，再由应用在 start 后 build。当前实现把贡献明确放在装配期：调用 `Router.Builder.contributing(...)` 时立即执行贡献，应用随后 `build()` 冻结表，再启动插件与 adapter。历史 ADR 用于理解决策，不能覆盖当前源码。

## 先想清楚再写

第一种方案是在 core 定义通用 `ExtensionPoint<T>` 与 `ExtensionRegistry`。它看似可复用，实际没有消费者：路由贡献需要 Router.Builder，事件贡献需要 EventBus，未来每个扩展点输入都不同。通用 registry 还需要查找、排序和生命周期，很快就会长成第二个容器。ADR-0047 选择为一个真实需求声明一个窄接口。

第二种方案是让插件在 initialize 中动态注册路由。它的问题不是“注册太晚”，而是应用可能在 initialize 之前已经把 Router 交给 adapter，或某插件 initialize 失败后仍留下部分路由。冻结表的语义也变得模糊：究竟是 build 时的状态，还是 start 后的状态？装配期贡献让路由在启动前完整决定，生命周期只负责运行资源。

第三种方案是让 Router 自动扫描实现了 RouteContributor 的插件。这样 Router 必须依赖 core Plugin 或某种发现机制，web 的零 compile 依赖与模块方向都会被破坏。更小的方案是应用显式传入贡献者列表，Router 只负责按迭代顺序调用，不关心列表来自手工构造、发现还是其他来源。

`RouteContributor` 的目标是 `Router.Builder`，不是 `Router`，也不是 `List<Route>`。builder 可以在冻结前继续注册；Router 没有公开注册或卸载方法。贡献者只表达“我要添加哪些 method + pattern + handler”，不获得路由表所有权，也不能替换已有路由。

安全边界也要提前说清。贡献一条 GET 路由不会自动应用 Authentication 或 Authorization。Router 的职责是匹配，security middleware 仍由应用显式包装 Handler。插件若需要受保护端点，应在设计上提供可装配的安全 handler，或由应用在注册时明确配置；不能把“插件贡献了路由”解释为“插件自动受到框架保护”。

## 动手

web 的接口只有一行，位于 [RouteContributor.java:43](../../framework/barezen-web/src/main/java/com/barezen/web/RouteContributor.java#L43)：

```java
@FunctionalInterface
public interface RouteContributor {
  void contributeRoutes(Router.Builder routes);
}
```

它是函数式接口，因为一次贡献就是对 builder 的一组操作。它不继承 Plugin，不继承 LifecycleParticipant，也没有 `id`。一个对象可以同时实现两个接口，但两个职责保持独立：Plugin 说明自己是谁，RouteContributor 说明自己贡献什么路由。

Router.Builder 的入口位于 [Router.java:361](../../framework/barezen-web/src/main/java/com/barezen/web/Router.java#L361)：

```java
public Builder contributing(Iterable<? extends RouteContributor> contributors) {
  Objects.requireNonNull(contributors,
      "the route contributors; a null list is indistinguishable from a caller that meant to contribute nothing,"
          + " and the difference is a route table that quietly lacks a plugin's endpoints");
  for (RouteContributor contributor : contributors) {
    Objects.requireNonNull(contributor,
        "a null route contributor; every contributor is asked in turn, so a null element would fail halfway"
            + " through a table that already holds the routes registered before it");
    contributor.contributeRoutes(this);
  }
  return this;
}

public Router build() {
  return new Router(List.copyOf(registrations));
}
```

调用 contributing 时，贡献按迭代顺序立即执行；null 列表与 null 元素都拒绝。build 使用 `List.copyOf` 冻结注册快照，之后继续使用 builder 注册路由不会改变已构建 Router。贡献者不应在贡献中启动线程、打开 socket 或执行数据库迁移，因为此时应用仍在装配，失败应作为装配错误出现。

路由冲突规则沿用 Router：身份是 `HttpMethod + 规范化 shape`。`GET /users/{id}` 与 `GET /users/{userId}` 形状相同，即使参数名不同也会冲突；不同方法可以共享同一路径。应用路由与贡献路由冲突、两个贡献者互相冲突，都抛 `IllegalArgumentException`，没有 last-writer-wins。

匹配仍按最字面优先：`/users/new` 胜过 `/users/{id}`。贡献者不能用 priority 改变这条规则，也不能注册一个同名 registry 自己决定覆盖。路由表在构建后只读，并发请求不需要与注册竞争，因为注册阶段已经结束。

plugins 的收窄函数位于 [RouteContributions.java:46](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/routes/RouteContributions.java#L46)：

```java
public static List<RouteContributor> of(Iterable<? extends Plugin> plugins) {
  Objects.requireNonNull(plugins,
      "the plugin list; null is not an empty plugin set, and a caller that meant to pass no plugins passes List.of()");
  List<RouteContributor> contributors = new ArrayList<>();
  for (Plugin plugin : plugins) {
    Objects.requireNonNull(plugin,
        "a null plugin in the list; skipping it would silently drop whatever it was meant to contribute, and"
            + " failing says which assembly is wrong");
    if (plugin instanceof RouteContributor contributor) {
      contributors.add(contributor);
    }
  }
  return List.copyOf(contributors);
}
```

这段代码拒绝 null 列表与 null plugin，非贡献者跳过，贡献者保持输入顺序，返回不可变快照。它是无状态工具，没有 install/start/stop。允许同时持有 Plugin 与 RouteContributor 的位置被限制在 plugins.routes，应用不需要自己写一串 instanceof。

ReportsPlugin 是一个最小真实贡献者，见 [ReportsPlugin.java:28](../../examples/src/main/java/com/barezen/examples/plugins/ReportsPlugin.java#L28)：

```java
public class ReportsPlugin implements Plugin, RouteContributor {
  @Override
  public PluginDescriptor descriptor() {
    return new PluginDescriptor("reports", List.of("user"));
  }

  @Override
  public void contributeRoutes(Router.Builder routes) {
    routes.route(HttpMethod.GET, "/reports/status", (request, ignored) ->
        new Response(200, Headers.of("Content-Type", "text/plain"),
            "reports ready".getBytes()));
  }
}
```

它声明依赖 user，但当前 handler 并不查询用户表；这个依赖表达的是端点领域归属与未来协作顺序，不是隐式字段注入。它拥有公开 no-arg 构造器，为下一步 ServiceLoader 发现做好准备。

应用装配见 [PluginExample.java:132](../../examples/src/main/java/com/barezen/examples/plugins/PluginExample.java#L132)：先注册 `/health`，再 `contributing(RouteContributions.of(plugins))`，最后 build。这样 ReportsPlugin 的同一个实例先在装配期交出 handler，随后在 start 阶段作为 Plugin 被 orchestrator 驱动。若应用重新 new 一个 ReportsPlugin 来贡献路由，就会出现“路由属于一个对象、生命周期属于另一个对象”的分裂。

## 常见的第一次写错

1. **错误：在 core 定义通用 RouteRegistry 或 ExtensionRegistry。** 正确：web 声明 RouteContributor，plugins 只做窄化，应用负责汇合。
2. **错误：让 Router  import core Plugin。** 正确：Router 只接收 RouteContributor，保持 web 的编译边界。
3. **错误：在 start 后继续修改运行中的 Router。** 正确：装配期贡献，build 冻结，再交给 adapter。
4. **错误：把 contributeRoutes 当成新生命周期阶段。** 正确：它是装配操作，不由 orchestrator 调用。
5. **错误：贡献重复路由时覆盖旧 handler。** 正确：按 method + shape 拒绝冲突并抛 IllegalArgumentException。
6. **错误：认为贡献路由自动获得 security。** 正确：认证与授权仍需显式包装或配置。
7. **错误：在贡献中打开端口或启动线程。** 正确：贡献只注册路由，资源生命周期仍由 adapter/participant 拥有。
8. **错误：沿用旧 Javadoc 写 `RouteContributions.apply(...)`。** 正确：当前真实 API 是 `RouteContributions.of(...)`。
9. **错误：为路由和生命周期创建两个 reports 实例。** 正确：对同一 validated 列表完成收窄和注册。

## 怎么确认这一步没造错

运行 web 与 plugins 的扩展点测试：

```bash
mvn -o -B -ntp -pl framework/barezen-web,framework/barezen-plugins -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=RouteContributorTest,BarezenWebArchitectureTest,RouteContributionsTest,ClassMajorContractTest
```

本章统一检查点实跑：RouteContributorTest 16、BarezenWebArchitectureTest 23、RouteContributionsTest 12；web 与 plugins 的 ClassMajorContractTest 各 4，全部通过。web 检查 92 个 class、plugins 检查 82 个 class，唯一 major 均为 61。

RouteContributorTest 覆盖函数式形状、builder 目标、执行顺序、null 拒绝、重复形状冲突与冻结快照。RouteContributionsTest 覆盖只收窄贡献者、保持顺序、拒绝 null、无状态，以及 shipped auth/user/openapi 都不是 RouteContributor。ReportsPlugin 在示例中才是同时实现 Plugin 与 RouteContributor 的类。

测试必须检查构建前后两个时间点：build 之后向 builder 添加路由，旧 Router 不应变化；新 build 才应看到新路由。只断言 `routes.toString()` 包含路径不够，因为它不能证明表已冻结。冲突测试还应覆盖参数名不同但形状相同的两条模式，避免实现退回字符串比较。

当前真实示例在装配期发生路由冲突，因此错误是 IllegalArgumentException，不是 ADR-0019 历史场景中的 StartupException。这个区别要写准确：如果开发者今天仍把贡献放进 initialize，那是另一套自行设计的时序，不再是本框架示例与扩展点契约所保证的路径。

## 此刻的代码长什么样

web 现在拥有一个具体扩展点，但仍然不知道 Plugin；plugins 知道 SPI 与 web，可以把 validated 列表中的贡献者筛选出来；应用把应用路由与插件路由放进同一个 builder，并在启动前冻结。Router 依然只是 method + path 到 handler 的表，不拥有 socket，也不执行 handler。

AuthPlugin、UserPlugin、OpenApiPlugin 都不是 RouteContributor。它们提供认证、授权、密码验证和 metadata，不自动拥有 URL。ReportsPlugin 是唯一在示例中贡献路由的插件。这个差异说明“插件”不是一个万能接口，每个组件只在拥有它的扩展点上发表能力。

下一步增加发现机制。ReportsPlugin 已经满足 public 类型与 public no-arg 构造器，只要 services 文件声明它，PluginDiscovery 就能创建它。应用仍会把手动构造的 auth/user/openapi 与发现的 reports 合并后校验，不会让发现结果直接绕过本章的装配顺序。
