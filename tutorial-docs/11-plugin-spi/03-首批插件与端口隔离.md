# 第 11 章第 3 步：首批插件与端口隔离

## 这一步要解决什么

SPI 与校验器只能处理抽象对象。现在要第一次写出真实插件，并证明它们可以在同一个应用中协作，而不互相依赖具体实现。提交 `68e0c672b6f7610b4840d7f7a1353e6c14655285` 新增 `framework/barezen-plugins` 模块，发布七个生产类型：`AuthPlugin`、`PasswordVerifier`、`UserPlugin`、`UserRepository`、`UserAccount`、`OpenApiPlugin` 与 `OperationMetadata`。

这些插件组合了前三章已经存在的边界：security 提供 Authentication、Authorization、SessionStore、PasswordHasher 等端口；data 提供 Database 与 Transaction；web 提供 HttpMethod 等 HTTP 值。插件模块不是另一套安全或持久化框架，它用显式构造参数把既有能力装成参与者。

最重要的结构问题是 auth 与 user 的关系。auth 需要验证用户名和密码，user 恰好能做这件事。最省事的写法是 `new AuthPlugin(..., UserPlugin user)`，但这样 auth 就绑定了 sibling 的具体类，user 的内部 repository、schema 和启动方式也进入 auth 的编译依赖。正确做法是在 auth 包声明窄端口 `PasswordVerifier`，让 UserPlugin 实现它，应用把 user 传给 auth。

本步还要限制 OpenAPI 插件的野心。当前 `OpenApiPlugin` 只收集 operation metadata：方法、路径、summary、tags。它不读取 Router，不自己生成 JSON，也不贡献文档路由。第 12 章会把 metadata 组装为 ApiDocument；本章必须保留这个边界，否则很容易把“有一个 openapi 插件”误写成“框架自动拥有完整 API 文档”。

## 先想清楚再写

第一种方案是让每个插件自己读取 Configuration 或 System.getProperty，创建 DataSource、SessionStore 与密码哈希器。这样插件的无参构造器很方便，却发现机制也很方便，代价是应用无法在测试中替换依赖，插件之间会共享隐藏全局状态。ADR-0015 已把配置解析放在应用装配处，插件只能接收已经决定的值。

第二种方案是让 user 把整个 Database 或 Connection 交给 auth。auth 随后可以直接执行 SQL，甚至自行 commit，这就越过数据边界并重复事务管理。更窄的协作是：auth 只问 `PasswordVerifier.verify(username, password)`，user 在内部使用 repository 与 PasswordHashing 端口完成密码检查。auth 不需要知道表名、连接或 schema。

第三种方案是让 auth 在每次 bearer token 请求中重新验证密码。这混淆了两个时间点：登录时验证密码并创建 session；请求时只验证 session token 是否有效。重新验证会增加密码哈希成本，还会让已创建 session 的生命周期失去意义。正确 authenticate 只查 SessionStore，查不到就 anonymous。

用户枚举也需要认真处理。`issueSession` 在 username/password 为 null、密码验证失败时都返回 `Optional.empty()`，不区分“用户不存在”和“密码错误”。当前 `UserRepository` 还为未知用户准备虚拟哈希并执行验证，避免完全跳过 PBKDF2；但测试只证明验证被调用，没有恒定时间统计。数据库查询、历史哈希次数与调度噪声仍可能形成 timing side channel，因此不能把统一返回值夸大为完全消除枚举。

Schema 创建应放在 UserPlugin.initialize，而不是插件构造器。构造器只接收 repository，不接触数据库；initialize 在 orchestrator 的全局 initialize 阶段执行，用一个 transaction 创建两张可重启幂等表。这样应用在 start 前失败时，orchestrator 能按既有 abort/rollback 规则处理；测试也能明确观察到“start 之前用户表尚不存在”。

## 动手

模块 POM 的 compile 依赖是 core、web、security、data，H2、JUnit、AssertJ、ArchUnit 都是 test scope。这个方向意味着具体插件知道自己使用哪些框架端口，框架却不知道 auth/user/openapi。ArchUnit 规则同时禁止 sibling 插件引用对方具体 Plugin 实现，因此 `AuthPlugin` 不能 import `UserPlugin`。

auth 的构造参数位于 [AuthPlugin.java:54](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/auth/AuthPlugin.java#L54)：

```java
public AuthPlugin(
    SessionStore sessions, PasswordVerifier passwords, String scheme, Duration lifetime)
```

scheme 不能 blank，lifetime 必须为正。descriptor 固定为 `new PluginDescriptor("auth", List.of("user"))`，所以校验器知道 user 必须先启动；但真正提供密码验证能力的是构造参数，而不是 descriptor 的某种隐式注入。

```java
@Override
public AuthenticationResult authenticate(Credential credential) {
  if (credential == null) {
    return AuthenticationResult.anonymous();
  }
  if (!scheme.equalsIgnoreCase(credential.scheme())) {
    return AuthenticationResult.failure("authentication scheme rejected");
  }
  return sessions.lookup(credential.value())
      .<AuthenticationResult>map(
          session -> AuthenticationResult.authenticated(session.principal()))
      .orElseGet(() -> AuthenticationResult.failure("session rejected"));
}
```

源码见 [AuthPlugin.java:79](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/auth/AuthPlugin.java#L79)。null credential 返回 anonymous；scheme 不匹配、未知或过期 token 返回 failure，不会伪造 Principal。`issueSession` 则先调用 passwords.verify，验证成功才创建 session；失败返回 empty。`toString()` 只输出 scheme，不输出 token、密码或 session。中间件对 anonymous 与 failure 都返回固定 401，因此三态诊断不会改变 wire 契约。

user 同时实现 `Authorization` 与 auth 包的 `PasswordVerifier`：

```java
public final class UserPlugin implements Plugin, Authorization, PasswordVerifier {
  private final UserRepository users;

  public UserPlugin(UserRepository users) {
    this.users = Objects.requireNonNull(users, "users");
  }

  @Override
  public void initialize() {
    users.database().transaction(tx -> {
      users.createSchema(tx);
      return null;
    });
  }
}
```

源码见 [UserPlugin.java:34](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/user/UserPlugin.java#L34)。descriptor 是 `user`，无依赖。`authorize` 对 `Permission.ANY` 直接 ALLOW，不查数据库；命名权限通过 `permissionsOf` 判断，命中 ALLOW，否则 DENY。未知 principal 对命名权限也是 DENY。`verify` 委托 repository，auth 不接触 repository。

SQL 集中在 [UserRepository.java:25](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/user/UserRepository.java#L25)。构造器接收 `Database` 与内部端口 `PasswordHashing`；后者只有 `hash` 与 `verify` 两个方法。`create`、`find`、`verifyPassword`、`grant`、`permissionsOf` 全部使用参数化 SQL。schema 为 `barezen_user` 与 `barezen_user_permission`，后者以 username 和 permission 为联合主键；CREATE 使用 `IF NOT EXISTS`，使重启不因表已存在而失败。

这套 SQL 是 H2 示例，不是已经证明的数据库无关账户模型。`grant` 使用 H2 的 `MERGE ... KEY` 语法；权限表没有指向用户表的外键，因此可以给不存在的用户名授权；`permissionsOf` 的有序查询结果经 `Set.copyOf` 后不承诺迭代顺序，现有单权限测试也没有证明多权限顺序。用户删除、停用、改名、改密、撤销权限、并发初始化和用户 schema 版本迁移都不在 `UserPlugin` 当前能力中。应用不能仅因参数化 SQL 成立，就把这些产品级账户语义当作已经具备。

`UserAccount` 是 username/passwordHash 的值对象，username 不能 null 或 blank，`toString()` 只打印 username，不打印 hash。`database()` 与 `createSchema(Transaction)` 是 package-private，让 UserPlugin 能完成初始化，却不把 Database 或建表能力公开给 auth 与普通调用者。

应用仍需把 security 的 final `PasswordHasher.standard()` 适配到 user 的 `PasswordHashing`。Java 没有 structural typing，不能仅因方法签名相同就自动赋值，所以 `PluginExample.hashing()` 写了一个四行委托。这个适配属于应用装配，不属于 auth/user 任何一方，也正是显式组合应有的样子。

OpenApiPlugin 的公共入口位于 [OpenApiPlugin.java:51](../../framework/barezen-plugins/src/main/java/com/barezen/plugins/openapi/OpenApiPlugin.java#L51)。`add(method, path, summary, tags)` 与三参数重载收集 operation；同一个 method + path 重复添加会拒绝，并指出两个 summary。内部使用有序 map，`operations()` 返回不可变快照，按 path、再按 method text 排序；`size` 与 `clear` 是明确的 collector 操作。

这里必须写清当前能力：OpenApiPlugin 没有读取 Router，没有提供 route enumeration，没有生成或提供 OpenAPI JSON。同包已经存在 `ApiDocument`、`OpenApiJson`、`Schema` 等后续模型与生成器类型，但它们不是这个 collector 自动调用的结果。第 12 章会解释显式文档组装。

## 常见的第一次写错

1. **错误：AuthPlugin 构造参数直接写 UserPlugin。** 正确：依赖 auth 包的 PasswordVerifier，由 UserPlugin 实现；sibling 只通过端口认识。
2. **错误：把 Database 传给 auth。** 正确：auth 只接受 SessionStore、PasswordVerifier、scheme、lifetime。
3. **错误：authenticate 每次重新 verify password。** 正确：登录时验证密码，请求时查 session；两者成本与生命周期不同。
4. **错误：未知用户与错误密码返回不同 Optional 或异常，或未知用户直接跳过哈希。** 正确：都返回 empty，未知用户也验证虚拟哈希；同时不要宣称已经完全消除 timing 差异。
5. **错误：在 UserPlugin 构造器建表。** 正确：在 initialize 的一个 transaction 中创建 restart-idempotent schema。
6. **错误：把 SQL 放进 security 或 auth。** 正确：SQL 留在 UserRepository，安全包只拥有消费端口。
7. **错误：把 UserAccount.toString 写成默认 record 输出。** 正确：覆盖为只打印 username，避免 passwordHash 进入日志。
8. **错误：把 OpenApiPlugin 描述成文档服务器。** 正确：当前只收集 metadata，文档生成属于第 12 章。
9. **错误：给插件加静态 DataSource 或 SessionStore。** 正确：实例字段加构造参数；架构规则禁止静态可变状态与环境读取。

## 怎么确认这一步没造错

运行首批插件的行为、组合与架构测试：

```bash
mvn -o -B -ntp -pl framework/barezen-plugins -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=AuthPluginTest,UserPluginTest,OpenApiPluginTest,PluginCompositionTest,BarezenPluginsArchitectureTest,ClassMajorContractTest
```

本章统一检查点实跑：AuthPluginTest 8、UserPluginTest 13、OpenApiPluginTest 11、PluginCompositionTest 10、BarezenPluginsArchitectureTest 7、ClassMajorContractTest 4，共 53 项，全部通过。字节码检查覆盖 82 个 plugins class，唯一 major 为 61。

Auth 测试覆盖构造参数、session 签发、scheme 大小写、无效 scheme、未知/过期/撤销 token 的 Failure、null credential 的 Anonymous 与摘要不泄密。User 测试用真实 H2 验证表可重复创建、用户查找、密码错误、grant 与 permission 查询；AuthorizationPort 覆盖 ANY 与命名权限。CompositionTest 则把 auth/user/openapi 放进同一集合，验证依赖顺序、一个 orchestrator 和实例隔离。

OpenApiPluginTest 的 11 项集中在 collector：operation 值、重复 method + path 拒绝、快照不可变、清空与排序。它没有测试“生成完整文档”，因为该能力不属于这个类。Architecture 规则禁止插件引用 sibling 具体实现、JDBC 驱动、adapter、`com.sun.net.httpserver`、ThreadLocal、系统属性、环境变量和静态可变状态；唯一 JDBC 例外是 `java.sql.ResultSet`。

## 此刻的代码长什么样

应用现在可以显式构造 `Database`、`UserRepository`、`UserPlugin`、`SessionStore`、`AuthPlugin` 与 `OpenApiPlugin`，把它们交给 validate，再注册进 orchestrator。auth 与 user 通过 PasswordVerifier 协作，SQL 与 schema 留在 user 侧，密码哈希实现通过应用适配到内部端口。

这些插件还没有贡献 HTTP 路由。auth 是 Authentication 能力，不是自动拦截所有请求的 filter；user 是 Authorization 与密码验证能力，不会自动保护路径；openapi 是 metadata collector，不会自动提供 `/openapi.json`。谁把能力应用到哪条路由，必须在路由与 middleware 装配中明确决定。

下一步让真正拥有路由的 web 模块声明扩展点。插件若想贡献路由，只实现 RouteContributor；应用在 build 前统一收集并冻结。这样既能扩展 URL 空间，又不需要把 Router、service locator 或第二个生命周期塞进 PluginContext。
