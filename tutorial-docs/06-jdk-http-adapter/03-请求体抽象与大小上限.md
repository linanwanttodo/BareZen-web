# 03 请求体抽象与大小上限

## 这一步要解决什么

初版 bridge 会把请求体完整读进 `byte[]`，响应也使用完整 `byte[]`。这个选择让 Handler 简单，却没有回答一个生产边界：如果客户端声明巨大长度、持续发送 chunked 数据或永不结束，服务器要读到哪里？完整内存模型不自动等于无界读取。本步要保留模型，同时在进入 Request 之前设置一个所有构造路径都生效的上限。

请求体与响应体在这里不应一起抽象。响应是否需要 streaming，取决于真实消费者、线程和取消所有权，以及 HEAD framing；请求体当前已经需要“有界读入内存”，因为 Handler 的 `byte[] body()` 不接受流。若为了请求限制先引入一个通用 Body 类型，Handler 就要决定何时关闭流、异常何时发生、body 能读几次，公共契约会显著膨胀。项目因此只增加 `BodyLimit` 这个包内值对象，Response 三字段保持不变。

上限必须覆盖三条路径：默认两参数构造、借用 ThreadProvider 的构造和读取 Configuration 的构造。不能只有配置构造有限制，而测试或示例常用的默认构造无限。`BodyLimit.unconfigured()` 提供统一的 1 MiB 默认值；Configuration 中的值在 adapter 构造时解析一次，负数或错误类型立即失败，0 则合法地表示“任何非空 body 都不接受”。

本步还要解决一个时序问题：发现超限后，能否马上关闭 exchange？剩余 body 可能仍在 socket 上，JDK 关闭时会尝试 drain；若 surplus 无法读完，drain 可能阻塞，413 就写不出去。项目选择先停止读取、先发送 413，再让 dispatcher 的 finally 关闭 exchange，把 drain 放到答案已经提交之后。

## 为什么这样设计

检测“超过 limit”不能只读取 limit 个字节后看流是否结束，因为恰好等于 limit 的合法 body 也会在读取满 limit 后等待下一次 read。若此时直接判超限，恰好相等的请求会被错误拒绝。算法把容量设为 limit+1，读满 limit+1 才确定超限；如果遇到 EOF 且 size 不超过 limit，就返回完整 body。这个多读一个字节的空间，是区分“等于”和“大于”的必要条件。

自动增长也不能按配置上限预分配。默认 1 MiB 已不算大，但用户可以配置很大的值；每个并发请求预分配上限会迅速放大内存。实现从最多 8192 字节开始，按实际读取量增长，最大不超过 limit+1。增长后，下一次 read 的 offset 是已经保存的 size，而可用 room 同时受两个边界约束：逻辑容量减去 size，以及当前 buffer 长度减去 size。

`184c774` 修复的正是这个细节。错误实现把 `buf.length - size` 错当成容量，或把 `buf.length` 当成 read length，可能在 offset 非零时越过实际数组。只测试小于 8192 的 body 不会触发增长，因而必须加入跨第一 buffer 的请求。测试写在大 body 上不是“额外覆盖”，而是保护算法真正改变状态的位置。

已知 Content-Length 是另一条快速路径。若字段只有一个值、可解析且大于 limit，就没有必要读取任何 body；直接抛 Exceeded 可以避免等待剩余数据，也避免分配 buffer。若长度重复、非法或不存在，bridge 不把它当可信声明，而由实际读取判断。chunked 没有已知总长度，因此读到第一个越界字节才停止；surplus 不会被主动吸干。

`Exceeded` 必须是 unchecked，不能继承 IOException。dispatcher 的读取 catch 顺序是 Exceeded、IllegalArgumentException、IOException；如果 Exceeded 是 IOException 子类，它会被折叠成 400，客户端会误以为请求不完整，而不是内容过大。413 正文固定为 `Content Too Large`，长度 17，不包含 path 或具体 limit；这些信息对诊断有用，但不该被反射给未认证客户端。

默认 0 也不是“无限”。它表示上限为零，已知正长度会预拒绝，未知长度读取第一个字节即越界，合法空 body 仍可到达 Handler。负数则没有有意义的读取语义，构造时就应拒绝。错误配置在构造时失败还确保没有端口被绑定，应用可以在统一装配阶段报告是哪一项配置不可用。

## 怎么验证

运行请求体限制测试：

```bash
mvn -o -B -ntp -pl framework/barezen-http-jdk -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=JdkRequestBodyLimitTest
```

当前为 28 项：KnownLength 9、UnknownLength 5、ParserOwnedShapes 4、ConnectionOrder 2、Resolution 8。注意 ADR 与源码应以当前测试为准，不能凭旧数量猜。KnownLength 覆盖恰好相等、多一个字节、巨大声明、HEAD、截断 body；UnknownLength 覆盖 chunked 增长与停止读取；Resolution 覆盖配置值、默认值、0、负数、类型错误和 null Configuration。

连接顺序测试用 keep-alive socket 连续发送两次请求，并按第一响应的 Content-Length 精确读取一帧。可 drain 的 surplus 让 JDK 在关闭后继续处理下一请求；不可 drain 的 surplus 则关闭连接。这个测试不是要求所有 413 都强制 `Connection: close`，而是固定真实边界：能否保持连接取决于 JDK 是否能完成 drain，adapter 不承诺一个它无法保证的结果。

413 的 HEAD 断言同样重要。HEAD 请求超限时，状态是 413，Content-Length 是 17，但 body 字节为 0。若错误路径绕过普通 bridge 而直接写 JDK 默认页，这个测试会失败；若把 413 当无 body 状态，也会出现错误长度。413 是普通可携带正文的错误，只是请求方法 HEAD 抑制发送。

可以做三组反向验证。把容量从 limit+1 改成 limit，恰好相等的测试应变红；把 buffer 增长关闭，跨 8192 的 body 测试应暴露偏移或截断；把 declared length 的提前检查删除，巨大声明测试应失去“未读取”证据。若只修改生产代码而没有对应测试变红，说明测试可能只覆盖了小 body 或只检查状态码，没有检查读取边界。

## 常见错误与失败后果

把默认上限设成 `Long.MAX_VALUE` 或 0 表示无限，都会破坏“未配置也有界”的规则。前者让默认部署暴露在无界读取下，后者会让所有非空请求得到 413。负数若被解释成“距离最大值还有空间”，更会得到巨大 buffer；因此配置边界必须在构造时拒绝，而不是运行到 read 才发生 ArithmeticException。

只按 Content-Length 判断也不够。HTTP 请求可以 chunked，字段可以重复或格式错误，攻击者可以让声明长度与实际传输不同。可信长度用于快速拒绝，实际有界读取才是最终边界。反过来，完全忽略已知长度会失去提前拒绝巨大声明的好处，也会让客户端等待一个本来可以立即答复的 413。

超限后立即 close 是另一个经典错误。关闭 exchange 会触发 JDK 清理剩余请求，若客户端仍在发送或 socket 已不可读，清理可能等待；此时 413 尚未提交，客户端只看到超时。项目先 send 再 close 的顺序不是随意排列，而是由这个 drain 行为决定的。与此同时也不能无限读取 surplus 来“保持连接”，因为那就放弃了上限，正确选择是交给 JDK best effort。

文档还应避免把 JDK parser 之前的问题算到 BodyLimit 上。非法 chunk header、超时、连接重置和畸形请求行可能由 parser 或网络层处理；BodyLimit 只对进入 bridge 的读取负责。413 不是完整防护体系，认证、连接数、读取超时和其它资源限制仍属于其它层，不能宣称一个配置键解决了所有拒绝服务风险。

## 本步交付物

本步交付包内 `BodyLimit`、统一的 1 MiB 默认值、构造时配置解析、可信长度预拒绝、limit+1 有界读取和先答后关的 413 路径。所有 adapter 构造路径均有界，Response 仍保持 status、Headers、byte[] 三字段，没有提前引入流式抽象。

同时交付 28 项请求体测试，覆盖已知与未知长度、恰好相等、跨 buffer、截断、parser 边界、HEAD、连接顺序和配置错误。`184c774` 的修复提醒我们：自动增长算法需要大输入和偏移测试，不能靠少量 happy path 证明内存安全。下一步将把注意力转向这些 body 在哪个线程执行，以及停止时谁拥有执行器。
