# 06 检查点：真实套接字往返

## 这一步要解决什么

前五步分别建立了适配器接缝、exchange 翻译、请求体上限、线程归属和响应 framing，但只有组合到真实服务器才能证明它们没有互相破坏。一个 Provider 可以创建两个实例，bridge 可以保留原始 path，BodyLimit 可以拒绝超限，HEAD 可以少写 body；然而并发交错时共享参数 Map、串用状态或错误关闭 exchange，仍可能让单个独立测试全部通过。

检查点因此使用真实 TCP 端口和原始字节，而不是 mock HttpExchange。`RawHttp` 默认一请求一连接，写入 Host 与 Connection: close，读取状态行、逐行字段和 ISO-8859-1 字节保真 body；需要 keep-alive 的测试自己按 Content-Length 消费每一帧。高级 HttpClient 只在“真实客户端能否接受 204/HEAD 并继续连接”这类消费者视角使用，不替代 wire 断言。

验收还必须把数量说准确。当前阳性清单为 201 项；完整适配器模块为 216 项，即加上 JdkMethodCaseSemanticsTest 的 15 项。2026-11-27 在 Java 24.0.2 上完整运行 216 项全部通过，此前记录的控制字符 method token 405 已经消失：非法 token 在 JDK parser 或 HttpMethod.of 处得到 400。绿色清单证明所选择的行为，不把“没有失败”扩展成所有 JDK、容器或协议矩阵的承诺。

## 先想清楚再写

RawHttp 的职责不是成为一个通用 HTTP 客户端，而是让测试控制请求线、字段拼写、重复字段、连接行为和截断时机。`valuesOf` 只负责大小写不敏感匹配，`fieldLines` 保留原行，`countOf` 证明 Content-Length 没有重复；这三点组合起来才能判断 framing，而不是只判断“服务器返回了 200”。

真实 socket 还能区分错误由谁写出。`OPTIONS *` 的正文是 `<h1>404 Not Found</h1>No context found for request`，长度 50，无 Date、Allow、Server，长度字段拼写为 uppercase L，并且关闭连接；同端口 adapter 的普通 404 正文是 `Not Found`，有 Date，长度字段经 canonicalize。两个 404 状态码相同，但 body 和字段指纹证明请求是否进入 dispatcher。

截断与 reset 测试解决的是异常路径。正常请求一切正确，不能证明半截 body 会得到 400，也不能证明客户端中途断开后服务仍能处理下一请求。`requestWithTruncatedBody` 用 shutdownOutput 制造真实 EOF；`readThenReset` 用 SO_LINGER=0 制造 reset；CapturedLogs 则确保异常进入服务端日志而没有出现在 socket 响应中。没有日志捕获，就可能出现“500 正确但异常被吞”的假安全。

并发测试针对共享状态而不是吞吐量。3200 个请求各自带 id、marker 和 body，响应必须回显同一组值；任何 exchange、参数 Map、header 或 buffer 串用都会产生不匹配。另一组 1200 个请求混合 200、500、404，证明状态不串；mixedShapes 再混合 200 empty、204、304、HEAD、405、404、OPTIONS *，证明 framing 不串。测试的 throughput 不是 SLO，真正断言的是请求隔离。

TLS 与字节码测试把两个容易混淆的边界固定下来。TLS 由 `326c25a` 后续加入，使用两个配置键和包内 Tls，HttpsServer 仍走同一生命周期；测试每次用运行 JDK 的 keytool 在 TempDir 生成证书，不提交 keystore 或密码。字节码测试不信任 pom 的 release 声明，而是读取 class 文件前八字节，要求 magic 正确且 major 为 61。

TLS 的证据也有明确边界。未配置 keystore path 时保持明文；显式空白 path 现在在装配期失败，不再静默回退。配置只在构造时读取一次，keystore 后续变化不会触发重载或轮换。密码以 String 留在配置快照中，加载时的 `char[]` 没有显式清零，因此日志不打印密码不等于内存中没有密码。13 项测试覆盖真实 TLS 路由、默认信任拒绝、明文误入、日志脱敏和主要启动失败，但没有覆盖私钥不可用、过期证书、损坏链、不支持 keystore 类型或 ALPN/HTTP 2。

## 常见的第一次写错

把“201 项通过”写成“所有测试通过”是最直接的诚实性错误。完整 216 项模块回归与本章阳性选择分别报告；含控制字符、引号或非 ASCII 的方法 token 由 JDK parser 或 `HttpMethod.of` 拒绝为 400，不再被当作扩展方法的 405。2026-11-27 的完整模块运行没有剩余已知差异；若升级 JDK 后出现新差异，应先确认职责归属，不能为了让数字变绿而改变正确的路由语义。

使用高级客户端断言所有 wire 行为也会掩盖问题。它可能折叠重复字段、规范化方法或拒绝星号 target；RawHttp 存在的目的就是让这些输入真正到达服务器。高级客户端适合验证客户端互操作，例如 204 后 keep-alive，但不适合证明原始字段拼写和重复 Content-Length 数量。

只跑性能式并发测试也容易误判。请求数很多不代表隔离正确；如果断言只检查 status 200，串 body 仍会通过。本章每个并发响应都核对请求相关值、header、长度、body 和调用计数。失败列表限制为 20 条，是为了在大量失败时保留最早证据，而不是忽略后续请求；最终仍要求总正确数精确匹配。

旧 Surefire 报告也可能造成假绿灯。完整运行后报告包含全部类，聚焦运行不会删除未执行类的旧 XML；统计当前结果必须依据本次命令与执行时间，或先清理对应模块报告。教程不把 target 当资产，只记录可复现命令和输出摘要。临时 probe 测试如果已从源码删除，其旧报告更不能计入当前数量。

最后，不要把 JDK 24 的单项差异扩大成“适配器不可靠”，也不要缩小成“无所谓”。含控制字符的方法 token 现在由两层共同拒绝：JDK parser 若先拒绝，就不创建 exchange；若 JDK 把 token 交给 adapter，`HttpMethod.of` 会在路由前拒绝。两种路径都必须是 400，不能把非法输入当作扩展方法的 405。这个边界由完整模块回归固定，后续升级 JDK 时应重跑并确认状态仍一致。

## 怎么确认这一步没造错

下面是一条明确的 201 项绿色检查点命令：

```bash
mvn -o -B -ntp -pl framework/barezen-http-jdk -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-Dtest=JdkHttpServerAdapterProviderTest,JdkHttpServerLifecycleTest,JdkHeaderAndBodyTest,JdkHttpServerAdapterEndToEndTest,JdkErrorSemanticsTest,JdkOptionsStarTest,JdkResponseBodySemanticsTest,JdkRequestBodyLimitTest,JdkHttpServerConcurrencyTest,JdkTlsSemanticsTest,BarezenHttpJdkArchitectureTest,ClassMajorContractTest'
```

2026-11-27 在 Java 24.0.2、Maven 3.9.12 上实测：Tests run: 201，Failures: 0，Errors: 0，Skipped: 0，BUILD SUCCESS，总耗时 7 分 03 秒。构成为 Provider 18、Lifecycle 22、Header/Body 18、EndToEnd 12、ErrorSemantics 22、OptionsStar 10、ResponseBody 26、RequestBodyLimit 29、Concurrency 3、TLS 13、Architecture 24、ClassMajor 4。

完整模块命令为：

```bash
mvn -o -B -ntp -pl framework/barezen-http-jdk -am test
```

当前完整结果为 216 项、0 失败、0 错误、0 跳过，`BUILD SUCCESS`。旧测试曾把含控制字符的 token 当作可路由扩展方法并期待 405；`HttpMethod.of` 增加 token 校验后，基线测试已改为接受 400，并不再要求 `Allow`。JDK parser 与契约校验的职责不同，但拒绝结果一致。

注意 Surefire 的排除语法。使用 `-Dtest=!JdkMethodCaseSemanticsTest` 仍可能执行该类的嵌套测试，因此不能凭命令“看起来排除了”就宣称绿色。本教程采用阳性类清单，并核对最终数量。类似地，嵌套类常显示外层 Tests run: 0，总数必须从 XML 汇总，不能把 0 当成类没有测试。

失败时可以按证据层定位：

| 现象 | 首先检查 | 不能如何修复 |
| --- | --- | --- |
| Provider 找不到 | service 文件路径、打包资源、id | 在核心写死 new JdkProvider |
| `%2F` 404 或参数错误 | bridge 是否使用 getRawPath | 在 Router 提前解码 |
| 空 200 卡住或 chunked | 空 body 是否传 length 0 | 让客户端等待 EOF |
| HEAD 无长度或 body 串 | raw token、representation length | 调用 GET Handler 代替 |
| 小写 HEAD 长度错误 | 是否误用 folded enum | 删除大小写测试 |
| 413 写不出 | 是否 close 早于 send | 无限 drain surplus |
| stop 后端口仍占用 | server/provider 清理、bind 失败边界 | 强制 kill 所有 Java 进程 |
| 一类通过另一类串值 | 共享字段、buffer、参数 Map | 给所有匹配加锁掩盖共享 |
| 完整测试出现红 | 失败类、JDK 版本与最近提交 | 为绿灯修改正确 framing |

如果修改生产代码，应做反向验证而不是只跑原测试。例如把 HEAD 判断改为 folded enum，小写行应失败；删除 413 提前 send，drain 测试应失败；让 borrowed provider 被关闭，ExecutorOwnership 应失败；删掉 SPI 注册，Provider Discovery 应失败。若对应测试仍绿，先检查测试是否命中真实源码，而不是宣称保护充分。
