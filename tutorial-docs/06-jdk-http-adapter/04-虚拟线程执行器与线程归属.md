# 04 虚拟线程执行器与线程归属

## 这一步要解决什么

服务器要并发处理请求，就必须决定任务在哪个 ExecutorService 上执行。若 adapter 内部直接 `Executors.newCachedThreadPool()`，运行期能力探测和统一关闭策略就都被绕过；若所有 adapter 共享一个全局池，停止一台服务器可能影响另一台，阻塞 Handler 也会跨应用互相耗尽资源。本步要建立的是“一台服务器拥有或借用哪个 ThreadProvider”的明确模型。

ThreadProvider 本身不是全局线程池注册表。它按 ThreadPolicy 与 RuntimeCapabilities 创建执行器，并记录自己创建了哪些执行器；close 只关闭这些执行器。AUTO 在 JDK 21+ 选择虚拟线程，在 JDK 17 回退平台线程；显式 VIRTUAL 在能力不存在时失败，不能悄悄降级。字节码仍是 release 17，运行期才探测虚拟线程，因此“JDK 21 项目”和“JDK 17 项目”都不是准确表述。

adapter 的两参数构造自行创建 provider，所以拥有它，stop 或启动失败时负责关闭。三参数构造接受外部 provider，只是借用，stop 不能关闭它，否则应用继续复用时就会拿到已终止执行器。`ownsThreadProvider` 这个私有布尔值把“对象字段非 null”与“资源属于我”分开，是启动失败清理和借用测试的核心。

生命周期同样保持很小：NEW、RUNNING、STOPPED。start 只能从 NEW 到 RUNNING，重复 start 失败；stop 后实例作废，不能 restart；NEW 直接 stop 合法。适配器不实现核心 LifecycleParticipant，因为应用编排器可以显式持有它并纳入启动/停止顺序，而不需要让核心生命周期认识 HTTP 类型。

## 为什么这样设计

start 不能只做一次 `HttpServer.create`。它要创建 server、设置请求 executor、注册根 context、调用 start，并把新 server 放进字段供 port/isRunning 查询。这些动作被放在 lifecycle 锁内，避免并发 start 创建两个 server，或 stop 与启动交错。state 表示当前实例是否可服务，server 字段表示底层对象是否存在；两者一起支持 NEW→STOPPED 和失败后的幂等清理。

默认 backlog 为 0，因为 0 在 JDK API 中表示采用默认值，而不是“不允许连接”。stop grace 固定 3 秒，是 server.stop(delay) 的等待预算；它不是整个应用无限期停止的承诺。停止顺序先标记 STOPPED 并清空 server，确保再次 stop 没有对象可操作，也让 isRunning 立即变 false、port 立即为空；然后才停止正在服务的 server，最后关闭自有 provider。

先标记再停止还有一个并发意义：新的 start 会看到 STOPPED 并失败，不会在旧 server 尚在关闭时重新创建一个。port() 从当前 server 的 address 读取，而不是缓存构造时的端口；对于 port 0，只有绑定后才知道 OS 分配了什么。清空 server 后自然返回 empty，不需要额外缓存一个“最后端口”。

自建 provider 的关闭责任不能只写在成功 stop 路径。start 中创建 server 后，setExecutor、createContext 或 server.start 都可能抛 IOException 或 RuntimeException。catch 中若 created 非 null，要先 stop(0)，再关闭自有 provider，最后把 state 设为 STOPPED。借用 provider 即使启动失败也不能关闭，因为资源从来不属于 adapter。原异常应继续传播，IOException 包装为 UncheckedIOException 并保留 cause，不能让清理掩盖首次失败原因。

选择无界 executor 并不代表服务器没有资源边界。JDK server 的 exchange 任务需要交给能处理阻塞 Handler 的执行器；虚拟线程适合一任务一线程，平台 provider 使用 cached pool。请求体已有 BodyLimit，连接与吞吐量仍需要部署层控制。若改用固定小池，长请求会排队并改变超时语义；若把池做成全局共享，停止和故障隔离又无法维持。当前选择优先保持 adapter 局部所有权和 Handler 的直接执行模型。

不实现 LifecycleParticipant 是另一个有意的边界。核心生命周期引擎只认识自己的 participant 协议，不应该为了 HTTP 导入 `com.sun.net.httpserver` 或 adapter 模块。应用可以把 adapter 作为一个资源，在自定义 participant 的 initialize/start 中显式调用它；生命周期测试正是这样驱动，并验证 adapter 没有偷偷获得核心回调能力。

## 怎么验证

运行生命周期聚焦测试：

```bash
mvn -o -B -ntp -pl framework/barezen-http-jdk -am test \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dtest=JdkHttpServerLifecycleTest
```

当前为 21 项：Transitions 10、ExecutorOwnership 5、ThreadModel 3、ThroughTheAssembly 1、NotAParticipant 2。Transitions 覆盖未启动不 bind、启动服务、重复 start、stop 后 restart 失败、幂等 stop、NEW→STOPPED、try-with-resources、端口释放、第二 binder 失败和 bind 失败 cause。

ExecutorOwnership 是资源归属的直接证据。自建 provider 在 stop 后不能创建新 executor；借用 provider 在 adapter stop 后仍能创建并执行任务。启动失败也分两种：拥有者关闭自己的 provider，借用者不碰外部 provider。测试不能只检查 close 被调用，因为一个 mock 的 close 计数无法证明外部 executor 仍然可执行任务。

ThreadModel 在 JDK 21+ 检查默认请求线程为虚拟线程，并允许显式借用 PLATFORM provider 覆盖默认选择。它验证的是运行期能力，而不是 class major。停止测试使用有 deadline 的线程枚举，等待请求线程消失，避免 JDK 17 平台线程终止调度造成偶发失败；`6b08501` 正是为消除这种时间断言抖动而提交。

有一个必须如实记录的失败边界：`aStartThatFailedAfterBindingSpendsTheAdapterAndClosesNothingItDidNotCreate` 固定 bind 成功后、start 前失败时，端口可能直到 JVM 结束都不能重新绑定。测试用 `assertThat(canBind(bound)).isFalse()` 固定当前 JDK 行为，不把设计债写成已解决。遇到它应知道实例已作废、资源已按所有权清理，而不是重试 restart 或隐藏失败。

反向验证可沿三条线进行：把 stop 中的 `threads.close()` 移到 borrowed 分支，自有 provider 测试应失败；让 borrowed 也关闭，外部 executor 测试应失败；允许 STOPPED 再 start，restart 规则应失败；先 start 再设置 state，并发状态测试应暴露问题。架构测试还会禁止适配器直接 new Thread/Executor、禁止额外生命周期 accessor 和第二个 restart 入口。

## 常见错误与失败后果

把所有 provider 当静态共享资源会最早暴露于停止：一台 adapter 关闭整个池，另一台正在服务的请求突然失去执行器。反过来，借用却不标记所有权又可能泄漏：外部 provider 被 adapter 关闭，应用后续任务全部 IllegalStateException。正确判断不是“这个字段是否为空”，而是“这次构造是否创建了它”。

只处理 start 的 IOException 也不够。setExecutor 或 context 注册可能抛 RuntimeException，清理逻辑必须覆盖它；只关闭 server 而忘记自有 provider，则虚拟线程工厂仍保留终止状态；只关闭 provider 而忘记 created.stop(0)，绑定中的 server 可能继续持有端口。清理要按 server、provider 两层分别归属，任何一层遗漏都会留下不同资源。

把 stop 设计成抛异常会让 try-with-resources 掩盖主异常，也让重复停止变得危险。当前 stop 幂等且不抛参与者异常，server.stop 的失败不重新抛出，close 也不扩展新协议。调用者需要知道的是“尽力停止后实例不再运行”，而不是把 JDK 关闭实现细节变成公共异常契约。日志可以记录问题，但不能用异常破坏停止路径。

最后，不能用“JDK 24 上跑了虚拟线程”证明项目只能跑 JDK 24。构建使用 release 17，输出 class major 61；运行时能力探测决定是否启用虚拟线程。JDK 17 回退平台线程，JDK 21+ AUTO 选择虚拟线程，显式 VIRTUAL 才在缺少能力时失败。混淆编译基线、运行期最低版本和可选能力，会让部署文档给出错误结论。

## 本步交付物

本步交付 NEW/RUNNING/STOPPED 的一次性服务器生命周期、默认与借用两种 ThreadProvider 所有权、AUTO 运行期线程选择、3 秒 server stop grace 和启动失败的双层清理。适配器保持 AutoCloseable，但不进入核心 LifecycleParticipant 体系；应用可显式编排它。

同时交付 21 项生命周期测试和一个明确的已知 bind 失败边界。这里证明了端口释放、provider 存活、停止后无请求线程和运行期虚拟线程选择；bridge 的 HEAD/304 framing 与方法 token 边界仍需要下一步用矩阵固定。
