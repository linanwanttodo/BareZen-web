Data module

barezen-data provides Database, Transaction, RowMapper, and Migration — a minimal JDBC layer with transactions and schema migrations.

Module overview

The barezen-data module provides a thin, product-agnostic data layer built on JDBC. It takes a DataSource and provides queries, updates, transactions, and schema migrations — without knowing which database it talks to.

Key types:

TypeRole
DatabaseEntry point: queries, updates, transactions
TransactionTransaction-scoped access for multi-statement units of work
RowMapperMaps a ResultSet row to a domain object
MigrationOne schema or data change, identified by a version number
MigratorApplies pending migrations in version order
DataAccessExceptionRuntime exception wrapping SQLException

Database

Database is the entry point of the data layer. It takes a DataSource and never names a driver, URL, user, or password — the application's assembly code creates the data source and hands it over.

Creating a Database

// With H2 in-memory database (for tests)
JdbcDataSource dataSource = new JdbcDataSource();
dataSource.setURL("jdbc:h2:mem:test;DB_CLOSE_DELAY=-1");
Database db = new Database(dataSource);

// With a connection pool (for production)
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:postgresql://localhost/mydb");
config.setUsername("user");
config.setPassword("password");
DataSource dataSource = new HikariDataSource(config);
Database db = new Database(dataSource);

Two access styles

The difference between them is the whole transaction story (ADR-0039):

Auto-commit style (single statement)

query() and executeUpdate() run on a connection borrowed for the call, in the pool's auto-commit default. Use these for statements that are complete units by themselves:

// Single query
List<User> users = db.query(
    "SELECT id, name, email FROM users WHERE active = ?",
    (rs, rowNum) -> new User(
        rs.getLong("id"),
        rs.getString("name"),
        rs.getString("email")),
    true);

// Single update
int rows = db.executeUpdate(
    "UPDATE users SET name = ? WHERE id = ?",
    "Alice", 1L);

Transaction style (multi-statement unit of work)

transaction() opens one connection, puts it in transaction scope, runs a callback, and commits when the callback returns normally. A unit of work that spans more than one statement uses this path:

db.transaction((tx) -> {
    tx.executeUpdate("INSERT INTO users (name, email) VALUES (?, ?)",
        "Alice", "alice@example.com");
    long userId = tx.queryForLong(
        "SELECT last_insert_id()");
    tx.executeUpdate("INSERT INTO profiles (user_id, bio) VALUES (?, ?)",
        userId, "Hello!");
    return userId;
});  // Commits automatically on success, rolls back on failure

Transaction guarantees

ScenarioOutcome
Callback returns normallycommit() — changes are durable
Callback throws SQLExceptionrollback() — failure is translated to DataAccessException
Callback throws RuntimeExceptionrollback() — failure propagates untranslated
Callback returns but commit failsRolls back first, then throws DataAccessException

In every case, the connection is closed before transaction() returns.

Transaction API

Inside a transaction callback, you receive a Transaction with the same methods as Database:

MethodDescription
query(sql, mapper, params)Execute a query and map rows
executeUpdate(sql, params)Execute an insert/update/delete, returns affected row count
queryForLong(sql, params)Execute a query returning a single long value

Connection lifecycle

Every connection is closed before any public method returns, on every path — normal return, translated failure, application exception, or cleanup failure. PreparedStatement and ResultSet are managed internally and never handed to the caller.

Exception translation

Every SQLException leaving this module is rethrown as DataAccessException with the SQL or operation named, and the driver exception kept as the cause. A runtime exception thrown by a callback is not translated — it is the application's own failure type.

RowMapper

A RowMapper is a functional interface that maps a ResultSet row to a domain object:

@FunctionalInterface
public interface RowMapper<T> {
    T map(ResultSet rs, int rowNum) throws SQLException;
}

Usage example

RowMapper<User> userMapper = (rs, rowNum) -> new User(
    rs.getLong("id"),
    rs.getString("name"),
    rs.getString("email"),
    rs.getTimestamp("created_at") != null
        ? rs.getTimestamp("created_at").toLocalDateTime()
        : null);

List<User> users = db.query(
    "SELECT id, name, email, created_at FROM users",
    userMapper);

Schema migrations

Migrations are versioned schema or data changes applied in order. The Migrator tracks which versions have been applied in a history table and runs only the pending ones.

Migration interface

public interface Migration {
    long version();       // Positive, unique, strictly increasing
    String description(); // Human label stored in the history table
    void apply(Connection connection) throws SQLException;
}

Writing a migration

Migration createUsersTable = new Migration() {
    @Override
    public long version() {
        return 1L;
    }

    @Override
    public String description() {
        return "Create users table";
    }

    @Override
    public void apply(Connection conn) throws SQLException {
        try (Statement stmt = conn.createStatement()) {
            stmt.execute("""
                CREATE TABLE users (
                    id BIGINT PRIMARY KEY AUTO_INCREMENT,
                    name VARCHAR(255) NOT NULL,
                    email VARCHAR(255) NOT NULL UNIQUE,
                    password_hash VARCHAR(500) NOT NULL,
                    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
                )
            """);
        }
    }
};

Applying migrations

Migrator migrator = new Migrator(db);
migrator.migrate(List.of(
    createUsersTable,
    createProfilesTable,
    addEmailVerifiedColumn
));

Migration guarantees

  • A recorded version never runs again.
  • Migrations run in version order.
  • Each migration runs in its own transaction.
  • If a migration fails, its version is not recorded, and no later migration runs.
  • A failed migration may leave schema behind — write DDL idempotently (IF NOT EXISTS) so a retried migration completes.

History table

The migrator creates a applied_migrations table automatically:

CREATE TABLE applied_migrations (
    version BIGINT PRIMARY KEY,
    description VARCHAR(255) NOT NULL,
    applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)

DataAccessException

A runtime exception wrapping SQLException. It carries the SQL or operation name and the original driver exception as the cause:

try {
    db.query("SELECT * FROM nonexistent", mapper);
} catch (DataAccessException e) {
    // e.getMessage() — "query failed: SELECT * FROM nonexistent"
    // e.getCause() — the original SQLException from the driver
    log.error("Database error: {}", e.getMessage(), e);
}

Complete example: User repository

public class UserRepository {

    private final Database db;

    public UserRepository(Database db) {
        this.db = db;
    }

    public Optional<User> findById(long id) {
        List<User> users = db.query(
            "SELECT id, name, email, password_hash, created_at FROM users WHERE id = ?",
            (rs, rowNum) -> new User(
                rs.getLong("id"),
                rs.getString("name"),
                rs.getString("email"),
                rs.getString("password_hash"),
                rs.getTimestamp("created_at").toLocalDateTime()),
            id);
        return users.stream().findFirst();
    }

    public User create(String name, String email, String passwordHash) {
        long id = db.transaction((tx) -> {
            tx.executeUpdate(
                "INSERT INTO users (name, email, password_hash) VALUES (?, ?, ?)",
                name, email, passwordHash);
            return tx.queryForLong("SELECT last_insert_id()");
        });
        return findById(id).orElseThrow();
    }

    public void updateEmail(long id, String newEmail) {
        db.executeUpdate(
            "UPDATE users SET email = ? WHERE id = ?",
            newEmail, id);
    }
}

Best practices

Database access

  • Use query() and executeUpdate() for single-statement operations.
  • Use transaction() for multi-statement units of work.
  • Never nest transaction() calls — each opens a new connection.
  • Use parameterized queries (?) — never concatenate SQL with user input.

Migrations

  • Write DDL idempotently: use IF NOT EXISTS and IF EXISTS.
  • Assign version numbers that are strictly increasing and never reused.
  • Keep descriptions descriptive — they appear in the history table for operators.
  • Test migrations against the actual database product you deploy to.

Connection pooling

  • Use a connection pool (HikariCP, Tomcat JDBC) in production.
  • Use an unpooled JdbcDataSource (H2) for tests.
  • The framework never asks what kind of DataSource it got — it behaves identically.

Common issues

"query failed: ..." with DataAccessException

The SQL query failed. Check the cause (e.getCause()) for the driver's SQLException for details. Common causes: syntax error, missing table, or type mismatch.

"could not acquire a connection from the data source"

The DataSource cannot produce a connection. Check that the database is running, the URL is correct, and the credentials are valid.

"transaction failed and was rolled back"

A statement inside the transaction callback failed. The transaction was rolled back, and no changes were committed. Check the callback's SQL and parameters.

"Migration version X already applied"

A migration with a version that was already recorded was submitted again. Version numbers must be unique and strictly increasing.
