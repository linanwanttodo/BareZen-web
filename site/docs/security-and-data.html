Security & data

Two capability modules that depend on the contract and on nothing else, so an application can take one and leave the other.

Security is a decorator, not a chain

SecurityMiddleware.wrap(...) takes a handler and returns a handler. It authenticates, then authorizes, then calls what it wrapped — and on every refusal the wrapped handler is never invoked, which is asserted with a counter rather than assumed (ADR-0033, ADR-0037).

  • Three states, not two. Authenticated, failed, and offered-nothing are different answers: the first 401-prompt is a challenge, the second 401 carries a reason that stays on the server. A sealed type holds that; an Optional collapses it into one wrong answer (ADR-0034).
  • Identity arrives as an argument. A handler that needs it implements SecuredHandler and receives a SecurityContext as a third parameter. There is no thread-local, because a container reuses threads and one request's principal becomes the next request's (ADR-0033).
  • Sessions are opaque and revocable. A 256-bit server-side record, not a JWT: revocation is one map removal, rotation kills the old token, expiry is an injected Clock checked on lookup. JWTs were refused on four grounds, the first being that revocation would need server state anyway (ADR-0036).
  • Passwords hash with PBKDF2-HMAC-SHA256 — 600,000 iterations, 16-byte salt, 32-byte key, encoded as algorithm$iterations$salt$key so the count can rise without invalidating stored hashes. bcrypt was refused as a new third-party dependency, Argon2 because the JDK has none. A malformed stored hash verifies false rather than throwing, and the module cannot name a logger, so no raw password or hash can reach one (ADR-0035).
  • 401 or 403, never a guess. No or failed identity is 401; a denied identity is 403; a throwing collaborator is 500; the default is deny (ADR-0037).

Data is one boundary and one decision the callback cannot make

Database database = new Database(pool);                       // your DataSource; the framework names no driver
List<String> names = database.query("select name from users where active = ?",
    (rs, row) -> rs.getString(1), true);
int updated = database.transaction(tx -> tx.executeUpdate("update users set name = ? where id = ?", name, id));
List<AppliedMigration> applied = Migrator.of(database).migrate(List.of(new AddUsersTable(1L, "users", ddl)));
  • Zero compile dependencies. barezen-data speaks javax.sql and receives a DataSource the application supplies; H2 is a test dependency, and a driver is never named in shipped code (ADR-0038).
  • A transaction is handed to you and cannot be decided by you. commit and rollback are package-private, so a repository bypass is a compile error — and a reflection probe guards the visibility itself, because a rule about behaviour that a future refactor can delete is worth less than a test that fails when it changes (ADR-0039).
  • Nesting has an answer. A second transaction(...) opens an independent transaction on a second connection, pinned by test rather than left implicit.
  • Every SQLException becomes one unchecked DataAccessException, while a runtime exception thrown by your own callback stays itself — the translation point is single and visible (ADR-0038).
  • Migrations promise one sentence. A version is recorded if and only if its apply completed, the row sharing the change's transaction. Schema integrity after a failure is the product's answer, because H2 was measured committing DDL implicitly — the first draft promised atomicity, a standalone probe falsified it, and the sentence was rewritten (ADR-0040).

Both modules are one arrow deep: barezen-security depends on barezen-web alone, barezen-data on nothing. Neither knows a server exists, which is why the same handler chain runs under the JDK adapter and inside Tomcat.
