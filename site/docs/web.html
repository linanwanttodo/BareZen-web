Web core

barezen-web defines the HTTP contract: Request, Response, Router, and Handler — server-agnostic and immutable.

Module overview

The barezen-web module defines the core HTTP abstractions. It depends only on barezen-core and has no server-specific dependencies. This is what lets the same handler run on any HTTP server — JDK HttpServer, Tomcat, Jetty, or Wildfly.

It contains ten types in a single package:

ResponseImmutable response: status, headers, body

Handler contract

A handler is the entire extension surface of the web layer. One method, synchronous, returning a value:

@FunctionalInterface
public interface Handler {
    Response handle(Request request, Map<String, String> parameters);
}

Two arguments, one return value. The handler receives the request and any path parameters captured by the router, and returns a response. There is no servlet context, no thread-local, no request scope — just data in, data out.

Parameters map

The parameters map contains the path parameters captured by the matched route pattern, keyed by the names declared in the pattern. It is immutable and raw (not percent-decoded). For a route with no parameters, it is an empty map (never null).

// Route: GET /users/{id}/posts/{postId}
// Request: GET /users/42/posts/7
// parameters: {"id": "42", "postId": "7"}

Failure semantics

  • An exception may propagate out of a handler — nothing in this contract catches it.
  • A handler that translates its own failure into a 500 is fine, and a handler that lets a database exception escape is too.
  • Who turns an escaping exception into a response to the client is an adapter's decision, not the handler's.

Thread safety

Handlers are invoked concurrently by an adapter. A handler must not hold mutable per-request state in fields. What belongs in a field is what was injected at construction. The parameters map is already per-request, immutable, and built by the route table.

Request

The Request type carries five facts about what the client sent (ADR-0018). Instances are immutable — arrays and lists are copied on access.

Fields

MethodTypeNotes
method()HttpMethodGET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS, CONNECT, TRACE
path()StringRaw path, percent-encoded, starting with / or * for OPTIONS *
query()Optional<String>Raw query without ?; absent is distinct from empty
headers()HeadersMulti-value header collection, never null
body()byte[]Complete body in memory; copied on each call. Empty array when no body.

Raw paths

The path is kept in the form that arrived on the wire. Nothing is percent-decoded:

  • /a%2Fb is one segment containing a slash, while /a/b is two segments.
  • /%2e%2e/x is not decoded to /../x — decoding is a decision about one resource, made by whoever owns it.

There is no uri(), no param(name), and no decoded twin of path(). A query parameter map is a parse with rules of its own and belongs to a helper, not the request type.

Query: absent vs empty

Absent and empty stay distinct: /search gives Optional.empty() while /search? gives Optional.of(""). A handler that treats those as one cannot tell "no filter given" from "filtered by nothing".

Body in memory

body() returns a copy of the whole body as byte[]. This is a deliberate trade-off: a streaming body would require the contract to say who closes the stream, what happens when a handler returns without reading it, and what happens when a handler hands it to another thread. None of those questions has an answer that does not depend on a server.

Constructor validation

The constructor validates that the path starts with / or is exactly * (for OPTIONS *). A relative path like user/1 is refused.

Response

A response is produced, not edited. A handler builds one and returns it — there is no setStatus, addHeader, or send:

new Response(200, Headers.of("Content-Type", "application/json"), jsonBytes);

Fields

MethodTypeNotes
status()intStatus code between 100 and 599
headers()HeadersResponse headers, never null
body()byte[]Response body; copied on each call. Empty array when no body.

Enforced rules

Two rules are enforced at construction (ADR-0027):

  1. Status that forbids a body is not given one. HTTP says 1xx, 204, and 304 carry no body. A non-empty body alongside one of those statuses is refused at construction with a clear error message.
  2. Content-Length and Transfer-Encoding are not a handler's to write. These fields describe how many bytes follow the header block — a fact about the connection, not the application's answer. Only the adapter writing bytes can state them truly.

HEAD responses

A handler returns the same Response for HEAD that it would for GET. The adapter decides both consequences: it writes no body bytes, and it derives the Content-Length of the body it did not write. A handler that returned an empty body for HEAD would be reporting a zero-length representation.

Status code validation

Status codes must be between 100 and 599 inclusive. An out-of-range code cannot be written on a response line, and a client branches on the status — so a wrong one is not a cosmetic error, it is the wrong answer delivered successfully.

Common response patterns

// 200 OK with JSON body
new Response(200,
    Headers.of("Content-Type", "application/json"),
    "{\"message\":\"ok\"}".getBytes(StandardCharsets.UTF_8));

// 204 No Content
new Response(204, Headers.empty(), null);

// 404 Not Found
new Response(404,
    Headers.of("Content-Type", "text/plain; charset=utf-8"),
    "Not Found".getBytes(StandardCharsets.UTF_8));

// 304 Not Modified (no body allowed)
new Response(304, Headers.of("ETag", "\"abc123\""), null);

// 302 Redirect
new Response(302, Headers.of("Location", "/new-path"), null);

Headers

Headers are a multi-value collection. Each name can have multiple values, preserving the HTTP semantics where Set-Cookie or Accept commonly carry multiple values.

API methods

MethodDescription
Headers.empty()Returns an immutable empty instance, shared.
Headers.of(String name, String value)Creates headers with one field.
with(String name, String value)Returns a new instance with one more field appended. Calling twice with the same name gives a field with two values.
first(String name)Returns the first value of a field as Optional<String>. Case-insensitive name matching.
values(String name)Returns all values of a field in order. Returns an empty list if the field was not sent.
names()Returns distinct field names in first-appearance order, spelled as given.

Four enforced rules

  1. Names are case-insensitive for matching, keep the case given for output. A response built with Content-Type is sent as Content-Type, not content-type.
  2. Repeated names keep every value, in order. values("Set-Cookie") returns all cookies.
  3. Absent and empty are different. A field sent as X-Cursor: exists with an empty value (Optional.of("")); a field that was never sent is Optional.empty().
  4. A name is an HTTP token and a value holds no control characters. This is a security rule: a CR or LF in a header value starts a new response line (HTTP response splitting).

Usage example

Headers headers = Headers.of("Content-Type", "application/json")
    .with("Cache-Control", "no-cache")
    .with("Set-Cookie", "session=abc")
    .with("Set-Cookie", "tracking=xyz");

List<String> cookies = headers.values("Set-Cookie");
// ["session=abc", "tracking=xyz"]

Optional<String> contentType = headers.first("Content-Type");
// Optional["application/json"]

HttpMethod

An HTTP request method is a type rather than a String, because the first thing a web component does with a request is compare its method, and a bare String makes that a trap: "Get".equals(request.method()) never matches.

Standard methods

ConstantDescription
GETRequest for a representation, answered with a body.
HEADGET with no response body. The adapter handles this.
POSTSubmit a representation for processing.
PUTReplace the target resource.
DELETERemove the target resource.
PATCHApply a partial modification.
OPTIONSAsk what options the target resource supports (CORS preflight).
CONNECTTurn the connection into a tunnel.
TRACEEcho the request back to the client.

Custom methods

This is a class rather than an enum, so it can hold methods not in the standard set (e.g., PROPFIND from WebDAV, PURGE from cache managers). Use HttpMethod.of("PURGE") to parse any method token.

Case rules

  • The nine standard names are recognized in any case: of("get") returns HttpMethod.GET.
  • Any other name is kept exactly as it arrived and compared exactly.

Router

The router is an immutable route table (ADR-0019). It answers "which handler is this request for" and does not answer "what should the client be told when the answer is nobody".

Building routes

Router router = Router.builder()
    .route(HttpMethod.GET, "/health", (req, params) ->
        new Response(200, Headers.of("Content-Type", "text/plain"), "OK".getBytes()))
    .route(HttpMethod.GET, "/users/{id}", (req, params) -> {
        String id = params.get("id");
        return new Response(200, Headers.of("Content-Type", "application/json"),
            ("{\"id\":\"" + id + "\"}").getBytes());
    })
    .build();

Matching semantics

Matching is decided in this order:

  1. Raw segments. The path is split on / and each segment is compared as the bytes arrived. Nothing is decoded or normalized.
  2. Exact segment count. /users and /users/ are two different routes (different segment counts).
  3. Literal segments match exactly. Case-sensitive, percent-encoding included.
  4. Parameter segments {name} match any non-empty segment. Captured undecoded.
  5. The most literal pattern wins. /users/new beats /users/{id} for GET /users/new.

Route conflicts

Two routes with the same method and the same shape are refused at build time. /users/{id} and /users/{userId} have the same shape and will collide — ambiguity is a question of shape, not spelling.

Pattern validation

Patterns are validated at registration time:

  • Must start with /.
  • Must not contain ? (query strings are not routing data).
  • Parameter names must be valid Java identifiers (letter followed by letters, digits, underscores).
  • A parameter name cannot be used twice in one pattern.
  • Braces must form a complete segment: {name} is valid, {name}suffix is not.

RouteContributor

Plugins can contribute routes without modifying the router directly. A RouteContributor is called during the router's build phase:

public interface RouteContributor {
    void contributeRoutes(Router.Builder builder);
}

Use contributing() to apply contributors:

Router router = Router.builder()
    .route(HttpMethod.GET, "/health", healthHandler)
    .contributing(List.of(userPlugin, authPlugin))
    .build();

Immutability

The router is immutable after build(). There is no unregister, replace, or reload. A request thread cannot race a registration because the race does not exist.

Methods for a path

methodsFor(String path) returns which methods have a route for a given path. This is how an adapter distinguishes 404 (no route for this path) from 405 (route exists but not for this method):

Set<HttpMethod> methods = router.methodsFor("/users");
// If GET /users is registered and POST /users is requested:
// match() returns empty, methodsFor() returns [GET]
// → Adapter answers 405 Method Not Allowed

HttpServerAdapter

The HttpServerAdapter interface defines what every server adapter must implement:

public interface HttpServerAdapter extends LifecycleParticipant {
    Optional<Integer> port();
}

It extends LifecycleParticipant, so the orchestrator drives its startup and shutdown. The adapter is responsible for:

  • Binding a network port
  • Reading bytes from the socket and building a Request
  • Calling Router.match() to find the handler
  • Invoking the handler and writing the Response back
  • Handling HTTP errors (404, 405, 414, etc.)

Module dependencies

barezen-web depends only on barezen-core. No server adapter, no database driver, no security library. Everything else is a module you add on purpose:

  • barezen-http-jdk — JDK HttpServer adapter
  • barezen-http-servlet — Servlet container adapter
  • barezen-security — Authentication and authorization
  • barezen-data — Database access
  • barezen-content — Static file serving

Best practices

Handlers

  • Keep handlers stateless — inject dependencies through constructors, not through request fields.
  • Return a response for every code path — never return null.
  • Let exceptions propagate for unexpected errors; the adapter will handle them.
  • For expected errors (validation, not found), return the appropriate status code explicitly.

Routing

  • Register literal routes before parameterized ones for clarity, though the router handles priority automatically.
  • Use RouteContributor for plugin routes to keep the main router clean.
  • Build the router once at startup — it is immutable and thread-safe.

Responses

  • Always set Content-Type on responses with a body.
  • Use Headers.empty() for responses with no headers (the adapter still writes Content-Length).
  • Never set Content-Length or Transfer-Encoding — the adapter derives them.

Common issues

"Route pattern must start with '/'"

All route patterns must start with /. A relative pattern like users/{id} is refused — the router needs an absolute path to match against.

"GET /users/{id} is already registered as /users/{userId}"

Two routes with the same method and the same shape (same pattern structure) cannot coexist. /users/{id} and /users/{userId} both match /users/42, so the router refuses the second one at build time.

"A 204 response cannot carry a body"

HTTP defines 1xx, 204, and 304 as responses with no message body. Return an empty body (null or new byte[0]) for these statuses.

"A response must not carry Content-Length"

The adapter derives Content-Length from the body bytes. Setting it manually causes duplicate headers or protocol errors. Remove the Content-Length header from your response headers.
