Core concepts

barezen-core provides the foundation: lifecycle management, configuration, dependency injection, event bus, and threading.

Module overview

The barezen-core module is the foundation of the entire framework. It has no external dependencies beyond slf4j-api (ADR-0001). Every other framework module depends on it, directly or indirectly.

It is organized into eight packages:

PackageResponsibility
com.barezen.core.kernelLifecycle orchestration, application states, shutdown hooks
com.barezen.core.configConfiguration snapshots, sources, type conversion
com.barezen.core.diExplicit dependency injection via ServiceAssembly
com.barezen.core.eventSynchronous event bus and subscriptions
com.barezen.core.concurrentThread providers, virtual threads, executor management
com.barezen.core.pluginPlugin interface, descriptors, discovery, registration
com.barezen.core.runtimeRuntime capability detection (virtual threads, etc.)
com.barezen.core.errorFramework exceptions: Assembly, Configuration, Lifecycle

Lifecycle management

Every BareZen application goes through a fixed set of states, managed by LifecycleOrchestrator. The orchestrator drives startup, shutdown, and startup rollback for all registered components.

Application states

StateMeaning
NEWJust built, not yet started. The orchestrator is ready to start.
STARTINGIn the middle of startup; initialize() and start() phases are in progress.
RUNNINGAll participants started successfully, accepting work.
STOPPINGShutting down participants in reverse order.
STOPPEDCleanly shut down. All resources released.
FAILEDStartup failed, rollback completed. No resources are left acquired.

LifecycleParticipant interface

Every component whose startup and shutdown is driven by the orchestrator implements LifecycleParticipant:

public interface LifecycleParticipant {
    default void initialize() {}  // Acquire resources, complete internal wiring
    default void start() {}       // Activate and begin serving work
    default void stop() {}        // Release resources, called during shutdown
    default void abort() {}       // Release resources after initialize() failed
}

All four methods have empty defaults, so an implementation writes only the phases it actually has. The orchestrator relies on these obligations:

  • stop() and abort() are idempotent and never throw.
  • stop() must tolerate a participant that only reached initialize(), because the orchestrator uses it for both orderly shutdown and rollback of an initialized participant.
  • Registration order is startup order. Choosing that order is the assembler's job.

Two-phase startup

Startup runs in two global phases (ADR-0003):

  1. Initialize phase — every participant's initialize() is called. This is where routes are registered, migrations are applied, and routes are contributed.
  2. Start phase — every participant's start() is called. This is where ports are bound and servers begin listening.

The two-phase ordering guarantees that a participant that makes work observable (such as an HTTP server binding a port) does so only after every earlier participant has finished its setup. Interleaving the two phases per component cannot express this invariant.

Startup rollback

If any participant fails during startup, the orchestrator performs a complete rollback (ADR-0004):

  • Every participant that entered successfully receives stop() in reverse order.
  • The failing participant receives abort() instead of stop().
  • The original failure is always what is reported; cleanup problems are attached as suppressed exceptions.
  • After rollback, the state is FAILED and nothing is left acquired.

Shutdown

Shutdown is best-effort and never throws (ADR-0005). Every entered participant is attempted even if one fails, and a ShutdownReport collects all failures. Calling stop() on an application that never started is legal and idempotent (ADR-0012), which makes try-with-resources usable.

Builder API

The LifecycleOrchestrator.Builder provides the following configuration options:

MethodDefaultDescription
register(String id, LifecycleParticipant)RequiredRegisters a participant. Call order defines startup order.
threadPolicy(ThreadPolicy)AUTOChooses the thread model: AUTO, PLATFORM, or VIRTUAL.
runtimeCapabilities(RuntimeCapabilities)Auto-detectedOverrides the detected runtime capabilities (used by tests).
threads(ThreadProvider)Resolved from policySupplies an externally created provider; the orchestrator still owns its shutdown.
threadCloseTimeout(Duration)10 secondsGrace period for terminating executors the owned provider created.

Usage example

LifecycleOrchestrator orchestrator = LifecycleOrchestrator.builder()
    .register("web", httpAdapter)
    .register("security", securityPlugin)
    .register("data", database)
    .build();

try {
    orchestrator.start();
    // application runs until stopped
} finally {
    orchestrator.stop();  // or use try-with-resources
}

Shutdown hooks

By default, the orchestrator registers a JVM shutdown hook for embedded applications. Turn it off when a host container (e.g., Tomcat) already owns process lifecycle:

LifecycleOrchestrator.builder()
    .registerShutdownHook(false)
    .build();

Querying state

The orchestrator provides two query methods:

// Check current state
ApplicationState state = orchestrator.state();

// List all participant IDs in registration order
List<String> ids = orchestrator.participantIds();

Configuration system

Configuration in BareZen is a read-only snapshot resolved before startup (ADR-0013). There is no write API: configuration is decided once and stays decided. This prevents two components from disagreeing about a value and prevents tests from leaving state behind for the next one.

Configuration sources

Three built-in source types, layered weakest-first:

SourcePrecedenceUse case
PropertiesConfigurationSourceLowestapplication.properties file
EnvironmentVariablesSourceMediumOS environment variables
SystemPropertiesSourceHighest-D JVM flags

Standard configuration

The framework provides a standard three-layer configuration:

Configuration config = Configuration.standard(
    Path.of("application.properties"));

// Layers: properties file < env vars < system properties
// A key's own default sits below all three layers

If the properties file does not exist, it contributes nothing rather than failing — running on defaults plus environment is a supported deployment.

Custom configuration

For custom layering, use Configuration.of():

Configuration config = Configuration.of(
    PropertiesConfigurationSource.fromFile(Path.of("defaults.properties")),
    EnvironmentVariablesSource.current(),
    SystemPropertiesSource.current());

In-memory configuration for tests

Tests use deterministic, file-free configuration:

Configuration config = Configuration.inMemory(Map.of(
    "server.port", "9090",
    "server.host", "0.0.0.0"));

Type-safe configuration keys

Configuration keys declare their type, so conversion errors fail fast. A component declares the keys it owns as constants, so a key name appears in exactly one place in the codebase and is greppable:

// Declare keys as constants
ConfigurationKey<Integer> PORT = ConfigurationKey.of(
    "server.port", Integer.class, 8080);

ConfigurationKey<Duration> TIMEOUT = ConfigurationKey.of(
    "request.timeout", Duration.class, Duration.ofSeconds(30));

ConfigurationKey<String> HOST = ConfigurationKey.of(
    "server.host", String.class, "127.0.0.1");

ConfigurationKey<ThreadPolicy> THREADS = ConfigurationKey.of(
    "barezen.runtime.threads", ThreadPolicy.class, ThreadPolicy.AUTO);

// Read values
int port = config.get(PORT).orElse(8080);
Duration timeout = config.get(TIMEOUT).orElse(Duration.ofSeconds(30));

Supported types

The configuration system supports the following types out of the box:

TypeFormatExample
StringPlain text"hello"
IntegerInteger number"8080"
LongLong number"9223372036854775807"
Booleantrue or false (case-insensitive)"true"
DurationISO-8601 duration"PT10S", "PT1H30M"
EnumsEnum name (case-insensitive)"auto" for ThreadPolicy.AUTO

Note: Boolean only accepts explicit true or false. A typo like tru will fail at startup rather than silently becoming false.

Keys without defaults

For optional configuration, declare a key with no default:

ConfigurationKey<String> OPTIONAL_KEY = ConfigurationKey.of(
    "optional.key", String.class);

// Returns Optional.empty() if not configured
Optional<String> value = config.get(OPTIONAL_KEY);

Key name validation

Key names must be dot-separated segments of letters, digits, dashes, and underscores. Empty segments (e.g., a..b) are refused:

// Valid
ConfigurationKey.of("server.port", Integer.class, 8080);
ConfigurationKey.of("my-app.host-name", String.class, "localhost");

// Invalid — throws IllegalArgumentException
ConfigurationKey.of("a..b", String.class);  // Empty segment
ConfigurationKey.of("", String.class);       // Blank name

Error handling

If a present value cannot be converted to the key's declared type, a ConfigurationException is thrown. A bad value is never replaced by a default, because a component quietly running on a fallback looks healthy while doing the wrong thing.

Dependency injection

BareZen uses explicit, reflection-free dependency injection (ADR-0014). There are no annotations, no classpath scanning, and no constructor picked by reflection. An application states what it has, and the framework works out the creation order.

ServiceAssembly

The assembly is where an application states what it has, and the framework works out the creation order:

ServiceAssembly assembly = ServiceAssembly.builder()
    .instance(DataSource.class, dataSource)          // caller-built, caller-owned
    .factory(UserRepository.class, services ->
        new SqlUserRepository(services.require(DataSource.class)))
    .factory(UserService.class, services ->
        new UserService(services.require(UserRepository.class)))
    .build();

UserService service = assembly.require(UserService.class);

Two registration methods

MethodOwnershipWhen to use
instance(Class, T)Caller owns the instanceFor objects created externally (DataSource, LifecycleParticipants)
factory(Class, Function)Assembly owns the instanceFor objects the assembly should create and close

Ownership rules

  • factory() — the assembly creates and owns the instance. close() releases it in reverse creation order.
  • instance() — the caller created it and releases it. The assembly never touches it.

A component that is also a LifecycleParticipant should be registered via instance(), because the orchestrator drives its stop(), and two owners releasing one object causes double-release bugs.

Services interface

The Services interface is the view a factory receives during assembly. It is not a service locator: only assembly code and factories should hold this type. Two ArchUnit rules enforce this boundary (ADR-0006).

// Inside a factory:
.factory(MyService.class, services -> {
    DataSource ds = services.require(DataSource.class);  // mandatory dependency
    EventBus bus = services.find(EventBus.class).orElse(null);  // optional dependency
    return new MyService(ds, bus);
})

Resolution behavior

  • require(Class<T>) — returns the object bound to the type, or throws AssemblyException if nothing is bound.
  • find(Class<T>) — returns Optional<T>, empty when nothing is bound.

Closing the assembly

When done, close the assembly to release all factory-created instances:

try (ServiceAssembly assembly = ServiceAssembly.builder()
    .factory(EventBus.class, s -> EventBus.create())
    .factory(AuthPlugin.class, s ->
        new AuthPlugin(s.require(EventBus.class)))
    .build()) {
    // use assembly
} // factory-created instances are closed in reverse order

Error scenarios

The assembly detects and reports the following errors at build time:

ErrorWhen
Missing dependencyA factory calls require() for a type that was never registered.
Circular dependencyA depends on B, B depends on A. The error message shows the full cycle path.
Duplicate registrationTwo instance() or factory() calls for the same type.
Factory returned nullA factory returned null instead of an instance.
Type mismatchA factory returned an object that is not an instance of the registered type.

Release order

The recommended release order is: stop the LifecycleOrchestrator first, then close the ServiceAssembly. A participant finishing work during stop() may still be using the infrastructure assembled here.

Event bus

The event bus is a synchronous, in-process pub/sub mechanism (ADR-0017). It has no executor, no queue, and no worker thread.

Dispatch contract

  • Synchronous. publish(event) invokes every handler on the calling thread and only then returns.
  • Exact type matching. A handler registered for UserCreated.class receives only exact instances — no supertype or interface matching.
  • Registration order is invocation order. First registered, first invoked.
  • First handler failure ends dispatch. The exception propagates unchanged; later handlers are not invoked.
  • No lifecycle. The bus is not a LifecycleParticipant and has no close().
  • Concurrent publishing is supported. Two threads may publish at the same time.

Usage

EventBus bus = EventBus.create();

// Define an event type
record UserCreated(String username) {}

// Subscribe
Subscription sub = bus.subscribe(UserCreated.class, event -> {
    log.info("User created: {}", event.username());
});

// Publish
bus.publish(new UserCreated("alice"));

// Unsubscribe when done
sub.cancel();

Wiring with ServiceAssembly

ServiceAssembly assembly = ServiceAssembly.builder()
    .factory(EventBus.class, s -> EventBus.create())
    .factory(AuthPlugin.class, s ->
        new AuthPlugin(s.require(EventBus.class)))
    .build();

When to use the event bus

The event bus is suitable for:

  • Decoupling components: a component publishes an event without knowing who listens.
  • Auditing: a handler logs every UserCreated event.
  • Notifications: a handler sends an email when an order is placed.

The event bus is not suitable for:

  • Asynchronous processing: use an executor or message queue instead.
  • Cross-process communication: use a message broker instead.
  • Reliable delivery: if a handler fails, later handlers are not invoked.

Thread model

BareZen supports both platform threads and virtual threads (Java 21+). The thread model is resolved at assembly time, not scattered across components.

Thread policies

PolicyBehavior
AUTOPicks virtual threads on Java 21+, platform threads otherwise. This is the default.
PLATFORMAlways platform threads, even on Java 21+. Use for legacy compatibility.
VIRTUALVirtual threads or fails startup. Use when virtual threads are required.

Runtime capability detection

RuntimeCapabilities.detect() probes the JVM for virtual thread support. The orchestrator uses this to resolve the thread provider:

LifecycleOrchestrator.builder()
    .threadPolicy(ThreadPolicy.AUTO)  // auto-detect
    .build();

Scoped providers

Each subsystem that needs executor ownership asks for its own ThreadProvider (ADR-0011). Shutting one down cannot affect another:

ThreadProvider provider = ThreadProviders.create(
    ThreadPolicy.AUTO, RuntimeCapabilities.detect());

ExecutorService executor = provider.newBoundedExecutor(4, "worker");
// ... use executor ...
provider.close();  // releases all executors created by this provider

ThreadProvider API

MethodDescription
kind()Returns Kind.PLATFORM or Kind.VIRTUAL.
name()Short stable identifier for logs, e.g., "virtual".
preferred()Returns true when this is the recommended choice (what AUTO resolves to).
newBoundedExecutor(int maxConcurrency, String namePrefix)Creates a bounded executor. Excess tasks are queued, not dropped.
newUnboundedExecutor(String namePrefix)Creates an unbounded executor. Prefer bounded whenever the workload reaches a limited resource.
close()Shuts down all executors created by this provider. Idempotent and never throws.

Default close timeout

The default close timeout is 10 seconds (ThreadProviders.DEFAULT_CLOSE_TIMEOUT). Executors that refuse to terminate within this timeout are logged and force-stopped.

Plugin interface

The Plugin interface in core defines the contract that all plugins implement. A plugin is a LifecycleParticipant that can contribute routes, handlers, or other capabilities (ADR-0016).

public interface Plugin extends LifecycleParticipant {
    PluginDescriptor descriptor();
}

Plugins are discovered via PluginDiscovery using ServiceLoader (ADR-0048), and registered through PluginRegistration (ADR-0041). See the Plugins page for writing plugins.

Best practices

Lifecycle management

  • Register participants in dependency order: infrastructure first, then business logic, then the HTTP adapter last.
  • Use try-with-resources for the orchestrator in embedded applications.
  • Turn off the shutdown hook when deploying to a container (Tomcat, Jetty).
  • Keep initialize() and start() fast — they block the startup thread.

Configuration

  • Declare all configuration keys as static final constants in the component that uses them.
  • Provide sensible defaults so the application runs without a properties file.
  • Use Configuration.inMemory() in tests for deterministic values.
  • Never write to configuration after startup — it is a read-only snapshot.

Dependency injection

  • Use instance() for objects the caller creates and owns (DataSource, LifecycleParticipants).
  • Use factory() for objects the assembly should create and close.
  • Never store the Services view in a field — it becomes invalid after build().
  • Pass dependencies through constructors, not through the Services view at runtime.

Event bus

  • Keep event handlers fast and synchronous — they run on the publisher's thread.
  • Use record types for events to make them immutable and self-documenting.
  • Cancel subscriptions when the subscriber is no longer needed to avoid memory leaks.

Common issues

"Cannot start in state RUNNING"

This means start() was called twice. The orchestrator is not reentrant — once it reaches RUNNING, it stays there until stopped.

"Nothing is registered as X"

A factory called require(X.class) but X was never registered. Check that all dependencies are registered before calling build().

"Dependency cycle: A -> B -> A"

Two or more types depend on each other. Refactor to break the cycle, for example by introducing an interface or moving one dependency to a different layer.

"Value 'abc' of configuration key 'server.port' is not a valid Integer"

A configuration value cannot be converted to the key's declared type. Check the properties file and environment variables for typos.
