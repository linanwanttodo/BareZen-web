Plugins

A plugin is a lifecycle participant that can name itself, plus whatever extension point the component it contributes to declares. The narrowness is the feature.

The SPI

public interface Plugin extends LifecycleParticipant {
  PluginDescriptor descriptor();                 // record PluginDescriptor(String id, List<String> dependencies)
}

Four phases come from LifecycleParticipant — initialize, start, stop, abort — all with empty defaults, driven by the one lifecycle engine in the build: every participant initialises before any starts, and stop() runs in reverse and reports what failed instead of throwing (ADR-0003, ADR-0005). There is no install(), because that is initialize() with a second name and a second order.

Contributing: routes today

An extension point in BareZen is one interface, declared by the component that owns the thing being contributed. Routing owns the first:

public final class ReportsPlugin implements Plugin, RouteContributor {

  @Override public PluginDescriptor descriptor() {
    return new PluginDescriptor("reports", List.of("user"));    // my collaborator is initialised before me
  }

  @Override public void contributeRoutes(Router.Builder routes) {
    routes.route(HttpMethod.GET, "/reports/status", this::status);
  }
}

A contributed route is a registered route: the duplicate refusal applies, so a plugin cannot win a path by running later, and no precedence or weight field exists to reason about. Contributions run at assembly time, before build() and before any phase, which is why a contributor may start no thread and open no socket.

There is no PluginContext, no ExtensionPoint<T> token and no contribute(point, item). A token could not work anyway: barezen-web ships a jar with no compile dependency at all, so routing could not declare or receive one — which is the fact that makes "owner declares an interface" the shape rather than a preference (ADR-0018 §12, ADR-0047).

Being found

META-INF/services/com.barezen.core.plugin.Plugin
  com.example.ReportsPlugin
List<Plugin> everything = new ArrayList<>(List.of(auth, user, openapi));  // need collaborators: built by hand
everything.addAll(PluginDiscovery.discover());                            // needs nothing: announced
List<Plugin> ordered = PluginRegistration.validate(everything);            // refuses duplicate id,
                                                                          // missing dependency, cycle
Router routes = Router.builder()
    .route(HttpMethod.GET, "/health", health)
    .contributing(RouteContributions.of(ordered))                          // the only instanceof in the mechanism
    .build();

Discovery keeps nothing: each call re-reads the provider configuration and returns fresh instances in a new immutable list, so it cannot answer "give me the auth plugin" and cannot hold a component past the call that made it. A provider that cannot be loaded aborts the call with the JDK's own message naming it — booting an application that quietly lacks an integration is the failure nobody can debug (ADR-0048).

The limit, stated. A ServiceLoader provider is a public class with a public no-argument constructor, so a plugin that needs a DataSource, a SessionStore or another plugin cannot be discovered. The application constructs those, which is the arrangement the SPI started with — and the only mechanism that would let a discovered plugin fetch a collaborator is a lookup, which ADR-0006 refuses. None of the three shipped plugins is discoverable; ReportsPlugin in examples/ is, and it owns a route.

Security: your routes are not protected because they came from a plugin

The security module decorates a handler, so a plugin that contributes a bare handler contributes a public endpoint. Protect your own by taking the ports in your constructor and wrapping what you register:

@Override public void contributeRoutes(Router.Builder routes) {
  routes.route(HttpMethod.GET, "/reports/status",
      SecurityMiddleware.wrap(authentication, authorization, Permission.of("report:read"), new StatusHandler()));
}

Nothing can attach policy to a contribution afterwards, and that is a decision: a route's protection is part of what it is, so it is composed where the route is composed.

Testing one

A plugin should be unit-testable with no database and no server, which is what constructor injection buys: AuthPlugin is tested against a lambda verifier. For the integration half, TestKit binds the real JDK adapter on an ephemeral port and asserts status, header, body, handler invocation count and delivered identity. Worth pinning for any plugin: the phase order it observed, that a collaborator's failure surfaces as a startup failure rather than a swallowed log line, and that stop() releases what start() opened.
