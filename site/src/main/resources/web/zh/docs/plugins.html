插件

插件是一个"能为自己命名的生命周期参与者"，再加上它所贡献的那个组件自己声明的扩展点。 这个范围窄，就是它的功能所在。

SPI

public interface Plugin extends LifecycleParticipant {
  PluginDescriptor descriptor();                 // record PluginDescriptor(String id, List<String> dependencies)
}

四个阶段来自 LifecycleParticipant —— initialize、start、stop、 abort —— 全部带空默认实现，由构建里唯一的那个生命周期引擎驱动：所有参与者先完成初始化， 然后才有任何东西 start；stop() 逆序执行，并且汇报失败项而不是抛出（ADR-0003、ADR-0005）。 没有 install()，因为它只是 initialize() 换了个名字、又多了一套顺序。

贡献：目前是路由

在 BareZen 里，一个扩展点就是一个接口，由"被贡献之物"的所有者声明。路由是第一个所有者：

public final class ReportsPlugin implements Plugin, RouteContributor {

  @Override public PluginDescriptor descriptor() {
    return new PluginDescriptor("reports", List.of("user"));    // 我的协作者在我之前初始化
  }

  @Override public void contributeRoutes(Router.Builder routes) {
    routes.route(HttpMethod.GET, "/reports/status", this::status);
  }
}

一条被贡献的路由就是一条已注册的路由：重复拒绝同样生效，所以插件不可能靠"跑得更晚"抢下一条路径， 也不存在任何优先级或权重字段需要推理。贡献发生在装配期，在 build() 之前、在任何阶段之前 —— 这就是为什么一个贡献者不许启动线程、也不许打开 socket。

没有 PluginContext，没有 ExtensionPoint<T> token，也没有 contribute(point, item)。token 本来也做不到：barezen-web 发布的是一个没有任何编译期依赖的 jar，所以路由层既无法声明也无法接收这样一个 token —— 让"所有者声明一个接口"成为这个形状的理由是这件事， 而不是偏好（ADR-0018 §12、ADR-0047）。

发现机制什么都不保留：每次调用都重新读取 provider 配置，返回一批新实例和一个新的不可变列表，所以它没法回答 "把 auth 插件给我"，也没法把某个组件留到那次调用之后。加载不起来的 provider 会用 JDK 自己的消息中止本次调用并点名它 —— 启动一个悄悄缺了某个集成应用，是没人能调试的那种失败（ADR-0048）。

把限制说清楚。ServiceLoader 的 provider 必须是一个公共类加一个公共无参构造， 所以一个需要 DataSource、SessionStore 或另一个插件的插件无法被发现。 这些东西由应用构造 —— 这正是 SPI 一开始的安排 —— 而唯一能让被发现的插件自己去取协作者的机制是查找， ADR-0006 拒绝它。三个内置插件没有一个可被发现；examples/ 里的 ReportsPlugin 可以， 而它拥有一条路由。

安全：你的路由不会因为来自插件就被保护

安全模块装饰的是 handler，所以一个贡献了裸 handler 的插件贡献的是一个公开端点。 要保护你自己的端点，就在构造函数里收下那些 port，并把注册的东西包起来：

@Override public void contributeRoutes(Router.Builder routes) {
  routes.route(HttpMethod.GET, "/reports/status",
      SecurityMiddleware.wrap(authentication, authorization, Permission.of("report:read"), new StatusHandler()));
}

事后没有任何东西能给一次贡献补上策略，这是一个决定：一条路由的保护是它"是什么"的一部分， 所以它就该在路由被组装的地方被组装。

测试一个插件

插件应当不需要数据库、不需要服务器就能单元测试 —— 这正是构造函数注入买来的东西：AuthPlugin 是对着一个 lambda verifier 测的。集成的那一半，TestKit 会在一个临时端口上绑定真实的 JDK 适配器， 然后断言状态码、头、body、handler 被调用的次数，以及送达的身份。对任何插件都值得钉住的三件事：它观察到的阶段顺序、 协作者失败会以启动失败的形式浮现而不是一条被吞掉的日志，以及 stop() 释放了 start() 打开的东西。

长版本（含打包方式与推迟清单）在 参考页，紧挨着它所依据的那些 ADR（ADR-0016、ADR-0041、ADR-0042、ADR-0047、ADR-0048）。
