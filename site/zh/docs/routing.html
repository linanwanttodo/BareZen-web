路由与 HTTP

路由器只回答一个问题。服务器决定线上写什么。把这两件事分开，是第二个服务器能作为一个模块存在、 而不是一次重写的原因。

一个模式允许是什么

一条路由是一个方法、一个原始路径模式和一个 handler。一个模式要么是一段字面路径，要么是一个恰好是 {name} 的段，捕获一个非空的原始段。没有通配符、没有正则、没有可选段、没有重复段、没有前缀匹配 —— 每一个都是在 build() 时被点名拒绝的（no_preemptive_routing_or_middleware_types， ADR-0019 §19），而不是"碰巧没实现"。

理由只有一句话：一个接受前缀的匹配器会让 GET /a/b 同时匹配两条路由，于是必须有东西来决定哪条赢。 那个"有东西"就是一条优先级规则，而优先级是一个路由器存在的理由恰恰是不去问的排序问题。

Optional<RouteMatch> match  = routes.match(request);      // 这个问题
Set<HttpMethod>   allowed = routes.methodsFor("/users/7"); // 空表示 404，非空表示 405
Router frozen    = routes.build();                        // List.copyOf：不是正在增长的 builder 的视图

重复 —— 同一个方法、同一个形状 —— 在注册时就被拒绝，永远不会靠"后者覆盖前者"来解决。就这一个决定， 让插件可以贡献路由，而应用不必去推理插件之间的顺序。

分帧、HEAD 与 304

  • Response 拒绝 Content-Length 和 Transfer-Encoding；一个重复的分帧头 即使两个值一致也会被拒绝（ADR-0027 §5、ADR-0029）。
  • 跑哪个 handler 取决于折叠后的方法；线上发哪些字节取决于服务器逐字比较的那个原始 token。于是 HEAD /doc 会声明一个它并不发送的 body 的长度，而一个 head /doc token 拿到的是 它的表示本来就有的 body。这个决定是实测之后才做的 —— ADR-0028 记录了 Temurin 17.0.20.1+1 与 21.0.12.1+1 两轮输出的对照，因为之前那条规则会造出一个假的 Content-Length: 0。
  • 304 不带 Content-Length。这个决策曾被推迟，直到有一个东西能知道已存储表示的大小； 当 StaticContent 到来并且确实知道之后，这个决策在真实 socket 上被重新测量并保留了下来 （ADR-0029 D1、ADR-0051）。
  • HTTP 规定不给 body 的那些状态码，在构造时就被逐个拒绝，而不是在 socket 上被悄悄丢掉。

Body 就是字节

请求 body 被完整地读取且有上限；响应 body 是一个 byte[]。流式写入对照三个列明的条件做过衡量， 最终没有构建 —— 因为一个活的 writer 会破坏上面那张分帧表，包括静态文件现在正依赖的 HEAD 那一行 （ADR-0030、ADR-0051）。两个服务器的默认上限都是 1 MiB，所以客户端不能靠选择部署模型来多发内容。
