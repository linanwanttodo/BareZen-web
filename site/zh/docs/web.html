Web 核心

barezen-web 定义了 HTTP 契约：Request、Response、Router 和 Handler — 与服务器无关且不可变。

模块概览

barezen-web 模块定义了核心 HTTP 抽象。它只依赖 barezen-core，没有任何服务器特定的依赖。这使得同一个处理程序可以在任何 HTTP 服务器上运行 — JDK HttpServer、Tomcat、Jetty 或 Wildfly。

它包含单个包中的十个类型：

类型角色
Handler函数式接口：Response handle(Request, Map)
Request不可变请求：方法、路径、查询、头部、主体
Response不可变响应：状态码、头部、主体
Headers多值头部集合
HttpMethodHTTP 方法：GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS、CONNECT、TRACE
Router路由表：将请求匹配到处理程序
RouteMatch匹配结果：处理程序 + 捕获的参数
RouteContributor插件添加路由的扩展点
HttpServerAdapter服务器特定适配器的接口
HttpServerAdapterProvider发现适配器的 SPI

Handler 契约

Handler 是 Web 层的整个扩展表面。一个方法，同步，返回一个值：

@FunctionalInterface
public interface Handler {
    Response handle(Request request, Map<String, String> parameters);
}

两个参数，一个返回值。Handler 接收请求和路由器捕获的任何路径参数，然后返回响应。没有 servlet 上下文、没有线程局部变量、没有请求作用域 — 只是数据进，数据出。

参数映射

parameters 映射包含匹配的路由模式捕获的路径参数，以模式中声明的名称为键。它是不可变的且原始的（未进行百分号解码）。对于没有参数的路由，它是一个空映射（永远不会为 null）。

// 路由：GET /users/{id}/posts/{postId}
// 请求：GET /users/42/posts/7
// parameters: {"id": "42", "postId": "7"}

失败语义

  • 异常可以从 handler 中传播 — 此契约中没有任何内容捕获它。
  • 一个将自己失败转换为 500 的 handler 是可以的，一个让数据库异常逃逸的 handler 也可以。
  • 谁将逃逸的异常转换为对客户端的响应是适配器的决定，不是 handler 的决定。

线程安全

Handler 由适配器并发调用。Handler 不得在字段中保存可变每请求状态。属于字段的是在构造时注入的内容。参数映射已经是每请求的、不可变的，由路由表构建。

Request

Request 类型携带关于客户端发送内容的五个事实（ADR-0018）。实例是不可变的 — 数组和列表在访问时被复制。

字段

方法类型说明
method()HttpMethodGET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS、CONNECT、TRACE
path()String原始路径，百分号编码，以 / 开头，OPTIONS * 时为 *
query()Optional<String>不带 ? 的原始查询；不存在与空不同
headers()Headers多值头部集合，永远不会为 null
body()byte[]内存中的完整主体；每次调用时复制。无主体时为数组。

原始路径

路径以线上传递的形式保留。不进行百分号解码：

  • /a%2Fb 是一个包含斜杠的段，而 /a/b 是两个段。
  • /%2e%2e/x 不会解码为 /../x — 解码是关于一个资源的决定，由拥有它的人做出。

没有 uri()、没有 param(name)、没有 path() 的解码副本。查询参数映射有其自己的解析规则，属于辅助工具，不属于请求类型。

查询：不存在与空

不存在和空保持区分：/search 给出 Optional.empty()，而 /search? 给出 Optional.of("")。一个将两者视为一个的 handler 无法区分"未给出过滤器"和"按无过滤"。

主体在内存中

body() 返回整个主体的副本作为 byte[]。这是一个有意的权衡：流式主体需要契约说明谁关闭流、handler 未读取就返回时发生什么、handler 将其交给另一个线程时发生什么。这些问题都没有不依赖于服务器的答案。

构造函数验证

构造函数验证路径以 / 开头或正好是 *（用于 OPTIONS *）。像 user/1 这样的相对路径会被拒绝。

Response

响应是产生的，不是编辑的。Handler 构建一个并返回它 — 没有 setStatus、addHeader 或 send：

new Response(200, Headers.of("Content-Type", "application/json"), jsonBytes);

字段

方法类型说明
status()int100 到 599 之间的状态码
headers()Headers响应头部，永远不会为 null
body()byte[]响应主体；每次调用时复制。无主体时为数组。

强制规则

两个规则在构建时强制执行（ADR-0027）：

  1. 禁止主体的状态码不给主体。 HTTP 规定 1xx、204 和 304 不携带主体。与这些状态码之一的非空主体在构建时被拒绝，并带有清晰的错误消息。
  2. Content-Length 和 Transfer-Encoding 不是 handler 要写的。 这些字段描述头部块后有多少字节 — 这是关于连接的事实，不是应用的答案。只有写入字节的适配器才能真正说明它们。

HEAD 响应

Handler 为 HEAD 返回与 GET 相同的 Response。适配器决定两个后果：它不写入主体字节，它派生它未写入的主体的 Content-Length。一个为 HEAD 返回空主体的 handler 会报告零长度表示。

状态码验证

状态码必须在 100 到 599 之间（含）。超出范围的状态码不能写在响应行上，客户端按状态分支 — 所以错误的状态码不是表面错误，而是成功交付的错误答案。

常见响应模式

// 200 OK 带 JSON 主体
new Response(200,
    Headers.of("Content-Type", "application/json"),
    "{\"message\":\"ok\"}".getBytes(StandardCharsets.UTF_8));

// 204 No Content
new Response(204, Headers.empty(), null);

// 404 Not Found
new Response(404,
    Headers.of("Content-Type", "text/plain; charset=utf-8"),
    "Not Found".getBytes(StandardCharsets.UTF_8));

// 304 Not Modified（不允许主体）
new Response(304, Headers.of("ETag", "\"abc123\""), null);

// 302 Redirect
new Response(302, Headers.of("Location", "/new-path"), null);

Headers

Headers 是一个多值集合。每个名称可以有多个值，保留 HTTP 语义，其中 Set-Cookie 或 Accept 通常携带多个值。

API 方法

方法描述
Headers.empty()返回一个不可变的空实例，共享。
Headers.of(String name, String value)创建一个字段的头部。
with(String name, String value)返回一个附加了一个更多字段的新实例。使用相同名称调用两次会得到一个有两个值的字段。
first(String name)返回字段的第一值作为 Optional<String>。不区分大小写的名称匹配。
values(String name)按顺序返回字段的所有值。如果字段未发送，则返回空列表。
names()按首次出现顺序返回不同的字段名称，拼写如给定。

四个强制规则

  1. 名称匹配不区分大小写，输出保持给定的大小写。 用 Content-Type 构建的响应作为 Content-Type 发送，而不是 content-type。
  2. 重复的名称保留每个值，按顺序。 values("Set-Cookie") 返回所有 cookie。
  3. 不存在和空是不同的。 发送为 X-Cursor: 的字段以空值存在（Optional.of("")）；从未发送的字段是 Optional.empty()。
  4. 名称是 HTTP 令牌，值不包含控制字符。 这是一条安全规则：头部值中的 CR 或 LF 开始新的响应行（HTTP 响应拆分）。

使用示例

Headers headers = Headers.of("Content-Type", "application/json")
    .with("Cache-Control", "no-cache")
    .with("Set-Cookie", "session=abc")
    .with("Set-Cookie", "tracking=xyz");

List<String> cookies = headers.values("Set-Cookie");
// ["session=abc", "tracking=xyz"]

Optional<String> contentType = headers.first("Content-Type");
// Optional["application/json"]

HttpMethod

HTTP 请求方法是一种类型而不是 String，因为 Web 组件对请求做的第一件事是比较其方法，而裸 String 使这成为一个陷阱："Get".equals(request.method()) 永远不会匹配。

标准方法

常量描述
GET请求表示，以主体回答。
HEAD不带响应主体的 GET。适配器处理此操作。
POST提交表示进行处理。
PUT替换目标资源。
DELETE移除目标资源。
PATCH应用部分修改。
OPTIONS询问目标资源支持哪些选项（CORS 预检）。
CONNECT将连接转换为隧道。
TRACE将请求回显给客户端。

自定义方法

这是一个类而不是枚举，所以它可以持有标准集中没有的方法（例如，来自 WebDAV 的 PROPFIND、来自缓存管理器的 PURGE）。使用 HttpMethod.of("PURGE") 解析任何方法令牌。

大小写规则

  • 九个标准名称在任何大小写中被识别：of("get") 返回 HttpMethod.GET。
  • 任何其他名称都按原样保留并按原样比较。

Router

路由器是一个不可变的路由表（ADR-0019）。它回答"这个请求是哪个处理程序的"，不回答"答案是没有人时应该告诉客户端什么"。

构建路由

Router router = Router.builder()
    .route(HttpMethod.GET, "/health", (req, params) ->
        new Response(200, Headers.of("Content-Type", "text/plain"), "OK".getBytes()))
    .route(HttpMethod.GET, "/users/{id}", (req, params) -> {
        String id = params.get("id");
        return new Response(200, Headers.of("Content-Type", "application/json"),
            ("{\"id\":\"" + id + "\"}").getBytes());
    })
    .build();

匹配语义

匹配按此顺序决定：

  1. 原始段。 路径在 / 上分割，每个段按到达的字节比较。不解码或规范化任何内容。
  2. 精确段计数。 /users 和 /users/ 是两个不同的路由（不同的段计数）。
  3. 文字段精确匹配。 区分大小写，包括百分号编码。
  4. 参数段 {name} 匹配任何非空段。 未解码捕获。
  5. 最文字的模式获胜。 /users/new 在 GET /users/new 上胜过 /users/{id}。

路由冲突

具有相同方法和相同形状的两个路由在构建时被拒绝。/users/{id} 和 /users/{userId} 具有相同的形状并会冲突 — 歧义是形状的问题，不是拼写的问题。

模式验证

模式在注册时验证：

  • 必须以 / 开头。
  • 不得包含 ?（查询字符串不是路由数据）。
  • 参数名称必须是有效的 Java 标识符（字母后跟字母、数字、下划线）。
  • 参数名称不能在一个模式中使用两次。
  • 大括号必须形成一个完整的段：{name} 有效，{name}suffix 无效。

RouteContributor

插件可以在不直接修改路由器的情况下贡献路由。RouteContributor 在路由器的构建阶段被调用：

public interface RouteContributor {
    void contributeRoutes(Router.Builder builder);
}

使用 contributing() 应用贡献者：

Router router = Router.builder()
    .route(HttpMethod.GET, "/health", healthHandler)
    .contributing(List.of(userPlugin, authPlugin))
    .build();

不可变性

路由器在 build() 后是不可变的。没有 unregister、replace 或 reload。请求线程不能与注册竞争，因为竞争不存在。

路径的方法

methodsFor(String path) 返回给定路径的哪些方法有路由。这是适配器区分 404（此路径没有路由）和 405（路由存在但不是此方法）的方式：

Set<HttpMethod> methods = router.methodsFor("/users");
// 如果注册了 GET /users 并请求了 POST /users：
// match() 返回空，methodsFor() 返回 [GET]
// → 适配器回答 405 Method Not Allowed

HttpServerAdapter

HttpServerAdapter 接口定义了每个服务器适配器必须实现的内容：

public interface HttpServerAdapter extends LifecycleParticipant {
    Optional<Integer> port();
}

它扩展 LifecycleParticipant，所以编排器驱动其启动和关闭。适配器负责：

  • 绑定网络端口
  • 从套接字读取字节并构建 Request
  • 调用 Router.match() 查找处理程序
  • 调用处理程序并将 Response 写回
  • 处理 HTTP 错误（404、405、414 等）

模块依赖

barezen-web 只依赖 barezen-core。没有服务器适配器、没有数据库驱动、没有安全库。其他一切是你有意添加的模块：

  • barezen-http-jdk — JDK HttpServer 适配器
  • barezen-http-servlet — Servlet 容器适配器
  • barezen-security — 认证和授权
  • barezen-data — 数据库访问
  • barezen-content — 静态文件服务

最佳实践

Handlers

  • 保持 handler 无状态 — 通过构造函数注入依赖，而不是通过请求字段。
  • 为每个代码路径返回响应 — 永远不要返回 null。
  • 让意外错误的异常传播；适配器会处理它们。
  • 对于预期错误（验证、未找到），显式返回适当的状态码。

路由

  • 为清晰起见，在参数化路由之前注册文字路由，尽管路由器会自动处理优先级。
  • 对插件路由使用 RouteContributor 以保持主路由器整洁。
  • 在启动时构建一次路由器 — 它是不可变且线程安全的。

响应

  • 始终在带主体的响应上设置 Content-Type。
  • 对无头部的响应使用 Headers.empty()（适配器仍会写入 Content-Length）。
  • 永远不要设置 Content-Length 或 Transfer-Encoding — 适配器会派生它们。

常见问题

"Route pattern must start with '/'"

所有路由模式必须以 / 开头。像 users/{id} 这样的相对模式会被拒绝 — 路由器需要绝对路径来匹配。

"GET /users/{id} is already registered as /users/{userId}"

具有相同方法和相同形状（相同模式结构）的两个路由不能共存。/users/{id} 和 /users/{userId} 都匹配 /users/42，所以路由器在构建时拒绝第二个。

"A 204 response cannot carry a body"

HTTP 将 1xx、204 和 304 定义为没有消息主体的响应。对这些状态码返回空主体（null 或 new byte[0]）。

"A response must not carry Content-Length"

适配器从主体字节派生 Content-Length。手动设置会导致重复头部或协议错误。从响应头部中移除 Content-Length 头部。
