核心概念

barezen-core 提供框架基础：生命周期管理、配置、依赖注入、事件总线和线程模型。

模块概览

barezen-core 模块是整个框架的基础。除了 slf4j-api 之外没有其他外部依赖（ADR-0001）。所有其他框架模块都直接或间接依赖它。

它包含八个包：

包职责
com.barezen.core.kernel生命周期编排、应用状态、关闭钩子
com.barezen.core.config配置快照、配置源、类型转换
com.barezen.core.di通过 ServiceAssembly 实现的显式依赖注入
com.barezen.core.event同步事件总线和订阅
com.barezen.core.concurrent线程提供者、虚拟线程、执行器管理
com.barezen.core.plugin插件接口、描述符、发现、注册
com.barezen.core.runtime运行时能力检测（虚拟线程等）
com.barezen.core.error框架异常：Assembly、Configuration、Lifecycle

生命周期管理

每个 BareZen 应用都会经历一组固定的状态，由 LifecycleOrchestrator 管理。编排器驱动所有注册组件的启动、关闭和启动回滚。

应用状态

状态含义
NEW刚构建，尚未启动。编排器准备启动。
STARTING启动中；initialize() 和 start() 阶段正在进行。
RUNNING所有参与者启动成功，正在接受请求。
STOPPING按逆序关闭参与者。
STOPPED已干净关闭。所有资源已释放。
FAILED启动失败，回滚完成。没有资源被占用。

LifecycleParticipant 接口

每个由编排器驱动启动和关闭的组件都实现 LifecycleParticipant：

public interface LifecycleParticipant {
    default void initialize() {}  // 获取资源，完成内部连接
    default void start() {}       // 激活并开始服务
    default void stop() {}        // 释放资源，关闭时调用
    default void abort() {}       // initialize() 失败后释放资源
}

所有四个方法都有空默认实现，所以实现类只需编写它实际有的阶段。编排器依赖以下约定：

  • stop() 和 abort() 是幂等的，永远不会抛出异常。
  • stop() 必须能容忍只到达 initialize() 的参与者，因为编排器用它来执行有序关闭和已初始化参与者的回滚。
  • 注册顺序就是启动顺序。选择这个顺序是组装者的工作。

两阶段启动

启动分两个全局阶段运行（ADR-0003）：

  1. 初始化阶段 — 调用每个参与者的 initialize()。在这里注册路由、应用迁移、贡献路由。
  2. 启动阶段 — 调用每个参与者的 start()。在这里绑定端口并开始监听。

两阶段排序保证了一个使工作可见的参与者（如绑定端口的 HTTP 服务器）只在每个前面的参与者完成设置后才这样做。按组件交错两个阶段无法表达这个不变量。

启动回滚

如果任何参与者在启动期间失败，编排器执行完整回滚（ADR-0004）：

  • 每个成功进入的参与者按逆序接收 stop()。
  • 失败的参与者接收 abort() 而不是 stop()。
  • 原始失败始终是报告的内容；清理问题作为抑制异常附加。
  • 回滚后，状态为 FAILED，没有任何资源被占用。

关闭

关闭是尽力而为的，永远不会抛出异常（ADR-0005）。即使一个失败，也会尝试每个进入的参与者，ShutdownReport 收集所有失败。对从未启动的应用调用 stop() 是合法且幂等的（ADR-0012），这使得 try-with-resources 可用。

Builder API

LifecycleOrchestrator.Builder 提供以下配置选项：

方法默认值描述
register(String id, LifecycleParticipant)必需注册参与者。调用顺序定义启动顺序。
threadPolicy(ThreadPolicy)AUTO选择线程模型：AUTO、PLATFORM 或 VIRTUAL。
runtimeCapabilities(RuntimeCapabilities)自动检测覆盖检测到的运行时能力（测试用）。
threads(ThreadProvider)从策略解析提供外部创建的提供者；编排器仍拥有其关闭权。
threadCloseTimeout(Duration)10 秒终止拥有者创建的执行器的宽限期。
registerShutdownHook(boolean)true是否注册 JVM 关闭钩子。容器部署的应用应关闭。

使用示例

LifecycleOrchestrator orchestrator = LifecycleOrchestrator.builder()
    .register("web", httpAdapter)
    .register("security", securityPlugin)
    .register("data", database)
    .build();

try {
    orchestrator.start();
    // 应用运行直到停止
} finally {
    orchestrator.stop();  // 或使用 try-with-resources
}

关闭钩子

默认情况下，编排器为嵌入式应用注册 JVM 关闭钩子。当宿主容器（如 Tomcat）已拥有进程生命周期时，请关闭它：

LifecycleOrchestrator.builder()
    .registerShutdownHook(false)
    .build();

查询状态

编排器提供两个查询方法：

// 检查当前状态
ApplicationState state = orchestrator.state();

// 按注册顺序列出所有参与者 ID
List<String> ids = orchestrator.participantIds();

配置系统

BareZen 中的配置是启动前解析的只读快照（ADR-0013）。没有写入 API：配置一旦确定就保持不变。这防止了两个组件对值不一致，也防止测试为下一个测试留下状态。

配置源

三种内置源类型，按最弱到最强分层：

源优先级用途
PropertiesConfigurationSource最低application.properties 文件
EnvironmentVariablesSource中等操作系统环境变量
SystemPropertiesSource最高-D JVM 参数

标准配置

框架提供标准的三层配置：

Configuration config = Configuration.standard(
    Path.of("application.properties"));

// 层级：属性文件 < 环境变量 < 系统属性
// 键自身的默认值位于所有三层之下

如果属性文件不存在，它不贡献任何内容而不是失败 — 使用默认值加环境运行是一种支持的部署方式。

自定义配置

对于自定义分层，使用 Configuration.of()：

Configuration config = Configuration.of(
    PropertiesConfigurationSource.fromFile(Path.of("defaults.properties")),
    EnvironmentVariablesSource.current(),
    SystemPropertiesSource.current());

测试用的内存配置

测试使用确定性的、无文件的配置：

Configuration config = Configuration.inMemory(Map.of(
    "server.port", "9090",
    "server.host", "0.0.0.0"));

类型安全的配置键

配置键声明其类型，所以转换错误会快速失败。组件将其拥有的键声明为常量，这样键名在代码库中只出现在一个地方，可以搜索：

// 将键声明为常量
ConfigurationKey<Integer> PORT = ConfigurationKey.of(
    "server.port", Integer.class, 8080);

ConfigurationKey<Duration> TIMEOUT = ConfigurationKey.of(
    "request.timeout", Duration.class, Duration.ofSeconds(30));

ConfigurationKey<String> HOST = ConfigurationKey.of(
    "server.host", String.class, "127.0.0.1");

ConfigurationKey<ThreadPolicy> THREADS = ConfigurationKey.of(
    "barezen.runtime.threads", ThreadPolicy.class, ThreadPolicy.AUTO);

// 读取值
int port = config.get(PORT).orElse(8080);
Duration timeout = config.get(TIMEOUT).orElse(Duration.ofSeconds(30));

支持的类型

配置系统开箱支持以下类型：

类型格式示例
String纯文本"hello"
Integer整数"8080"
Long长整数"9223372036854775807"
Booleantrue 或 false（不区分大小写）"true"
DurationISO-8601 持续时间"PT10S", "PT1H30M"
枚举枚举名称（不区分大小写）"auto" 对应 ThreadPolicy.AUTO

注意：Boolean 只接受显式的 true 或 false。像 tru 这样的拼写错误会在启动时失败，而不是静默变成 false。

没有默认值的键

对于可选配置，声明一个没有默认值的键：

ConfigurationKey<String> OPTIONAL_KEY = ConfigurationKey.of(
    "optional.key", String.class);

// 如果未配置则返回 Optional.empty()
Optional<String> value = config.get(OPTIONAL_KEY);

键名验证

键名必须是点分隔的字母、数字、连字符和下划线段。空段（如 a..b）会被拒绝：

// 有效
ConfigurationKey.of("server.port", Integer.class, 8080);
ConfigurationKey.of("my-app.host-name", String.class, "localhost");

// 无效 — 抛出 IllegalArgumentException
ConfigurationKey.of("a..b", String.class);  // 空段
ConfigurationKey.of("", String.class);       // 空白名称

错误处理

如果存在的值无法转换为键声明的类型，会抛出 ConfigurationException。错误的值永远不会被默认值替换，因为组件在回退值上静默运行看起来健康但做错了事。

依赖注入

BareZen 使用显式的、无反射的依赖注入（ADR-0014）。没有注解、没有类路径扫描、没有通过反射选择的构造函数。应用声明它有什么，框架计算出创建顺序。

ServiceAssembly

组装是应用声明它有什么的地方，框架计算出创建顺序：

ServiceAssembly assembly = ServiceAssembly.builder()
    .instance(DataSource.class, dataSource)          // 调用者构建，调用者拥有
    .factory(UserRepository.class, services ->
        new SqlUserRepository(services.require(DataSource.class)))
    .factory(UserService.class, services ->
        new UserService(services.require(UserRepository.class)))
    .build();

UserService service = assembly.require(UserService.class);

两种注册方法

方法所有权何时使用
instance(Class, T)调用者拥有实例用于外部创建的对象（DataSource、LifecycleParticipants）
factory(Class, Function)组装拥有实例用于组装应创建和关闭的对象

所有权规则

  • factory() — 组装创建并拥有实例。close() 按逆序释放它。
  • instance() — 调用者创建了它并释放它。组装从不碰它。

同时也是 LifecycleParticipant 的组件应通过 instance() 注册，因为编排器驱动其 stop()，两个所有者释放一个对象会导致双重释放错误。

Services 接口

Services 接口是工厂在组装期间接收的视图。它不是服务定位器：只有组装代码和工厂应持有此类型。两个 ArchUnit 规则强制执行此边界（ADR-0006）。

// 在工厂内部：
.factory(MyService.class, services -> {
    DataSource ds = services.require(DataSource.class);  // 必需依赖
    EventBus bus = services.find(EventBus.class).orElse(null);  // 可选依赖
    return new MyService(ds, bus);
})

解析行为

  • require(Class<T>) — 返回绑定到类型的对象，如果没有绑定则抛出 AssemblyException。
  • find(Class<T>) — 返回 Optional<T>，没有绑定时为空。

关闭组装

完成后，关闭组装以释放所有工厂创建的实例：

try (ServiceAssembly assembly = ServiceAssembly.builder()
    .factory(EventBus.class, s -> EventBus.create())
    .factory(AuthPlugin.class, s ->
        new AuthPlugin(s.require(EventBus.class)))
    .build()) {
    // 使用组装
} // 工厂创建的实例按逆序关闭

错误场景

组装在构建时检测并报告以下错误：

错误何时
缺少依赖工厂为从未注册的类型调用 require()。
循环依赖A 依赖 B，B 依赖 A。错误消息显示完整的循环路径。
重复注册同一类型的两个 instance() 或 factory() 调用。
工厂返回 null工厂返回 null 而不是实例。
类型不匹配工厂返回的对象不是注册类型的实例。

释放顺序

推荐的释放顺序是：先停止 LifecycleOrchestrator，然后关闭 ServiceAssembly。在 stop() 期间完成工作的参与者可能仍在使用这里组装的基础设施。

事件总线

事件总线是同步的、进程内的发布/订阅机制（ADR-0017）。它没有执行器、没有队列、没有工作线程。

分发契约

  • 同步。 publish(event) 在调用线程上调用每个处理程序，然后才返回。
  • 精确类型匹配。 为 UserCreated.class 注册的处理程序只接收精确实例 — 没有超类型或接口匹配。
  • 注册顺序就是调用顺序。 先注册，先调用。
  • 第一个处理程序失败结束分发。 异常原样传播；后面的处理程序不被调用。
  • 无生命周期。 总线不是 LifecycleParticipant，没有 close()。
  • 支持并发发布。 两个线程可以同时发布。

使用

EventBus bus = EventBus.create();

// 定义事件类型
record UserCreated(String username) {}

// 订阅
Subscription sub = bus.subscribe(UserCreated.class, event -> {
    log.info("用户创建: {}", event.username());
});

// 发布
bus.publish(new UserCreated("alice"));

// 完成后取消订阅
sub.cancel();

与 ServiceAssembly 连接

ServiceAssembly assembly = ServiceAssembly.builder()
    .factory(EventBus.class, s -> EventBus.create())
    .factory(AuthPlugin.class, s ->
        new AuthPlugin(s.require(EventBus.class)))
    .build();

何时使用事件总线

事件总线适用于：

  • 解耦组件：组件发布事件而不知道谁在监听。
  • 审计：处理程序记录每个 UserCreated 事件。
  • 通知：下单时处理程序发送邮件。

事件总线不适用于：

  • 异步处理：改用执行器或消息队列。
  • 跨进程通信：改用消息代理。
  • 可靠投递：如果处理程序失败，后面的处理程序不会被调用。

线程模型

BareZen 支持平台线程和虚拟线程（Java 21+）。线程模型在组装时解析，不分散在组件中。

线程策略

策略行为
AUTO在 Java 21+ 上选择虚拟线程，否则使用平台线程。这是默认值。
PLATFORM始终使用平台线程，即使在 Java 21+ 上。用于遗留兼容性。
VIRTUAL虚拟线程或启动失败。在需要虚拟线程时使用。

运行时能力检测

RuntimeCapabilities.detect() 探测 JVM 的虚拟线程支持。编排器使用它来解析线程提供者：

LifecycleOrchestrator.builder()
    .threadPolicy(ThreadPolicy.AUTO)  // 自动检测
    .build();

作用域提供者

每个需要执行器所有权的子系统请求自己的 ThreadProvider（ADR-0011）。关闭一个不会影响另一个：

ThreadProvider provider = ThreadProviders.create(
    ThreadPolicy.AUTO, RuntimeCapabilities.detect());

ExecutorService executor = provider.newBoundedExecutor(4, "worker");
// ... 使用执行器 ...
provider.close();  // 释放此提供者创建的所有执行器

ThreadProvider API

方法描述
kind()返回 Kind.PLATFORM 或 Kind.VIRTUAL。
name()日志的简短稳定标识符，例如 "virtual"。
preferred()当这是推荐选择时（AUTO 解析到的）返回 true。
newBoundedExecutor(int maxConcurrency, String namePrefix)创建有界执行器。超额任务被排队，不会丢弃。
newUnboundedExecutor(String namePrefix)创建无界执行器。当工作负载到达有限资源时，优先使用有界。
close()关闭此提供者创建的所有执行器。幂等且永不抛出异常。

默认关闭超时

默认关闭超时为 10 秒（ThreadProviders.DEFAULT_CLOSE_TIMEOUT）。在此超时内拒绝终止的执行器会被记录并强制停止。

插件接口

core 中的 Plugin 接口定义了所有插件实现的契约。插件是一个可以贡献路由、处理程序或其他能力的 LifecycleParticipant（ADR-0016）。

public interface Plugin extends LifecycleParticipant {
    PluginDescriptor descriptor();
}

插件通过 PluginDiscovery 使用 ServiceLoader 发现（ADR-0048），并通过 PluginRegistration 注册（ADR-0041）。有关编写插件，请参阅插件页面。

错误类型

异常何时
StartupException参与者在 initialize() 或 start() 期间失败。包含阶段（INITIALIZE/START）和参与者 ID。
LifecycleException非法状态转换（例如在 RUNNING 应用上调用 start()）。
AssemblyExceptionServiceAssembly 中缺少或循环依赖，或工厂返回 null。
ConfigurationException值无法转换为键声明的类型。命名键、原始值和源。
ThreadCapabilityUnavailableException请求虚拟线程但 JVM 不支持。

最佳实践

生命周期管理

  • 按依赖顺序注册参与者：先基础设施，再业务逻辑，最后 HTTP 适配器。
  • 在嵌入式应用中使用 try-with-resources 管理编排器。
  • 部署到容器（Tomcat、Jetty）时关闭关闭钩子。
  • 保持 initialize() 和 start() 快速 — 它们会阻塞启动线程。

配置

  • 在使用它们的组件中将所有配置键声明为 static final 常量。
  • 提供合理的默认值，使应用无需属性文件即可运行。
  • 在测试中使用 Configuration.inMemory() 获取确定性的值。
  • 启动后永远不要写入配置 — 它是只读快照。

依赖注入

  • 对调用者创建和拥有的对象使用 instance()（DataSource、LifecycleParticipants）。
  • 对组装应创建和关闭的对象使用 factory()。
  • 永远不要将 Services 视图存储在字段中 — 它在 build() 后失效。
  • 通过构造函数传递依赖，而不是在运行时通过 Services 视图传递。

事件总线

  • 保持事件处理程序快速且同步 — 它们在发布者的线程上运行。
  • 对事件使用 record 类型，使它们不可变且自文档化。
  • 当订阅者不再需要时取消订阅，以避免内存泄漏。

常见问题

"Cannot start in state RUNNING"

这意味着 start() 被调用了两次。编排器不可重入 — 一旦达到 RUNNING，它就会保持在那里直到停止。

"Nothing is registered as X"

工厂为从未注册的 X 调用了 require(X.class)。检查在调用 build() 之前是否已注册所有依赖。

"Dependency cycle: A -> B -> A"

两个或更多类型相互依赖。重构以打破循环，例如通过引入接口或将一个依赖移到不同的层。

"Value 'abc' of configuration key 'server.port' is not a valid Integer"

配置值无法转换为键声明的类型。检查属性文件和环境变量中的拼写错误。
