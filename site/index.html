Small core. Real seams.

BareZen is a Java web framework for people who have to put routing, sessions and persistence into a project that already exists — under its server, in its container, on its database.

JDK 17+ Plugin-based Zero mandatory dependencies SPI-driven 
Router routes = Router.builder()
  .route(GET, "/health", (req, params) -> ok())
  .route(GET, "/users/{id}", (req, params) -> user(params.get("id")))
  .build();

var server = new JdkHttpServerAdapter(loopback(0), routes);
server.start();

What it is for

You haveBareZen gives you
A Spring Boot, Tomcat, Jetty or Wildfly deployment BarezenServlet routes a Router inside the container you already run. It owns no port and no thread pool, because those are yours (ADR-0024, ADR-0049).
A small service that should not need a container The JDK adapter, with HTTPS turned on by naming a keystore rather than by a flag (ADR-0050).
Feature teams shipping their own endpoints A plugin implements Plugin plus RouteContributor and its routes are in the table before anything starts. A jar that announces itself in META-INF/services is picked up by PluginDiscovery (ADR-0047, ADR-0048).
An existing database and its driver Database takes your DataSource, names no driver, and hands a callback a Transaction whose commit and rollback are not callable from a repository (ADR-0038, ADR-0039).

The seams, and what they refuse

A plugin is a lifecycle participant that can name itself, plus whatever extension point the owning component declares. That is deliberately narrow: there is no PluginContext, no contribute(ExtensionPoint, T) registry and no require(Class), because that is the sequence of small conveniences that ends in an application context. A plugin that needs a collaborator takes it in its constructor, so a reader of the call site can see what it needs — and a plugin that needs a collaborator therefore cannot be discovered, since a ServiceLoader provider is a no-argument constructor. That limit is stated rather than worked around.

The route table answers two questions — method plus raw path to a handler, and which methods a path allows — and exposes nothing else. There is no wildcard pattern and no route enumeration, both refused by name, because a matcher that accepts a prefix turns routing into an ordering problem. Static files are served one file per route for exactly that reason (ADR-0019 §19, ADR-0051).

These pages are plain files: hand-written HTML, one stylesheet, every address relative, deployed as they are. That is the shape a static host can serve without running anything of ours, and the trade is named — no ETag negotiation, no generated /openapi.json here, and a page is what its file says (ADR-0054). The tree is checked before a deploy by scripts/check-site.sh, which follows every link on disk and requires each page to have its counterpart in the other language.
